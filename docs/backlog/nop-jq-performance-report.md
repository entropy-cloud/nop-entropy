# nop-jq Performance Comparison Report

**Date**: 2026-09-18
**Status**: Draft

## Executive Summary

nop-jq provides a zero-external-dependency JSON query engine for the Nop platform, replacing Jayway JsonPath. The architecture is designed for performance through:

1. **Compiled Segment pipeline** - JsonPath expressions compile to Segment[] arrays, avoiding repeated parsing
2. **Segment fusion** - Consecutive PropertySegments are merged into FusedPropertySegments
3. **Shared executor** - Single JsonPathExecutor instance reused across all queries
4. **Caffeine-backed compile cache** - Compiled paths cached with automatic eviction
5. **List propagation optimization** - PropertySegment maps over list results efficiently

## Architecture Comparison

| Feature | nop-jq | Jayway JsonPath | fastjson JSONPath |
|---------|--------|----------------|-------------------|
| External dependencies | 0 | json-smart, ASM | ASM, Spring |
| Parse model | Recursive descent → Segment[] | ANTLR → AST | Recursive descent → ASM bytecode |
| Execution model | Segment pipeline | AST visitor | ASM-generated bytecode |
| Compile cache | Caffeine LocalCache | ConcurrentHashMap | ASM class cache |
| Bean access | NopJsonAccessor (BeanTool/ReflectionManager) | JsonProvider SPI | ASM-generated accessor |
| Immutability | JsonValue sealed interface | Mutable objects | Mutable objects |

## Design Decisions for Performance

### 1. Segment Pipeline vs AST Visitor

nop-jq uses a Segment pipeline model (same as fastjson), where each JsonPath expression compiles to a list of Segment objects. The executor runs a simple for-loop over the segments:

```java
for (Segment segment : segments) {
    current = segment.eval(accessor, root, current);
    if (current == null) return null;
}
```

This is more cache-friendly than Jayway's AST visitor pattern, which involves virtual method dispatch on every AST node.

### 2. Segment Fusion

Adjacent PropertySegments (e.g., `.foo.bar.baz`) are fused into a single FusedPropertySegment at compile time, eliminating per-segment overhead:

```java
// Before fusion: 3 segments, 3 virtual calls
// After fusion: 1 segment, 3 direct field accesses in a loop
for (String name : propertyNames) {
    current = accessor.getProperty(current, name);
}
```

### 3. Shared Executor

The JsonPathExecutor is a singleton, avoiding per-query object allocation. The executor is stateless (only holds a reference to the JsonAccessor), so it's safe to share.

### 4. Compile Cache

Compiled paths are cached using Caffeine's LocalCache with automatic eviction:

```java
LocalCache.newCache("nop-jq-compile", newConfig(1000), this::doCompile);
```

Cache hit rate for typical workloads is expected to be >95% since most applications use a small set of recurring JsonPath expressions.

### 5. JsonAccessor Abstraction

The NopJsonAccessor provides a unified property access layer that handles:
- Map access (direct get)
- JavaBean access (via BeanTool/ReflectionManager)
- DynamicObject access
- Array access

This avoids the overhead of Jayway's JsonProvider SPI, which involves additional indirection.

## Benchmark Scenarios

The JMH benchmark suite (`JsonPathBenchmark.java`) covers 8 scenarios:

| Scenario | Description | Expected Behavior |
|----------|-------------|-------------------|
| simpleProperty | `$.expensive` | nop-jq: fast (single segment) |
| nestedProperty | `$.store.book[0].title` | nop-jq: fast (fused segments) |
| wildcardArray | `$.store.book[*].title` | Similar to Jayway |
| filterEquals | `$.store.book[?(@.category == 'fiction')].title` | Similar to Jayway |
| filterGreaterThan | `$.store.book[?(@.price > 10)].title` | Similar to Jayway |
| deepScan | `$..author` | Similar to Jayway |
| compiledPath | Pre-compiled path | nop-jq: faster (avoid re-parse) |
| readFromJson | Parse JSON + query | Similar (parsing dominates) |

## Performance Expectations

Based on the architecture analysis:

- **Simple property access**: nop-jq should be competitive with or faster than Jayway due to fused segments and direct BeanTool access
- **Filter expressions**: Similar performance to Jayway since both use iterative evaluation
- **Deep scan**: Similar performance since both use recursive traversal
- **Compile time**: nop-jq should be faster since it avoids Jayway's ANTLR parsing overhead
- **Memory**: nop-jq uses less memory due to simpler Segment objects vs Jayway's AST nodes

## Known Limitations

1. **No ASM bytecode generation**: fastjson's ASM-based approach generates specialized accessor code, which can be faster for hot paths. nop-jq uses reflection via BeanTool, which has more overhead but is simpler and safer.

2. **No streaming JSON parsing**: nop-jq operates on fully-parsed in-memory objects. For very large JSON files, a streaming approach would be more memory-efficient.

3. **jq execution is deferred**: The jq→XLang translator produces XLang expressions, but the actual execution depends on the XLang engine. Full jq execution performance will depend on XLang engine optimizations.

## Recommendations

1. Run JMH benchmarks on a production-like dataset to get accurate numbers
2. Profile with JFR to identify any remaining hot spots
3. Consider adding ASM-based property accessors for the most common JsonPath patterns (e.g., single-property access)
4. Monitor cache hit rates in production and adjust cache size if needed

## Conclusion

nop-jq provides a solid foundation for JSON querying in the Nop platform with zero external dependencies. The architecture is designed for performance through compiled segments, fusion optimization, and caching. Full benchmarking should be performed in a production environment to validate these design decisions.
