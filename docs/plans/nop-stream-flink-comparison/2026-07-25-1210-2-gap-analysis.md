## Goals

- 一份统一的缺口分析文档，涵盖所有 5 个对比维度
- 所有 gap 合并去重后，以统一分类法（Bug/Gap/Improvement/Hollow/No-Op/Doc）和优先级（P0-P3）排序
- 将 gap 映射到 roadmap 的 `completion-roadmap.md` 阶段，建议阶段划分调整（如有）
- 明确每个 gap 对应的修复 plan（items 9—13 的哪个 plan 负责修复）
- 从交叉对比中发现新的设计决策点（需要人确认的）
- 输出文档更新清单（哪些 owner-doc 需要更新）

## Non-Goals

- 不进行代码修复（属于 items 9—13）
- 不进行新的源码级对比（source audit 已经在 items 3—7 中完成）
- 不替代 `completion-roadmap.md` — 本计划与它对齐，做调整建议但不是覆盖
- 不涉及 Flink Table/SQL API 或 PyFlink

## Scope

### In Scope

- 汇总所有 5 篇对比文档的 gap table，合并去重
- 统一 gap 分类法（Bug/Gap/Improvement/Hollow/No-Op/Doc）和优先级（P0-P3），消除跨文档的分类不一致
- 对已经通过 Plan 303 或 checkpoint-lifecycle-fixes 修复的 gap，在最终表中标记为 `resolved`
- 优先级排序规则：P0 = correctness blocking, P1 = design contract violation, P2 = missing capability, P3 = optimization
- 将 gap 映射到 `completion-roadmap.md` 的阶段（Phase 0.x — Phase 5），对不一致或需要调整的阶段提出建议
- 明确每个 gap 的修复归属 plan（roadmap items 9—13 的对应关系）
- 识别交叉维度 gap（如 checkpoint × 状态管理、watermark × 窗口）
- 记录需要人确认的设计决策点（如 Key-Group vs StateShard 迁移路径）
- 产出文档更新清单：哪些 `docs-for-ai/` 或 `ai-dev/design/` 文档需更新
- 输出文件：`ai-dev/analysis/nop-stream/08-gap-analysis.md`

### Out Of Scope

- New source-level comparison or code audit
- Implementation of any gap fix
- Rewriting `completion-roadmap.md` — only adjustment suggestions
- CEP watermark integration specifics (gap identified in item 6, fix belongs to item 11)

### Analysis Depth Guardrails

- 优先汇总确认、去除重复，然后做优先级裁定
- 对来自不同对比文档但描述同一 gap 的条目：合并成一条，保留所有来源引用
- 对已修复的 gap：验证修复是否完整（确认依赖的 plan 已 closed），如果修复不完整则保留为 P1
- 对跨维度 gap：明确它是需要独立 plan 还是在某个现有 plan 中顺带解决
