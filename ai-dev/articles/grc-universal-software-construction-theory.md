# 为什么广义可逆计算是一个普适的软件构造理论

## 引言：软件构造需要的不只是“模块化”

软件工程已经提出了大量关于复用、扩展和演化的技术：

- 面向对象通过继承和组合扩展对象；
- 函数式编程通过函数组合构造程序；
- 组件技术通过接口组装模块；
- 插件系统通过扩展点增加能力；
- 生成式编程通过模型或 DSL 生成代码；
- 特征导向编程通过特征叠加构造软件产品线；
- Patch、Git、Kustomize 通过差异修改已有结构；
- Lens 研究不同表示之间的双向同步；
- Change Actions 研究变化如何作用和传播；
- 图变换研究结构的增删改；
- CRDT 研究分布式变化的合并；
- 可逆运行时研究组件的动态安装与卸载。

这些理论和技术都具有广泛价值，但它们大多聚焦于软件构造的某个局部问题。广义可逆计算理论（Generalized Reversible Computation，GRC）试图回答一个更基础的问题：

> 软件系统最一般的构造形式是什么？一个系统在持续演化时，怎样才能把共性、生成规则与个性变化统一组织起来？

GRC 给出的核心公式是：

```text
App = F(X) ⊕ Δ
```

其中：

- `X` 是结构化描述，可以是模型、DSL、配置、元数据或其他领域对象；
- `F` 是从一个结构空间映射到另一个结构空间的生成器；
- `F(X)` 是依据已有规律生成的基础结果；
- `Δ` 是作用于目标结构空间的差量；
- `⊕` 是目标结构空间中定义的差量合并运算。

这个公式看似简单，实际上同时统一了软件构造的两个基本方向：

```text
纵向：通过 F 从一种结构生成另一种结构
横向：通过 Δ 在目标结构空间中继续修改和定制
```

GRC 的普适性，正是来自这两个方向的结合。

需要注意的是，这个公式的真正含义比"生成一个主体，然后附加一个较小的补丁"要深刻得多。这里的普适性不是来自公式的宽泛描述能力，而是来自以下三个相互关联的构造性判断：

1. **表达普适性**：只要结构空间足够完备，函数变化和数据变化造成的最终影响，都可以外化为目标空间中的结构差量。软件演化不需要在"修改规则"和"修改数据"之间二选一。
2. **构造普适性**：软件构造可以统一组织为 App = F(X) ⊕ Δ，组合结果继续参与组合。Base 与 Delta 不存在本体论区别。全量与差量只是同一种结构在特定组合关系中扮演的相对角色。不存在"本质上是核心"的结构，也不存在"本质上是补丁"的结构。
3. **工程普适性**：App = F(X) ⊕ Δ 所描述的构造关系，可以被约束为一套具体、可机械执行的技术方案。全量文件和差量文件使用同一种 DSL，被解析为同一种规范化结构，合并结果仍然是同一结构空间中的合法对象。

这一理论由国内架构师 canonical 于 2007 年提出，Nop 平台（nop-entropy）是其参考实现。本文聚焦理论脉络；工程机制与形式化细节见文末延伸阅读。

## 一、从程序最基本的形式推导 GRC

### 1. 程序的基本构造是函数作用于数据

无论采用哪一种编程范式，程序最终都可以抽象为：

```text
Y = F(X)
```

这里：

- `X` 表示输入数据、模型、环境或状态；
- `F` 表示处理规则、算法、解释器或生成器；
- `Y` 表示程序产生的结果。

函数与数据是程序空间中最基本的两类构造元素，函数作用于数据则是计算最基本的形式。

软件发生演化时，变化也只能来自两个基本方向：

```text
F = F0 + F1
X = X0 + X1
```

其中：

- `F1` 表示函数或规则的变化；
- `X1` 表示数据、模型或配置的变化。

演化后的结果为：

```text
F(X) = (F0 + F1)(X0 + X1)
```

以原始结果 `F0(X0)` 为基准，可以把其余变化统一归入目标空间中的差量：

```text
(F0 + F1)(X0 + X1) = F0(X0) ⊕ Δ
```

从而得到：

```text
App = F(X) ⊕ Δ
```

这就是 GRC 核心公式最重要的启发式来源。

### 2. Delta 同时吸收函数变化与数据变化

如果借用线性展开的直觉（本节的 `+` 只是形式记号，表示各项贡献，不是差量合并运算 `⊕`），可以写成：

```text
(F0 + F1)(X0 + X1)
= F0(X0) + F0(X1) + F1(X0) + F1(X1)
```

因此：

```text
Δ = F0(X1) + F1(X0) + F1(X1)
```

三部分分别对应：

- `F0(X1)`：输入变化通过原规则传播到输出；
- `F1(X0)`：规则变化作用于原输入；
- `F1(X1)`：规则变化和输入变化产生的耦合影响。

这说明目标空间中的 Delta 不只是“输入数据改变了一点”，也不只是“对结果打一个补丁”。它可以统一表示：

```text
输入变化 + 生成规则变化 + 输入与规则的交叉变化
```

当然，一般程序并不是线性系统，并不存在上面的线性代数恒等式，上面的分解只是一种启发式的理解。严格的数学分解可以写成：



$$

F = F0 ⊕_F ΔF \\
X = X0 ⊕_X ΔX\\
Y  = F(X)\\
Y0 = F0(X0)\\

ΔY = Y ⊖_Y Y0\\
Y  = Y0 ⊕_Y ΔY\\
$$

这里不同空间可以具有不同的差量运算。GRC 并不要求函数、输入和输出共享同一种“加法”，也不要求任意变化都具有线性性质。

ΔY 综合包含了输入变化的影响、规则变化的影响以及两者的耦合影响。这里的关键不在于 Δ 的存在性——任意两个结构之间总能定义某种差异。而在于一个构造性判断：**函数变化可以被吸收为目标空间中的数据变化。** 你不需要修改生成器本身。你可以保持 F 稳定、纯粹、确定，把大部分可变性外推到目标空间的差量中去。

如果某类差量反复出现，就把它提升为数据或生成规则；如果生成器中的特殊分支不再具有普遍性，就把它剥离为独立差量。软件信息在 F ↔ X ↔ Δ 之间迁移，是一个持续的重构过程。


### 3. 图灵机、Lambda 演算与狄拉克图景

这一推导还可以追溯到计算机科学的两个基本理论。图灵机和 Lambda 演算具有相同的计算能力（图灵完备），却选择了两个相反的极端方向：

```text
图灵机：      目标输出 = 固定的机器（无限复杂的输入）
Lambda 演算： 目标输出 = 无限复杂的机器（固定的输入）
```

- 图灵机中，状态转移规则 `F` 固定不变，纸带上的数据 `X` 随计算逐步演化。这对应于量子力学中的薛定谔图景：算符固定，态函数演化。
- Lambda 演算中，函数的复合仍然是函数，机器通过递归组合不断产生更复杂的机器，而输入可以固定为常数 `0` 这样的对象。这对应于海森堡图景：态函数固定，算符演化。

两种极端都可以写成 `Y = F(X)`。真实的软件构造介于两者之间：`F` 与 `X` 都包含已知部分和未知部分，都需要演化：

```text
F = F0 ⊕_F ΔF
X = X0 ⊕_X ΔX
```

这与量子力学中狄拉克相互作用图景的做法一致：把哈密顿量拆分为已知部分 `H0` 和扰动部分 `H1`，集中研究系统如何偏离已知模型演化。它既不固定 `F`，也不固定 `X`，而是让两者的变化都被显式表示为差量。

需要强调，这是一个启发式对应，不是数学意义上的等价定理。它的价值在于解释 `F(X) ⊕ Δ` 为什么是比两种极端更贴近工程现实的构造形式。

狄拉克图景中真正关键的，不是 H1 比 H0 小——微扰展开的便利不构成图景成立的条件——而是 **H0 与 H1 不是两类不同对象，它们只是当前分解中承担不同角色的部分。** GRC 中的 Base 与 Delta 具有完全相同的关系：选择什么作为 Base，什么作为 Delta，是一种图景选择。它不改变系统的本体结构，但决定了哪些复杂性被吸收到背景中，哪些被显式处理。更换参考图景，剩余项的表达也随之改变。同一个系统可以有多种分解，没有哪一种在本体论上更真实，只有哪一种对当前的复用、演化或发布任务更有效。

### 4. GRC的公式在比特空间自然成立

GRC的公式不是一个启发式的描述，它是一个真正可以精确成立的数学公式。

首先，`App = F(X) ⊕ Δ` 是图灵完备的构造公式。值得注意的是，图灵完备性并不需要 `Δ` 来提供：任何软件实体最终都表现为二进制比特串，在二进制比特空间中执行 `F(X)` 的就是一台通用计算机器，此时 `F(X)` 已经是图灵完备的。`Δ` 的意义不是抬高表达能力的上限——图灵完备是一种能力边界，到达即封顶——而是改变变化信息的组织方式：哪些知识进入生成器和基础模型，哪些保留为可独立演化的差量。这也解释了为什么 DSL 核心不必图灵完备：超出声明式表达范围的逻辑可以作为差量引入命令式的逃生舱口。

其次，比特空间还提供了一个最廉价的差量构造。将 `⊕` 定义为按位异或（XOR），则它满足封闭性、结合律、交换律、恒等律（单位元 `0`）和归零律（每个元素以自身为逆元），构成一个阿贝尔群。于是任意两个结构之间的差量方程总是可解：

```text
A ⊕ X = B   ⟹   X = A ⊕ B

A ⊕ B = A ⊕ (A ⊕ X) = (A ⊕ A) ⊕ X = 0 ⊕ X = X
```

也就是说，在二进制比特空间中，任何两个软件结构之间差量总是存在的，GRC 的普适性在存在性层面由此得到机械保证。

但这个证明也引入了一个真正的设计问题：比特差量的代数性质完美，语义价值却趋近于零——既无法直观理解，也缺少便利的操纵和复用手段。**差量的存在是平凡的，有价值的差量空间从来不是现成的。**

这正是 GRC 的关键主张：

> 可逆计算的要点不在于某一种具体实现已经存在，而在于可以根据需要主动构建不同的差量空间。

Docker 构建了差量文件系统空间：坐标是资源路径，删除由 whiteout 文件表达。Cordis 构建了运行时结构空间：坐标是 service key 与作用域生命周期，正逆操作由 effect 注册与 disposer 表达。Nop 构建了 DSL 语义坐标空间：坐标是元模型定义的节点类型与属性，差量合并由 `x-extends` 表达。同一个系统可以同时投射到这些空间，得到粒度、稳定性和语义强度各不相同的差量形式——空间的质量差异与选择原则见第三节和第十节。


## 二、GRC 统一了生成与定制

传统软件构造理论通常偏向两个方向之一。

### 1. 生成式编程主要处理纵向映射

```text
X ──F──> Y
```

例如：

- 从 DSL 生成代码；
- 从数据库模型生成实体类；
- 从 OpenAPI 生成客户端；
- 从 Dockerfile 生成镜像；
- 从声明式配置生成运行时对象。

生成式编程能够大量复用规律，但存在一个长期难题：

> 生成结果中的特殊需求应该放在哪里？

如果直接修改生成物，下次重新生成时修改可能丢失；如果不断向生成器中加入特殊分支，生成器又会逐渐被偶然需求污染。

### 2. Patch 类理论主要处理横向变化

```text
Y' = Y ⊕ Δ
```

例如：

- Git patch；
- Kustomize patch；
- AST rewrite；
- 配置覆盖；
- 数据库 migration；
- 插件注册；
- 图结构重写。

这些技术能够修改已有结果，却通常不讨论基础结果是如何系统生成的，也没有将生成与定制组织成统一的软件生产方式。

### 3. GRC 将两者结合

GRC 的核心不是单独的 `F(X)`，也不是单独的 `Base ⊕ Δ`，而是：

```text
App = F(X) ⊕ Δ
```

其中：

- `F(X)` 承载稳定、规律、可重复生成的共性；
- `Δ` 承载局部、特殊、偶然、变化频繁的个性。

这样可以同时避免两种问题：

- 不必为了局部定制直接修改生成物；
- 不必为了所有特殊需求不断污染基础模型与生成器。

软件信息可以在三个位置之间重新组织：

```text
F ↔ X ↔ Δ
```

一般而言：

- 稳定而普遍的规律适合进入 `F`；
- 可参数化、可描述的变化适合进入 `X`；
- 局部、偶然和特化需求适合保留为 `Δ`。

当某类 Delta 被反复使用时，可以把它提升为数据或生成规则；当生成器中的特殊分支不再具有普遍性时，也可以把它剥离为独立 Delta。

所以 GRC 不只是 Patch 理论，而是一种关于**软件信息应如何分布和演化**的理论。

### 4. 落地为技术路线：App = Delta x-extends Generator<DSL>

上述公式并不停留在抽象层面。在参考实现 Nop 平台中，`App = F(X) ⊕ Δ` 被具体化为一条可操作的技术路线：

```text
App = Delta x-extends Generator<DSL>
```

各成分与核心公式的对应关系：

- **App**：需要构建的目标应用程序；
- **DSL**：领域特定语言写成的领域模型，是关键性领域信息的高密度文本表达；
- **Generator**：编译期反复应用生成规则、从领域模型推导大量衍生结构的生成器——对应 `F(X)`；
- **Delta**：生成逻辑与目标应用之间的差异被识别、收集而成的独立差量描述——对应 `Δ`；
- **x-extends**：差量合并算子——对应 `⊕`，以类似面向切面编程的织入方式把差量作用于生成结果，涵盖增加、修改、替换、删除等操作。

其中 `Generator<DSL>` 借用类似泛型的记法，表示生成器把 DSL 作为数据对象在编译期加工转换、动态产生差量将要覆盖的基线（`x-extends` 是一个完整的词，表示对面向对象 `extends` 继承机制的扩展，不是 "x 减去 extends"）。这条路线使得共性由 Generator 从 DSL 规律性地批量生成，个性被隔离为可独立存放、组合、审计的 Delta 文件，二者在统一的坐标体系中合并为最终应用；其工程机制（Delta 目录覆盖、`x:gen-extends`/`x:post-extends` 元编程等）见文末延伸阅读。

Generator 的特殊之处不在于它生成了"主体"，而在于它可以利用规律批量产生结构。手工编写的模型与生成得到的模型进入同一个结构空间之后，拥有相同的组合地位。生成、手写、插件和定制不是互斥的软件来源，它们最终都表现为目标结构空间中的贡献项。

## 三、为什么独立 Delta 必然要求结构坐标

并不是所有“变化”都已经是合格的结构 Delta。

如果一个变化要能够：

- 独立保存；
- 独立传输；
- 脱离基础系统管理；
- 与其他变化组合；
- 准确作用于目标结构；
- 在必要时被删除或撤销；

它必须能够回答：

> 这个变化作用于结构的哪个位置？

因此，Delta 的独立存在隐含要求系统具有稳定的结构坐标。

### 1. 变化所在的空间本身有质量差异

同一个业务修改，落在不同的差量空间中，质量完全不同：

```text
二进制空间    byte offset             机械完备，语义噪声极高
文本空间      文件路径 + 行号          生态成熟，坐标脆弱
AST 空间      类 / 方法 / 节点         结构化，但常绑定具体语法
文件层叠      路径 + 层                适合镜像叠加，粒度偏粗
DSL 语义空间  entity / column / step   坐标稳定，业务语义强
CRDT/OT 空间  操作 / id / 时钟         并发收敛强，领域语义需额外建模
```

同样是“把字段长度改成 40”，写成一行文本 diff 和写成一次 ORM 模型属性覆盖，局部效果相同，长期演化成本却完全不同。因此 GRC 的关键主张不是“要不要打补丁”，而是：

> 变化所在的表示空间本身是一等设计对象。与其被动接受源码文本这个低质量空间，不如主动设计高质量的语义坐标系。

这也解释了传统扩展点机制的局限：扩展点相当于预先挑选出来的少数坐标，变化只有恰好落在这些坐标上才能被容纳；DSL 元模型则把整个可模型化资产都变成可寻址空间。一句话概括：

> 扩展点机制预判变化位置，GRC 设计变化空间。

### 2. 坐标是差量独立存在的前提

差量总是相对于某个结构空间定义的。没有稳定的结构坐标，就无法回答：变化作用在哪里、新旧节点如何对应、删除了什么、哪些修改发生冲突、一个差量如何继续被另一个差量修改、基础升级后差量如何迁移。

典型坐标包括：

- 文件系统中的资源路径；
- 数据库中的表名、主键和字段名；
- DSL 中的节点类型与业务 key；
- AST 中的节点身份；
- Kubernetes 中的资源身份与字段路径；
- 运行时中的 service key、realm、scope 和 fiber；
- 插件系统中的工具名、事件名和服务名。

若坐标稳定，则局部变化不会因无关结构的增删而漂移。

例如，文件路径通常是稳定坐标：

```text
/config/app.yaml
```

增加另一个文件不会改变该路径。

而纯文本行号通常是不稳定坐标。前面插入一行，后续行号就会整体漂移。Git 因此不能只依赖行号，而需要上下文匹配、三方合并等补充机制。此外，merge 冲突产物已经脱离合法源码空间，patch 又与特定基线强耦合、难以脱离基线预先组合。这说明仅有差量记录并不够，差量的代数性质取决于坐标与合并运算的设计。

Dijkstra 反对 goto 的科学理由正是：无约束的 goto 使得 "it becomes terribly hard to find a meaningful set of coordinates in which to describe the process progress"。GRC 对 Dijkstra 思想的深化在于：不仅要有一个坐标系，还要让这个坐标系支持差量运算。

坐标化存在粒度层次。任意代码文件至少可以作为原子结构节点：

```text
文件 → 模块 → 声明 → AST 节点 → 领域语义节点
```

坐标越细，差量合并越精确，但成本也越高。GRC 允许每个层次明确自己的可逆边界。坐标化程度决定差量操作的粒度，而不是决定对象能否进入差量体系

### 3. 坐标建立之后才能定义差量代数

对于每一个结构坐标，需要进一步定义：

- 该坐标允许存放什么值；
- 新值如何与旧值合并；
- 同名贡献是覆盖、报错还是累加；
- 删除如何表达；
- 多个变化是否可交换；
- 冲突如何判断；
- 哪些差异在观测上可以忽略。

因此，不同结构空间可以具有不同的 `⊕`：

```text
文件系统：路径覆盖与 whiteout
配置树：字段覆盖和节点删除
集合：并集、差集
事件表：监听器累加与注销
中间件链：有序插入与反序撤销
CRDT：join
Cordis：effect 注册与 disposer
Nop DSL：x-extends 与 x-diff
```

GRC 不要求所有结构共享一种万能合并算法。它要求的是：

> 每一个结构空间都应显式建立自己的坐标体系、差量元素、组合运算和等价关系。

这使 GRC 成为元理论，而不是某一种特定 Patch 格式。

## 四、全量与差量在 GRC 中是统一的

传统系统经常把 Base 和 Patch 看成两种本体完全不同的对象：

```text
Base 是完整系统
Patch 是附加修改
```

GRC 则指出：

```text
A = 0 ⊕ A
```

任何全量结构都可以看作相对于零结构的差量。

这里的零并不意味着不存在运行环境，而是指目标结构空间中没有业务贡献的单位元。例如：

- 空目录仍然存在于文件系统中；
- 空配置仍然服从配置 schema；
- 空插件运行时仍然拥有 Context 和生命周期机制；
- 空模型仍然存在于某个元模型定义的结构空间中。

因此，“一切皆差量”的严格含义是：

> 在一个已经建立差量运算的结构空间中，全量只是相对于零元的特殊差量。

这种统一带来了重要的闭包性：

```text
Δ = Δ1 ⊕ Δ2
App = F(X) ⊕ Δ1 ⊕ Δ2
```

Delta 不再是依附于 Base 的二等对象，而是结构空间中的一等元素。

闭包还要求 `⊕` 具备良好的代数性质，其中最实用的是结合律：

> 只要 `(Δ1 ⊕ Δ2) ⊕ Δ3 = Δ1 ⊕ (Δ2 ⊕ Δ3)` 成立，一条差量链就可以先任意分组预合并成单个 Δ 再作用于基线，结果与逐步叠加一致。

这正是差量能够独立制作、离线组合、集中审计的数学前提。当然，这些性质并非自动成立，它依赖稳定的结构坐标以及“先合并、后验证”的阶段安排（见第六节第 3 小节）。

### 组合具有方向和顺序

结构叠加通常不可交换：

```text
A ⊕ B ≠ B ⊕ A
```

一个 Delta 定义节点，另一个覆盖它；一个插件注册服务，另一个依赖该服务。系统表现为有序组合：

```text
System = Δ_n ⊕ Δ_{n-1} ⊕ ... ⊕ Δ₁ ⊕ 0
```

差量层的顺序代表依赖关系、装载时序、覆盖优先级、产品派生层次。

## 五、GRC 为什么能够处理“差量的差量”

很多扩展系统只能在第一层增加功能：

```text
Base + Plugin
```

但当需要修改插件内部行为时，往往必须：

- Fork 插件；
- 增加新的专用扩展点；
- 引入插件的插件；
- 通过配置开关预埋所有可能需求；
- 复制代码后整体替换。

原因是插件本身虽然被当成差量，但插件内部仍然是不透明代码，没有暴露稳定的结构坐标。

GRC 要求 Delta 自身也是结构化对象，因此仍然可以继续接受 Delta：

```text
App = F(X) ⊕ Δ1 ⊕ Δ2
```

其中 `Δ2` 可以定制 `Δ1` 引入的节点。只要新增结构和基础结构使用同一个坐标体系，就不需要另造一套“扩展扩展点”的机制。

这就是所谓：

> 差量的差量仍然是普通差量。

它使定制机制具有递归性和闭包性：

- Base 可以被 Delta 定制；
- Delta 引入的结构可以被后续 Delta 定制；
- 生成结果可以被 Delta 定制；
- Delta 本身也可以由 Generator 生成；
- 最终结果仍然可以继续参与同一种合并运算。

这是 GRC 比普通插件系统和配置覆盖机制更具普遍性的关键原因之一。


## 六、正差量、负差量与逆的统一分析

GRC 中的 Delta 不只表示“增加”。

一个结构 Delta 可以同时包含：

```text
Δ = (+A, -B, modify C)
```

也就是：

- 增加结构；
- 删除结构；
- 修改结构；
- 替换结构；
- 移动或重组结构。

### 1. 逆不等于逆向执行

GRC 所说的可逆，并不要求把程序的每一步执行历史倒放，也不要求撤销所有物理副作用。

它关注的是：

> 结构空间中的变化是否可以被表示、分离和反向处理。

例如：

- 文件新增的逆可以是 whiteout；
- 节点增加的逆可以是节点删除；
- 监听器注册的逆可以是注销；
- 服务提供的逆可以是撤下绑定；
- 模型覆盖的逆可以通过相反结构 Delta 表达。

需要澄清的是，这里的“可逆”与物理学中的可逆计算（Landauer 原理讨论信息擦除与能耗下界）、逻辑可逆计算（Bennett 讨论运行时状态转移的双射性）不在同一层次。GRC 不承诺每一步操作都能无损回滚，也不讨论能耗；它研究的是构造期的结构变化能否被表示、组合、剥离和补偿。“可逆”在这里是一种分级承诺：核心结构变化尽量可组合、可剥离，真正不可逆的外部副作用被显式隔离在边界上。

### 2. 历史撤销和独立负差量并不相同

Cordis 一类运行时系统通常提供：

```text
执行 Δ
→ 当场得到 disposer
→ 以后调用 disposer 撤销 Δ
```

这是与正向历史绑定的逆。

而完整的结构差量还可以表达：

```text
Δ = -B
```

这个负差量可以：

- 独立保存；
- 脱离原始正向操作存在；
- 与其他 Delta 预先组合；
- 作用于满足条件的不同 Base；
- 继续接受后续差量。

因此，GRC 能够统一分析两种机制：

- 运行时的能力式撤销；
- 编译期或模型空间中的声明式负差量。

前者适合资源生命周期，后者适合细粒度结构定制。

### 3. 删除为什么可以安全表达

前面反复出现删除和覆盖，一个自然的问题是：合并过程中信息丢失了怎么办？

GRC 的做法是把合并和验证分成不同阶段。合并发生在一个潜在结构空间中：被删除的节点先标记为墓碑（tombstone）而不是立即物理抹掉，替换和顺序约束也作为证据保留下来；整条差量链合并完毕后，才统一执行规范化、投影和验证，清除中间证据，得到最终可运行的模型。

```text
S：Structure Merge    结构合并，允许墓碑与暂时不一致存在
N：Normalization      规范化，展开简写、规约顺序约束
V：Validation         验证，业务合法性只在链尾统一判定
```

这个阶段分离解释了 `⊕` 为什么可以可靠工作：中间状态不必立刻合法，合法性检查推迟到链尾统一进行；结合律等代数性质正是在这条边界内才成立。

### 4. 从“相同才可复用”到“相关即可复用”

负差量让软件复用的含义发生了变化：

```text
面向对象：A > B         继承，能表达“多”，不能表达“减”
组件化：  A = B + C     组合，“多的部分”成为可复用组件
可逆计算：B = A + (-C)  差量，相关即可复用
```

要从系统 `X = A + B + C` 得到系统 `Y = A + B + D`，传统方式必须把 X 拆解成干净的组件再重组；在 GRC 中只需一个包含 `-C + D` 的 Delta：

```text
Y = X ⊕ Δ    其中 Δ 包含 -C 和 D
```

复用不再要求事先拆出干净的组件，而是可以直接在任何已有系统上做加法和减法。这对产品线工程尤其重要——行业基线、区域适配、客户定制可以作为一串独立的差量层叠加：

```text
Effective System = Base ⊕ Δ_Industry ⊕ Δ_Region ⊕ Δ_Customer
```

## 七、编译期结构空间与运行时结构空间的统一

软件并不只存在于代码和配置中，也存在于运行时。

可以把软件相空间分为两个基本层次：编译期结构空间和运行时结构空间。

### 1. 编译期结构空间

包括：

- DSL；
- 配置；
- 模型；
- AST；
- schema；
- 生成规则；
- 部署描述。

其 Delta 通常表现为：

- 节点覆盖；
- 字段修改；
- 结构删除；
- 模型继承；
- Patch 合并；
- 差异提取。

### 2. 运行时结构空间

包括：

- 服务绑定；
- 依赖图；
- 插件实例；
- 事件监听器；
- 工具注册；
- 资源句柄；
- scope 和生命周期。

其 Delta 通常表现为：

- 注册和注销；
- 安装和卸载；
- 激活和停用；
- provider 替换；
- 依赖重新收敛；
- 运行时作用域创建与销毁。

> Nop平台提供了编译期空间的实现 **M ⊕ M → M**：差量文件与全量文件使用同一种 DSL，被解析为同一种规范化结构，合并结果仍然是合法模型。
> 而Cordis提供的是运行时结构空间的实现 **End(C) ∘ End(C) → End(C)**：插件是上下文变换 P: C → C，两个插件的复合仍然是上下文变换。TypeScript 只是插件的宿主语言，不决定它是否是 Delta。关键在于插件是否以统一协议向 Context 提供可组合、可追踪、可撤销的结构贡献。

于是完整软件可以进一步表示为：

```text
Model   = F(DSL) ⊕ Δcompile

Runtime = Activate(Model) ⊕ Δruntime
```

编译期 Delta 决定“注册什么”，运行时 Delta 决定“何时以及如何激活、撤销和重新收敛”。

这说明 GRC 不是仅适用于模型驱动开发，也不是仅适用于动态插件。两者只是差量思想作用于不同结构空间的具体形式。

### 3. 纵向分解：多阶段生成链

同一公式还可以沿生成过程纵向堆叠成生产线，每一段知识都可以选择进入上游模型或本阶段 Delta：

```text
XMeta = Generator<XORM>  ⊕ Δ_meta
XView = Generator<XMeta> ⊕ Δ_view
XPage = Generator<XView> ⊕ Δ_page
```

这解决了传统 MDA 的两难：上游模型不必预先内置所有信息，意外需求也不必回灌污染上游——它们都成为对应阶段的 Delta。

### 4. 横向协同：多 DSL 图册

单一 DSL 表达能力有限。多个 DSL 可以并行分工，各自生成目标结构的一部分，跨领域协调和意外需求交给残差 Delta：

```text
App = G1(DSL1) ⊕ G2(DSL2) ⊕ Δ
```

例如 ORM 模型描述数据、任务流模型描述流程、页面模型描述界面。每个 DSL 专注自己的领域，Δ 负责处理它们的接缝。

### 5. 多重表象：推导加修正

只要多个表象围绕同一语义内核，就可以无损互转：XML、JSON 乃至 Excel 都是同一模型的不同表象。可视化设计器也可以看作一种表象——由模型自动推导出基本界面，再通过 Delta 对推导结果做精细修正。“推导加修正”取代“从零绘制”，编辑行为本身也被差量化了。

### 6. 生成器实际上是一种坐标变换

如果：

```text
Y = G(X)
```

那么 X 和 Y 往往处于不同的结构空间。X 是领域模型，Y 是数据库模型、页面模型、代码或配置。生成器不只是“减少手工代码”的工具，它是一种从坐标空间 X 到坐标空间 Y 的变换：

```text
G : S_X → S_Y
```

关键问题在于，输入空间的差量不一定能自动映射为输出空间的差量：

```text
G(X ⊕ ΔX) ≟ G(X) ⊕ ΔY
```

即使 ΔY 存在，也未必能够低成本或唯一地求出。

可逆计算并不要求所有生成器都自动可逆，也不要求所有差量都能无损穿过生成器。实际的做法是允许在每个坐标空间中分别引入差量：

```text
Y_effective = G(X ⊕ ΔX) ⊕ ΔY
```

这样，能在上游表达的变化放在 ΔX 中；只对生成结果有意义的变化放在 ΔY 中；不必把所有信息强行塞入一个源 DSL；也不必直接手改生成结果。

因此生成与定制可以正交组合。生成器承担跨空间的规律性变换，差量承担各自空间内的局部修正。生成器的输出不是构造的终点，而是下一个差量叠加的基线。


## 八、为什么其他通用理论通常只是 GRC 的局部

### 1. Change Actions：研究变化如何作用和传播

Change Actions 的核心是：

```text
a' = a ⊕ δa
```

以及：

```text
f(a ⊕ δa) = f(a) ⊕ ∂f(a, δa)
```

它深入研究输入变化如何传播为输出变化，是增量计算的重要代数基础。

但它通常从已经给定的三元组开始：

```text
(A, ΔA, ⊕)
```

它不主要回答：

- 软件结构怎样建立稳定坐标；
- Delta 如何成为可独立部署的软件资产；
- 生成器自身变化如何进入统一构造；
- 生成结果如何在不修改源模型的情况下被定制；
- 正负差量如何用于产品化开发；
- 编译期与运行时结构如何统一。

因此，Change Actions 可以形式化 GRC 的“差量作用和传播”，但不能覆盖 GRC 的全部软件构造图景。

### 2. 图变换：研究结构如何匹配和重写

图变换使用：

```text
L ← K → R
```

精确表达：

- 删除 `L-K`；
- 保留 `K`；
- 增加 `R-K`；
- 规则匹配；
- 并发独立性；
- critical pair 和冲突。

它在图结构的局部重写方面形式化程度很高，但通常预设结构已经被表示为图，重写规则和匹配机制已经存在。

图变换主要回答：

> 一条结构修改规则怎样合法作用于一张图？

GRC 则还要回答：

> 这张图如何由其他模型生成？为什么特殊需求应保留为独立 Delta？Delta 如何跨产品复用？生成、定制、逆向提取和运行时演化如何进入同一构造体系？

所以图变换可以成为 GRC 中某种结构空间的具体 `⊕`，却不是完整的 GRC 替代品。

### 3. Patch Theory：研究变化的上下文、组合与逆

Patch Theory 把变化表示为：

```text
p : A → B
```

并研究：

- Patch 组合；
- Patch 交换；
- 上下文依赖；
- Merge 与 Rebase；
- 冲突；
- 逆 Patch。

它非常适合描述 Cordis 中：

```text
install : S → S'
dispose : S' → S
```

但它通常不负责解释：

- `A` 如何由 `F(X)` 生成；
- Patch 的结构坐标怎样由元模型建立；
- Patch 如何成为软件产品线中的独立定制层；
- 差量如何递归地继续差量化；
- 编译期模型与运行时结构如何统一。

因此 Patch Theory 深入处理的是 GRC 中“差量的组合、上下文和逆”这一局部。

### 4. Lens：研究双向同步

Lens 主要处理：

```text
Source ↔ View
```

以及往返规律和一致性维护。它适合形式化：

- 模型变换；
- 视图更新；
- 信息丢失；
- 变化反向传播；
- 往返等价。

从 `get`/`put` 的良性定律，到对称 Lens 的守静原则，再到把编辑本身作为传播实体的 δ-lens，Lens 理论为“两模型一致性”问题提供了深刻而优雅的形式化骨架。

但两者的基本公设不同：

- Lens 通常依赖对齐算法、踪迹（trace）或补语（complement）来判断“谁对应谁”，视图更新如何回写源模型是一个后验求解问题；
- GRC 则把稳定的结构坐标作为建模前提，变化精确锚定在坐标上，从源头上规避了对齐难题。

两者的差量地位也不同。Lens 中的差量多是一次同步过程中的瞬时输入；GRC 的差量是可独立保存、版本化、分发和审计的一等公民资产。在系统尺度上，Lens 刻画的是点对点的 `A ↔ B` 关系，多条链路的串接需要额外的组合证明；GRC 通过统一的坐标体系和合并运算支持系统级闭环。

因此，Lens 可以看作 GRC 在 `Y = F(X)` 这一受限情形（即 `Δ` 为空）下，对 `F` 与其近似逆之间关系的精细化研究。δ-lens 的编辑传播与 GRC 为生成器规定的同态契约 `F(X ⊕ ΔX) ≡ F(X) ⊕ ΔY` 直接对应：GRC 中的 `x-diff`、差量提取和表象转换可以借助 Lens 理论形式化和验证。但 GRC 还处理多层 Delta、生成后定制、产品差异、运行时插件等更大的问题域，Lens 只是其中一个局部的理论支撑。

### 5. FOP：以特征叠加构造产品线

Feature-Oriented Programming 把“特征”当作组合单元：特征是客户可感知、可选择的功能单位，产品由特征选择经生成器装配而成。它的两个基本洞见至今有效：

- 业务层面的特征往往无法与对象或函数分解结构对齐，几乎必然成为横切关注点——有用的特征都是分布式的；
- 用语言无关的特征结构树（FST）描述制品，用树叠加（superimposition）按节点名称逐级合并，就可以让合并算法与具体业务无关。Feature Algebra 进一步把这种组合刻画为具有代数性质的运算。

FST 实际上已经触及 GRC 的核心洞察：树中任意节点到根的路径唯一，因而可以作为坐标使用；坐标固定之后，坐标点上的合并过程完全通用。这是结构坐标思想在代码制品领域的重要先声。

但 FOP 存在一个关键缺口：它只定义了覆盖和新增，没有删除操作，无法从既有产品中移除特征，也就无法表达负向变化。这一缺陷直接催生了 DOP（Delta Oriented Programming）。此外，FeatureHouse 一类的工作虽然实现了跨语言的树合并，但它们始终是外置于语言的工具或框架，差量能力并没有内建到语言核心和加载机制之中。

### 6. Delta-Oriented Programming：研究产品变体

DOP 针对特征无法删除的缺陷，抛弃特征的业务解读，把变化直接定义为差量模块，引入了含删除语义的操作：

```text
Product = Core ⊕ Δ1 ⊕ Δ2 ...
```

后续工作甚至发现，在存在单位元的情况下，Core 本身也可以由纯差量组合而成。这条演进线索与 GRC“全量和差量互相转化”的判断完全一致。

但从 GRC 的视角看，DOP 仍存在几个结构性局限：

- **Core 的来源被排除在外**。DOP 的理论焦点是差量的组合，Core 如何构造通常被假定为外部给定问题。GRC 通过 `Generator<DSL>` 把基线的生成也纳入统一构造理论。
- **坐标系由实现语言承载**。DOP 的差量作用于通用编程语言的类结构之上，这类坐标容易受重构和风格变化影响；GRC 主张主动设计 DSL，建立更稳定的领域语义坐标。
- **差量与全量不同构**。DOP 的差量以修改动作的形式出现，与全量的表达方式截然不同，因此难以进一步表达“差量的差量”。GRC 中全量只是相对零元的差量，两者可以用同一个 schema 约束，差量的差量仍然是普通差量。
- **停留在同一抽象层次**。DOP 主要在同层管理产品线可变性；GRC 引入生成器后，差量可以跨抽象层次传输，生成器需满足宽松同态定律：

```text
G(X ⊕ ΔX) ≈ G(X) ⊕ transport_G(ΔX)
```

即源空间中的差量可以被翻译为目标空间中的等价差量。

因此 DOP 可以看作 GRC 在软件产品线领域的一个重要特例。GRC 将这一模式进一步推广到任意 DSL、模型、配置、文件系统、数据结构和运行时插件，并补充了多阶段编译、统一加载器等工程基建；多 DSL 协同本来就不是 DOP 的核心问题。

### 7. SPLE：有变体管理，缺统一的构造机制

软件产品线工程（SPLE）通过领域工程与应用工程的分离管理产品家族的共性和差异，特征模型刻画问题空间中的可变性。GRC 与其目标一致，但给出了更底层的构造机制：一个客户特性不是特征选择矩阵里的一个勾选项加一段手工映射，而是一组直接作用于 ORM、流程、页面、权限等 DSL 坐标的同构差量文件。特征选择由此直接进入构造链 `Base ⊕ Δ1 ⊕ ... ⊕ Δn`，而不是停留在配置决策层。

因此 GRC 可以看作 SPLE 的一种代数化实现路线，而不是 SPLE 方法论的替代物。

### 8. MDE 与语言工作台：有生成、有编辑，缺差量代数

模型驱动工程以生成为中心，与 GRC 公式中的 `Generator<DSL>` 高度一致，但经典 MDE 在处理生成后的例外需求时较为刚性，往往退回到手写修改、文本补丁或模板条件分支。GRC 要求生成结果继续落在可寻址的结构空间中，使 `F(X)` 成为后续差量的基线，而不是生成流程的终点。

以 MPS 为代表的语言工作台提供了强大的 DSL 定义与投影编辑能力，但没有内置差量合并与分解的概念。GRC 则把异构 DSL 归一到统一结构层，在其上定义显式的差量代数，并为同一模型提供多种可逆表象。在这幅图景中，语言首先是变化坐标系，其次才是编辑对象。

### 9. 范畴论：比 GRC 更抽象，但不等于更有软件解释力

范畴论可以把：

- 结构视为对象；
- 变化视为态射；
- 变化组合视为态射复合；
- 可逆变化视为同构；
- 生成器视为函子。

这种表达比 GRC 更抽象，也能够容纳更一般的数学对象。

但“所有变化都是态射”并不能直接告诉软件工程师：

- 如何建立稳定坐标；
- 如何组织 Delta 文件；
- 如何表达节点删除；
- 如何隔离产品定制；
- 如何避免生成器被特殊需求污染；
- 如何实现统一模型 Loader；
- 如何把编译期 Delta 与运行时资源生命周期结合。

更高的抽象程度不自动意味着更强的软件工程解释力。GRC 的优势在于它位于数学抽象与工程实践之间：既足够一般，又能够导出具体的软件构造原则。

## 九、GRC 的解释力来自完整闭环

GRC 的优势不是每一个局部数学问题都比现有理论研究得更深，而是它形成了一个更完整的软件构造闭环。前文各节分别论证过的能力，可以排列为一条完整的链路：

```text
X                                          结构描述（第一节）
F(X)                                       Generator 生成基础结构（第二节）
App = F(X) ⊕ Δ                             独立 Delta 完成个性化（第二节）
Δ = Δ1 ⊕ Δ2 ⊕ Δ3                           Delta 预先组合（第四节）
A = 0 ⊕ A                                  全量只是特殊差量（第四节）
Δ' = Δ ⊕ Δ2                                差量的差量（第五节）
Δ = (+A, -B, modify C)                     正负变化统一表达（第六节）
Δ = diff(App, F(X))                        从结果反向提取差量（第六节）
Runtime = Activate(Model) ⊕ RuntimeDelta   扩展到运行时（第七节）
```

这些环节不是互不相关的功能集合，而是围绕同一个结构差量概念首尾相接：

```text
生成 → 合并 → 定制 → 删除 → 组合 → 逆向提取 → 继续演化
```

Change Actions、图变换、Patch Theory、Lens 以及 FOP/DOP 分别深入研究闭环中的一环；GRC 则提供它们在软件构造中的总体位置。

## 十、GRC 的广泛适用范围

只要某个领域能够建立稳定结构坐标，就可以在该领域定义 Delta：

```text
文件与镜像：DockerImage = DockerBuild<Dockerfile> ⊕ OverlayLayers
Kubernetes：DeploymentConfig = Build<BaseYaml> ⊕ KustomizePatch
DSL 与模型：ApplicationModel = Generate<DomainDSL> ⊕ ModelDelta
软件产品线：CustomerProduct = Generate<ProductModel> ⊕ CustomerDelta
数据库与事件：CurrentState = Fold<InitialState, Events> ⊕ CorrectionDelta
UI：UI = Render<State> ⊕ RuntimePatch
Agent 运行时：AgentRuntime = Activate<Profile> ⊕ PluginDelta
```

## 十一、普适并不意味着“所有东西都自动可逆”

GRC 的普适性不应被误解为：

- 所有业务副作用都可以自动回滚；
- 所有 Delta 都天然可交换；
- 所有结构都已经具备稳定坐标；
- 任意删除都能够无损恢复；
- 所有合并都不会产生冲突。

相反，GRC 会迫使设计者明确回答：

1. 差量作用于哪个结构空间？
2. 该结构空间的稳定坐标是什么？
3. `⊕` 如何定义？
4. 删除信息是否被保存？
5. 逆是严格逆、局部逆还是补偿？
6. 哪些操作可以交换？
7. 哪些顺序必须通过依赖显式表达？
8. 恢复采用什么观测等价？
9. 不可逆副作用位于什么边界？
10. 生成器是否确定？是否隐式依赖时钟、随机数或外部状态？
11. 并发产生的差量如何交换与合并？是否需要 CRDT、OT 或三方合并机制接入？

因此，GRC 的作用不是取消领域差异，而是提供一个统一框架，使不同领域的差量问题能够被系统地识别和组织。

## 十二、GRC 的工程实现

GRC 能够指导具体的软件组织：

- 共性进入生成器和基础模型；
- 个性进入独立 Delta；
- 不直接修改生成物；
- 不让偶然需求污染核心；
- 通过统一坐标实现深层定制；
- 通过差量链组织产品演化；
- 通过运行时逆管理动态结构；
- 通过差量提取恢复变化来源。

这使 GRC 不只是一个事后解释框架，也是一种能够指导架构设计和工具实现的软件构造方法论。

GRC 的实现不是将 apply/diff/merge 等抽象为一个通用的接口——那样做虽然有一定价值，但统一程度很弱：接口统一了，具体差量语义仍然散落在各个领域中，无法形成可递归组合的结构空间。GRC 的设想，不是为每种对象发明一种补丁算法，而是把不同对象映射到可统一处理的结构空间。

具体路径是：

1. 先把不同领域结构统一投影到规范化模型空间；
2. 在该结构空间中建立通用坐标；
3. 使用统一的差量合并语义；
4. DSL 只声明领域结构与少量特定规则；
5. 通用模型装载器完成大部分差量操作。

因此，它不是：

```text
为每种对象发明一种补丁算法
```

而是：

```text
把不同对象映射到可统一处理的结构空间
```

这与编译器把不同高级语言降低到统一 IR 有某种相似性：

> 统一并不发生在任意原始对象层面，而发生在一个经过设计的中间表示层面。

## 结语

本文从程序最基本的 `F(X)` 形式出发，经由结构坐标、差量代数与正负变化的论证，得到软件构造的通用标准形 `App = F(X) ⊕ Δ`。它的普适性并不是因为把一切变化简单地重新命名为 Delta，也不是要取代 Change Actions、图变换、Patch Theory、Lens、FOP 或 DOP——这些理论分别深入研究了闭环中的一环，GRC 为它们提供的是一张更完整的软件构造地图。

从这个意义上说，广义可逆计算不是某一种插件技术、模型合并技术或 Patch 算法，而是一种关于**软件如何生成、如何偏离、如何组合以及如何持续演化**的普适构造理论。
