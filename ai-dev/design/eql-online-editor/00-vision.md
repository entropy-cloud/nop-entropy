# EQL 在线编辑与测试工具 Vision

## 1. 产品定位

EQL 在线编辑与测试工具（下称「EQL 控制台」）是 Nop 平台的**开发/运维工具**，不是一个面向终端用户的通用数据库客户端。

- 使用者：Nop 应用的开发者、实施人员、运维排障人员。
- 核心价值：让 EQL 从「写进代码/配置、重启或发版才能验证」变成「在浏览器里即时编写、校验、执行、看结果」。
- 差异化：多数开源 SQL 客户端只把 SQL 文本丢给数据库执行；EQL 控制台在**执行前**即可完成语法解析、实体/属性语义校验、目标方言 SQL 编译与列元数据推导，因此能提供更早、更准确的错误提示与「EQL → SQL」预览。

## 2. 使用场景

| 场景 | 用户动作 | 期望结果 |
|---|---|---|
| 编写/调试实体查询 | 选实体 → 编辑器补全属性路径 → 执行 | 正确生成 SQL 并返回结果；错误定位到行列 |
| 验证语义 | 输入 EQL → 校验 | 指出未知实体/属性/别名/缺 JOIN 条件，并给出编译后 SQL |
| 排查数据问题 | 在预发/测试环境执行只读查询 | 结果表格可翻页、复制、导出；执行耗时可见 |
| 验证写语句（受控） | 显式开启写权限后执行 DML | 影响行数可见；默认只读下被拒绝 |
| 学习 EQL 语法 | 从实体树/片段库插入模板 | 快速获得可执行的最小查询 |
| 集成到排障流程 | 页面 URL 可分享、可带 querySpace/实体参数进入 | 打开即定位到目标实体 |

## 3. 成功标准

- S1：开发者无需离开浏览器即可完成 EQL 的「写—校验—执行—看结果」闭环，且结果列名/类型与 JDBC/ORM 一致。
- S2：EQL 语义错误能在 1 秒内以行列级诊断展示；compiled SQL 可作为可复制文本查看。
- S3：新增一种 SQL-like 方言只需提供配置（profile），不需要修改 `code-editor` 执行分支或新增 renderer type。
- S4：默认配置下工具不会造成写库操作；只读、行数、权限、数据权限四条护栏在服务端强制执行，且权限链路为 fail-closed（action-auth 未开启时控制台拒绝服务而非放行）。
- S5：`nop.debug=false` 的应用中控制台 API 不可用；生产应用默认不装配控制台模块（因此页面/菜单不出现）；若已装配，页面显示「未启用」并提供排障提示。
- S6：交付通过「flux → next → entropy」三仓同步链路完成；主路径能力（打开页面/实体树/补全/校验/执行/结果/错误定位/权限拒绝/标签切换状态保持）可在 demo 应用被 Playwright E2E 覆盖，增强能力（格式化/导出/历史/写开关二次确认/元数据失败态）由前端单测 + 页面验收覆盖。

## 4. 不可违反的约束

| # | 约束 | 说明 |
|---|---|---|
| C1 | 单一事实源 | 方言能力、诊断协议、执行结果字段只在一处定义（本目录 `01/02/03`）；前后端不得各存一份能力矩阵 |
| C2 | 配置化方言 | EQL 是「SQL-like Dialect Profile」的一个实例；通用组件不出现 EQL 专有分支 |
| C3 | 薄前端 | 前端不解析 SQL 做权威语义判断、不做安全判定；语义/安全以后端编译与 gate 为准 |
| C4 | 安全默认拒绝 | 默认只读；DML 需显式配置与权限；DDL 由 EQL 文法结构性排除、事务语句编译期拒绝；控制台必须先启用数据权限过滤（`enableFilter`），其实际生效还依赖平台 data-auth 配置 |
| C5 | 诊断可定位 | 语法/语义错误若携带位置，必须能映射为 1-based 行列并驱动编辑器标注；无位置时显式降级 |
| C6 | 零回归 | 改造不得破坏 `code-editor` 现有 13 种语言、5 个 SQL 方言、diff/colorize/fullscreen/变量面板行为 |
| C7 | 授权边界 | 外部实现的架构可借鉴，源码不可复制（GPL/自定义许可项目只做 clean-room 实现） |
| C8 | 交付可验证 | 主路径能力必须通过三仓同步后在 demo 应用被 E2E 验证；增强能力至少被前端单测/页面验收覆盖；不手改 `nop-web-site` 产物 |

## 5. Non-goals

- 不做通用多数据库客户端：不托管数据库连接凭据、不做驱动管理 UI、不做 ER 图、不做数据编辑（v1）。
- 不做 DDL 执行：EQL 文法结构性排除 DDL；commit/rollback 虽在文法中，但编译期显式拒绝。
- 不做原生 SQL 控制台（可作为后续独立能力；其安全模型与本工具不同）。
- v1 不做 EQL 语言级命名参数（控制台用「命名参数映射 + 顺序」覆盖 UX），也不做注释 hint/数据库 `/*+ */` 透传；后者列入 v2 评估。
- 不做 Notebook/DataDoc 模型、团队协作与分享、查询定时调度。
- 不做 AI/NL2EQL。
- 不引入 Monaco/Ace 作为第二套编辑器内核；编辑器继续基于 CodeMirror 6。
- 不替代 `nop-metadata` 的联邦元数据/BI 语义层，也不替代 `nop-report` 的报表渲染。

## 6. 必须由人裁定的决策点

以下问题不由 AI 自行决定，需 owner 明确：

1. **生产启用策略**：控制台是否允许出现在生产环境（当前设计以 `nop.debug=true` 为总开关；生产是否可临时开启、如何审批）。
2. **写操作开放度**：默认只读；是否允许在特定环境（dev/uat）开放 DML，以及是否要求「无 WHERE 更新/删除」二次确认。
3. **元数据暴露粒度**：普通只读用户是否可见全部实体名/属性，还是按 action-auth/白名单裁剪。
4. **历史与保存查询的归属**：v1 使用浏览器本地存储；是否需要在服务端持久化、是否涉及多租户隔离与保留策略。
5. **独立 app 交付形态**：是否提供 `nop-eql-console-app` 独立 Quarkus 宿主。设计默认 v1 不交付独立 app、先挂 demo 应用联调；如需改变由 owner 裁定并更新本目录。

## 7. 收敛路径

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| V1 核心闭环 | Dialect Profile + entity-path 补全 + 格式化 + validate/execute API + 工作台页面（单语句、默认只读）；querySpace 只能选择已配置数据源；受控写模式随 V1 交付但默认关闭，开放度由 owner 裁定 | S1/S2/S4/S5 达成；E2E 主路径通过 |
| V1.5 体验完善 | 多标签状态、历史/收藏（浏览器本地）、结果分页、复制为 CSV/JSON、错误定位跳转、写开关二次确认 | 页面可用性达到「日常调试可用」 |
| V2 扩展 | EXPLAIN、多 querySpace 切换/多数据源、服务端历史/保存查询、异步执行/结果物化、文件导出、NL2EQL | 由 owner 另行裁定并单独立项 |

阶段之间的边界为能力边界，不是交付承诺；任何进入 V2 的能力必须先更新本目录设计文档。
