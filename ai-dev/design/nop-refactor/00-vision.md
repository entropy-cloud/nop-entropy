# Nop Refactor — Vision：AI-First 代码修改工具

**日期**：2026-09-25
**范围**：nop 平台代码修改能力（重构/批量改写/codemod）的产品定位与设计原则
**状态**：active（本篇为用户裁定的设计原则，约束后续全部 design/plan）

---

## 一、设计结论

1. **nop 平台代码工具链的第一用户是 AI agent，不是使用 IDE 的人类开发者。** 平台为"AI 自动编写代码和修改代码"提供最方便、最快速的工具；人类开发者是第二用户。任何接口设计先回答：AI 调用是否最快、最方便、结果是否可自检。
2. **代码修改能力以 GraphQL 操作接口组织，不以 LSP 组织。** Nop 不实现 LSP，也不需要实现 LSP——LSP 是人类编辑器（光标、会话、交互确认）的协议，不是 AI 工具调用的最优形态。AI 通过结构化的 GraphQL 操作完成修改，通过结构化的结果反馈完成自检。
3. **每个修改操作必须返回机器可核验的反馈载荷**，让 AI 在不依赖第二次工具调用的前提下完成大部分"是否满足预期"的检查（diff + 语法完整性 + 残留诊断 + 统计）。

## 二、背景与动机

平台已有两个面向 AI 的代码工具先例：nop-code（GraphQL 查询代码智能：大纲/类型层级/调用层级/依赖图）与 nop-lint（GraphQL 检查：`Lint__checkSource`/`Lint__checkFile`/`Lint__listRules`）。二者共同点是**无状态结构化调用**——AI 一次调用拿到一次完整答案。代码修改能力（refactor）补上第三件：读（nop-code）→ 查（nop-lint）→ 改（refactor），构成 AI agent 操作代码的完整闭环。

这条闭环的接口形态必须统一：如果"读"和"查"是 GraphQL 而"改"是编辑器协议，AI agent 就要维护两套调用模型，且 LSP 的会话同步（didOpen/didChange）、光标定位、交互式确认对自动化调用方全是无意义的负担。

## 三、核心设计原则（硬约束，后续 design/plan 不得违反）

1. **GraphQL-first 操作面**：全部修改能力以 GraphQL 操作暴露（`@BizModel` + `Obj__action` 大写惯例，与 `Lint__checkSource` 同款）；CLI 是同一引擎的批处理形态，不是第二套语义。命名契约见 01 §3。
2. **无状态请求**：优先 source-in → result-out；文件操作以路径入参。服务端不持有 LSP 式的文档会话状态（无 didOpen/didChange 等价物）；引擎内部的缓存/增量解析是实现细节，不进 API 契约。
3. **机器可核验反馈（self-verification 载荷）**：每个修改操作返回统一结构——是否落盘、per-file 结构化编辑、unified diff、**修改后重解析的语法完整性（error node 计数）**、残留 lint 诊断、影响统计。载荷契约见 01 §4。AI 的核实循环 = 读 diff + verification，自检不再需要起第二 round 工具调用（允许再调 `Lint__checkSource` 深查，但不依赖）。
4. **两段式 + 原子性**：preview（dry-run）与 apply 分离；apply 原子写、失败整体回滚、绝不半写。AI 的标准用法是先 preview 审读 diff 再 apply。
5. **批量一等公民**：操作入参支持多目标/多文件，返回成功/失败/跳过分桶统计。只支持单点交互式操作的接口形态是被禁止的（codemod 场景逐文件循环是反模式）。
6. **结构化错误、fail-closed**：错误必须结构化（错误码 + 消息 + 操作上下文 + 建议下一步），禁止静默降级——AI 需要可编程地决定重试、缩小范围或放弃。
7. **快**：AI 反馈循环对延迟敏感。默认路径纯 Java 进程内（无 native 库、无子进程冷启动）；外部进程桥（如 TS 类型服务）必须常驻池化，并在结果载荷中标注成本档位。
8. **自完备，能力源自建**：本能力的全部能力源（语法引擎、语义解析、引用索引、改写机制）自建或复用自家资产（nop-treesitter / nop-java-parser / nop-code / nop-lint），**不引入外部大型系统**（jdt.ls 之类的语言服务器、外部引擎包装）。平台级约束见 [../self-contained-design.md](../self-contained-design.md)。
9. **复杂度预算 + 性价比门**：本能力的总复杂度**不超过 nop-lint 模块族的复杂度量级**（上界锚点：main Java 约 2.2 万行 / 6 模块，2026-09-25 实测 21,927 行——计数口径 = src/main/java 全量、排除生成物与测试；超出即砍功能，不加预算）。功能取舍按**性价比排序**：AI 使用价值 × 不可替代性 ÷ 新增复杂度，只做最有价值的功能。

## 四、显式 Non-Goals

- **不做 LSP**：refactor 能力不提供 LSP 面；rename/quickfix 等编辑器形态由消费方（若未来需要）基于 GraphQL 自行适配，不是平台职责。
- **不做交互式向导/确认 UI**：JDT 式 wizard、逐处 confirm 是人类交互形态。
- **不做编辑器会话管理**：无文档同步、无光标概念、无 keystroke 预算。
- **不做 IDE 插件**：IDE 集成是下游生态的事。
- **不做结构变换型重构机器**（Extract Method / Inline / Change Signature / Move / PullUp/PushDown / 类型约束类）：见下方价值排序——AI 直接生成/重写代码 + verify 闭环，边际价值低于专用机器的复杂度。

**Non-Goals 的推导——按 AI 修改代码的真实形态做价值排序**（不照搬人类 IDE 的价值排序；JDT 清单为人类编辑摩擦而生，AI 的摩擦结构不同）：

| AI 修改代码的形态 | 需要的能力 | 价值/复杂度判断 |
|---|---|---|
| 直接生成新代码（大多数修改） | verify 闭环（已在设计中） | 不需要专用重构机器——AI 重写受影响代码比调 extract/inline 更快更准 |
| **批量机械变更**（API 迁移、约定统一、pattern 替换、N 文件同改） | pattern 匹配 + fix 应用 + 批量 verify | **价值最高、边际复杂度最低**（复用 nop-lint 存量，主要工作在契约面）→ **P0** |
| **精确符号级修改**（rename 是唯一高频项） | 符号解析 + 编辑计划 + verify | 价值高（文本改名漏动态引用）；复杂度中等（单模块符号域内可控）→ **P1** |
| 结构变换（extract/inline/change signature/move 族） | 选区数据流/签名传播/继承链分析 | AI 直接重写 + verify 可替代，专用机器复杂度（JDT 单操作即数千行）远超边际价值 → **out** |

## 五、成功标准

- AI 单次调用获得判断"是否达预期"所需的全部信息（diff + 语法完整性 + 残留诊断 + 统计）。
- 从发起到拿到可核验结果的往返全程无人工介入；批量改造 N 文件与单文件同量级完成。
- 全部操作可 preview、可原子 apply、失败可结构化归因。
- 总复杂度（主代码量级/模块数）不超过 nop-lint 模块族锚点；超出预算时砍功能而非扩预算。

## 六、拒绝了什么

- **LSP 作为代码修改接口**：为人类编辑器设计（会话同步/光标/一次性交互确认）；WorkspaceEdit 只有文本编辑列表，没有语义自检面（改了多少符号、是否引入语法错误、残留什么诊断），AI 拿到后无法自检；会话状态管理对无状态工具调用是纯负担。
- **外部大型系统作为能力源**（违反平台自完备约束 [../self-contained-design.md](../self-contained-design.md)）：jdt.ls 进程桥（Eclipse 工程模型强制、OSGi 部署、上游版本绑定、架构支柱外移）；OpenRewrite 引擎包装为本平台能力面。语义级重构全集不可自建时收敛范围（做窄做精、降档、延期），不以引入外部大型件换功能面。
- **全量复刻 JDT 式重构清单**（33 种操作逐个补齐）：违反复杂度预算与性价比门——结构变换类对 AI 用例边际价值低（AI 直接重写 + verify 可替代），专用机器复杂度（JDT 单操作数千行量级）远超其值。
- **会话化 plan-token（preview 发 token、apply 凭 token）**：引入服务端会话与 TTL 治理，违反原则 2。选**无状态重执行**——修改操作本身廉价且确定性（同输入同结果），apply 重新计算编辑计划后原子落盘。
- **以 IDE 插件为第一形态**：与本平台"AI 在服务端/工具链中调用"的使用场景错位。

## 七、与已有设计的关系

- **nop-lint**（[../nop-lint/](../nop-lint/README.md)）：fix 管线（dry-run/原子写/multipass/冲突仲裁）是修改执行层的既有资产，本能力的 apply/verification 面复用其机制；nop-lint 既有 LSP v1 作为已交付存量原样保留、零扩张，其定位是编辑器兼容面而非本能力的组织形式。
- **nop-code**：修改前的"读"（符号/依赖图查询）与修改中的引用搜索底座。
- 三件套接口形态统一为 GraphQL，是平台 AI agent 闭环的接口一致性约束。
