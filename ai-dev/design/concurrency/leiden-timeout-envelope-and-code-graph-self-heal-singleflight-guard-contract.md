## 裁定① W-04：LeidenDetector runWithTimeout 超时包络（幽灵线程治理，P1）

**决策**：

1. **包装设施 = 每调用一次性 daemon 工作线程 + `FutureTask`**（与 8.36 W-08 同纪律、不共享线程设施实例——2529 裁定⑥.8 软注记兑现）：调用线程构造任务体（仅 `leiden.findClustering(network)`，现调用点 :113-114 零漂移）并以 `NamedThreadFactory("nop-graph-leiden", true)`（nop-commons `concurrent/thread` 使用面引用，与 W-08 同款、独立实例）产出的 daemon 工作线程执行，调用线程按墙钟 `get(timeoutMs, MILLISECONDS)` 等待。`Executors.newSingleThreadExecutor()`（:197 既有形态）废弃——其缺省工厂产出非 daemon `pool-N-thread-1` 线程，shutdownNow 对不可中断任务无效，即缺陷本体。无池、无队列、无驻留：每调用至多一个线程，完成即亡。
2. **cancel 布尔终判 = `cancel(false)`**（超时与中断两路径均显式调用——补 :202 shutdownNow 无效且无 cancel 的缺口）。理由：①CWTS networkanalysis-1.3.0 全库 0 interrupt 引用（反汇编取证在案），中断无法提前结束计算，cancel(true) 唯一增量是设置一个任务体内无任何读取点的中断标志——制造「已尝试中断」的误导性 affordance 且零收益；②与 2529 裁定⑥.4 同纪律（该处 cancel(false) 另保护 IGraph 回调中的阻塞 I/O，本处任务体为纯 CPU CWTS 计算、无回调面——纪律统一而理由侧重不同）。**生命周期配对闭环维持（C6-CL-031 裁定兑现）**：成功路径线程自然终结；超时/中断路径 cancel(false) 后 daemon 线程继续至自然结束、不阻塞 JVM 退出；awaitTermination 补等待维持不采（C6-CL-031 负修复裁定——CWTS 无中断检查点，awaitTermination 仅延长调用方阻塞）。
3. **超时终态 = 放弃等待 + 既有降级，非显式错误（与 W-08 bizFatal 形态的有意差异）**：`TimeoutException` → WARN（结构化标签 `nop.graph.leiden-timeout`，记录放弃等待与节点规模，附语义边界文案）→ 异常原样上抛 → `runLeiden` 既有 catch（:136-140）兜底降级 LabelPropagation。**降级语义与可观测标签零变更（R1 Blocker-1 选型 (a)）**：detect :79-85 无条件以字面量 "LEIDEN" 重建 CommunityResult（:84）维持零 diff，超时降级的 "LABEL_PROPAGATION" 标签（LabelPropagation.java:80）经 detect 出口维持不外泄；「超时降级后仍报 LEIDEN」为既有行为，标签透传归 plan Non-Blocking Follow-up（需 GraphQL DTO/GRAPH_SUMMARY 持久值消费面评估，不入本批）。**差异论证**：社区检测存在设计内降级路径——超时降级是质量回落的功能语义而非失败，调用方契约（algorithmUsed 字面量）不受影响；Betweenness 分数查询无降级语义，静默返回部分分数会污染分析，故必须显式 bizFatal 失败。零新错误码（`NopGraphErrors` 两既有码零触碰——Leiden 超时走降级不抛码）。
4. **异常传播成文**：`ExecutionException` 一律解包 cause 原样重抛——运行/兜底面永不出现 ExecutionException 外壳，:136-140 的降级 WARN 记录根因而非包装壳（与 2529 裁定⑥.4 习语同）。**Error 逃逸声明（显式行为修正点）**：pre-fix 任务体的 Error 经 ExecutionException 外壳被 :136 `catch (Exception)` 捕获吞入降级；解包后 Error 原样重抛、不再被 catch(Exception) 捕获——Error 不应静默降级（OOM 等致命态被包装成降级会掩盖首因），此为降级语义零变更承诺的范围界定（承诺范围 = Timeout→LabelPropagation 路径与标签，不含 Error 逃逸修正）。`InterruptedException` 路径：恢复中断标志 + cancel(false) + 上抛 InterruptedException → 既有 :136 catch → 降级。**中断标志恢复为第二个显式行为修正点（评审 R1 Minor-2）**：pre-fix get() 抛 InterruptedException 时中断标志按 JDK 语义被清除且无人复位，post-fix 显式复位——调用线程后续代码可观测到中断状态差异；「零变更」限定为**降级结果语义**（超时/中断两路径终点均为 LabelPropagation 降级），不涵盖 Error 逃逸与本中断标志复位两修正点。
5. **包络范围显式声明：仅 findClustering**（:113-114 现状零漂移）：detect 的图转换段（:54-74，O(V+E) 出边枚举）与 convertClustering/cohesion 计算（:121、:143-190）留在调用线程。不扩包络的理由：扩至全 runLeiden 会把兜底降级（LabelPropagation）搬入工作线程、复杂化生命周期配对，而转换段成本相对可忽略；label 图转换在调用线程也是红① (a) 行为锚可经探针观测的前提。`timeoutMs <= 0` 维持既有同步直跑分支（:115-117）零 diff——该分支为调用方显式传参面（非配置缺省面），与 W-08 配置键缺省的禁用 WARN 场景不同源，不加 WARN。**零新配置键**：超时由 `LeidenConfig` 既有字段承载（LeidenConfig.java:9 缺省 30000），两生产消费方均已显式 `setTimeoutMs(60000)`（CodeGraphService.java:752 / GraphMetricMaterializer.java:121）——与 W-08 新配置键形态差异的理由：W-08 需为无既有配置对象的两调用方提供缺省包络，W-04 的配置对象与显式传参均已存在。
6. **幽灵可观测设计**：命名前缀 `nop-graph-leiden`（NamedThreadFactory 产物名形如 `nop-graph-leiden-<pool>-<n>`，与 W-08 `nop-graph-betweenness-` 同族）+ daemon 标志（JVM 退出永不被阻塞）+ 放弃等待 WARN。**语义边界声明（C10 义务文案）双落点**（类 javadoc + WARN）：「底层 CWTS Leiden 计算不可中断（networkanalysis-1.3.0 全库 0 interrupt 反汇编在案），超时仅为放弃等待 + 既有 LabelPropagation 降级——放弃后计算在后台 daemon 线程继续至自然结束（不阻塞 JVM 退出、无线程池驻留、按名可辨识），放弃后计算自身的失败不再上报」。放弃路径的 CPU 残留 = 并发放弃数 × 单次 findClustering 时长，有界且自终止。
7. **被否决的备选**：模块级共享有界池/背压设施（CS-001 建议(3) 中期项，plan Non-Goal——池化涉排队与背压设计，per-call 线程已闭合幽灵本体）；`CompletableFuture.supplyAsync().orTimeout`（2529 裁定⑥.7 同款否决——JDK 内部调度器组合无增益、CompletionException 解包噪声）；cancel(true)（见第 2 条）；awaitTermination（C6-CL-031 负修复）；标签透传（可观测行为变更，Blocker-1 选型 (a) 否决）；扩包络至全 runLeiden（见第 5 条）；Leiden 超时 bizFatal 化（见第 3 条差异论证）。

**零触碰边界**：`LeidenConfig` 及 nop-graph-api 全部 14 文件零 diff；`LabelPropagation` 零 diff；detect 的图转换/convertClustering/cohesion 逻辑零 diff；detect :84 "LEIDEN" 字面量重建零 diff；`NopGraphErrors` 零新码零改动；`GraphExporter` 字面量零触碰（2529 follow-up 维持）。

## 裁定② 6.3-W-03：materialize 收口单飞 + 失败退避冷却窗（P1）

**决策**：

1. **设施位置 = `GraphMetricMaterializer.materialize` 入口（:85）一处封死 6 触发点**。6 触发点全清单（live 复核）：detectCommunities :114、getGraphAnalysis :199、ensureMaterializedForGraphMetrics :335（getSurprisingConnections :308 / getExplorationQuestions :344 / exportGraphWiki :372 三入口共用）、getCriticalNodes :439、CodeIndexService.materializeGraphMetrics :727（biz 面 triggerFullIndex :65）、ShardBuildCoordinator :111（未接线）——全部经 materialize 唯一入口，门在收口点即 6 触发点全覆盖且各触发点调用面零改动。
2. **单飞形态 = per-index ReentrantLock + tryLock 立即降级（skip-and-degrade）**，否决「阻塞互斥 + 锁内双重复查」：①排队放大——物化时长分钟级（全量图重建 + Leiden 60s 上界 + Betweenness + 大事务逐行落库），n 个 GraphQL worker 阻塞排队即 worker 池耗尽；②阻塞形态为避免「排队后冗余重执行」必须引入锁内复查跳过，而 materialize 语义是**无条件重算**（triggerFullIndex 全量重索引后 summary 已存在但内容陈旧，必须重算——summary 存在性不能作跳过判据；「completedAt 晚于到达时间」式时间戳双查无法区分「前驱读的是重索引前旧图」，语义不闭合）；③skip 形态下赢家正在计算的正是输家想要的结果，输家走既有内存兜底即刻返回，后续读命中物化行——风暴的两条驱动链（并发首触全量重算、失败回滚后再重算）均被单一门截断。锁容器 = materializer 内 per-index `ConcurrentHashMap<String, ReentrantLock>`（CodeIndexService.indexLocks :123 既有形态先例；`withIndexLock` :125-141 为 CodeIndexService 私有设施，复用需跨类接线触碰其产品码——plan 零触碰声明禁选）；map 容量与索引数量同阶（indexLocks 同族先例，非请求维度）。**tryLock 非阻塞 → 结构上无死锁面**：无人持门阻塞等待，门锁与 DB 事务锁分属两域且无嵌套等待——ShardBuildCoordinator 事务内调用（:111）的锁序论证由「非阻塞试探」结构闭合（单锁、无逆序环可能），其测试 :89-109 直接 new 装配形态零回退（门在 materializer 内部，`newCoordinator` :55-59 直接 new materializer 的装配路径完整含门设施，零容器依赖）。triggerFullIndex biz 幂等不变（物化成功语义零变化）。
