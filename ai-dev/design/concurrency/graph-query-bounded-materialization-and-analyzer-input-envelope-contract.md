## 裁定① W-01 loader 上界与三动作守卫形态（P1，TP-001 主面）

**决策**：

1. **上界形态 = 分批截断 + 截断标志 + 显式 WARN（R02 三范式取「分批截断」，与列投影组合降级为 follow-up）**：`CodeRelationGraphLoader`（io.nop.code.service.graph，live :44）四表加载（load :48-57，calls/inheritance/annotation/semantic 四表 addAll :51-54；batched :180-197 offset 分页全量累积、BATCH_SIZE :46=5000 仅分页粒度）在**四表累计边数达到总量上界时停止拉取后续批次**——截断按 load 固定表序（calls→inheritance→annotation→semantic）先到先得，截断发生即置被动截断标志并输出结构化 WARN（含 indexId/上界值/已加载边数）。上界值缺省 **50000**（对齐同模块 `AnnotationPatternExtractor.MAX_EDGES = 50000` 既有惯例 :29 及其达到即截断返回形态 :92——audit 建议原文指定的对齐锚）。**总量口径而非单表口径**：三动作的内存风险载体是 `CodeRelationGraph` 构造器的两份邻接表 + 每边 attrs（≈3 倍放大、构造期间两份并存——CodeRelationGraph 构造器 out/in 邻接 + per-edge attrs，live 构造段亲读在案），约束对象是进入构造器的总边集，单表分别设界不约束总量。

## 裁定② findByMetric 上界与常量单源（P1 共享根，TP-001 上界面承载）

**决策**：

1. **上限形态 = 固定常量 + 截断可观测（否决按 rankNo setLimit 全量替代）**：`GraphMetricStore.findByMetric`（:158-165 无 setLimit，对照同文件 hasMaterialized :48 setLimit(1) 独立通路）补显式行数上限——**共享私有 finder 一处封口**，loadCommunities :52-62 / loadScores :64-73 / loadHubs :79-89 / loadCommunityInfo :92-101 / loadSummary :104-110 / loadEntryPoints :130-135 / loadBetweenness :138-143 七公共 finder 全部经它。hasMaterialized 独立通路零改动；loadSummary 单行语义不受影响（GRAPH_SUMMARY family 恒 1 行——materializer summaryRows 单行构造在案，上界 ≥1 无行为变化）。
2. **上限值 = 10000（对齐 `BETWEENNESS_MAX_NODES = 10000` 惯例——同族分立新命名常量，不跨类引用 materializer 私有常量 :63）**。**与物化守卫的协调论证（plan 强制输入）**：逐 family 行数上界亲读——COMMUNITY ≤10⁴（materializer 社区守卫 :189-194）、COMMUNITY_INFO ≤10⁴（同守卫）、BETWEENNESS ≤10⁴（betweennessRows 守卫 :262-266）、GRAPH_SUMMARY =1——此四 family 截断**不可达**，上界为纵深防御；ENTRY_POINT ≤ `MAX_CACHE_SYMBOLS` 10⁵（CodeCacheManager :45）、PAGE_RANK/HUB = 调用图节点集（无节点守卫，受 MAX_CACHE_EDGES 5×10⁵ 间接约束）——此三 family 截断**可达**。故「cap ≥ 物化守卫 10⁴ 使截断不可达」论证仅对前四 family 成立、对后三 family 不成立——这正是第 3 条 rank 序下推预设的根据。**被否决：cap 提至 10⁵ 对齐 MAX_CACHE_SYMBOLS 使全 family 不可达**——等于把 10⁵ 行 metric 查询放行为合法态，无界物化族缺陷在查询面复活。
3. **rank 序 finder 截断排序语义论证（Minor-4 强制输入；唯一预设 = orderBy 下推）**：loadEntryPoints/loadBetweenness（:130-143）在 findByMetric 结果上按 rankNo 升序内存排序（:132-133/:140-141）——若 cap 先于排序生效则丢 top-rank 行。二选一裁定：**采 orderBy 下推**——rank 序 finder 的查询侧按 rankNo 升序排序 + 上限截断取前 cap 行（`QueryBean.addOrderField(name, desc)` 既有设施，nop-api-core :435-443 使用面引用零平台触碰），语义等价于「排序后取前 cap」且截断保留最高 rank 行。**等价性论证**：现内存排序为稳定排序，其 tie 序保持的是 DB 返回序，而 DB 返回序本就未指明——查询侧排序把「rankNo 序」变为显式保证、tie 序仍由 DB 决定，保证不弱于现状。脚注（评审 R1 Minor-4）：materializer 恒写 rankNo（entryPointRows/scoreRows :313/:332）——rank family 行 rankNo 非空，null 分支（内存排序的 Integer.MAX_VALUE 哨兵）不参与截断序、仅为防御性兜底；既有内存稳定重排（:132-133）零 diff 保留为查询侧排序之后的次级保证。**截断可达 family 按消费面分列（评审 R1 Major-1 修正——禁以「容忍语义一致」一笔带过）**：①**HUB 有错值面**——loadHubs 消费方为度数 map 装配（CodeGraphService :257/:835，top-degree god nodes/关键节点选取面），任意序截断可丢最高度数行 → 错值而非仅缺失：**orderBy 下推扩展至 loadHubs**（查询侧按 score 降序 + cap——HUB 行 score 即 totalDegree，materializer hubRows 亲读在案；top-degree 行保序，度数正确性维持）。②**PAGE_RANK 主链零读**——loadScores 全部调用面仅 METRIC_BETWEENNESS（CodeGraphService :361-366 唯一调用点亲读核对），PAGE_RANK 无读消费方，其截断仅为 WARN 可观测的上界兜底（不产生错值消费）。③**其余 membership/topN 聚合面**（COMMUNITY membership map 等）按查询返回序截断 + WARN——缺失型降级，与生产行为变更声明（第 6 条）分列登记。**被否决：cap 先截后排序**（丢 top-rank/top-degree，违背 rank 序与度数序消费契约——GraphMetricStore javadoc :127-129 明文「readers must not re-sort by score」）。
4. **注入缝唯一预设（Major-1）= 实例字段 + 包内可见 setter，缺省 = 编译期常量值**：GraphMetricStore 为 direct-new 装配（CodeGraphService :86；测试直构先例 TestGraphMetricMaterialization :121——红② 驱动器同形态），非 IoC bean，包内可见 setter 是零生产 diff 的唯一注入形态（2530 materializer 冷却窗 setter 先例同型同纪律）。红②/TP-001 注入低上限经 setter，生产零 diff。**被否决：纯常量形态**（则红② 须改行数夹具——超 10⁴ 行 family 夹具成本违背 TP-001 注入意图）；**被否决：@NopTestProperty 配置注入**（守卫参数配置化 = plan Non-Goal）。
5. **截断可观测范式**：对齐 `CodeQueryService.warnIfCapped`（:52，resultSize/cap/context 结构化 WARN）既有范式——graph 包内同型实现（impl 包私有 helper 不跨包复用），按 finder 上下文输出 family/indexId/行数/上限。**常量单源移交声明**：本批上限常量为该语义的**单一事实源**，R4-31/W-17 承接面禁发明第二常量（2530 MAX_NODES 常量单源先例同款约束）。
6. **生产行为变更声明（owner doc 落点）**：「ENTRY_POINT/PAGE_RANK/HUB family 行数超 10⁴ 的索引，读路径 metric family 查询返回前 10⁴ 行 + WARN（rank 序 family 保 top-rank；HUB 保 top-degree——评审 R1 Major-1）；此前全量返回。检测/装配面语义分列：截断 = 部分行返回（hasMaterialized/hasRequiredFamilies 为 presence 检查 setLimit(1)，不受截断影响——不触发自愈重算）；COMMUNITY 缺行 = 零行 → assemble null → 内存兜底（2530 既有降级链）——两链语义不同、互不替代」。

**零触碰边界**：hasMaterialized/hasRequiredFamilies 零改动；materializer 全部行构造与守卫逻辑零 diff；CodeGraphService 对 metricStore 的调用面零 diff；`nop-code-api`/orm 零触碰。

## 裁定③ W-02 输入面守卫激活 + 触发面预检 + 驻留释放形态（P1，TP-002；含 W-28 收敛载体）

**决策**：

1. **死常量激活形态 = skip + truncated 标志 + WARN（预设；否决 fail-fast）**：`MAX_FILE_SIZE_BYTES`（ProjectAnalyzer :54）/`MAX_FILE_COUNT`（:55）激活——单文件读取前超大小上限 → 跳过该文件（WARN 含路径与实际大小）+ 截断标志置位；遍历中已分析文件数达上限 → 停止遍历后续文件（WARN）+ 截断标志置位。标志载体 = `ProjectAnalysisResult` 新增被动截断标志（nop-code-core 手写模型，先例同裁定①第 2 条）。**否决 fail-fast（NopException）的理由**：①目录扫描的输入内容不受 admin 控制，skip 保索引可完成性与部分结果可用性，fail-fast 使一次误提交即中断全部索引工作流；②`TestIndexNopXlangModule`（:90 indexDirectory 真实模块树全链零回退锚）在 skip 形态下确定性维持绿，fail-fast 形态对未来仓库混入大源文件脆弱（plan Risks 节同款论证）；③模块惯例为截断降级（CodeCacheManager partial-data 先例）。**触发面语义分立声明**：单文件显式输入面已有 fail-fast 先例（`NopCodeIndexBizModel.indexFile` 的源码上限校验，:39/:136-140，`ERR_CODE_SOURCE_CODE_TOO_LARGE`）——「显式单一输入 = fail-fast，目录批量扫描 = skip+WARN」为分立面契约，非双标。**常量值维持 1MB/50000**：与触发面预检阈值（第 3 条）共同构成输入包络；调整缺证据，不动。
