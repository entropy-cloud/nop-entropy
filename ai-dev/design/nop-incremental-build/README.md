# nop-incremental-build — 增量编译与测试反馈服务

> 状态：草案。**实测结论**：ROI **高**——适用面 **63.4%** 的真实编辑，单次省下的是构建骨架成本（实测 2.2s 空闲 / 4.7s 四路并发 / 7.8s 八路并发，均为顶配机器下限）。**推荐立项**；已预设收缩退路（只做测试选择）。是否立项属人工决策（见 Vision G1）

## 定位

面向 AI 编辑流程的变更反馈服务：判定受影响测试、委托既有构建工具执行、把结果结构化回传给调用方。

**核心立场**：速度是目的，可信是前提。本轮实测得出三条结论，直接决定了本设计的形态：

1. **瓶颈是构建骨架，不是编译**。骨架成本（本机空闲 2.2s）与模块大小几乎无关——3 文件模块与 59 文件模块耗时落在同一区间，javac 的边际成本接近于零。
2. **骨架成本随负载近似线性放大**（四路并发 4.7s、八路并发 7.8s），而 javac 边际成本不变。因此收益随机器变慢、负载升高而**放大**。
3. **跨模块阻断必须带签名谓词**。只改方法体是二进制兼容的，实测 64.3% 的编辑不触及签名；带上谓词后适用面从 3.8% 升到 **63.4%**（提升 16.8 倍），编译最耗时的模块全部进入快路径。

**成本必须按机器与负载参数化**：本仓数字来自 M4 Max / 16 核 / 128 GB，是乐观下限。目标机器的基线测量是部署前置步骤（Phase 0）。

## 与现有子系统的关系

完整表述见 [01 §十六](01-architecture-baseline.md#十六与已有设计的关系)。要点：

- **复用** `nop-code` 的**零 DB 层**（`nop-code-core` + `nop-code-lang-java`，7 依赖、零 ORM）；**不引入**其服务层（26 依赖 + IoC + DB）
- **互补** `nop-lint`：它已有常驻 LSP 与快速档（单文件数十毫秒），本服务补上它唯一缺的**类型检查 + 增量编译**
- **参考实现** `nop-bytecode`：其测试夹具是"文件式编译 + release + 输出目录"的现成参考（G10 的 (c) 路径）；漏测率 oracle 用它算可达性闭包
- **不被依赖**：任何发布型模块不得反向依赖本服务

## 开工前置

本设计**尚不具备开工条件**。需先关闭：

1. **目标机器成本基线测量**（Phase 0，见 [Vision §2.3](00-vision.md#23-成本模型的正确表述裁定)）——本仓数字是顶配机器下限，必须在真实部署机器重测。这是收益预期的前置条件
2. 裁定 [Vision §八](00-vision.md#八必须由人决策的决策点) 的 12 个决策点，其中 **G1 是否立项** 与 **G10 编译能力来源** 是前置阻塞项
3. 按 `AGENTS.md` 的 plan-first 流程落 `ai-dev/plans/` 计划——本设计触及 `nop-code` 内部复用与构建产物写入，超出 `implement` autonomy
4. 建立 roadmap（按 `AGENTS.md`，roadmap 归 `ai-dev/backlog/`）——本仓每个在建子系统都有 roadmap，本设计目前是唯一有 design 无 roadmap 的
5. 若采纳模块归属，需同步 `docs-for-ai/01-repo-map/module-groups.md`、`docs-for-ai/INDEX.md`、`docs-for-ai/04-reference/source-anchors.md`
6. 把 [03 §二](03-alternatives-and-roi.md#二成本侧可省下的是什么实测) 的成本构成与负载敏感性写入构建/测试 owner 文档，作为共享基线
