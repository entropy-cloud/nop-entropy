## 一、产品定位

为 AI 编辑流程提供**常驻的增量编译与测试服务**，把"改动 → 编译 → 受影响测试 → 结构化结论"从秒级压到亚秒级。

服务只服务于 AI 编辑流程，不接管 IDE 编译，不替代 CI 全量构建。

## 二、成本基线【实测】

### 2.0 测量条件（必读，否则数字会被误用）

| 项 | 值 |
|----|-----|
| 机器 | Apple M4 Max，16 物理核，128 GB 内存 |
| 负载 | 测量时段 load average 8–9（16 核），**并非空闲** |
| Maven | `./mvnw` = 4.0.0-rc-5 |
| JDK | OpenJDK 26 |

**这是台顶配笔记本芯片，单线程性能通常是普通开发机的 2–4 倍。因此下表所有数字都应视为乐观下限，而非通用值。** 真实部署机器的成本必须重新实测——这是本设计的一条硬要求，见 §2.3。

### 2.1 每次调用的成本构成

| 环节 | 实测耗时 | 性质 |
|------|---------|------|
| JVM + Maven 引导（`mvnw -v`） | 0.42 – 0.50s | 固定 |
| 项目模型构建 + 生命周期骨架（`validate`，不编译） | 2.20 – 2.49s | **固定，且主导** |
| 实际编译：3 文件模块（`compile`） | 2.17 – 2.29s | 相比骨架 **+0** |
| 实际编译：59 文件模块（`compile`） | 2.33 – 2.87s | 相比骨架 +0.2 – 0.6s |
| 实际编译：675 文件模块（no-op / dirty） | 2.73s / 4.05s | 相比骨架 +0.5 – 1.8s |

**结论**：每次调用的成本几乎全部是**骨架**（引导 + 模型构建 + 生命周期解析 + 插件装载），**与模块大小几乎无关**——3 文件模块与 59 文件模块的耗时落在同一区间。javac 的边际成本在小中型模块上接近于零。

### 2.2 负载敏感性（本轮最重要的发现）

同一机器、同一命令，仅改变并发度：

| 并发度 | 每次调用耗时 | 墙钟 | load average |
|--------|------------|------|-------------|
| 1（空闲） | 2.2s | 2.2s | ~9 |
| 4 路并发 | 3.4 – 5.1s | 5.1s | — |
| 8 路并发 | **6.4 – 8.8s** | 8.8s | **28 / 16 核** |

**每次调用成本随并发近似线性放大**（2.2s → 4.7s → 7.8s），而 javac 的边际成本不变。这有两个直接推论：

1. **在多 agent / 多 worktree 并发构建的场景下，Maven 的单次调用成本是空闲时的 2–4 倍。** 本仓有 7 个活跃 worktree，且已有构建排队工具（`ai-dev/tools/mvnq`，`build.lock`）——说明并发构建是常态而非例外。
2. **负载放大的是骨架，不是编译。** 因此"绕开 Maven 日常调用"的价值随负载**上升**，而不是下降。

### 2.3 成本模型的正确表述【裁定】

**不得**把任何单机绝对值当作本仓或 Maven 的通用属性。本设计采用的成本模型是：

```
单次验证成本(机器, 负载) = 骨架成本(机器, 负载) + javac 边际成本(模块规模)
                            └── 主导项，随负载放大 ──┘   └── 次要项 ──┘
```

其中**骨架成本 ≫ javac 边际成本**这一**比值关系**是跨机器稳健的（它在同一台机器、同一负载下通过 3 文件 / 59 文件 / 675 文件三档对照得出，不依赖绝对速度）；而骨架成本的**绝对值**必须实测。

因此服务上线时必须做一次**目标机器基线测量**，并把它作为部署前置步骤。若目标机器的骨架成本显著高于本机下限，则本设计的收益按比例放大，Phase 划分不变。

## 三、适用面【实测】

### 3.1 判定规则

一个改动可以走增量编译快路径，当且仅当：

| 条件 | 依据 |
|------|------|
| 所在模块不在 non-goal 集合内 | 见 §六 |
| 改动落在手写源码（不在 `_gen/` 下） | 生成产物由 Maven 生命周期产出，见 §五约束 5.4 |
| **模块无 intra-project 下游依赖方**，**或**本次改动**未变更任何签名** | 见下 |

第三条是本轮的关键修正。

### 3.2 下游依赖只在签名变更时才阻断

有下游依赖方意味着：若改了公开签名，下游的既有产物失效，必须重建。但**只改方法体是二进制兼容的**，下游既有产物仍然有效，无需重建。

因此判定必须带**签名谓词**，而不是"有下游就回退"。实测签名变更率（对 Top-12 高频模块各抽样 40 次提交、按增删行形态判定）：

| 模块 | 抽样变更行 | 签名变更 | 占比 |
|------|-----------|---------|------|
| stream-core | 16,810 | 6,267 | 37.3% |
| nop-ai-agent | 36,952 | 12,449 | 33.7% |
| metadata-service | 35,989 | 13,005 | 36.1% |
| stream-runtime | 14,868 | 4,763 | 32.0% |
| nop-code-service | 12,082 | 5,555 | 46.0% |
| nop-ai-core | 14,537 | 5,634 | 38.8% |
| lint-core | 24,546 | 8,155 | 33.2% |
| nop-xlang | 11,518 | 4,789 | 41.6% |
| nop-orm-eql | 41,090 | 12,234 | 29.8% |
| job-coordinator | 6,011 | 2,748 | 45.7% |
| auth-service | 22,000 | 8,518 | 38.7% |
| nop-orm | 5,903 | 2,289 | 38.8% |
| **合计** | **242,306** | **86,406** | **35.7%** |

即 **64.3% 的编辑不触及任何签名**。（该口径为形态启发式，含少量误判；敏感性见 §3.4。）

### 3.3 适用面测算

8 个月 git 历史，4,621 commits、**23,252 次 Java 文件改动事件**（对应 10,650 个去重文件），master 分支：

| 分类 | 事件数 | 占比 |
|------|-------|------|
| non-goal 模块内的手写编辑 | 22,444 | 96.5% |
| ├ 无下游依赖方（恒可增量） | 876 | 3.8% |
| └ 有下游依赖方 | 21,568 | 92.8% |
| &nbsp;&nbsp;└ 其中仅方法体变更（签名谓词放行） | 13,868 | **59.6%** |
| **可走增量编译快路径** | **14,744** | **63.4%** |

**对比修正前**：无签名谓词时适用面为 **3.8%**，加上签名谓词后为 **63.4%**，提升 **16.8 倍**。上一版把"有下游依赖"当作无条件回退条件，误杀了 92.8% 的编辑中的绝大部分——这是本设计最严重的一次错误。

### 3.4 敏感性

签名变更率是启发式测得，取不同值时适用面：

| 仅方法体变更占比 | 快路径适用面 |
|----------------|------------|
| 50%（保守） | 50.1% |
| **64.3%（实测）** | **63.4%** |
| 75%（乐观） | 69.9% |

即**在任何合理取值下，适用面都在 50% 以上**。结论对该参数不敏感。

### 3.5 适用面按模块看

修正后，编辑量最大的模块全部进入快路径（仅方法体变更时）：

| 编辑事件 | 模块 | 下游依赖方 | 资格 |
|---------|------|-----------|------|
| 2,371 | stream-core | 10 | 仅方法体可增量 |
| 2,299 | nop-ai-agent | 2 | 仅方法体可增量 |
| 1,771 | metadata-service | 3 | 仅方法体可增量 |
| 1,609 | stream-runtime | 5 | 仅方法体可增量 |
| 530 | nop-code-service | 2 | 仅方法体可增量 |
| 494 | nop-ai-core | 11 | 仅方法体可增量 |
| 491 | lint-core | 6 | 仅方法体可增量 |
| 482 | nop-xlang | 46 | 仅方法体可增量 |
| 432 | nop-orm-eql | 4 | 仅方法体可增量 |
| 396 | job-coordinator | 3 | 仅方法体可增量 |

这与修正前"Top-15 高频模块零覆盖"完全相反。**原因**：这些模块全部有下游依赖方，因此被过钝的规则整体排除；而它们恰恰是编译最耗时、最值得增量化的模块。

## 四、收益测算【实测 + 外推】

| 情景 | 单次可省 | 一个 AI 任务（约 15 次验证循环）净省 |
|------|---------|-------------------------------|
| 本机空闲（骨架 2.2s） | 2.0 – 4.0s | 约 30 – 60s |
| 本机 4 路并发（骨架 4.7s） | 4.5 – 6.5s | 约 68 – 98s |
| 本机 8 路并发（骨架 7.8s） | 7.5 – 9.5s | 约 113 – 143s |
| 典型较慢机器（骨架按 2–4 倍估） | 按比例放大 | 按比例放大 |

按 8 个月历史折算（以空闲条件为基准）：**累计可省约 10 小时以上；并发条件下的实际节省显著更高**。

**收益随负载与机器速度同向放大**——这与"加速编译"的直觉相反，但符合 §2.1/§2.2 的实测：被省掉的是骨架，而骨架正是随负载放大的那一部分。

## 五、成功标准与度量协议

### 5.1 延迟【初值，须在目标机器上调参】

测量协议：热态（服务已完成全量初始化 + ≥20 次预热）；计时从请求入口到反馈返回，包含索引更新与传播计算；N=200 次真实单文件改动；报 median 与 p95；冷启动首请求单独统计。

| 场景 | 目标（p95，热态） |
|------|-----------------|
| 改一个方法体（无下游依赖的模块） | ≤ 500ms |
| 改一个方法体（有下游依赖，仅方法体变更） | ≤ 1s |
| 改一个方法签名（小型模块） | ≤ 1.5s |
| 跑受影响测试（小型模块） | ≤ 2s |
| 冷启动首请求 | 不设阈值，单独统计 |

**适用前提**：仅对 §三 的快路径适用面（63.4% 的编辑）生效。其余走 Maven 回退，延迟等于 §二 的实测骨架成本。

### 5.2 编译一致性（目标 100%）

oracle（**不可**用"跑一次 `mvn clean compile` 比对"这种写法——`clean` 会删掉要比对的产物）：

1. 增量编译后落**类清单**：每个 `.class` 的类全名 → 内容 sha256，排序稳定。
2. 在**同一 commit 的另一个独立检出**上、**以 patch 形式施加同一改动**，执行 `./mvnw -T 1C compile test-compile`，落同格式清单。（`git worktree` 天然指向同一 commit，服务工作树的未提交改动**不会**自动出现——这是必须显式补的一步。）
3. 独立检出必须先完成一次完整安装，否则它的 intra-project 依赖会解析到冻结产物，基线本身就是错的。
4. 差异 = 缺失集 ∪ 多余集 ∪ 哈希不符集。任一非空即判定不一致，触发全量重建并记录。
5. **禁止在服务工作树上原地 `clean`**（会删掉服务正在使用的构建产物，并作废开发者 IDE 的增量状态）。
6. 校验期间服务进入独立状态并拒绝增量请求。

频率与范围属【待裁】（G5）。成本现实：全量编译是分钟级、GB 级产物重写。

### 5.3 漏测率（目标 0%）

1. 种子物化为**仓内可重放清单**：9 类改动（签名改 / 方法体改 / 注解增删 / 常量改 / 新增类 / 删除类 / 跨模块 API 改 / 测试数据文件改 / 模型文件改），**总样本 N = 200**、每类固定配额；不可编译的种子剔除并记账；分母为 0 的类别单独列出而非静默丢弃。
2. ground truth = 基准检出中 `./mvnw test` **实际执行**的测试类集合，并入改动符号的**字节码可达性闭包**（闭包计算复用 `nop-bytecode`）。种子以 patch 形式施加到基准检出。
3. `漏测率 = (ground_truth \ 服务选择的集合) / ground_truth`。
4. ground truth 采集是**离线一次性基线**（小时级预算）。
5. 过测率单独统计，上限【初值 ≤ 20%】。反馈必须暴露"选择集规模 + 是否为该模块全量"。

### 5.4 回退率与覆盖率（观测指标）

| 指标 | 说明 |
|------|------|
| 快路径命中率 | 实测基线 63.4%（§3.3）。**这是本设计最重要的运行时指标** |
| 回退率 | 回退 Maven 的占比，按枚举化原因分类 |
| 目标机器骨架成本 | 上线时实测，作为部署验收项（§2.3） |

## 六、不可违反的约束

### 6.1 正确性优先于速度【裁定】

无法证明安全的判定一律降级为 Maven。**假绿比慢危险得多**——它让 AI 在错误基础上继续叠加改动。

### 6.2 不修改项目构建结构【裁定】

不改构建语义、不新增构建插件、不要求模块声明本服务。Maven 调用限于：只读元数据提取 + 委托构建（含回退）。

### 6.3 复用而非平行建设，且必须复用对层【裁定】

- 影响分析复用 `nop-code-core` 的传播器与 `nop-code-lang-java` 的分析器（7 依赖、零 ORM），**不引入 `nop-code-service`**（26 依赖 + IoC 容器 + 数据库 + 每次查询多次 SQL 往返）。
- 编译能力**不能**复用 `nop-kernel/nop-javac`（实测无编译入口、只吃内存源码、无 release 通道），见 G10。

### 6.4 生成代码与 AOP 产物不进入增量编译路径【裁定】

`_gen/` 生成源码与模型文件走 Maven。**但不是所有生成模块都要回退**——实测生成只覆盖 139 个 pom（生效 137）中的部分模块，AOP 产物只落在 10 个叶模块；过度回退是上一版把适用面压到 3.8% 的原因之一。正确做法是**按模块能力分级**（见 Baseline §六）。

### 6.5 测试执行不得污染服务进程【裁定】

系统属性、静态缓存、全局容器生命周期、cwd 在常驻 JVM 内**不可回滚**。因此测试必须在隔离子进程中执行，且录制模式硬禁用。

### 6.6 一 worktree 一实例【裁定】

快照与索引写在工作树内。服务不并行服务多个工作树；一致性校验用的独立检出由服务独占管理。

## 七、显式 Non-Goals

| Non-Goal | 理由 |
|----------|------|
| 替代 CI 全量构建 | 不处理打包、发布、部署 |
| 接管 IDE 编译 | 双编译系统产物会冲突 |
| 做跨模块构建编排 | 跨模块传播与依赖图刷新超出本设计；跨模块改动一律回退 |
| 复用 `nop-code-service` 作为符号来源 | 需 IoC 容器 + 数据库；`nop-code-core` 已足够 |
| Delta 定制合并 | 属另一子系统 |
| JDK 门控模块 | 仅在满足门控 JDK 的实例中可用；收到其变更**显式拒绝** |
| JMH benchmark 模块 | 需注解处理器与独立运行环境 |
| Spring / Quarkus 宿主集成模块 | 注解处理器、IoC 装配与 native-image 前提与增量前提冲突 |
| GraalVM polyglot 上下文 | 常驻 JVM 的上下文隔离未设计 |
| 模型校验 | 由 `xdef-declarative-validation-design` 拥有 |
| 非 Java 语言 | 本期仅 Java |
| 分布式编译 | 单进程足够 |
| 修改代码生成管线 | 生成仍由 Maven 生命周期驱动，服务只消费产物 |

## 八、必须由人决策的决策点

| # | 决策点 | 选项 | 建议 |
|---|--------|------|------|
| G1 | **是否立项** | (a) 按本设计立项；(b) 只做测试选择不做增量编译；(c) 不立项，改为强化既有快速检查通道；(d) 先做低成本试验 | **(a)**，或 (c) + Phase 0 试验。依据见 §3.4 与 §四 |
| G2 | **模块归属** | 新顶层模块组 / `tools/` / 并入 `nop-code` / 并入 `nop-autotest` / 开发期工具组下新模块 | 开发期工具组下新模块（该组已在 reactor 内且有常驻调试服务先例）；**不新增 `-api` 模块**以避开受保护区域门禁 |
| G3 | 自建增量编译 | 做 / 不做 / 条件触发 | **做**。适用面 63.4%（§3.3），且对签名变更率不敏感（§3.4） |
| G4 | 传播深度与回退闸门 | 深度 1/2/3；绝对量 vs 比例 | 绝对量 + 比例双闸门；深度按模块规模自适应。**注意绝对量闸门近乎不是约束**（多口径下通过率 47%–100%），真正的约束是下游依赖与签名谓词 |
| G5 | 一致性校验 | (a) 校验环境：独立检出【裁定】；(b) 频率与范围【待裁】 | (b) 初值每日一次、范围全量 |
| G6 | 对外暴露形态与绑定地址 | HTTP loopback / unix socket / CLI-only / 跨机 | **CLI-only**。开发期工具经网络暴露会引入一整类不需要的安全裁定 |
| G7 | 注解处理器模块 | 全部回退 / 映射为处理器路径 | 全部回退。实测只影响少数模块（10 个 pom 配处理器，其中多数在测试侧） |
| G8 | 是否列为受保护区域 | 是 / 否 | 建议**是**（写构建产物，超出 `implement` autonomy） |
| G9 | 快照录制能力 | 不暴露 / 独立端点 | 不暴露【裁定】 |
| G10 | **编译能力来源** | (a) 扩展既有编译封装；(b) 自建文件式编译驱动；(c) 复用仓内已有的文件式编译实现 | 【待裁】。实测生产封装**三项能力全无**（无编译入口 / 只吃内存源码 / 无 release 通道），且它正被 AOP 生产链消费。但**仓内测试代码已有文件式 + `--release` + 输出目录的实现**（字节码分析模块的测试夹具），(c) 是成本最低的路径 |
| G11 | 索引召回率闸门方向 | 解析器级别 `==` release / `>=` release / 不设语言闸门 | **`>=`**（超集方向才安全）。`==` 会使服务对几乎所有模块**永久拒绝启动** |
| G12 | 构建环境固化程度 | 记录哪些环境要素并在漂移时拒绝增量 | 至少固化：`./mvnw` 绝对路径、Maven 版本、本地仓库路径、`settings.xml` 路径与哈希、JDK 主版本、`.mvn/jvm.config` 内容 |

## 十一、关键设计张力

| 张力 | 收敛方向 |
|------|---------|
| 速度 vs 正确性 | 正确性优先；假绿比慢危险得多 |
| 判定精度 vs 适用面 | **签名谓词是分水岭**：加它使适用面从 3.8% 升到 63.4%，而不加它会把收益最大的模块整体排除 |
| 成本认知 vs 部署现实 | 骨架成本是机器与负载的函数，不是常数。**上线必须实测**，不得沿用任何单机数字 |
| 覆盖广度 vs 维护成本 | 按模块能力分级，而非一刀切回退——过度回退是上一版最严重的错误来源 |
| 索引精度 vs 召回 | JavaParser 无类型绑定，召回率无上界；用保守放宽（宁可过测）与健康闸门换正确性 |
