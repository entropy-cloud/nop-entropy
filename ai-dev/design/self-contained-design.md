# 自完备设计（Self-Contained Design）——平台级跨域约束

**日期**：2026-09-25
**范围**：nop-entropy 平台全部子系统的技术选型与能力建设
**状态**：active（用户裁定的平台级设计原则，约束后续全部 design/plan；本篇为跨域约束层，各子系统 Vision 不得与本篇冲突）

---

## 一、原则

**nop 整体设计是自完备设计：核心能力自建，不引入外部大型的库/系统作为能力源或架构支柱**（例：jdt.ls 之类的语言服务器、IDE 平台、外部引擎、商业系统）。

平台的能力面（代码分析、代码修改、执行引擎、代码智能等）一律构建在自研引擎与自家基础设施之上；外部世界只以两类身份进入：**普通工具库依赖**或**窄桥接数据点**（见 §二）。

## 二、判定标准（不按依赖体积机械划线，按"是否成为架构支柱/能力源"判定）

| 类别 | 判定 | 例子 |
|------|------|------|
| **禁止引入** | 平台级/系统级外部件成为某条能力链的引擎或架构支柱 | jdt.ls（语言服务器当重构引擎）、OSGi/Equinox 运行时、把 ESLint/ast-grep/OpenRewrite 等外部引擎包装成本平台能力面、商业闭源系统 |
| **允许：普通依赖** | 职责单一的工具库，作为普通 Maven/npm 依赖，且**收敛在适配层内**、外部类型不向业务面扩散 | javaparser（经 `nop-utils/nop-java-parser` 包装）、协议实现库 |
| **边界场景：窄桥接** | 为获取**单一数据点**且无等价自建替代；必须进程隔离、常驻池化、fail-visible；外部系统不得借桥升格为能力链引擎 | nop-lint-js 的 `NodeTscBridge`（仅查 tsc 类型；TS 语法层仍是自家 nop-treesitter） |

架构支柱测试：如果移除该外部件，这条能力链是否整体消失？是 → 违反自完备；否（只是某个数据点/工具函数的提供者，可替换） → 允许。

## 三、既有一致性证据（平台已按此原则运行）

- **nop-treesitter**：tree-sitter C runtime 的**纯 Java 重写**（GLR parser/arena/query/scanner VM，上游 parser.c 仅作 blob 提取源），而非 JNI/FFM 绑定或 WASM 嵌入——本原则的样板决策。
- **nop-lint**：自研 pattern DSL 引擎、规则体系、fix 管线，而非集成 ESLint/PMD/ast-grep/Semgrep。
- **nop-code**：自研符号表/依赖图/调用层级，而非接入 LSIF/SCIP 外部索引器体系。
- **XLang**：自研执行后端族（解释器 / Java 转译 / Truffle），而非嵌入外部脚本引擎为骨架。

## 四、拒绝的替代与接受的代价

- **拒绝**：包装 jdt.ls 获得现成的 Java 重构全集（代价：Eclipse 工程模型强制、OSGi 部署体积、上游版本绑定、架构支柱外移到 nop 不可控的外部系统）。
- **接受的代价**：自建慢于引入现成件；某能力的外部全集不可得时，**收敛范围（做窄做精、降档、延期），不以引入外部大型件换功能面**。功能完整性让位于平台可控性与自完备性。

## 五、对后续 design/plan 的硬约束

1. 任何选型类 design 必须显式回答"为什么不引入外部大型件"，被拒候选留档。
2. 候选中含外部依赖时，须说明其非架构支柱（可替换、收敛在适配层、通过 §二 架构支柱测试）。
3. 自建方案与"引入外部件快速获得全集"冲突时，默认取自建；例外须在 design 中由用户裁定。
