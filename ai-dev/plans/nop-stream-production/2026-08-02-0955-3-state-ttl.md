## Purpose

为 keyed state 引入生存时间（TTL）与过期清理。状态条目在指定 TTL 后自动失效，通过 lazy eviction（访问时检查）+ RocksDB compaction filter（后台批量清理）实现。解决 `state-management-design.md` §11 列出的"无 TTL/无驱逐"限制。

**Phase 1-2（Memory TTL）可在 Stage 30 之前独立执行。Phase 3（RocksDB TTL + compaction filter）blocked on Stage 30。**

## Current Baseline

- `StateDescriptor`（`nop-stream-core/.../state/StateDescriptor.java`）携带 `name`/`valueType`/`defaultValue`/`serializer`——**无 TTL 配置项**；是 plain `Serializable`（非 `@DataBean`，无 `equals/hashCode`），添加字段在 Java 序列化层面向后兼容
- 所有 keyed state 实现（memory）**无任何过期逻辑**——状态只增长不收缩
- `MemoryStateSerDe`（749 行）是 checkpoint 快照的 normative spec：8 种 stateType 分支（`snapshotValueState`/`snapshotMapState`/`snapshotAppendingState`/`snapshotListState`/`snapshotReducingState`/`snapshotAggregatingState`/`snapshotInternalAggregatingState`/`snapshotListStateFromPublic`），**每个方法内部直接序列化存储 value**。`MemoryKeyedStateBackend.snapshotState()`（`:310`）仅委托 `new MemoryStateSerDe(this).snapshotState(states)`——**entry 遍历逻辑在 SerDe 的 per-type 方法内，不在 backend 层**
- `MemoryStateSerDe.restore*` 方法从 type names 重建 `StateDescriptor`（如 `restoreValueState` 构造 `new ValueStateDescriptor<>(stateName, valueClass)`）——**不携带 TTL config**。`getState()` 对已恢复 state 仅调用 `verifySchemaCompatibility`，不替换 descriptor
- **存储表示因 state 类型而异**：`MemoryReducingState` 存储 `SimpleAccumulator<T>` 对象；`MemoryInternalAppendingState` 存储 raw ACC 值；`MemoryValueState` 存储 `T`；`MemoryMapState` 存储 `Map<UK,UV>`——统一 `TtlValue<T>` 包装不可行
- `StateSchemaResolver.fromDescriptor` 只读 `stateType`/`valueType`/`mapKeyType`/`accumulatorType`/`aggregateFunctionType`——TTL 自然不进入 schema 签名（无需代码改动保证）
- `state-management-design.md` §11.1 列出"无内存控制——状态只增长不收缩... 无 TTL/驱逐/spill"为已知限制
- G42（P2）: 缺少 `StateTtlConfig`；G43（P2）: 缺少 TTL 装饰器 + compaction filter

## Goals

- `StateTtlConfig`：TTL 时长、更新类型（OnCreateAndWrite / OnReadAndWrite）、清理策略
- `StateDescriptor` 可选携带 `StateTtlConfig`，且 TTL config 在 checkpoint restore 后保持活跃
- Memory 后端：lazy eviction（访问时检查 sidecar 时间戳，过期返回默认值/空）
- RocksDB 后端（Stage 30 前置）：lazy eviction + compaction filter（后台批量清理）
- TTL 过期的 entry 在 checkpoint snapshot 时不被包含

## Non-Goals

- RocksDB backend 本身（Stage 30 前置——Phase 3 only）
- Operator state 的 TTL（仅 keyed state）
- Event-time / watermark-based TTL（首版仅 processing-time）
- CEP SharedBuffer 的 TTL（CEP 有自己的过期逻辑）

## Scope

### In Scope

- `StateTtlConfig` + `StateTtlUpdateType` 枚举 + `TtlCleanupStrategy`
- `StateDescriptor.setTtlConfig(StateTtlConfig)` 可选配置
- TTL 上下文（sidecar 时间戳追踪）：`Map<TypedNamespaceAndKey, Long> lastAccessTimestamps` 由 backend 维护，**与存储 value 分离**（兼容 accumulator-based states）
- Memory 后端 TTL lazy eviction + snapshot 过期排除
- RocksDB 后端 TTL（Phase 3，blocked on Stage 30）：lazy eviction + `AbstractCompactionFilter`
- `state-management-design.md` 更新

### Out Of Scope

- Event-time TTL（需 watermark 集成）
- Per-map-entry TTL（首版 MapState TTL 为 per-key+namespace 粒度——整 map 作为单元过期；per-UK-entry 为后续优化）

### Design Decisions

- **时间戳追踪方式**：**per-state sidecar map**（每个 state 持有自己的 `Map<TypedNamespaceAndKey, Long> lastAccessTimestamps`），不修改存储 value 结构。Rationale：(1) accumulator-based states（Reducing/Aggregating/Appending）存储 `SimpleAccumulator`/raw ACC 值，包装为 `TtlValue<T>` 会破坏 `(ACC) current` 类型转换和 fusion 逻辑；(2) 不同 state 可有不同 TTL duration，全局 sidecar 会因 `TypedNamespaceAndKey`（不含 state name）在不同 state 间碰撞
- **TTL 拦截机制**：**intrusive modification**——每个 state 类（`MemoryValueState`/`MemoryMapState`/etc.）增加可选 `TtlContext` 字段。TTL 启用时，read 方法（`value()`/`get()` 等）先检查 sidecar 时间戳，过期则返回默认值 + **同时删除存储 entry**（`storage.remove(key)`，不只删 sidecar）；write 方法更新 sidecar 时间戳。**不使用 wrapper/decorator pattern**——`MemoryStateSerDe.snapshotState()` 使用 `instanceof` 分发（`:77-96`），wrapper 会破坏分发逻辑。TTL 上下文绑定后，SerDe 的 `instanceof` 分发不受影响（state 类类型不变，TTL 是内部行为）
- **TTL 粒度**：per-key+namespace（一个 `TypedNamespaceAndKey` 一个时间戳）。MapState 的整 map 作为单元过期（per-UK-entry 为后续优化）
- **TTL config 持久化**：`StateTtlConfig` **不通过 `MemoryStateSerDe` 持久化**（它是运行时行为，非 schema 契约）。restore 后，`getState()` 用 **live descriptor**（用户代码中携带 TTL config 的 descriptor）注册 state——即用户代码在 restore 后重新调用 `getState(descriptor)` 时传入带 TTL 的 descriptor。**关键不变量**：`getState()` 在 state 已存在（restored）时，需检查 live descriptor 是否携带 TTL config，若是则将 TTL 上下文绑定到该 state（当前 `getState()` 仅 `verifySchemaCompatibility`，需增加 TTL rebind 逻辑）
- **清理策略**：lazy eviction（所有后端，访问时检查）+ RocksDB compaction filter（后台批量清理，RocksDB 专属）；snapshot 时跳过已过期 entry
- **Processing-time only**：首版不实现 event-time TTL

## Deferred But Adjudicated

### Event-time / watermark-based TTL

- Classification: `optimization candidate`
- Why Not Blocking Closure: Event-time TTL 需要 watermark 集成与乱序处理，复杂度显著高于 processing-time TTL。首版 processing-time TTL 覆盖主要使用场景。
- Successor Required: no
- Successor Path: (future enhancement, not on current roadmap)

### Per-UK-entry TTL for MapState

- Classification: `optimization candidate`
- Why Not Blocking Closure: 首版 MapState TTL 为 per-key+namespace 粒度（整 map 过期）。per-UK-entry 需更复杂的 sidecar 结构，为后续优化。
- Successor Required: no
- Successor Path: (future optimization)

### RocksDB native compaction filter（JNI）

- Classification: `out-of-scope improvement`
- Why Not Blocking Closure: plan 原计划用 RocksDB `AbstractCompactionFilter`（JNI）做后台清理。执行期核实 `rocksdbjni` 9.11.2（亦见于 7.9.2）未暴露纯 Java compaction-filter 回调——`AbstractCompactionFilter` 仅有 protected native 构造器，无 `filter()` 可覆盖；自定义过滤需 C++/JNI native 扩展，超出 `nop-stream-rocksdb` 纯 Java 模块范围。已交付纯 Java `RocksDBKeyedStateBackend.cleanupExpiredEntries()` sweep 作为**语义等价**的后台批量清理（在 `snapshotState()` 起始处执行，物理删除过期 entry；scalar/list/accumulator 单键删除，MapState 前缀删除）。TTL 正确性不依赖 compaction filter：lazy eviction + snapshot 排除 + sweep 已保证过期语义。compaction filter 仅为性能优化（compaction 时回收空间，避免 sweep 全扫描），非正确性需求。
- Successor Required: no
- Successor Path: (future: 当 `nop-stream-rocksdb` 引入 native 扩展时，可改用 native compaction filter 替代/补充 sweep)
