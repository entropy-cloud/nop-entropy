## Purpose

把 nop-stream 的 keyed state 分片模型从「固定不可变 `stateShardCount` + `Object.hashCode()`」演进为「`maxParallelism` + 稳定哈希 + KeyGroup」模型，使 key→group 映射在并行度变化时保持稳定，为 Stage 35 的 rescale 局部恢复和 Stage 37 的存量迁移奠定前置基础。同时交付 Stage 30 deferred 的「二进制复合键 key-group 可排序前缀」，使 RocksDB 后续可做 range 交集读取。

## Current Baseline

- `StateShard`（`nop-stream-core/.../common/state/shard/StateShard.java:22-111`）是 immutable `@DataBean`：`stateShardCount` / `stateShardId` / `ownerSubtask` / `hashPolicy`。`computeShardId`（`:69-74`）= `(stableHash(key) & 0x7FFFFFFF) % stateShardCount`。
- **G38 现状**：`StateShard.stableHash`（`:76-78`）= `key != null ? key.hashCode() : 0`，直接用 `Object.hashCode()`。String/Long/Integer 等内置类型稳定，但用户 POJO 的 `hashCode()` 跨 JVM 实例不稳定。
- key→shard 路由**内联在两个后端**，不经过 `StateShard` 实例：
  - `MemoryKeyedStateBackend.routeKey`（`MemoryKeyedStateBackend.java:344-350`）= `(StateShard.stableHash(key) & 0x7FFFFFFF) % shardCount`，结果包成 `ShardPrefixedKey`。
  - `RocksDBKeyedStateBackend.computeShardId`（`RocksDBKeyedStateBackend.java:248-253`）同公式。
- `StateShard` DataBean 类的 `new StateShard(...)` 构造在生产运行时无调用者（仅 `TestStateShard*.java`）。**但** `StateShard.stableHash(...)` **静态方法在生产路径被两个后端调用**（`MemoryKeyedStateBackend.java:348`、`RocksDBKeyedStateBackend.java:252`）。且 `StateShard` 是 `TaskEpochSnapshot.shards`（`TaskEpochSnapshot.java:25`）的元素类型，经 `CheckpointSerDe` JSON 持久化——改其字段会影响 checkpoint JSON 表面（向后兼容需默认值）。生产路径只用裸 `shardCount` 整数（构造器参数）。
- **RocksDB 复合键布局**（`RocksDBKeyEncoder.encode`，`RocksDBKeyEncoder.java:57-69`）：`[nsLen:int32 BE][nsJsonBytes][shardId:int32 BE][keyLen:int32 BE][keyJsonBytes]`。`shardId` 嵌在**中间**（namespace 之后、key 之前），**不是可排序前缀**，无法做单 shard/group 的 range scan。
- **`maxParallelism` / `KeyGroup` / `KeyGroupRange` / `MurmurHash` 在 nop-stream 全代码库零命中**（`maxParallelism` 仅出现在 Stream DSL 模型层 `_StreamSourceModel` 等，与 state 分片无关）。
- 并行度是 `PartitionedPlan.VertexPlan`（`PartitionedPlan.java:62-81`）上的 per-vertex `int parallelism`；`TaskLocation`（`io.nop.stream.core.checkpoint.TaskLocation`）以 `taskIndex` 标识 subtask。无全局 maxParallelism 概念。
- 设计文档现状：`state-management-design.md` §3（`:74-89`）描述 StateShard 为「非 Flink key-group，只承担稳定路由」；`comparison.md` §6.3（`:337-355`）记录 Key-Group vs StateShard 对比，并注明 nop-stream 暂不引入。`00-vision.md:81` 把「complete key-group redistribution」列为**已移除**。
- 决策点 D1（`roadmap.md:847`）：推荐「StateShard 增加 `maxParallelism` + 稳定哈希（最小侵入）」而非另起 KeyGroup 抽象。
- Stage 30 plan（`2026-08-02-0955-1-rocksdb-state-backend.md:196-201`）已将「Binary composite key encoding」deferred 到本 Stage 34。
- 无 rescale 恢复能力：`stateShardCount` 改变需显式迁移（`checkpoint-design.md:824`、`state-management-design.md:89`）。`TestStateShardRescale.java` 仅验证单后端实例跨 shardCount 快照保留 key，不验证并行度变化或 subtask 切片。

## Goals

- **G37**：引入 `KeyGroup` 模型与 `maxParallelism`（默认 128）。`key → keyGroupId = stableHash(key) % maxParallelism`。`maxParallelism` 作为 keyed 作业的稳定上界，作业生命周期内不变。
- **G38**：用确定性稳定哈希（与 JVM 实例、`System.identityHashCode`、POJO `hashCode()` 无关）替代 `StateShard.stableHash` 的 `Object.hashCode()`。同一 key 在不同 JVM、不同进程重启后映射到同一 group。
- **G39**：提供 `KeyGroupRange`（连续区间 `[start, end)`）的交集、包含、分割/切分操作，供 Stage 35 做 range 交集恢复。
- **Binary composite key prefix（Stage 30 deferred）**：RocksDB 复合键改为以 `keyGroupId` 为**可排序二进制前缀**，使同一 group 的 key 在 SST 中连续存储，Stage 35 可做 range 交集读取。新布局下现有全量 snapshot/restore 仍正确工作（编码有真实消费者，非空壳）。
- **group→subtask 映射函数**：给定 job-global `maxParallelism` + per-vertex `parallelism`，subtask `i` 拥有连续 `KeyGroupRange`。本 plan 交付函数 + 单测，生产 rescale 接线在 Stage 35。
- Owner-doc 更新：`state-management-design.md` §3 记录「StateShard 演进为 KeyGroup 路由」决策；`comparison.md` §6.3 同步现状。

### 关键架构决策（Decision，draft review 裁定）

> **`maxParallelism` 语义 = job-global（状态后端实例属性），非 per-vertex。**

- **现状基线**：`shardCount` 当前是 **job-global**——存在 `MemoryStateBackend`/`RocksDBStateBackend` **实例**上，用户在 `env.setStateBackend(new MemoryStateBackend(shardCount))` 时设定，全作业所有 keyed vertex 共享同一值（`IStateBackend.createKeyedStateBackend(Class<K>)` 无 parallelism 入参）。
- **本 plan 决策**：`maxParallelism` 沿用同一 job-global 模型（后端实例属性，默认 128，构造时设定），**替代** `shardCount`。**不**做 per-vertex DSL `keyBy → VertexPlan` 透传。
- **理由**：(a) 与现有 `shardCount` 架构一致，最小侵入；(b) vision §十明确排除 Flink ExecutionGraph 三层调度，per-operator maxParallelism 属被排除复杂度；(c) rescale（Stage 35）只改变 per-vertex `VertexPlan.parallelism`（已有字段），`maxParallelism` 保持固定即可满足 key→group 映射不变性。
- **避免 DSL 命名冲突**：`maxParallelism` 已存在于 `_StreamSourceModel`/`_StreamSinkModel`（source/sink 并行度 hint，与 state 无关）。因本 plan 不把 maxParallelism 放进 DSL/keyBy 路径，二者位于不同类（后端构造器 vs DSL 模型），无冲突。

## Non-Goals

- **rescale 局部恢复 / savepoint 跨并行度 restore**（Stage 35）——本 plan 只交付模型与编码，不实现部分恢复。
- **per-vertex `maxParallelism`**——`maxParallelism` 为 job-global（见上方架构决策）；不引入 Flink per-operator maxParallelism（vision §十排除）。`KeyGroupRange`/group→subtask 映射函数的生产 rescale 接线亦属 Stage 35。
- **StateShard→KeyGroup 存量 savepoint 自动迁移 + vision Non-Goal 更新**（Stage 37）。
- **BroadcastState**（Stage 36，vision-gated，未决策不做）。
- 改变 `stateShardCount` 默认不可变的语义约束。
- Flink `KeyGroupRangeAssignment` / `ExecutionGraph` 三层调度抽象移植（vision 约束排除）。
- 跨 JVM key-group 路由（Stage 40/42 数据面）。

## Scope

### In Scope

- `KeyGroup` / `KeyGroupRange` / `maxParallelism` 模型类与稳定哈希实现。
- 替换 `StateShard.stableHash` 与两个后端内联路由公式为基于 `maxParallelism` 的 key→group 映射。
- RocksDB 复合键二进制布局重构：`keyGroupId` 可排序前缀 + 现有全量 snapshot/restore 适配。
- `maxParallelism` 作为 **job-global** 状态后端实例属性（替代 `shardCount`，默认 128），从 `env.setStateBackend(new XxxStateBackend(maxParallelism))` 接入；group→subtask 映射函数（消费 job-global `maxParallelism` + per-vertex `VertexPlan.parallelism`）。
- 单测：哈希稳定性、key→group 映射确定性、KeyGroupRange 集合操作、新键布局 round-trip、路由等价性、`TaskEpochSnapshot` JSON 向后兼容。

### Out Of Scope

- range 交集 partial restore（Stage 35）。
- per-subtask state slice 物理切分与 `TaskEpochSnapshot.shards` 生产填充（Stage 35）。
- 增量 checkpoint SST 的 group 前缀读取（Stage 35 消费本 plan 编码）。
- 存量 savepoint 迁移工具（Stage 37）。
