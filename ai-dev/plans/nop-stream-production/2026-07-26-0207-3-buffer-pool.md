# 26 — Buffer pool 抽象（跨 partition 全局内存治理）

> Plan Status: active
> Last Reviewed: 2026-07-26
> Source: `ai-dev/backlog/nop-stream-production-roadmap.md` Stage 26 (G53); `ai-dev/design/nop-stream/01-architecture-baseline.md` §六
> Mission: nop-stream-production
> Work Item: 26 (Phase 1 — 分布式运行时基础)
> Related: Stage 24 plan (`2026-07-26-0207-1-deployment-plan-discovery.md`)（**建议顺序**：两 plan 改不同代码面——Stage 24 改 DeploymentPlan/`IDeploymentPlanProvider`/`JobCoordinator.assignTasks`，本 plan 改 `GraphExecutionPlan.build`/`ResultPartition`，无代码冲突；建议 Stage 24 先 landing 仅因 Phase 1 依赖关系，非硬阻塞）；为 Stage 28（G27 进程内 backpressure）提供有界缓冲底座

## Purpose

引入最小化 `IBufferPool` SPI 统一治理**跨 partition 的全局进程内内存上限**，闭合当前「每个 ResultPartition 各自硬编码 1024 容量、`EdgeConfig.queueCapacity` 声明未接线、`MemoryBudget.networkBuffers` 纯声明」的缺口。

**价值定位校正**：进程内 per-partition backpressure **已存在**（`ResultPartition.queue.put()` 满时阻塞生产者）。本 plan 的真实价值不是「引入 backpressure」，而是**跨多 partition 的全局聚合内存上限与公平性治理**（防止 fan-out 场景下 N 个 partition 各占 1024 导致 OOM）。为 Stage 28（G27 进程内 backpressure 契约）提供有界缓冲底座。

## Current Baseline

经 live 仓库核对：

- **`IBufferPool` 不存在**：grep `IBufferPool|BufferPool|bufferPool` in `nop-stream/` = 零匹配。
- **`ResultPartition`**（`nop-stream-core/.../execution/ResultPartition.java`）：单条 `LinkedBlockingQueue<StreamElement>`，`DEFAULT_CAPACITY=1024`（`:46`，**单位=元素数，非字节**），`write()` 用 `queue.put()`（`:87`）满时阻塞生产者。每个 partition **独立拥有自己的队列，无共享 arena**。
- **构造路径**：`ResultPartition` 由 **静态工厂 `GraphExecutionPlan.build(...)`**（`GraphExecutionPlan.java:167-168`）在 `:189` 以默认构造创建，调用方为 `StreamExecutionEnvironment.java:280` 及 `GraphModelCheckpointExecutor.java:448-467` 多个重载。`EdgeConfig.queueCapacity`（`:20`，元素数）**未传入** `new ResultPartition()`（恒用默认 1024）。
- **跨 JVM 子类绕过队列**：
  - `RemoteResultPartition extends ResultPartition`（`RemoteResultPartition.java:42`），`super(1)`（`:70`，队列不用），**override `write()`（`:87`）直接 `messageService.send()` 绕过队列**——生产端无 bound。
  - `RemoteInputChannel`（`RemoteInputChannel.java:97`）`super(new ResultPartition(1))`（dummy partition），自带 `LinkedBlockingQueue`（cap 1024，`:54`）。
- **`RecordWriter.validateFlowControlPolicy`**（`:130`）对非 `BLOCKING_QUEUE` 抛 `UnsupportedOperationException`。`CREDIT_BASED`/`ACK_WINDOW` 枚举存在但不可用。
- **`MemoryBudget`**（`MemoryBudget.java`）：`networkBuffers` 桶（`:40`，**单位=字节**）**纯声明，从不约束任何缓冲**。
- **`IWriteStatus`**（`IWriteStatus.java`）：`isBackpressured`/`getAvailableCapacity`/`getTotalCapacity`，`ResultPartition`（`:168-180`）实现读取 per-partition 私有队列。

### 真正剩余的 gap

- **G53**：无 `IBufferPool` SPI；无跨 partition 全局聚合内存上限（各 partition 私有 1024，fan-out 下无总量约束）。
- 附带：`EdgeConfig.queueCapacity` 未接线（恒用 1024 默认值）。

## Goals

- 引入 `IBufferPool` SPI + Memory 实现（**元素计数制**，与 `ResultPartition`/`EdgeConfig.queueCapacity` 单位一致），承担跨 partition 全局聚合上限。
- `ResultPartition` 在生产 `build()` 路径下从私有硬编码队列改为向**单一 per-job pool**（一次执行共享一个 pool 实例）申请容量配额；直接构造（测试/Remote）保持当前 per-partition 有界行为（pool=null）。
- `EdgeConfig.queueCapacity` 接线到 partition 容量。
- pool 满时全局 backpressure 可观测；`IWriteStatus` per-partition 指标语义明确（不变）。

## Non-Goals

- **credit-based / ACK_WINDOW 网络层 flow control（G27 跨 JVM 部分不在本 plan）**：vision 约束 7 排除 Flink Netty 网络栈；跨 JVM backpressure 由 `IMessageService` 后端（Stage 40）提供。
- **`RemoteResultPartition` 生产端无界修复（Stage 40）**：本 plan 的 pool 仅作用于**本地 `ResultPartition` 路径**；`RemoteResultPartition` 显式排除（见 Phase 1 决策）。
- **`MemoryBudget.networkBuffers`（字节制）与 pool（元素制）的换算**：单位不可比（元素大小可变），本 plan 不做字节↔元素换算（见 Phase 1 决策裁定）。
- RocksDB / off-heap 内存管理（Stage 30+）。
- 内存超限 spill-to-disk（G66 推迟项）。

## Scope

### In Scope

- `IBufferPool` SPI + Memory 实现（元素计数制，per-job 单实例，全局聚合上限可配）。
- `ResultPartition` 从 pool 申请容量配额（保留满时阻塞生产者语义）。
- `EdgeConfig.queueCapacity` 接线到 partition 容量。
- pool 注入路径：经 `GraphExecutionPlan.build(...)` 工厂参数传入（per-job 单实例），由 `StreamExecutionEnvironment`/`GraphModelCheckpointExecutor` 调用处创建。
- 明确排除 `RemoteResultPartition`/`RemoteInputChannel`（Stage 40）+ `MemoryBudget.networkBuffers` 换算。

### Out Of Scope

- credit-based / ACK_WINDOW flow control（Flink Netty 概念，vision 排除）。
- 跨 JVM 生产端 bound（`RemoteResultPartition`，Stage 40）。
- `MemoryBudget.networkBuffers` 字节制换算（单位不可比，裁定为不换算）。
- spill-to-disk（G66 推迟）。

## Execution Plan

### Phase 1 — IBufferPool SPI + Memory 实现 + 注入路径（G53）

Status: planned
Targets: `nop-stream-core/.../execution/`（新增 buffer pool 包）, `ResultPartition.java`, `EdgeConfig.java`, `GraphExecutionPlan.java`, `StreamExecutionEnvironment.java`, `GraphModelCheckpointExecutor.java`

- Item Types: `Fix | Decision`

- [ ] 新增 `IBufferPool` SPI（元素计数制：申请/归还容量、per-job 全局聚合上限可配、容量计量）+ Memory 实现（有界 arena）。
- [ ] **pool 耗尽契约（已裁定，不留 open）**：pool 容量耗尽时**阻塞**申请方（与现有 `ResultPartition.write()` 用 `queue.put()` 阻塞生产者的语义一致，兑现 Goal「backpressure 可观测」），**不抛 RuntimeException**。因此 `RecordWriter.emit()` 既有 `InterruptedException` 处理路径无需新增异常分支。阻塞须可被 cancel/interrupt 唤醒（不永久死锁）。
- [ ] **pool 基数决策（已裁定）**：pool 为 **per-job 单实例**（一次 `execute()` 执行内所有 partition 共享一个 pool），非 per-partition、非 per-process。这样「跨 partition 全局上限」才可观测。
- [ ] **注入路径决策（已裁定，含 build + ResultPartition 双 overload 策略）**：
  - `IBufferPool` 经 **`GraphExecutionPlan.build(...)` 工厂**传入。`build` 是 4 重载链（`GraphExecutionPlan.java:119/134/152/167`），被 6 个生产调用点（`StreamExecutionEnvironment.java:280` + `GraphModelCheckpointExecutor.java` 5 个重载）+ ~38 个测试调用点消费。**build overload 策略**：旧重载（无 pool 参数）**内部默认创建一个 per-build pool**（每次 `build()` = 一次执行，自建 pool 满足 per-job 语义，向后兼容、不强制迁移调用点/测试）；新重载显式接收 pool 参数。
  - `ResultPartition` 当前 2 构造（`ResultPartition()` `:54`、`ResultPartition(int)` `:64`），被 ~130+ 测试直接构造 + `RemoteResultPartition`(`super(1)`)/`RemoteInputChannel`(`super(new ResultPartition(1))`) 使用。**ResultPartition overload 策略**：**保留现有 2 构造向后兼容**（pool=null 表示无全局聚合约束，仅 per-partition 队列有界=当前行为，130+ 测试 + Remote 子类不改）；**新增 pool 感知构造**供 `build()` 生产路径使用（pool 非 null 时向 pool 申请配额，受全局上限约束）。即：**生产 build() 路径才强制全局 pool；直接构造（测试/Remote）保持当前行为**——这与「Remote 排除」决策一致。
- [ ] 接线 `EdgeConfig.queueCapacity`（元素数）→ partition 容量（`GraphExecutionPlan` 创建 partition 时传入 pool 感知构造）。
- [ ] **pool 所有权/关闭（已裁定）**：`GraphExecutionPlan` 持有 pool 引用（新增字段），供 `execute()` 结束/异常时关闭 pool；恢复重建（见下条）创建新 pool。
- [ ] **pool 生命周期于 checkpoint 恢复（已裁定）**：`GraphModelCheckpointExecutor` 恢复后重建 plan 时**创建新 pool**（不复用失败 attempt 的 pool，避免 leaked permits 饿死恢复）。
- [ ] **`MemoryBudget.networkBuffers` 关系裁定（已裁定，不留 open）**：pool 为元素计数制、`networkBuffers` 为字节制，**单位不可比、不做换算**；pool 不读取 `networkBuffers`。`MemoryBudget.networkBuffers` 保持现有纯声明状态，其字节制治理留给未来 off-heap/RocksDB 工作（Stage 30+）。本裁定记录于 design doc。

Exit Criteria:

- [ ] `IBufferPool` SPI + Memory 实现有单测：全局聚合上限被尊重、申请/归还正确、pool 满时申请**阻塞**（裁定契约，非抛异常）且可被 interrupt 唤醒。
- [ ] pool 为 per-job 单实例：`GraphExecutionPlan.build` 接收 pool 参数（旧重载内部默认创建 per-build pool，向后兼容），所有 partition 共享同一实例（单测验证多 partition 共享同一 pool 引用；单测验证旧重载自建 pool 行为）。
- [ ] `ResultPartition` 容量受 pool 约束（非恒定 1024）：单测验证多 partition 共享 pool 时总量受限。
- [ ] `EdgeConfig.queueCapacity` 真实影响 partition 容量（单测：queueCapacity=10 断言 partition 容量=10）。
- [ ] **端到端验证**（#22）：从 `execute()` → per-job pool 创建 → 多 partition 共享 → 生产者超过全局上限时 backpressure 生效 的完整路径跑通（E2E 断言生产者在 pool 耗尽时阻塞/放缓）。
- [ ] **接线验证**（#23）：测试断言 ResultPartition 运行时确实从注入的 pool 申请容量（mock/计数器 verify），而非仍用私有硬编码队列；断言 `GraphExecutionPlan.build` 调用方确实创建并传入了 pool。
- [ ] **无静默跳过**（#24）：pool 容量耗尽时按裁定**阻塞**（非静默丢弃/返回 null）；阻塞可被 cancel/interrupt 唤醒。
- [ ] owner-doc：`01-architecture-baseline.md` §六（IBufferPool per-job 单实例 + 元素计数制 + 不换算 networkBuffers + RemoteResultPartition 排除）已更新。
- [ ] `ai-dev/logs/` 对应日期条目已更新。

## Deferred But Adjudicated

### 跨 JVM 生产端 backpressure（RemoteResultPartition 无界）

- Classification: `out-of-scope improvement`
- Why Not Blocking Closure: `RemoteResultPartition` 生产端无界属跨 JVM 数据面问题，由 `IMessageService` 后端（Stage 40）提供 bound；本 plan 的 pool 明确仅作用于本地 ResultPartition 路径，Remote 路径有意排除并文档化。当前 DISTRIBUTED 路径仍为进程内 `EmbeddedDistributedExecutor`，跨 JVM 生产端 bound 未引入不破坏 supported baseline。
- Successor Required: yes
- Successor Path: Stage 40 (`40-data-plane`)

### MemoryBudget.networkBuffers 字节制治理

- Classification: `out-of-scope improvement`
- Why Not Blocking Closure: pool 为元素计数制，`networkBuffers` 为字节制，单位不可比；字节制治理属 off-heap/RocksDB 工作（Stage 30+）。本 plan pool 不读取 networkBuffers，二者关系已裁定为不换算并记录。
- Successor Required: yes
- Successor Path: Stage 30 (`30-rocksdb-backend`)

### credit-based / ACK_WINDOW flow control

- Classification: `out-of-scope improvement`
- Why Not Blocking Closure: vision 约束 7 明确排除 Flink Netty 网络栈；本 plan 不重建网络层 flow control，仅做进程内有界缓冲。
- Successor Required: no
