# Stage 49 — Source split 体系（FLIP-27 风格）

> Plan Status: completed
> Last Reviewed: 2026-08-04
> Source: `ai-dev/backlog/nop-stream-production-roadmap.md` Stage 49；`ai-dev/design/nop-stream/connector-design.md §4`（已规划 Beam-SDF 风格 SourceWorkUnit/SplitAssignmentRecovery 协议，设计态）；`ai-dev/design/nop-stream/comparison.md:503,684`
> Related: Stage 24（DeploymentPlan）、Stage 38（Leader election/HA）、Stage 39（跨 JVM 控制 RPC）、Stage 42（TaskDeploymentDescriptor）

## Purpose

把 nop-stream 的 source 层从「仅 `SourceFunction`（单线程、无 split 概念）」推进到「FLIP-27 风格 split-based Source（`Source` / `SplitEnumerator` / `SourceReader`）」，使 source 支持动态 split 发现/分配、并行 split 消费、以及 split cursor 级 checkpoint/restore。本 plan 收口 Stage 49 的框架 + 一个参考实现，让 split-based source 端到端可用。

## Current Baseline

- nop-stream source 层**完全基于 `SourceFunction`**（Flink legacy 风格）。核心接口 `SourceFunction<T>` 在 `nop-stream-core/.../source/SourceFunction.java:22`。
- **不存在** new-style `Source` / `SourceReader` / `SplitEnumerator` 接口（全仓库 grep 零命中）。
- 存在**未接线的原型脚手架**（concrete，非接口）：
  - `SourceSplit`（`nop-stream-runtime/.../source/SourceSplit.java:17`）— concrete 类，非泛型，字段 `splitId/description/cursor`。
  - `SourceEnumerator`（`nop-stream-runtime/.../source/SourceEnumerator.java:44`，326 行完整实现）— concrete 类，round-robin 分配，仅被 `TestSourceEnumerator`（15+ 引用）和 `TestDistributedExactlyOnce`（6+ 引用）直接构造，**无生产类引用**，未流经 `addSource`。
  - `SourceEnumeratorState`（`nop-stream-core/.../checkpoint/SourceEnumeratorState.java:22`）— `@DataBean` 快照 holder。
  - `SourceWorkUnit`（`nop-stream-core/.../connector/SourceWorkUnit.java:24`）— `@Internal`，javadoc 明确「Reserved for future FLIP-27 style connector framework. Not yet used.」
- `StreamExecutionEnvironment.addSource` 只接受 `SourceFunction`（`nop-stream-core/.../environment/StreamExecutionEnvironment.java:202,209`），无 `addSource(Source)` 重载。
- `SourceTransformation`（`nop-stream-core/.../transformation/SourceTransformation.java:36`）持 `private final SourceFunction<OUT>`；`StreamGraphGenerator.java:214-242` 据此 `new SourceOperatorFactory<>(getSourceFunction())`。
- `StreamSourceOperator`（`nop-stream-core/.../operators/StreamSourceOperator.java:43`）是唯一 source 算子；checkpoint 仅理解 `ReplayableSourceFunction`/`CheckpointedSourceFunction`（snapshot `:302`/restore `:319`），无 per-split state、无 enumerator-side checkpoint。
- **不存在 coordinator-side 状态 checkpoint 槽位（代码层）**：grep `enumeratorState|coordinatorState` 在生产代码零命中；`CheckpointCoordinator` 仅处理 task 级 operator-state 快照（`TaskEpochSnapshot`），EpochManifest 代码层无 enumerator-state section。但**设计层已有**：`checkpoint-design.md §2.6`（L181 manifest 字段 `sourceEnumeratorSnapshots`）+ §5.3（6-state 分解：discovered/unassigned/assigned/finished/pending-ack/discovery-cursor + restore 规则）+ §5.3.1 G35（明确把 source enumerator state checkpointing 列为 Stage 49 successor scope）。→ 本 plan 需**落地该设计**为代码（非复用代码，但**复用设计** §2.6/§5.3），并统一字段名为 `sourceEnumeratorSnapshots`。
- `DeploymentPlan`（`@DataBean`，84 行）/ `TaskDeploymentDescriptor`（199 行，含 `JobGraph` 算子模板 + checkpointRestorePath）**均无 split 字段**，且 `TaskDeploymentDescriptor` 按其设计**不携带 live runtime 对象**。→ 初始 split **不能**塞进 descriptor，须 deploy 后经控制 RPC 下发。
- 现有 source 连接器均为 SourceFunction 形态：`MessageSourceFunction`、`BatchLoaderSourceFunction`、`DebeziumCdcSourceFunction`。Kafka 经 `KafkaMessageService` 用 consumer-group 分配，**非显式 partition split**；分区用 topic-name 后缀 hack 模拟。
- 设计文档 `connector-design.md §4`（L125-276）是 **Beam-SDF 风格**（`SourceWorkUnit` + `RestrictionTracker<R>` + `DynamicSplitRequest{fraction}` + `WatermarkEstimator` + `SplitAssignmentTracker`），与 roadmap 要求的「FLIP-27 风格」是**不同范式**——需在本 plan 裁定。
- `comparison.md:503` gap 表明确列 nop-stream「❌ 不实现」。

## Goals

- 引入 FLIP-27 风格的 split-based Source 契约：`Source<OUT,SplitT,EnumStateT>`、`SplitEnumerator<SplitT,StateT>`、`SourceReader<OUT,SplitT>`、`SourceSplit`（接口）。
- 新增 `addSource(Source)` 入口，接到新的 `SourceReaderOperator`，端到端可执行。
- split 发现/分配 + checkpoint 集成：enumerator state（**新增 coordinator-state checkpoint 槽位**）+ reader per-split cursor（task operator state）都参与 checkpoint/restore。
- 交付一个参考 `Source` 实现（bounded `FileSource`，按文件枚举 split、按字节 offset 作 cursor），证明路径端到端可用。
- 收敛现有未接线原型：用新接口体系取代 standalone 的 concrete `SourceEnumerator`/`SourceSplit`，不保留两套竞争系统。

## Non-Goals

- Flink `Source`/`SplitEnumerator`/`SourceReader` API 全表面 parity（v1 不引入 `SourceEvent` 自定义 coordinator↔reader 事件、不引入 enumerator-side watermark estimation）。
- Beam-SDF 的 `RestrictionTracker`/claim-position-within-restriction/`DynamicSplit{fraction}` 范式（§4）——本 plan 选 FLIP-27，Beam-SDF 元素裁定为 rejected/deferred（见 Phase 0 D1）。
- 迁移现有 SourceFunction 连接器（MessageSourceFunction/BatchLoaderSourceFunction/Debezium）到新 API——保持现状可用。
- 跨运行 reader 的弹性 split 再分配（split stealing）——v1 只在 deploy + restore 时做分配，reader 经 `handleSplitRequest` 拉取更多 split。
- 真实 Kafka partition-as-split source——属后续连接器 plan；本 plan 只交付框架 + bounded 参考源。
- 持续后台轮询发现 unbounded split 的完整调度（见 Phase 0 D4 裁定）。

## Scope

### In Scope

- 新接口（`nop-stream-core`）：`Source`、`SplitEnumerator`、`SourceReader`、`SourceSplit`（接口）。
- `addSource(Source)` 重载 + `SourceTransformation` 路由（新分支或新 transformation 类，见 Phase 0 D5）+ 新 `SourceReaderOperator`（与 `StreamSourceOperator` 并列）。
- **新增 coordinator-state checkpoint 槽位**（EpochManifest 新 section + CheckpointCoordinator 段）承载 enumerator state（非复用，新机制）。
- enumerator 运行在 JobCoordinator；初始 split 经控制 RPC（Stage 39）deploy 后下发（不嵌入 descriptor）；reader 上报 finished split。
- checkpoint 集成：enumerator state（coordinator 新槽位）+ reader split cursor（task operator state）。
- 参考 bounded `FileSource`：目录→文件 split 枚举、按字节 offset cursor。
- E2E：source → 算子 → sink 完整跑通；checkpoint + kill + restore 后无丢失、cursor/enumerator-state 正确恢复。
- 收敛旧原型：`SourceEnumerator`(concrete)/`SourceSplit`(concrete) 适配或删除并迁移测试。

### Out Of Scope

- 上述 Non-Goals 全部；`StreamSourceOperator` 现有 SourceFunction 路径不变；union/sideOutput（Stage 50 deferred）。

## Deferred But Adjudicated

- Successor Path: 引入 `OperatorCoordinator` 的后续 plan。

### 持续后台轮询发现 unbounded split（push 模型完整调度）

- Classification: `optimization candidate`

- Successor Required: `yes`
- Successor Path: 后续 unbounded source 连接器 plan。
