## Purpose

Execute the full MA4 (Code Quality Audit) milestone across all nop-ai modules: type safety & generics, code style & standards, test coverage, unit test effectiveness, and documentation-code consistency. This unblocks MR2 (P1 batch fix for MA3+MA4 findings).

## Current Baseline

- MA1, MA2, MA3 are complete and documented
- MA4 sub-items (4.1–4.5) are all `todo` in both roadmap and arm-index.md
- MR2 depends on MA4 completion (MA3 already done)
- nop-ai module group: ~1275 main Java, ~426 test Java across 18 sub-modules
- No prior code quality audit exists for nop-ai modules
- MA5.1/MA5.2/MA5.3 (residual risk scans) are done and uncovered 2 P1 findings each for hollow/silent-noop/wiring

## Goals

- Produce audit report for MA4.1 (type safety & generics: raw types, unchecked casts, generic erasure)
- Produce audit report for MA4.2 (code style: naming, imports grouping, file length, comment quality)
- Produce audit report for MA4.3 (test coverage: coverage gaps, assertion strength, mock usage patterns)
- Produce audit report for MA4.4 (test effectiveness: bug-catching ability, boundary coverage, exception paths)
- Produce audit report for MA4.5 (doc-code consistency: javadoc vs actual behavior, stale comments)
- Update `ai-dev/audits/arm-index.md` with findings and status

## Non-Goals

- Fixing any findings discovered (will be addressed in MR2)
- Re-auditing MA1, MA2, MA3 items (already done)
- Auditing MA5 or MA6 items (separate plans)
- MCP modules (excluded per roadmap)

### Phase 2 — MA4.2: Code style audit

### Phase 3 — MA4.3: Test coverage audit

Status: planned
Targets: All nop-ai `src/test/java/` + `src/main/java/`

- Item Types: `Proof`

- [ ] Load `ai-dev/skills/deep-audit-prompts.md` Dimension 16 for audit methodology
- [ ] Per-module test class mapping: match `src/test/java/` directory names against `src/main/java/` — report classes that lack corresponding test classes

Exit Criteria:

- [ ] Report documents coverage gaps with specific class names — methodology: directory-level matching + BizModel spot-check

- [ ] Assertion quality issues documented with examples
- [ ] No owner-doc update required (audit-only phase)
- [ ] `ai-dev/logs/` corresponding date entry updated

### Phase 4 — MA4.4: Test effectiveness audit

Status: planned
Targets: All nop-ai `src/test/java/`

- Item Types: `Proof`

- [ ] Load `ai-dev/skills/deep-audit-prompts.md` Dimension 21 for audit methodology
- [ ] For each BizModel test suite, check existence of null-input tests (count test methods with null arguments)
- [ ] Check boundary coverage: test methods exercising edge values (empty strings, 0, MAX_VALUE, MIN_VALUE)
- [ ] Check exception path coverage: test methods asserting exceptions (look for `assertThrows` or expected exception usage)
- [ ] Audit test isolation: shared mutable static state, field pollution between tests
- [ ] Produce report `2026-07-31-XXXX-arm-MA4.4-nop-ai-test-effectiveness.md`

Exit Criteria:

- [ ] Report documents test quality gaps with severity — quantified by counts (how many classes lack null tests, how many lack exception path tests)
- [ ] Boundary/exception path coverage quantified as: BizModels with null-input tests / total BizModels
- [ ] Test isolation issues (shared state, order dependency) identified with file:line references
- [ ] No owner-doc update required (audit-only phase)
- [ ] `ai-dev/logs/` corresponding date entry updated
