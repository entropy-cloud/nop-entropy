## Purpose

为编辑器场景交付 **LSP 服务器 v1**：`NopLintLanguageServer`（传输无关的消息处理核心）+ stdio 入口（VS Code / Neovim 等 LSP 客户端开箱即用）。诊断经 **fast 档**（<50ms/文件预算）+ **增量解析**（didChange 的 full-document sync 经 EditCalculator → parseIncremental 复用未变叶子）。零平台修改。

## Current Baseline（live 核对 2026-09-24）

- `LintLanguage.parseIncremental(oldTree, newSource)` 与 `EditCalculator` 已落地（item 16，corpus gate 126 实例增量 ≡ 全量）；`LintEngine.lint(rules, languageId, path, source)` 单文件口径；`LintProfile.FAST` 存在（FAST_CAPABILITIES = {L1}，deep 规则 skipByProfile）。
- 语言发现 = `LanguageRegistry.discoverDefaults()`（ServiceLoader）；规则集 = `RuleSetLoader`（classpath VFS 前缀）。
- 仓库无 LSP 面；nop-java-parser 依赖树内无 lsp4j（**依赖形态 spike 在 Phase 1**：lsp4j 本地可得性 → 不可得则手写 Content-Length JSON-RPC 帧 + 最小 JSON 序列化——诊断结构简单，手写面可控；裁定随执行记录）。

## Goals

1. **`NopLintLanguageServer`（传输无关核心）**：处理 `initialize`（capabilities：full-document sync + 文本诊断）、`textDocument/didOpen`（解析 + lint + 诊断缓存）、`didChange`（full sync：新旧树 EditCalculator → parseIncremental → lint）、`didClose`（清缓存 + 清诊断）、`shutdown/exit`。诊断以 `textDocument/publishDiagnostics` 推送（LSP line/character 0-based 换算）。
2. **stdio 入口** `NopLintLspLauncher`（main）：Content-Length 帧循环读写 stdin/stdout，日志走 stderr。
3. **语言/规则装配**：与 item 38 同款懒单例——registry discoverDefaults + 规则集一次加载；fast 档钉死（编辑器预算面，design 11）。
4. **测试**：消息核心单测（initialize→didOpen→didChange→didClose 全生命周期 + 诊断推送断言 + 未注册语言 fail-closed）+ stdio 帧回环端到端（launcher 进程内起一条真实帧流）。

## Non-Goals

- incremental range sync（v1 全文档同步；range sync 归后续优化）
- codeAction/quickfix、formatting、definition 等编辑器扩展能力（v1 只做诊断推送）
- VS Code 插件打包 / Neovim 配置分发（客户端对接文档一节说明通用 LSP 配置即可）
- watch 模式与 CI 缓存（item 43）
