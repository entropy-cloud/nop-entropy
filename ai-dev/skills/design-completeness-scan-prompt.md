# 设计完整性扫描提示

使用此提示主动扫描 `ai-dev/design/`，查找目标产品范围内缺失的域、文档和功能点，并生成优先级差距列表，驱动增量设计文档添加。

在产品增长时定期使用，在里程碑范围锁定前使用，或在考虑新业务域时使用。不要将其用作需求综合、设计文档审计（验证现有文档）、状态机审查或计划审计的替代品。它是 `design-doc-audit-prompt.md` 的前瞻性对应：该提示审计存在的内容；此提示查找缺失的内容。

```text
您是高级产品架构师。以下是当前的 `ai-dev/design/` 树和目标产品范围。扫描缺失的域、现有域内缺失的文档以及现有文档内缺失的功能点。生成优先级差距列表，驱动下一轮设计文档添加。

首先阅读这些文件：
- `AGENTS.md`
- `docs-for-ai/INDEX.md`
- `docs-for-ai/00-start-here/project-context.md`
- `ai-dev/design/README.md`（如果存在）
- `ai-dev/design/` 下的所有现有文件（包括子目录）
- 产品路线图或待办文件（如果存在）

扫描维度：

0. **开源功能对标（新增维度—此前多轮审计遗漏的根本原因）**
   > 此前多轮审计聚焦于已有文档间的内部一致性，未系统性地对照开源产品功能清单做缺失检测。本维度强制补上这一环。
   - 基于审计者的领域知识，提取同类开源/商业产品的**关键差异化功能**。
   - 对于提取出的每个功能，检查 `ai-dev/design/` 下是否有对应的 owner doc。
   - **特别注意**：不要只查"域存在与否"，要查**功能深度**。

1. 域覆盖
   - 列出目标产品范围隐含的每个业务域。
   - 对于每个域，标记是否存在 `ai-dev/design/<domain>/` 目录。
   - 标记范围要求但没有设计所有者的缺失域。
   - 标记作为代码或待办存在但没有设计文档的域。

2. 每个域内的文档覆盖
   - 对于每个现有域目录，检查是否至少有一个 `README.md`。
   - 对于工作流密集的域，检查是否存在 `state-machine.md` 以及是否遵循 `state-machine-business-review-prompt.md` 的审查维度。
   - 对于跨域耦合密集的域，检查是否存在 `cross-domain.md` 或等效文件。
   - 标记 README 是唯一文档但业务复杂性显然需要更多文档的域。

3. 每个文档内的功能点覆盖
   - 对于每个域 README，检查核心业务对象是否列出了业务含义。
   - 检查状态机（如果有）是否涵盖：状态定义、转换完整性、终端/恢复、异常路径、可达性、角色/权限、TODO/任务策略、设计文档一致性。
   - 检查触及此域的跨域流程是否描述或路由到其所有者。
   - 检查保护区域行为是否明确定义或路由。

4. 跨域流程覆盖
   - 检查宏观流程是否涵盖范围要求的端到端业务路径。
   - 检查跨域规则是否涵盖需要它们的每个域对的过账触发器、对账等。

5. 术语表和角色覆盖
   - 检查术语表是否涵盖任何新域文档引入的术语。
   - 检查角色/权限文档是否涵盖每个域中状态机转换隐含的角色。

6. 与范围的一致性
   - 将设计的域和功能集与产品范围定义进行比较。
   - 标记没有设计所有者且没有显式推迟的范围隐含功能。
   - 标记描述当前范围之外行为的设计文档（设计蔓延）。

要检查的已知反模式：

| 反模式 | 症状 | 正确做法 |
| --- | --- | --- |
| 统一文档结构 | 每个域都强制有 state-machine.md，即使只有 active/inactive | 结构因域复杂性而异 |
| 缺少设计所有者 | 域有代码或待办，但没有 `ai-dev/design/<domain>/` | 在实现之前或同时创建设计所有者文档 |
| 状态机没有审查维度 | state-machine.md 列出状态/转换但省略异常路径、角色 | 遵循 `state-machine-business-review-prompt.md` 的维度 |
| 孤立功能 | 流程文档中提到功能点但没有域所有者文档 | 创建所有者文档或路由到现有文档 |
| 范围-设计不匹配 | 设计描述范围推迟的域，或范围要求设计省略的域 | 对齐：添加设计、更新范围或标记显式推迟 |
| 术语表漂移 | 新域引入不在术语表中的术语 | 添加域时将术语添加到术语表 |
| 角色差距 | 状态机转换在角色文档中没有定义角色 | 将每个转换绑定到角色 |

严重性指南：
- `blocker`：范围要求的域没有设计所有者，或工作流密集的域缺少状态机，或保护区域行为未定义。
- `major`：域缺少其复杂性所需的文档，或跨域流程不完整，或术语表/角色覆盖滞后于新域。
- `minor`：文档可以更清晰或更完整，但路径仍然有效。
- `note`：未来观察项或优化建议。

按严重性排序，首先返回发现。对于每个发现，包括：严重性、维度、受影响区域、差距描述、重要性原因、建议操作，以及如果建议新文档则建议的文档路径。

然后返回：
- 裁决：完整/有差距/有阻塞
- 审查范围
- 域覆盖摘要
- 每个域的文档覆盖摘要
- 状态机覆盖摘要
- 跨域流程覆盖摘要
- 术语表和角色覆盖摘要
- 建议的下一轮文档添加（带建议路径的优先级列表）
- 剩余风险或跳过的区域

如果没有 blocker 或 major 发现，说 `Verdict: complete` 并仍然列出剩余风险和建议的下一轮添加。
```
