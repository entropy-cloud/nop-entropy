### Consequences of `MAX_RESERVED_WORD_SET_SIZE == 0`

The plan's Phase 2 speculated that bash "has reserved words such as
`if`/`then`/`esac` together with external tokens" and therefore sits in the
high-risk shape for `Language.decode`'s reserved-word validation (the shape that
misjudged the Go grammar en route). **That speculation is wrong.** `grammar.json`
has `"reserved": {}` and the C macro is `0`, so bash allocates zero reserved-word
sets. The `reserved_word_set_id` / `reservedWords` decode path in
`Language.decode` is exercised with `reservedWordSetCount == 0` and takes its
empty branch. No fix is needed on this path for bash.

## 3. External token enumeration

Ordinals are `enum ts_external_scanner_symbol_identifiers`
(`src/parser.c`, immediately after `ts_external_token_map[]`). `scanner.c`'s
`enum TokenType` uses **different names for the same ordinals** in three places
(`NEWLINE` vs `heredoc_redirect_token1`, `CLOSING_BRACE` vs `RBRACE`,
`CLOSING_BRACKET` vs `RBRACK`, `OPENING_PAREN` vs `LPAREN`, `ERROR_RECOVERY` vs
`__error_recovery`); the Java translation uses the `scanner.c` names, which is
what the hand translation is written against.

| # | `parser.c` name | `scanner.c` name | Trigger |
|---|---|---|---|
| 0 | `heredoc_start` | `HEREDOC_START` | word after `<<` / `<<-`; records whether the delimiter is quoted |
| 1 | `simple_heredoc_body` | `SIMPLE_HEREDOC_BODY` | heredoc body of a delimiter with no expansions |
| 2 | `_heredoc_body_beginning` | `HEREDOC_BODY_BEGINNING` | first slice of a heredoc body |
| 3 | `heredoc_content` | `HEREDOC_CONTENT` | literal slice between expansions |
| 4 | `heredoc_end` | `HEREDOC_END` | the delimiter line |
| 5 | `file_descriptor` | `FILE_DESCRIPTOR` | a bare number immediately before `>` / `<` |
| 6 | `_empty_value` | `EMPTY_VALUE` | zero-width; whitespace, EOF, `;` or `&` |
| 7 | `_concat` | `CONCAT` | a non-delimiter character gluing two words together |
| 8 | `variable_name` | `VARIABLE_NAME` | the name inside `${...}` |
| 9 | `test_operator` | `TEST_OPERATOR` | a `-x` style `[[ ]]` operator |
| 10 | `regex` | `REGEX` | right side of `=~` |
| 11 | `_regex_no_slash` | `REGEX_NO_SLASH` | `${x/pat/rep}` body, ends at `/` |
| 12 | `_regex_no_space` | `REGEX_NO_SPACE` | regex flavor that must find a terminating space |
| 13 | `_expansion_word` | `EXPANSION_WORD` | a literal glued to an expansion |
| 14 | `extglob_pattern` | `EXTGLOB_PATTERN` | extended-glob / case-arm pattern |
| 15 | `_bare_dollar` | `BARE_DOLLAR` | a lone `$` |
| 16 | `_brace_start` | `BRACE_START` | the `{` of a `{1..10}` brace expansion |
| 17 | `_immediate_double_hash` | `IMMEDIATE_DOUBLE_HASH` | `##` in `${x##...}` |
| 18 | `_external_expansion_sym_hash` | `EXTERNAL_EXPANSION_SYM_HASH` | `#` operator symbol inside `${...}` |
| 19 | `_external_expansion_sym_bang` | `EXTERNAL_EXPANSION_SYM_BANG` | `!` operator symbol inside `${...}` |
| 20 | `_external_expansion_sym_equal` | `EXTERNAL_EXPANSION_SYM_EQUAL` | `=` operator symbol inside `${...}` |
| 21 | `RBRACE` | `CLOSING_BRACE` | the `}` that closes an expansion |
| 22 | `RBRACK` | `CLOSING_BRACKET` | the `]` that closes a subscript |
| 23 | `LT_LT` | `HEREDOC_ARROW` | `<<` |
| 24 | `LT_LT_DASH` | `HEREDOC_ARROW_DASH` | `<<-` |
| 25 | `heredoc_redirect_token1` | `NEWLINE` | the newline token inside a heredoc redirect |
| 26 | `LPAREN` | `OPENING_PAREN` | `(` opening a command group |
| 27 | `esac` | `ESAC` | the `esac` keyword |
| 28 | `__error_recovery` | `ERROR_RECOVERY` | error-recovery sentinel |

**Ordinal 25 is the trap.** `scanner.c` calls it `NEWLINE`; reading the
`parser.c` name (`heredoc_redirect_token1`) and assuming it is not the newline
token produces an `ArrayIndexOutOfBoundsException` against the 29-long valid
array. It was hit during implementation and is called out here so the next
reader does not repeat it.

Note that the plan's Baseline claimed the enum ran "`HEREDOC_START` …
`ERROR_RECOVERY`" — correct in count and endpoints, but the 29 tokens are **not**
grouped by subsystem: the heredoc family is 0-4 *plus* 23-25, the `${...}`
operator family is 17-22. Any implementation that assumes contiguity will be
wrong.

(`heredoc_redirect` vs `herestring_redirect`), and the external-token layer never
sees a herestring.

One correction to the plan's Phase 0 checklist: it listed
"`heredoc_redirect` 的 `redirect:`". `redirect:` is declared on **six** nodes, and
on `heredoc_redirect` it holds the `*_redirect` children *inside* the heredoc
redirect (`heredoc_redirect` can nest redirects before the body), not the
heredoc itself. The semantic layer must take the heredoc from
`redirected_statement`'s `redirect:` field, then read `heredoc_redirect`'s
**named children in order** — not from `heredoc_redirect`'s `redirect:` field.

anything. The official CLI was still used as the oracle for the

## 9. Provenance backfill adjudication

The plan asked whether the other seven vendored grammar directories should get
per-directory `PROVENANCE.md` files with tag + SHA. **Not backfilled**, and the
reason is a measurement, not a preference:

- `tree-sitter-python` and `tree-sitter-rust` vendor **only** `parser.c`. Their
  hand-translated scanners (`PythonScanner`, `RustScanner`) were written against
  a `scanner.c` that is not in the repository, so no SHA can be attached to the
  scanner source that produced them.
- The local reference copies are not pinned and have moved past the vendored
  bytes, so their current `HEAD` describes the reference copy, not the fixture.

Writing an unverified SHA would create exactly the owner-doc drift this exercise
is meant to eliminate. Instead, a **module-level** policy file
`nop-treesitter/src/test/resources/upstream/grammars/PROVENANCE.md` records the
rules, the measured per-directory state, and the two blockers; and
`tree-sitter-bash/PROVENANCE.md` establishes the normalized format (tag + SHA +
license + generator version + "never modified" + SHA-256 of each vendored file)
for all future vendoring.

**Successor Required: yes** — vendoring the missing `scanner.c` for python and
rust, and pinning the reference copies, is real work that is out of this plan's
scope. Tracked in `ai-dev/plans/nop-treesitter/2026-10-04-1830-1-vendored-grammar-provenance-backfill.md`.

## 10. Known divergence found while building the scanner idioms test

`echo ${x!y}` — malformed bash, the official CLI recovers to
`(program (command name: (command_name (word))) (ERROR (variable_name) (word)))`
while this runtime throws `TreeSitterException: error recovery made no progress
at byte offset 8`.

Localized with a controlled experiment: the same input parses fine with **no**
scanner attached and with an always-`false` stub scanner; only with a faithful
`BashScanner` does it trip `GLRParser`'s 100-round no-progress guard. The
`expansion_word:` region is the trigger, and upstream `scanner.c` produces the
same token in the same state — the region deliberately has **no**
`in_error_recovery` guard. So the scanner is faithful and the gap is in
`GLRParser`'s recovery, i.e. shared runtime code that bash merely exposes.

This is a **confirmed live defect**, not an optimization candidate, and it is not
this plan's to fix (its Non-Goals exclude runtime changes beyond the primary-API
addition). It is therefore owned by a successor plan rather than left implicit:
`ai-dev/plans/nop-treesitter/2026-10-04-1900-1-glr-recovery-livelock-guard.md`,
and disclosed in `docs-for-ai/03-modules/nop-treesitter.md`. No test pins the
current throw, so the successor can change it without fighting a test.

The behavior is at least **loud, not silent**: it throws rather than returning a
wrong tree. Every other malformed-bash input probed (`if then ...`, `echo ${x`,
`echo \`x`, `${x!}`, `${!x}`) matches the CLI, and the upstream corpus is 100/100.
