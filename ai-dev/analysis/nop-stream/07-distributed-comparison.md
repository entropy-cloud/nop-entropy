## 1. Execution Graph Layers

### Flink Architecture

Flink uses a **three-layer graph model** (StreamGraph → JobGraph → ExecutionGraph). JobGraph is a serializable intermediate plan; ExecutionGraph is the runtime scheduling DAG. This analysis uses **graph-model layer count** as the comparison caliber (consistent with `graph-model-design.md` §1.1 and `01-architecture-baseline.md` §四 / §8.1):

1. **`StreamGraph`** (logical DAG) — `StreamNode` + `StreamEdge`, built by `StreamGraphGenerator` from `Transformation` DAG. Integer vertex IDs, operator factories, parallelism, chaining strategy.

2. **`JobGraph`** (serializable execution plan) — `JobVertex` + `JobEdge` + `IntermediateDataSet`. Built by `StreamingJobGraphGenerator` from `StreamGraph`; performs operator chaining and serializes to the `JobGraph` submitted to the JobManager.

3. **`ExecutionGraph`** (runtime DAG) — built by `DefaultExecutionGraphFactory` / `SchedulerBase` from `JobGraph`:
   - **`ExecutionJobVertex`** — one per `JobVertex` (one chained operator group). Holds `ExecutionVertex[] taskVertices` (one per parallel subtask), `IntermediateResult[] producedDataSets` (outputs), `SlotSharingGroup`, `CoLocationGroup`, `OperatorCoordinatorHolder[]`.
   - **`ExecutionVertex`** — single parallel subtask. Holds `Execution currentExecution` (current attempt), `ExecutionHistory` (past attempts), `Map<IntermediateResultPartitionID, IntermediateResultPartition> resultPartitions`, `int subTaskIndex`.
   - **`Execution`** — single attempt to run an ExecutionVertex. State machine: `CREATED -> SCHEDULED -> DEPLOYING -> INITIALIZING -> RUNNING -> FINISHED/FAILED/CANCELED`. Holds `ExecutionAttemptID attemptId`, `LogicalSlot assignedResource`, `JobManagerTaskRestore taskRestore` (checkpoint restore).
   - **`IntermediateResult`** — logical data set produced by one `ExecutionJobVertex`. Holds `IntermediateResultPartition[] partitions` (one per parallel producer).
   - **`IntermediateResultPartition`** — one partition of an `IntermediateResult`, produced by one `ExecutionVertex`. Holds `EdgeManager edgeManager` (manages consumer vertex groups).

   Source: `org.apache.flink.runtime.executiongraph.DefaultExecutionGraph`, `ExecutionJobVertex`, `ExecutionVertex`, `Execution`

3. **Flink states** (at `ExecutionGraph` level): `CREATED`, `RUNNING`, `FINISHED`, `CANCELING`, `CANCELED`, `FAILING`, `FAILED`, `SUSPENDED`, `RECONCILING` — mapped to `JobStatus` enum.

   At `Execution` level: `CREATED`, `SCHEDULED`, `DEPLOYING`, `INITIALIZING`, `RUNNING`, `FINISHED`, `FAILED`, `CANCELED`.

### nop-stream Architecture

nop-stream uses a **two-layer graph model** (StreamGraph → JobGraph). `PartitionedPlan` and `DeploymentPlan` are an **independent deployment-abstraction dimension** and are **not counted as graph-model layers** (see `graph-model-design.md` §1.1 "为什么不是三层" and `01-architecture-baseline.md` §四 for the intentional-design rationale — nop-stream rejects Flink's ExecutionGraph third layer via `IStreamExecutionDispatcher` SPI).

1. **`StreamGraph`** (logical DAG) — `StreamNode` (Integer ID, operatorFactory, parallelism, KeySelector, WindowAssigner, ChainingStrategy) + `StreamEdge`. Built by `StreamGraphGenerator` from `Transformation` DAG.

2. **`JobGraph`** (optimized DAG) — `JobVertex` (String ID, operatorChains, invokable, parallelism) + `JobEdge` (sourceVertex, targetVertex, ResultPartitionType, IPartitioner, EdgeConfig). Built by `JobGraphGenerator`: identifies chains via DFS, creates fused OperatorChain per vertex.

   Source: `nop-stream-core/.../jobgraph/JobGraph`, `JobVertex`, `JobEdge`

3. **`PartitionedPlan`** (deployment-agnostic plan) — `Map<String, VertexPlan>` (vertexId, parallelism, operatorId) + `List<EdgePlan>` (sourceVertexId, targetVertexId, PartitionPolicy) + `checkpointAckSet` + `StreamModelFingerprint`. Generated by `PartitionedPlanGenerator` from `JobGraph` + `StreamModelFingerprint`.

   Source: `nop-stream-core/.../execution/plan/PartitionedPlan`

4. **`DeploymentPlan`** (deployment-specific plan) — references `PartitionedPlan`, adds `transportBackend` (local/remote), `stateBackendBinding`, `checkpointStorage`, `Map<String, EdgeConfig>` (flow control per edge), `MemoryBudget`. Generated by `DeploymentPlanGenerator`.

   Source: `nop-stream-core/.../execution/plan/DeploymentPlan`

The actual runtime DAG is **`GraphExecutionPlan`** (built from `JobGraph` + `DeploymentPlan`) — allocates `ResultPartition[][]` matrices per edge, creates per-subtask `StreamTaskInvokable` with wired `RecordWriter` + `InputGate` + `InputChannel[]`. Plan structure maintained as adjacency maps + sorted vertex lists (topological).

Source: `nop-stream-core/.../execution/GraphExecutionPlan`

### Comparison

| Aspect | Flink | nop-stream | Gap |
|--------|-------|-----------|-----|
| Graph layers (graph-model caliber) | **3 layers**: StreamGraph → JobGraph → ExecutionGraph | **2 layers**: StreamGraph → JobGraph (PartitionedPlan/DeploymentPlan are a separate deployment-abstraction dimension, not graph-model layers — see `01-architecture-baseline.md` §四) | **Doc**: graph coverage equivalent at the 2-layer logical/optimized level; nop-stream rejects ExecutionGraph via `IStreamExecutionDispatcher` SPI; deployment concerns are split into explicit plan objects |
| Runtime DAG | `ExecutionJobVertex` + `ExecutionVertex` + `IntermediateResult` with state machine | `GraphExecutionPlan` + adjacency maps + per-subtask `Subtask`/`StreamTaskInvokable` | **Improvement**: nop-stream's plan is simpler but lacks state machine tracking |
| Vertex ID system | `JobVertexID` (UUID) for logical; `ExecutionVertexID` (JobVertexID + subtaskIndex) for physical | `String` IDs for JobVertex; integer indices for subtasks | No gap — functionally equivalent |
| Intermediate data | `IntermediateResult` + `IntermediateResultPartition` with `ResultPartitionType` (PIPELINED/BLOCKING/HYBRID) | `ResultPartition[][]` matrix (pre-allocated per source × target parallelism) | **Improvement**: nop-stream's matrix approach is simpler but lacks `IntermediateResult` abstraction |
| State machine | `Execution` state machine (8 states) with CAS transitions + `ExecutionHistory` for retries | `Task` states: `CREATED/RUNNING/COMPLETED/FAILED/CANCELED` via `AtomicReference<State>` | **Gap**: nop-stream lacks intermediate FAILING/CANCELING/SCHEDULED/DEPLOYING states |
| Execution retry | `ExecutionHistory` with `nextAttemptNumber`; reset `currentExecution` via `resetForNewExecution()` | No retry mechanism — single attempt per Task | **Gap**: no retry/attempt tracking |
| Operator coordinators | `OperatorCoordinatorHolder[]` attached to `ExecutionJobVertex` | No operator coordinator concept | **Gap**: no operator-level coordination |
| Slot/co-location groups | `SlotSharingGroup` + `CoLocationGroup` attached to `ExecutionJobVertex` | Not applicable (single-JVM scheduling) | **Hollow**: scheduling groups not designed yet |
| Deployment concept | No separate "deployment plan" — all in `ExecutionGraph` | `DeploymentPlan` as explicit deployment configuration | **Doc**: nop-stream makes deployment a first-class concern |

### Classification

| Finding | Classification | Severity | Evidence |
|---------|---------------|----------|----------|
| Missing intermediate execution states (FAILING, SCHEDULED, DEPLOYING, INITIALIZING) | **Gap** | **P1** | nop-stream: `Task.java` enum has 5 states; Flink: `Execution` has 8 states with CAS transitions |
| No execution retry / attempt tracking | **Gap** | **P2** | nop-stream: single attempt per Task; Flink: `ExecutionHistory` with `nextAttemptNumber` |
| No operator coordinator concept | **Gap** | **P2** | Flink: `OperatorCoordinatorHolder[]` per ExecutionJobVertex; nop-stream: none |
| Two-layer graph model + explicit deployment plans (D71) | **Doc** | — | nop-stream: 2 graph-model layers (StreamGraph→JobGraph) + PartitionedPlan/DeploymentPlan as separate deployment dimension; Flink: 3 graph-model layers (StreamGraph→JobGraph→ExecutionGraph). See `graph-model-design.md` §1.1/§8 and `01-architecture-baseline.md` §四 for the intentional-design rationale |

## 2. Task Lifecycle

### Flink Architecture

**`StreamTask`** (abstract base):
```
invoke()
  -> restoreInternal()           // restore checkpoint state
  -> mailboxProcessor.runMailboxLoop()
       while (isNextLoopPossible):
         1. processMail()        // drain mailbox (timers, checkpoints, control)
         2. processInput()       // default action: inputProcessor.processInput()
  -> afterInvoke()               // finish operators, close
  -> cleanUp()                   // on failure
```

Key classes:
- **`MailboxProcessor`** — `runMailboxLoop()` is the core execution engine. Interleaves mail processing (checkpoint barriers, timer events) with the default action (record processing).
- **`MailboxExecutorImpl`** — facade for submitting actions to the mailbox from external threads (e.g., checkpoint RPC callbacks).
- **`TaskMailboxImpl`** — priority-based blocking queue, uses `PriorityQueue<Mail>` internally, supports `processAll()` and `tryProcessAll()`.
- **Subclasses**: `SourceStreamTask`, `OneInputStreamTask`, `TwoInputStreamTask`, `MultipleInputStreamTask` — override `init()` to set up specific input processors.

The **mailbox model** is the key differentiator: it ensures checkpoint barriers and timer events are interleaved with normal record processing within the same single-threaded event loop, preventing concurrent modification of operator state.

Source: `org.apache.flink.streaming.runtime.tasks.StreamTask` (2161 lines), `MailboxProcessor` (536 lines)

### nop-stream Architecture

nop-stream has **two parallel execution paths**:

#### Path A: `Task` + `Invokable` (primary, for `GraphExecutionPlan`)

```
Task.run()
  1. CAS state: CREATED → RUNNING
  2. openOperatorChains()     // iterate vertex operatorChains, call .open() on each
  3. invokable.invoke()       // actual StreamTaskInvokable
     -> dispatch to invokeSource/invokeMiddle/invokeSink/invokeSelfContained
     -> for MIDDLE/SINK: loop processInputGate():
        inputGate.read() -> headInput.processElement()/processWatermark()/processBarrier()
     -> for SOURCE: run StreamSourceOperator.run(), emit MAX_WATERMARK
     -> uses ChainingOutput/RecordWriterOutput to emit downstream
  4. closeOperatorChains()    // iterate reverse, call .close() on each
  5. CAS state: RUNNING → COMPLETED
```

Source: `nop-stream-core/.../execution/Task.java` (329 lines), `StreamTaskInvokable.java` (480 lines)

#### Path B: `SubtaskTask` + `Subtask` (for `GraphModelCheckpointExecutor`)

```
SubtaskTask.run()
  1. CAS state: CREATED → RUNNING
  2. open chains
  3. subtask.getInvokable().invoke()  // in a loop (breaks after one iteration)
  4. handle CANCELING → CANCELED transition
  5. close chains
```

Source: `nop-stream-core/.../execution/SubtaskTask.java` (179 lines), `Subtask.java` (61 lines)

#### OperatorChain Lifecycle Issue (Bug/P1)

Both `Task.openOperatorChains()` and `StreamTaskInvokable.invoke()` → internal chain setup call `.open()` on the same `OperatorChain` objects. Specifically:
1. `Task.run()` calls `openOperatorChains()` — iterates `JobVertex.getOperatorChains()`, calls `chain.open()` on each.
2. Then `Task.run()` calls `StreamTaskInvokable.invoke()` — the `wireOperators()` method inside `invoke()` creates `ChainingOutput`/`RecordWriterOutput` and calls `operatorChain.open()` again.

This creates a **double-open condition**: the same `OperatorChain.open()` method is invoked twice on the same chain objects, once at Task-level lifecycle and once at Invokable-level lifecycle. The same issue exists for `closeOperatorChains()`.

Source: `Task.java:61-68` (openOperatorChains), `StreamTaskInvokable.java:170-185` (wireOperators opens chain again), `OperatorChain.java:85-92` (open javadoc claims "forward order" but code iterates reverse — **additional doc bug AR-6**)

### Comparison

| Aspect | Flink | nop-stream | Gap |
|--------|-------|-----------|-----|
| Execution model | Mailbox loop: interleave mail + data processing | Synchronous processing loop: `inputGate.read()` blocks | **Gap**: no mailbox/interleaving model |
| State machine | `CREATED→SCHEDULED→DEPLOYING→INITIALIZING→RUNNING→FINISHED/FAILED/CANCELED` (8 states) | `CREATED→RUNNING→COMPLETED/FAILED/CANCELED` (5 states) | **Gap**: missing SCHEDULED, DEPLOYING, INITIALIZING states |
| Cancellation | `cancel()` → `mailboxProcessor.quiesce()` + poison mail | `cancel()` → `CAS(RUNNING→CANCELING)` + `Thread.interrupt()` (SubtaskTask) or `CAS(CREATED→CANCELED)` (Task) | **Improvement**: SubtaskTask has CANCELING state, Task does not |
| Checkpoint handling | Mailbox-based: barrier arrives as mail, interleaved with processing | `CheckpointBarrierTracker` on `StreamTaskInvokable`, barrier processed inline via `processBarrier()` path | **Improvement**: simpler but no interleaving guarantees |
| Input gate loop | `CheckpointedInputGate.pollNext()` → `BufferOrEvent` | `InputGate.read()` → `StreamElement` (blocks with 50ms poll) | No gap |
| Multi-input handling | Subclass-specific `StreamTaskInputProcessor` (OneInputStreamTask, TwoInputStreamTask, etc.) | Generic `processInputGate()` round-robin across `InputChannel[]` | **Improvement**: simpler but lacks input-type-specific optimization |
| OperatorChain lifecycle | Single lifecycle: `openOperatorChain()` once in `invoke()` | **Two overlapping lifecycles:** (a) `Task.openOperatorChains()` + (b) `StreamTaskInvokable.invoke()` → internal `.open()` | **Bug/P1**: double-open condition |
| Thread model | Single thread per Task (main mailbox loop) | Single thread per Task (Runnable submitted to ExecutorService) | No gap |

### Classification

| Finding | Classification | Severity | Evidence |
|---------|---------------|----------|----------|
| OperatorChain double-open (Task-level + Invokable-level) | **Bug** | **P1** | `Task.java:61-68` calls `openOperatorChains()`, then `StreamTaskInvokable.invoke()` calls `wireOperators()` which calls `chain.open()` again |
| No mailbox/interleaving model | **Gap** | **P1** | nop-stream: synchronous blocking loop; Flink: mailbox with priority interleaving of mail and data |
| Missing SCHEDULED/DEPLOYING/INITIALIZING states | **Gap** | **P2** | nop-stream: `Task.java` enum has 5 states |
| CANCELING state only in SubtaskTask, not Task | **Improvement** | **P2** | `Task.java` and `SubtaskTask.java` have inconsistent state machines |
| OperatorChain javadoc says forward order, code does reverse | **Doc** | **P2** | `OperatorChain.java:92-93` vs `:98-110` (from prior audit AR-6) |

## 3. Scheduling Model

### Flink Architecture

**`SchedulerNG`** (interface) → **`SchedulerBase`** (abstract) → **`DefaultScheduler`** / **`AdaptiveScheduler`**.

```
SchedulerBase.startScheduling()
  -> executionGraphFactory.createAndRestoreExecutionGraph(JobGraph)
  -> DefaultExecutionGraph.attachJobGraph() -- builds ExecutionJobVertex + ExecutionVertex + IntermediateResult
  -> schedulingStrategy.startScheduling()

DefaultScheduler:
  -> PipelinedRegionSchedulingStrategy: groups vertices into pipelined regions
  -> for each ready region: allocateSlotsAndDeploy()
     -> ExecutionSlotAllocator.allocateSlotsFor(List<ExecutionAttemptID>)
        -> SlotSharingExecutionSlotAllocator groups by SlotSharingGroup
        -> requests slots from ResourceManager via SlotPool
     -> ExecutionVertex.deploy() -> Execution.deploy()
        -> TDD serialization -> submitTask via TaskManagerGateway

Slot allocation chain:
  ResourceManager.requestSlot(SlotRequest)
    -> TaskManager offers slot -> SlotPool assigns to Execution
    -> LogicalSlot with TaskManagerLocation + slot index
```

Key concepts:
- **SlotSharingGroup** — vertices can share slots (same JVM)
- **CoLocationGroup** — vertices must share slots (iteration head/tail)
- **PipelinedRegionSchedulingStrategy** — deploy entire pipelined region atomically
- **AdaptiveScheduler** (state-machine based): `Creating→WaitingForResources→Executing→Restarting→Failing`
- **SchedulingStrategy** (interface): `startScheduling()`, `restartTasks()`, `onExecutionStateChange()`, `onPartitionConsumable()`

Source: `org.apache.flink.runtime.scheduler.SchedulerNG`, `SchedulerBase` (1208 lines), `DefaultScheduler` (588 lines), `AdaptiveScheduler` (1858 lines), `strategy/PipelinedRegionSchedulingStrategy`

### nop-stream Architecture

**`IStreamExecutionDispatcher`** (interface):
- `boolean supportsDeploymentMode(DeploymentMode mode)`
- `StreamExecutionResult execute(JobGraph, PartitionedPlan, DeploymentPlan)`

**`EmbeddedDistributedExecutor`** (single implementation):
```
execute()
  1. Create InMemoryClusterRegistry
  2. Create N TaskManager instances (default 2)
  3. Create CheckpointCoordinator with LocalFileCheckpointStorage
  4. Create JobCoordinator, set up bidirectional RPC references
  5. Use RemoteGraphExecutionPlanBuilder.buildRemoteOnly() -> GraphExecutionPlan
  6. Assign subtasks to TaskManagers via round-robin (subtaskIndex % nodeCount)
  7. Call receiveAssignment() + installInvokable() on each TaskManager
  8. Wait for completion with timeout
  9. Check task results for failures
```

**`GraphModelCheckpointExecutor`** (second path, for checkpoint-enabled execution):
```
executeWithCheckpoint()
  1. Build JobGraph -> GraphExecutionPlan (GraphExecutionPlan.build())
  2. Create CheckpointCoordinator, CheckpointPlan
  3. Create CheckpointBarrierTracker per subtask
  4. Wire operator snapshot callbacks
  5. Start periodic barrier scheduler
  6. Restore from latest checkpoint if available
  7. Create SubtaskTask instances, submit via TaskExecutor
  8. Handle job termination (CANCEL/DRAIN/SUSPEND/EXPORT_SAVEPOINT)
  9. Check failures, log metrics, shutdown
```

Local scheduling: `TaskExecutor.submitJobVertex(JobVertex)` — creates N `Task` instances per parallel subtask, submits to fixed thread pool.

Source: `nop-stream-runtime/.../execution/EmbeddedDistributedExecutor.java` (225 lines), `nop-stream-core/.../execution/IStreamExecutionDispatcher.java` (21 lines), `nop-stream-core/.../execution/TaskExecutor.java` (452 lines)

### Comparison

| Aspect | Flink | nop-stream | Gap |
|--------|-------|-----------|-----|
| Scheduler interface | `SchedulerNG` (241 lines) with 15+ methods | `IStreamExecutionDispatcher` (21 lines) with 2 methods | **Gap**: nop-stream dispatcher interface is minimal; no scheduling lifecycle methods |
| Scheduling strategy | `PipelinedRegionSchedulingStrategy` or `VertexwiseSchedulingStrategy` | Round-robin fixed assignment in `EmbeddedDistributedExecutor` | **Gap**: no region-aware or topology-aware scheduling |
| Slot management | `ExecutionSlotAllocator` → `SlotPool` → `ResourceManager` → TaskManager | Capacity semaphore per TaskManager (fixed capacity) | **Gap**: no slot abstraction or resource negotiation |
| Slot sharing | `SlotSharingGroup` + `CoLocationGroup` | Not implemented | **Gap**: no slot sharing concept |
| Resource manager | `ResourceManager` (1615 lines) — handles TM registration, slot allocation, heartbeats, leader election | `ClusterRegistry` (99 lines interface) — handles coordinator/node registration and lease renewal | **Gap**: no dedicated resource manager component |
| Pipelined region scheduling | Pipelined region = set of vertices connected by PIPELINED edges; fail/restart as unit | No pipelined region concept | **Gap**: no region-aware deployment |
| Adaptive scheduling | `AdaptiveScheduler` with dynamic scaling | Not implemented | **Gap**: no adaptive scheduling |
| Local executor | `LocalExecutor` (Flink test/local mode) | `GraphModelCheckpointExecutor` | No gap — both have local and distributed executors |
| Deployment descriptor | `TaskDeploymentDescriptor` (serialized, sent via Akka/gRPC) | `TaskAssignment` + invokable install via `IStreamTaskRpcService.receiveAssignment()` | **Improvement**: nop-stream separates assignment + invokable installation |

### Classification

| Finding | Classification | Severity | Evidence |
|---------|---------------|----------|----------|
| No region-aware or topology-aware scheduling | **Gap** | **P2** | nop-stream: round-robin assignment only; Flink: `PipelinedRegionSchedulingStrategy` |
| No slot sharing or co-location groups | **Gap** | **P2** | nop-stream: no `SlotSharingGroup`/`CoLocationGroup` equivalent |
| No resource manager component | **Gap** | **P2** | nop-stream: `EmbeddedDistributedExecutor` embeds all logic; Flink: dedicated `ResourceManager` RPC endpoint |
| IStreamExecutionDispatcher interface is a hollow shell | **Hollow** | **P1** | 2 methods, 21 lines; no scheduling lifecycle, no state tracking |
| ClusterRegistry handles some RM duty | **Improvement** | — | `ClusterRegistry` provides node registration, lease, task assignment — partially fills RM gap |
| No adaptive scheduling | **Gap** | **P3** | Flink: `AdaptiveScheduler` with dynamic scaling state machine |

## 4. RPC Abstraction

### Flink Architecture

**`RpcGateway`** (interface): `getAddress()`, `getHostname()`

**`RpcEndpoint`** (abstract):
- Lifecycle: created non-running → `start()` → `onStart()` scheduled → running → `closeAsync()` → `onStop()` → terminated
- `RpcService rpcService` — underlying implementation (Akka, Pekko)
- `ComponentMainThreadExecutor mainThreadExecutor` — single-threaded execution model
- `runAsync(Runnable)`, `callAsync(Callable, Duration)` — schedule on main thread

**`AkkaRpcService`** / **`PekkoRpcService`**:
- `startServer(RpcEndpoint)` — starts endpoint
- `connect(String address, Class<C> gatewayClass)` — creates remote proxy
- Uses Akka actor system under the hood; messages serialized via Akka serialization
- Timeout/retry: configurable via `RpcTimeout`, automatic retry on AskTimeout

**`FencedRpcEndpoint`** — adds fencing token validation (used by ResourceManager, JobMaster for HA).

Key RPC endpoints:
- `JobMaster` (RpcEndpoint) — coordinates job execution
- `TaskExecutor` (RpcEndpoint) — executes tasks
- `ResourceManager` (FencedRpcEndpoint) — manages resources
- `RpcGateway` subclasses for each: `JobMasterGateway`, `TaskExecutorGateway`, `ResourceManagerGateway`

Flink RPC supports: actor model messaging, message serialization, timeout/retry, leader election integration, fencing.

Source: `org.apache.flink.runtime.rpc.RpcGateway`, `RpcEndpoint` (601 lines), `flink-rpc-akka/AkkaRpcService`

### nop-stream Architecture

**`IStreamTaskRpcService`** (interface, 25 lines):
```java
void receiveAssignment(TaskAssignment assignment);
void triggerCheckpoint(CheckpointBarrier barrier, String fencingToken);
void cancelTask(String jobId, String vertexId, int subtaskIndex);
void updateFencingToken(String newToken);
```

**Implementation**: `TaskManager` (569 lines) implements `IStreamTaskRpcService` directly.

**`IStreamCoordinatorRpcService`** (interface, 18 lines):
```java
void receiveCheckpointAck(CheckpointAckMessage ack);
```

**Implementation**: `JobCoordinator` (643 lines) implements `IStreamCoordinatorRpcService`.

**Wiring in `EmbeddedDistributedExecutor`**:
```
TaskManager tm = new TaskManager(...);
JobCoordinator coordinator = new JobCoordinator(...);
tm.setCoordinatorRpcService(coordinator);  // direct Java reference
coordinator.setTaskRpcService(nodeId, tm); // direct Java reference
```

All RPC calls are **direct Java method calls** within the same JVM. There is:
- No message serialization
- No network transport layer
- No timeout/retry mechanism
- No actor model
- No service discovery

### Comparison

| Aspect | Flink | nop-stream | Gap |
|--------|-------|-----------|-----|
| RPC technology | Akka/Pekko actor system (or gRPC in newer versions) | Direct Java method calls (same JVM) | **Gap**: no cross-JVM RPC |
| Interface granularity | Rich per-component interfaces: `JobMasterGateway` (50+ methods), `TaskExecutorGateway`, `ResourceManagerGateway` | Minimal: `IStreamTaskRpcService` (4 methods), `IStreamCoordinatorRpcService` (1 method) | **Hollow**: interfaces exist but cover only assignment + checkpoint control |
| Message serialization | Akka serialization framework | N/A (local calls only) | **Gap**: no serialization for cross-JVM |
| Timeout / retry | Configurable `RpcTimeout`, automatic retry | N/A | **Gap**: no timeout model |
| Actor model | Yes — message-driven, async | No — synchronous calls | **Gap**: no async messaging |
| Fencing | `FencedRpcEndpoint` with leader session ID | `fencingToken` (UUID) in every RPC interface method | No gap — both have fencing |
| Service discovery / endpoint registry | Akka actor system address resolution | Direct Java references | **Gap**: no registry for remote endpoint discovery |
| RPC lifecycle | `RpcEndpoint.start()` → `onStart()` → running → `closeAsync()` → `onStop()` | No explicit RPC lifecycle | **Gap**: no `start()`/`stop()` on RPC services |

### Classification

| Finding | Classification | Severity | Evidence |
|---------|---------------|----------|----------|
| RPC interfaces have no remote implementation | **Hollow** | **P1** | `IStreamTaskRpcService` (4 methods) and `IStreamCoordinatorRpcService` (1 method) — both implemented locally only |
| No message serialization for cross-JVM | **Gap** | **P1** | No equivalent of Flink's Akka serialization framework in nop-stream RPC |
| No timeout/retry model | **Gap** | **P2** | No `RpcTimeout` equivalent in nop-stream RPC interfaces |
| No RPC lifecycle management | **Gap** | **P2** | nop-stream: no `start()`/`stop()` on RPC service interfaces |
| Fencing token is well-designed | — | — | `fencingToken` (UUID) correctly included in all RPC method signatures |
| Strongly-typed interfaces are intentional simplification | **Doc** | — | nop-stream design doc explicitly calls out planned cross-JVM wiring |

## 5. Data Exchange

### Flink Architecture

**`ResultPartition`** (abstract) — producer side. One per `ExecutionVertex`.
- **`PipelinedResultPartition`** — data immediately available to consumers.
- **`SortMergeResultPartition`** — blocking shuffle with sort-merge.
- **`TieredResultPartition`** — hybrid tiered storage (memory + disk + remote).
- Key methods: `emitRecord(ByteBuffer, targetChannel)`, `broadcastRecord(ByteBuffer)`, `finish()`, `close()`.
- Each contains `ResultSubpartition[]` (one per consumer task instance).

**`InputChannel`** (abstract) — consumer side.
- **`LocalInputChannel`** — same TM, direct memory access to `ResultSubpartitionView`.
- **`RemoteInputChannel`** — network, uses `PartitionRequestClient` for netty-based communication.
- Key methods: `requestSubpartitions()`, `getNextBuffer()`, `releaseAllResources()`.

**`NetworkBufferPool`** — fixed-size pool of `MemorySegment` instances for entire network stack on a TM.
- `totalNumberOfMemorySegments`, `memorySegmentSize` — configurable.
- `createBufferPool(numRequired, max)` → `LocalBufferPool`.
- `requestMemorySegment()`, `recycle(MemorySegment)` — segment lifecycle.
- Credit-based flow control: `RemoteInputChannel` sends credit announcements; sender only sends if receiver has credit.

**`PartitionRequestClient`** — netty-based client for remote partition requests. Handles `requestSubpartition()`, `notifyCreditAvailable()`, `resumeConsumption()`.

Source: `org.apache.flink.runtime.io.network.partition.ResultPartition`, `consumer.InputChannel`, `consumer.RemoteInputChannel`, `consumer.LocalInputChannel`, `buffer.NetworkBufferPool` (681 lines)

### nop-stream Architecture

**`ResultPartition`** (class) — producer side.
- `LinkedBlockingQueue<StreamElement> queue` (capacity 1024).
- `write(StreamElement)` — `queue.put(element)` (blocking on full queue).
- `read()` — `queue.take()` (blocking on empty queue).
- `IWriteStatus`: `isBackpressured()`, `getAvailableCapacity()`, `getTotalCapacity()`.

**`InputChannel`** (class) — consumer side.
- Holds a `ResultPartition` reference.
- `read()`, `read(timeout, unit)`, `isFinished()` — all delegate to partition.

**`InputGate`** (class) — multi-channel consumer.
- `List<InputChannel> channels`, `long[] currentWatermarks`.

**`RecordWriter`** (class) — operator output facade.

- `close()` — closes all partitions.

**`RemoteResultPartition`** (extends `ResultPartition`) — remote producer.
- Uses `IMessageService.send(topic, StreamMessageEnvelope)` per element.
- No internal queue — writes go directly to message service.
- Topics follow `nop-stream.{jobId}.{edgeId}.{sourceSubtask}.{targetSubtask}`.

**`RemoteInputChannel`** (extends `InputChannel`) — remote consumer.
- `LinkedBlockingQueue<StreamElement> queue` — local receive buffer.
- `EnvelopeConsumer` (inner class, `IMessageConsumer`) — subscribes to topic, decodes elements via `StreamElementCodec`, enqueues.

**Implementations:**

**`JobCoordinator`** (class, 643 lines):
- Coordinates task assignment, checkpoint triggering, failure detection.
- `start()` — registers with `ClusterRegistry`, generates `fencingToken`, starts failure detector (5s interval).
- `assignTasks()` — round-robin across active nodes, records assignments in `ClusterRegistry`.
- `detectFailures()` — checks node lease expiry, triggers `globalRecovery()`.
- `globalRecovery()` — new fencing token, clear assignments, optionally restore from checkpoint, reassign.
- Fencing: UUID token generated on start and every `globalRecovery()`.

**`TaskManager`** (class, implements `IStreamTaskRpcService`, 569 lines):

- No leader election — runs as subordinate to `JobCoordinator`.

- `SysDaoLeaderElector` — **not found** in nop-stream codebase (designed but not implemented).

## 8. Roadmap Gap Verification

### Gap: "Distributed RPC cross-JVM not wired"

**Status**: ✅ **Confirmed with source-level evidence**

**Evidence**:
- `IStreamTaskRpcService` (4 methods) and `IStreamCoordinatorRpcService` (1 method) are both implemented via direct Java references in `EmbeddedDistributedExecutor`
- `TaskManager` implements `IStreamTaskRpcService` directly; `JobCoordinator` implements `IStreamCoordinatorRpcService` directly
- The wiring in `EmbeddedDistributedExecutor`: `tm.setCoordinatorRpcService(coordinator)` and `coordinator.setTaskRpcService(nodeId, tm)` — all same-JVM
- No network transport, no serialization, no timeout/retry in the RPC layer
- `RemoteResultPartition` and `RemoteInputChannel` already use `IMessageService` for data plane — but control plane (RPC) remains local-only
- **Repair direction**: Implement remote RPC backend (gRPC or IMessageService-based) for the control plane, separate from the data plane IMessageService usage

### Gap: "Leader election planned (ILeaderElector)"

**Status**: ✅ **Confirmed — designed but has zero code**

**Evidence**:
- `ILeaderElector` — **not found** anywhere in nop-stream source code (`nop-stream/`, all subdirectories)
- `SysDaoLeaderElector` — **not found** anywhere in nop-stream source code
- Current `EmbeddedDistributedExecutor` creates a single `JobCoordinator` with no HA, no standby, no election
- `JobCoordinator.start()` registers with `ClusterRegistry` but there is no contention resolution
- **Repair direction**: Implement `ILeaderElector` with JDBC-based or ZooKeeper-based backend; wire into `JobCoordinator.start()` with leader contention

### Gap: "End-to-end parallelism > 1 not verified"

**Status**: ⚠️ **Partially addressed**

**Evidence**:
- `EmbeddedDistributedExecutor` creates N `TaskManager` instances (default 2) with round-robin assignment — distributed execution path exists
- `GraphExecutionPlan.build()` correctly creates per-subtask `RecordWriter` + `InputGate` + `InputChannel` with `ResultPartition[][]` matrices
- `JobGraphGenerator` creates `OperatorChain.deepCopy()` per subtask for parallelism > 1
- However, the code paths are tested only in unit tests (no end-to-end integration test with >1 parallelism)
- The `GraphModelCheckpointExecutor.executeWithCheckpoint()` path uses `SubtaskTask` + `TaskExecutor` with fixed thread pool, which supports parallelism via `submitJobVertex()`
- **Conclusion**: Implementation supports parallelism > 1 structurally, but no E2E test verifies correctness at scale
