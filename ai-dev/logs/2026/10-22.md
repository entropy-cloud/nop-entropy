### nop-lint LTYPE 能力：单文件局部类型推断 + 规则级 localTypeOf/anyOf/allOf 约束

- 需求承接（review 问答落定）：regex 规则的接收者判定从纯名字启发式升级为**类型感知**，且规则自己标记是否启用类型——`requires: [LTYPE]`。LTYPE 的类型面来自**单文件局部推断**（新 `JavaLocalTypeIndex`）：一次树遍历绑定 locals/fields/parameters/同文件方法返回类型，`var` 从初始化式推断（字符串字面量→String、构造→类名、`Pattern.compile(..)`→Pattern）；不需要 project resolver，production CLI 默认门禁即可执法（对照 L2 需外接 TypeResolver、当前全场景跳过）。文件级全局命名表（首声明优先）——facade 树的 parent() 指针不可靠，方法级作用域不在模型内，冲突即未知。
- 引擎面：`LintCapability.LTYPE`（三个 profile ceiling 均含，`isLocalAnalyzer` gate=语言绑定不支持则 DEGRADE 计数）；`LintLanguage.supportsLocalTypes()/localTypeIndex(tree)` 默认 false/null（XML 绑定天然不服务，fail-closed）；`ConstraintContext` 增加 `localTypes` 分量（每 lint 调用构建，同 TypeQuerySupport 的 per-file 语义）；`RuleSetRunner`/`LintEngine` 线程化传递。
- 约束 DSL：新增 `localTypeOf {capture, is}`（`is: unknown` 反相面=索引答不出；null 索引 fail-loud）与组合约束 `anyOf`/`allOf`（嵌套列表即值，深度上限 1 层嵌套 fail-closed；typeOf→L2 / localTypeOf→LTYPE 的 requires 门递归校验）。xdef 元模型同步：`LintConstraint` define（可递归）替换原扁平 constraint 枚举。
- 规则切型：`quality/no-string-regex-methods` requires [LTYPE]，约束 union = `anyOf[localTypeOf is String, allOf[localTypeOf unknown, regex 启发式]]`——可解析为 String 命中（含同文件方法返回）、解析为 Pattern/Matcher 永不命中、解析不出回退启发式。fixture 五形态命中 + 三惯用法豁免 + var-Pattern/同文件返回两个新面。
- 坑账（全部探针实锤）：①JDK glob `X/**/Y` 要求至少一层中间目录、前导 `**/` 不匹配零目录（规则 include 用双形态）；②facade `for (node)` 是子树深迭代非直接子节点，递归遍历必须用 `children()`（首版栈溢出）；③tree-sitter-java 的 `var` 是文本 "var" 的 `type_identifier` 而非 `implicit_type` 节点；④`type_identifier` 不以 `_type` 结尾——endsWith 判断漏掉所有常规类型；⑤RuleTestRunner 真实路径门按 `requires` 非空放行会把 LTYPE 规则拖进 files 作用域（fixture 在 src/test/resources 下被清零），收紧为仅 `isDeepAnalyzer`；⑥模块间测试用**已安装** jar——改 nop-lint-core/java 后必须先 install 再测下游（duckdb 老坑 lint 版）。
- 新测试：`TestJavaLocalTypeIndex`（参数/var 推断/字段/同文件返回/未知即 null）、`TestDeepProfileGate` ceiling 登记 LTYPE、套件 fixture 扩面。三模块 818/107/94 全绿；端到端探针（CLI 重建重装）：3 预编译惯用法 0 诊断、参数 String 与同文件返回 String 各 1 诊断。
- Doc-sync: 规则头注即 LTYPE 语义记录；design 01 的约束清单以 xdef+源码为准（本次为增量登记，design 增注留待 LTYPE 稳定后随 01 修订统一做）。

### nop-lint L2 project 级 TypeResolver：JavaTypeResolver 项目模式 + CLI --project-root 接线

- 现状确认：TypeResolver 接口/引擎门/l2Ready 齐备但 production CLI 从未接（LintEngine 构造传 null，L2 规则全场景降级）；JavaTypeResolver 是"单文件+反射"模式（JDK 可解析、项目内类型 Unsolved→降级），注释自述 project-classpath 为 successor surface。本次两层都补齐。
- JavaTypeResolver 项目模式：`initProject(root)` 扫描根下全部 `src/main/java`/`src/test/java` 源根（隐藏/target/build/node_modules 剪枝，4096 上限 runaway guard），每根一个 `JavaParserTypeSolver` 挂到 ReflectionTypeSolver 后面——项目内类型经各自编译单元解析。无源根的声明项目 fail-closed 报错（绝不静默退化为 reflection-only）；null root 重置单文件模式；缓存总是失效。`parseUnit` 拆出 `parseUnitWith(solver, source)`（静态反射版保留给映射契约测试）。
- 位置语义修正（项目模式暴露的真缺陷）：`typeOf` 桥传 capture **起点**，`minimalContaining` 落到最内层标识符（`b.tag().toString()` 的 `b`→类型 B 而非 String）。`JavaNodeIndex` 新增 `outermostExpressionStartingAt`：起始字节等于查询位置的**最外层表达式**优先（capture 起点=整个捕获表达式起点），无则回退旧行为——简单标识符 face（旧 ladder 用例）语义不变。
- CLI 接线：`--project-root <dir>`（CliOptions 新字段+解析+usage）→ CheckRunner 最深 run 面新增 projectRoot 参数：ServiceLoader `TypeResolverDiscovery.discover()`（新发现类，同族形状）→ `initProject` → 传入 LintEngine；无 provider 的 `--project-root` 是选项层 fail-closed 错误。`TypeResolver` 服务文件注册 `JavaTypeResolver`。
- 测试：`TestJavaTypeResolverProjectMode`（跨文件接收者解析=单文件模式做不到的核心面，engine 层 L2 规则 0 降级报出；空源根 fail-closed；null 重置）；`TestJavaTypeResolver` 旧 initProject 用例迁移进源根。三模块 818/110/94 全绿。CLI 探针：无选项行为不变；`--project-root` 空源根目录响亮报错；正常项目运行正常。
- 边界：JavaParserTypeSolver 是源码求解器（不读 class/jar 依赖）——三方依赖类型仍走 ReflectionTypeSolver（classpath 上有则可解析）；解析器初始化成本在首次查询（lazy 不变）。design 增注与 LTYPE 一并留待统一修订。
