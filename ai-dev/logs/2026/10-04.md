### 2026-10-04（Plan 2308 Phase 1：空序 emission 算法与边界裁定——9 条决策，只依赖一个能力位）

- Plan: `ai-dev/plans/2308-eql-orderby-nulls-first-multi-dialect.md`，本条记录 Phase 1（`Decision`）。Phase 1 是纯设计裁定，不写生产代码，但**每条裁定都先核对了它依赖的 AST/语法事实**。
- **核对到的关键实现约束**：`AstToEqlGenerator#visitSqlOrderBy`（`:582-586`）用 `printList(node.getItems(), ",")` 做列表级拼接 ⇒ **CASE 键必须在 `visitSqlOrderBy` 覆写里插入兄弟键，只覆写 `visitSqlOrderByItem` 做不到**（无法在逗号之间插键）。窗口两处（`AstToEqlGenerator:980`/`:1035`）都经 `visitChild(node.getOrderBy())` 路由到同一个 `visitSqlOrderBy`，故窗口上下文只能靠**向上遍历 `getASTParent()`** 区分。`SqlQuerySelect` 的 `distinct`/`projections` 字段存在（`EqlAST.xjava:153/156`），DISTINCT 判定可实现。
- **D1 算法**：只读 `supportNullsFirst`。true→原生输出；false/null→CASE 改写；未写 NULLS→不处理。**不做**「请求==缺省则省略」，`defaultNullsFirst` 全程不读。
- **D2 改写适用条件（保守档）**：仅**纯列引用**（`SqlColumnName`）。三类不可复制形态各有具体后果：含绑定参数标记（复制后两个 `?` 而 AST 只有一个 param 节点，参数靠遍历 AST 收集而非扫文本 → 错位）、序号定位（`order by 1` 改写后 `case when 1 is null` 恒不命中 → 排序失效）、易变函数（求值两次，NULL 判定与排序值不同源）。扩展到"无 marker 的任意表达式"留待后续——需要易变函数白名单，易错。
- **D3 DISTINCT**：原生路径不受影响；CASE 路径要求排序列**已在投影列表**（PG 对 DISTINCT 的 ORDER BY 表达式限制），否则 fail-fast。
- **D4 窗口边界**：`sqlOrderBy` 三个使用点，只有查询级可改写；`SqlWindowExpr.orderBy`（OVER）与 `SqlWindowDecl.orderBy`（命名窗口 `WINDOW w AS`）均 fail-fast。
- **D5 CASE 键位置**：必须是**前置同级键**（紧邻其排序项、同列表内），**不得** prepend 到列表头——多键场景 prepend 会把「先按 b 的 nullness 再按 a」写反且**不报错**。
- **D6 错误码**：新增 `ERR_EQL_NULLS_ORDER_NOT_SUPPORTED`，reason 三值 `window-not-supported` / `expression-not-duplicable` / `distinct-column-not-projected`。三条路径全为响亮失败。
- **D7 落点**：`AstToSqlGenerator` 覆写 `visitSqlOrderBy` 承载方言逻辑，基类保持方言无关（仅字面输出 nulls 标记，保证 `toSqlString()` round-trip）。**不**新增可配置扩展点——`IPaginationHandler` 那套"xml 配类名"必须改 `dialect.xdef` schema，与本计划 Non-Goal 冲突。

### 2026-10-04（Plan 2307 Phase 1：V3/V4/V5/V8/V9 裁定——实测推翻了初版对 V3 的定性，并发现一个独立新缺陷）

- Plan: `ai-dev/plans/2307-eql-live-defect-and-dead-surface-remediation.md`，本条记录 Phase 1（`Decision`）。
- **V3 定性被实测推翻（比 plan 初版更准确、也更易修）**：用含 `coll` **真实列**的实体走编译通道实测 WHERE / 投影 / ORDER BY 三处，`coll[x > 1].count()` **全部**抛带错误码的 `ERR_EQL_UNKNOWN_COLUMN_NAME`（`colName=x`）—— `[...]` 的内容被当作列名解析，必然失败。故「静默错误 SQL」**只发生在 `toSqlString()` 调试旁路**（未 transform 的原始 AST），不发生在真正执行查询的编译通道。
- **但 V3 仍裁定删除语法 + AST 节点**，三条理由：(a) 无 printer、无语义分析，永不可能产出正确 SQL；(b) 实现 `coll[where].func(args)` 属**新增 EQL 表达能力**，是本 plan 显式 Non-Goal；(c) plan 初版设想的「降级到 `_some`/`_all` EXISTS 路径」**语义错误**——`_some`/`_all` 是存在性量词、`.count()` 是聚合量词，`count(coll) > 2` 与 `exists(coll)` 不等价，映射会**改变查询语义**，正是本 plan 要消灭的那类缺陷。
- **V6a 实测比 plan 描述的更严重**：plan 说 V6a 的触发前提是 `WITH RECURSIVE`、残留隐患是 `exprMeta` 无判空。实测 `with recursive t as (select 1 union all select 2 from t) select 1 from t` 直接抛**裸 `NullPointerException`**（`Cannot invoke "ISqlExprMeta.getColumnNames()" because "exprMeta" is null`），无错误码、无定位。即 **EQL 的递归 CTE 当前整体不可用**，而非边缘隐患。另实测 `select *` / `o.*` 作 UNION 左支同样触发该 NPE（说明 plan 关于「`SqlAllProjection` 已被替换、该强转不可达」的推断对**本条 NPE 路径**不成立——强转成功但 `exprMeta` 为 null）。V6b（`EqlCompiler:96`）与 V6c（`SqlSelect:70`）实测**不可达**（顶层 `select *` 与 union 均已展开为 `SqlExprProjection` 且 exprMeta 已解析），按 plan 定性为纯加固。
