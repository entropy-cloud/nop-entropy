### 方案 B（BIGINT+string）过滤参数绑定缺陷修复：SqlParamTypeResolver 按列 SQL 类型定型

- 缺陷核实（来源：`~/recv/2026-10-20-postgres-bigint-string-filter-binding.html`）：QueryBean/EQL/DataAuth 过滤参数在 `SqlParamTypeResolver` 只按列声明的 Java stdDataType 绑定；BIGINT+string 列（orm-model-design.md 方案 B）参数以 String 发送，PostgreSQL 无 `bigint = varchar` 算子报 42883。`__get`/insert/update 走列 binder（AutoConvertDataParameterBinder）不受影响——两条路径 binder 不一致，属平台缺陷。
- 复现（修复前）：新增独立测试模型 `_vfs/nop/test/orm/bigint-string.orm.xml` + `AbstractBigIntStringFilterCase`（26 用例）+ H2/PG/MySQL 子类。H2 上核心断言（`CompiledSql.buildParams` 产出类型）8 红：eq/gt/pk/UPDATE SET 参数为 String 而非 Long；IN/BETWEEN 元素为 String；"abc" 走 DB 层 `nop.err.dao.sql.data-type-conversion-fail` 而非平台转换错误。E2E 在 H2 因隐式转换可执行（缺陷现场仅 PG）。
- 修复（A0，单文件）：`nop-orm-eql/.../compile/SqlParamTypeResolver.java`——比较谓词（`isCompareOp`，含 `<=>`，不含 LIKE）/ UPDATE SET 经 `resolveBindType`、IN/BETWEEN 经 `resolveInBetweenBindType`（非数值+String 回退 ANY 保持透传），当「Java 类型 STRING + SQL 类型数值」时按列 SQL 类型绑定（BIGINT→Long）；IN/BETWEEN 对照列元数据只用于选绑定类型，不写入参数节点 resolvedExprMeta。无 API/签名变更。
- 验证：修复后 `TestBigIntStringFilterH2` 26/26 绿；`nop-orm-eql` 904/0；`nop-orm` 512/0（77 skipped 为 Docker 门控用例，本机无 Docker）。PG/MySQL Testcontainers 子类（`-Dnop.test.docker.enabled=true` 门控）已就位，待有 Docker 环境复跑（修复前 PG 预期 42883 全红、修复后全绿）。
- 边界行为钉住：非数字 String → `nop.err.api.convert-to-type-fail`（早于且清晰于 DB 错误）；空串 eq→is null；`9007199254740993`（>2^53）精确命中；VARCHAR 列 LIKE 保持 String。
- Doc-sync: `docs-for-ai/02-core-guides/orm-model-design.md`（方案 B 强制规则：过滤参数按列 SQL 类型绑定 + PG 42883 修复注记 + 落地实证补链）；`docs-for-ai/00-start-here/application-project-pitfalls-backend.md` 铁律 3 补 PG 验证提示。
