## ConvertHelper 秒/毫秒时间戳区分修正

`ConvertHelper.stringToLocalDate` / `stringToLocalDateTime` 原对纯数字串一律按**毫秒**解析(`isAllDigit` → `millisToLocalDate(ts)`)。AMIS `input-date` 默认序列化为**秒级** Unix 时间戳(10 位),导致秒时间戳被静默解析成 1970 年附近日期(不报错,比抛异常更危险)。

根因来自 nop-app-erp plan `2026-07-12-1321-3`:6 个报表 BizModel 手写 `LocalDate.parse(v.toString())` strict 解析秒时间戳/空串抛 `DateTimeParseException`。调研发现即便改用平台 `ConvertHelper.toLocalDate`,秒时间戳仍会因单位不匹配被解析成 1970 年。

### 改动
- `ConvertHelper.java` `stringToLocalDate` / `stringToLocalDateTime`:纯数字串 `str.length() <= 10` 按**秒**(`ts * 1000L` 后复用 `millisToLocalDate/Time`,保持默认时区行为一致),>10 位(13 位毫秒)不变。两处对称修正,避免 Date 与 DateTime 对同一秒时间戳解析不一致。
- 边界安全:10 位最大值 `9999999999 * 1000` 远在 long 范围内;`isAllDigit` 已保证纯数字,`length()` 判断可靠。
- 回归面:仅影响"传入 ≤10 位纯数字串且原期望当毫秒"的调用方(10 位毫秒 = 1970-01-01 后约 115 天,作为业务 LocalDate 几乎不可能);13 位毫秒行为不变。大量 `_gen` DAO 实体的 `toLocalDate` 经此路径,但它们的输入来自 DB/序列化,非秒级时间戳,不受影响。

### 验证
- `mvn test -pl nop-kernel/nop-api-core -Dtest=TestConvertHelper` → Tests run: 9, Failures: 0, Errors: 0, BUILD SUCCESS
- 新增 `testEpochString`:13 位毫秒保持毫秒、10 位秒按秒(`assertNotEquals` 证明不再误当毫秒)、空串→null,Date/DateTime 对称。断言基于 `millisToLocalDate/Time` 自洽,不硬编码日期(规避时区不稳)。
