### nop-batch 分区 IntRangeSet 化 + PartitionResolver 抽取（Plan 325）

- 将批处理任务的分区配置从单区间 `IntRangeBean` 统一为多区间 `IntRangeSet`，并把 nop-job / nop-retry 中重复的 cluster 分区解析逻辑上提到 nop-cluster-core。
- 改动：
  - `QueryBean.addPartitionFilter` 修正为纯实例方法 `addPartitionFilter(IntRangeSet, String)`（原签名把 query 当参数传入，怪异），内部复用 `FilterBeans.inRanges`
  - `IBatchTaskContext` / `BatchTaskContextImpl` 的 `get/setPartitionRange` 类型改为 `IntRangeSet`
  - `JdbcBatchLoaderProvider` / `OrmQueryBatchLoaderProvider` 改用 `query.addPartitionFilter(partitions, partitionIndexField)`，去掉手写 `FilterBeans.between`
  - nop-cluster-core 新增 `io.nop.cluster.naming.PartitionResolver`（assignedPartitions 优先 → NamingService 动态分配 → 10s 缓存）
  - `JobPartitionResolver` 退化为 `extends PartitionResolver` 的缺省配置子类（仅绑 `nop.job.cluster.*`）
  - `RetryScannerImpl` 组合内部 `PartitionResolver`，转发 setter，删除复制的 `resolvePartitions` 逻辑
- 新增测试：`TestQueryBeanPartitionFilter`（5 case）、`TestPartitionResolver`（10 case）
- 验证：`./mvnw test -pl nop-batch-core,nop-batch-jdbc,nop-batch-orm,nop-cluster-core,nop-job-coordinator,nop-retry-engine` 全绿；`TestJobPartitionResolver` 继承后无需改动仍 10/10 通过
- Doc-sync: `docs-for-ai/04-reference/xdefs/batch.xdef` 的 `@partitionIndexField` 注释更新（多区间 OR）；`ai-dev/design/nop-sys/sys-event-architecture.md` §3.4.1 loader 过滤约定同步
- NopJobTask.partitionRange String 持久化格式不动；`PartitionTaskBuilder.PARTITION_HASH_RANGE`（AR-98）不动
