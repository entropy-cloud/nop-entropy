### 3. 可逆计算公理体系（提炼）

中心命题：`Y = F(X) ⊕ Δ`（paper-v2 §2.2, Abstract line 10）。关键公理：

1. **构造关系自递归**：公式递归适用，空基线即"创世差量" `M = ∅ ⊕ M`（paper-v2 §2.2 L72-77）
2. **差量分解（一等资产）**：Δ 可独立命名/存储/组合/审计；差量与全量同构（同一 schema 约束），"差量的差量仍是普通差量"（paper-v2 §2.4 L99-105；proof-v2 §1.3 L110-111）
3. **Delta 结合律（条件化）**：proof-v2 在 3 个 carrier 上证明 `(P, ⊕, ∅)`/`(P_O, ⊗, ∅)`/`(NOp_p/≡, ⊙, [Id])` 均为幺半群；Corollary D 给出工程陈述：满足 A1-A9 + 10 项实现符合性时，任意括号化得同一 `Ok(Model)` 或 `Err(ErrorSet)`（proof-v2 §12, §13, §14）
4. **逆元 = 删除语义**：**注意**——"生成即逆元"并非这三篇文档的字面引用；逆概念体现为 (a) 复用公式 `B = A + (-C)`（overview L30-33, L85：变化必含正元素+逆元素）与 (b) 形式证明中的 tombstone `⊥_c` / `Remove` 端函数（proof-v2 §1.2, §5.4）。生成器 `F` 是确定性基线生产者，未被形式化为"逆"
5. **语义坐标系**：由 DSL 元模型提供稳定寻址规则；满足唯一性/稳定性/层级性/可规范化/可验证 5 性质（paper-v2 §2.3 L81-97）。**类型系统/类-成员结构不是充分坐标系**（数组下标漂移）→ stable key 必须由 XDef 显式声明
6. **合并算子 `⊕` = 右覆盖（Last-Write-Wins）**：proof-v2 §1.4 L116-134
7. **XDef = 元模型 = 坐标系来源**：paper-v2 §5.2 "语言即坐标系"；stable key 由 XDef 声明而非默认 name/id

9. **潜在结构空间 + 终端验证（S-N-V 阶段分离）**：合并须在潜在空间完成，中途有损投影会破坏结合律（proof-v2 §2.4 反例 L354-404）；S 合并→N 规范化→V 验证编译，运行时面对无 delta 历史的静态模型（paper-v2 §5.6 L334-344）

**关键工程含义**：结合律是 delta 栈可预合并（`Base ⊕ Δ_1 ⊕ ... ⊕ Δ_n ≡ Base ⊕ NF(Δ_1..Δ_n)`）、独立版本化、缓存、重新叠加到新基线的数学许可。

### 4. 理论→工程映射（XLang/XDSL/XDef 三件套）

- **XDef 同态设计 + 自举**：元模型与模型同构（元模型即嵌 def-type 微语言的"示例"）；`xdef.xdef` 自定义自身，闭环无需更高元元模型。成本从 O(N) 降到 O(1)（deep-dive §四 L253, §五 L306）
- **三阶段 extends（加载期合并顺序）**：`x:extends`（继承基模型）→ `x:gen-extends`（Generator，编译期生成）→ body → `x:post-extends`（后处理）。完整顺序 `F -> E -> Model -> D -> C -> B -> A`（why-xlang §2.1 L408-410）。**全部在加载期完成**，运行时操作"烘焙"好的静态模型（deep-dive §二 L485-486）
- **结构层而非对象层**：`XNode = XNode + Delta`，`Model = Parser(XNode)`（非 `EntityModel = EntityModel + Delta`）——这是 Delta 合并通用性的根源（delta-vs-extension §2.1 L45；xlang-explained §1 L103）

### 1. Model-Driven Software Development (MDSD) / MDA

- **该框架做什么**：以模型（通常 UML/图形设计符号）为一等制品，输入建模工具，生成目标语言代码。OMG 的 MDA（Model-Driven Architecture）是其特定愿景，基于 UML，分离业务逻辑与平台。Fowler 持谨慎怀疑态度：模型未必总是比编程语言更高抽象；需要 projectional editing 工具支撑；源码控制是典型痛点。
  - 来源：https://martinfowler.com/bliki/ModelDrivenSoftwareDevelopment.html（访问 2026-07-24）；https://www.omg.org/mda/（访问 2026-07-24）
- **nop 做什么**：以结构化 DSL（XML/JSON/YAML 形式的 XDSL）为模型，XDef 元模型驱动解析/校验/Java Bean 生成；模型与差量（Delta）同构，可叠加、可预合并、可版本化。
- **差异点**：(a) nop 的"模型"是可执行的结构化差量载体，非一次性 codegen 输入——`Y = F(X) ⊕ Δ` 中 Δ 可独立于基线组合；(b) nop 内置 Delta 合并机制使模型可演化（客户定制可重新叠加到新基线），MDSD 生成后代码即"冻结"；(c) nop 不依赖图形/projectional 编辑器，用文本 DSL + XDef 完成元模型驱动。

### 2. Language Workbench / Projectional Editing（JetBrains MPS）

- **该框架做什么**：JetBrains MPS 是 projectional 编辑器——直接编辑 AST 而非文本，绕过解析器限制；支持近乎无限的语言扩展与组合（language composition）。适合构建复杂 DSL，但工具链重、源码控制（存 AST 而非文本）有摩擦。
  - 来源：https://www.jetbrains.com/mps/、https://www.jetbrains.com/mps/concepts/、https://en.wikipedia.org/wiki/JetBrains_MPS（访问 2026-07-24）
- **nop 做什么**：XDef 元模型驱动 + 文本/XML DSL（解析式，非 projectional）；"语言即坐标系"——XDef 声明 stable key 与结构约束，使每个 DSL 语法要素有稳定领域坐标。
- **差异点**：(a) MPS 聚焦**语言组合**（多语言在 AST 层混合），nop 聚焦**模型差量组合**（同构 Delta 在结构层叠加）；(b) MPS 用 projectional 编辑器解决"无法解析的语言扩展"，nop 用 XDef 元模型 + `x:extends`/`x:override` 在结构层（XNode）实现通用差量，无需 projectional 编辑器；(c) MPS 的扩展难以规约回基础形式，nop 的 xpl/xlib 元编程**总是规约回基础 DSL 形式**（保留 Delta 可叠加性）。

### 3. Delta-Oriented Programming (DOP, Schaefer 等, SPL 领域)

- **该框架做什么**：面向软件产品线（SPL）的编程方法。产品线 = 核心模块 + 一组 delta 模块；delta 操作对已有代码做增加/删除/修改（add/delete/modify）。Schaefer & Bettini 2010 (LNCS SPLC, 引用 562+) 提出，为产品线配置提供灵活性，含组合类型检查基础。
  - 来源：Schaefer & Bettini, "Delta-Oriented Programming of Software Product Lines", SPLC 2010 — https://www.researchgate.net/publication/220789518、https://flore.unifi.it/bitstream/2158/1039579/2/Delta-Oriented%20Programming%20of%20Software%20Product%20Lines%20LNCS-splc-2010.pdf（访问 2026-07-24）；DeltaJava 案例 Nieke 2022 — https://pure.itu.dk/files/86606380/DeltaJava_Teamprojekt_Paper.pdf
- **nop 做什么**：结构层（XNode）通用 Delta 合并；差量与全量同构（同一 schema 约束），"差量的差量仍是普通差量"；满足结合律使差量可预合并、独立于基线组合。
- **差异点**（本仓库 `docs/theory/delta-oriented-programming.md` §四 已有论述）：(a) DOP 的 delta 用**与全量不同的形式**（修改动作）表达，"delta 的 delta"问题未解决；nop 使 delta 与全量同构、同 schema 约束；(b) DOP 绑定特定编程语言（如 DeltaJava）；nop 的 Delta 在无语义的结构层（XNode）通用，"定理证一次，所有模型复用"；(c) nop 显式形式化了结合律（3 carrier 证明），DOP 未提供等价的差量预合并代数保证。

### 4. 双向变换（bx / lenses / synchronization）

- **该框架做什么**：source 与 view 之间的一对映射：`get` 从 source 抽取 view，`putback` 将 view 的更新反向传播回 source。需满足 lens laws（GetPut / PutGet / PutPut）。用于 view-source 同步、数据同步。Haskell lens 库是其代表性实现。
  - 来源：Matsuda et al., "Applicative Bidirectional Programming with Lenses", ICFP 2015 — https://www2.sf.ecei.tohoku.ac.jp/~kztk/papers/kztk_icfp2015.pdf（访问 2026-07-24）；Haskell lens 库 https://hackage.haskell.org/package/lens（访问 2026-07-24）
- **nop 做什么**：可逆计算的"可逆"**不是** bx 的 view-source 双向同步。nop 的"可逆"指构造期的**差量组合代数**——差量可叠加、可预合并、可条件剥离，核心是结合律与坐标系稳定性，运行时面对静态模型。
- **差异点**（本仓库 `docs/theory/reversible-compuation-vs-bidirectional-transformation.md` 已系统对比）：(a) bx 关注**两个表示之间的双向同步**（get/putback 闭环），nop 关注**单向构造链上的差量组合**（`Y = F(X) ⊕ Δ`，Δ 叠加到基线）；(b) bx 的 lens laws 约束单对 get/putback 的一致性，nop 的结合律约束**多条差量链**的可重排性（预合并许可）；(c) bx 通常处理数据同步（运行时），nop 的差量合并全部在加载期完成，运行时无差量历史。
