### MFA 多因子验证（nop-auth）设计文档定稿（经五轮独立审查达成共识）

针对"短信验证码登录 + 多因子验证"需求（geekai/n8n 对比调研识别的差距），完成 nop-auth MFA 子系统设计并经独立子 agent 五轮审查修订后达成共识。

- **设计文档**：`ai-dev/design/nop-auth/`（README.md + 00-vision.md + 01-architecture-baseline.md），并更新 `ai-dev/design/README.md` 索引。
- **核心决策**：不新增模块，改造 nop-auth 登录体系。登录改两阶段（第一因子通过 → `ERR_AUTH_MFA_REQUIRED` 异常携带 challenge token → `mfaVerify` 第二因子验证通过才签发会话）；**MFA 拦截覆盖 loginAsync（密码类）与 createSessionForUserAsync（SSO/信道类）两条入口**；短信验证码登录 loginType=5（同步修复 dict SSO 4/10 不一致 + 补 2/3/5）；TOTP（RFC 6238）secret 用 AESTextCipher 加密、防重放基于 lastVerifiedWindow；恢复码 BCrypt 加盐哈希 + 使用后强制重绑；**新增 MfaChallengeStore/SmsCodeStore（Local + Redis 双实现，Redis 复用 nop-nosql：INosqlKeyValueOperations/NosqlCache/INosqlRateLimiter/INosqlCounter）**——不复用 IUserContextCache 验证码通道（仅 Local、无 TTL 参数、String-only 无 remove）；失败计数分界（第一因子锁账号、第二因子计 challenge 内）；跨模块改造 nop-ai-gateway 扫码适配。
- **拒绝的方案**：独立 nop-mfa 模块、复用 IUserContextCache、复用 loginType=3、challenge 用 JWT、MFA 拦截用标记 IUserContext/LoginResult 字段、secret 入 nop-credential、恢复码无盐 SHA-256、第三方 TOTP 库、按角色强制 MFA（一期）、外部 MFA 服务、操作级 MFA。
- **五轮审查关键发现**：轮1 发现 IUserContextCache 三重事实（仅 Local/无 TTL/无 remove）与 SSO/信道无拦截点（P0×2）；轮2 发现 createSessionForUserAsync 契约未闭环（MFA 拦截统一改异常携带方案 + nop-ai-gateway 适配 + 扫码时序图）与平台已有 nop-nosql 基础设施（"Redis 为新增工作量"不实）；轮3 发现 incrFailCount Redis 原子性缺口；轮4 补齐全局开关/恢复码消费/plan-first 标注；轮5 达成共识，实施裁决点（INosqlCounter 复用 vs 接口扩展、双类恢复码、Redis 写路径 TTL 约束）已写回设计文档。
- 验证：doc link checker 通过（无本次引入断链）；轮次遗留的 plan-first 门禁已标注（ISessionBootstrap/LoginApi/LoginResult/ScanLoginResult/INosqlKeyValueOperations）。

### 加密凭证库（nop-credential）设计文档定稿（经三轮独立审查达成共识）

针对 geekai/n8n 对比调研（`~/ai/agent-survey/`）识别的平台差距"无加密凭证库"，完成 nop-credential 子系统设计并经独立子 agent 三轮审查修订后达成共识。

- **设计文档**：`ai-dev/design/nop-credential/`（README.md + 00-vision.md + 01-architecture-baseline.md），并更新 `ai-dev/design/README.md` 索引。
- **核心决策**：新建独立可复用模块 `nop-credential`（api/dao/meta/service/web + model/orm.xml）；**复用** nop-commons `AESTextCipher`（AES-256-GCM + PBKDF2，v1: 密文），凭证密文用 `cv1:{keyId}:{v1密文}` 双前缀格式支持多密钥轮换；凭证类型用 register-model 机制声明（credential-type.xdef 元模型 + *.credential-type.xml 实例文件，无类型 DB 表）；消费 SPI `ICredentialProvider`（接口在 api、实现+唯一解密点在 service，明文边界结构性强制：data 列 published=false + findPage 置空 + maskList）；配置加密复用既有 `@sec:`，不做 `@credential:` resolver；一期不做 RBAC/OAuth/KMS/租户隔离；删除语义=软删除+registerUsage 引用计数（NopCredentialUsage 表）。
- **拒绝的方案**：并入 nop-sys/nop-auth/nop-integration、仅扩展 nop-security、只依赖 @sec:、nop-dyn 动态实体、自研算法、@credential: resolver 一期。
- **审查发现的平台事实（重要教训）**：平台已有 `nop-commons/crypto/AESTextCipher`（v1: 版本化格式）与 `nop-config` `@sec:` 配置加密（DefaultConfigValueEnhancer）——初稿遗漏导致"下沉 nop-security"重复造轮子、v1: 前缀冲突；`graphql:query` 属性在 obj-schema.xdef 不存在（正确机制是 published=false）；xdef 是元模型格式，业务定义文件应走 register-model.xml + *.xml 实例文件惯例（参照 ai-tool.register-model.xml）。
- 三轮审查结论：P0×2、P1×4（轮1）、P1×3（轮2）全部修复；轮3 达成共识"可以进入实施"（剩余 P2：引用计数解绑路径与存储落点，已随终修补入设计）。
