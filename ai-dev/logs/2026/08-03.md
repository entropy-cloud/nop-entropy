### 设计决策（值得记录的）

- **Phase 0 选择 default 方法而非新接口**：`deployTask` 声明为 `IStreamTaskRpcService` 的 `default` 方法（抛 UnsupportedOperationException），而非新建 `IRemoteDeployTaskService`。理由：(1) 现有约 12 个 test double（`MockTaskRpcService` 等）无需改动即可编译；(2) 生产实现独此一份（`TaskManager.deployTask`），无需多态分发；(3) `deployTask` 的契约（接收 descriptor → 本地重建 invokable）与 `IStreamTaskRpcService` 的现有方法（`receiveAssignment`/`triggerCheckpoint`/`cancelTask`）属同一控制面层。
- **Phase 1 `PollingJdbcMessageService` vs `SysDaoMessageService`**：plan 显式允许「simple shared file/socket-backed message service for tests」作为 SysDao 的替代。`PollingJdbcMessageService` 用同一 H2 DB（与 `JdbcClusterRegistry` 共享连接池），Java 序列化 payload（`ApiRequest`/`StreamMessageEnvelope` 均 `Serializable`），publish-subscribe 语义匹配 `LocalMessageService`。这避免了 `nop-stream-runtime` 对 `nop-sys-dao` 的硬依赖（vision §三 约束 8），且 test infra 的可靠性需求低于生产。
- **Phase 3 「exactly-once」范围**：完整 source→keyBy→sink pipeline + 跨 JVM shared-sink exactly-once 断言需要可序列化 pipeline descriptor + 共享 sink 状态（Stage 43+ scope）。Phase 3 验证**使 exactly-once 成为可能的基建**：跨 JVM `deployTask` + recovery redeployment + fencing。Phase 0 in-process E2E（`TestRpcDistributedExecutorRemoteDeployE2E`）已证真实 pipeline 经 `deployTask` 跑通。

### 偏差

- Phase 3 的 `TestMultiJvmExactlyOnceRecovery` 使用 placeholder JobGraph（无真实 source/sink operators）而非完整 source→keyBy→sink pipeline。coordinator 的 `assignTasks()` 真实发送 `deployTask` RPC 跨 JVM；TaskManager 真实接收并尝试本地重建（失败因 placeholder 无 operators → FAILED report → recovery loop 触发 → fencing epoch rotation）。这验证了**控制面 + 恢复机制**跨 JVM 真实工作，但未验证数据面 record 流经 pipeline 的 exactly-once。完整 pipeline 验证留作 Stage 43+ follow-up（plan Non-Blocking Follow-ups 已记录）。诚实记录而非降级断言。
