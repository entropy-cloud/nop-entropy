### 设计修正：多实例恢复（用户质疑）

### 示例：coeffect 用法 + agent 场景组装

### 补充：可逆计算落实 = loader 抽象（被动模式）+ 张量坐标

- 用户指出：可逆计算的落实可封装为 **loader 抽象（被动模式）**——按**张量坐标**（特征向量）加载合并 delta 得到静态 model，再在 model **外部**应用运行时参数。
- 对比文档 `2026-08-14-...comparison.md` §5.3 图后新增"loader 抽象"段落：`modelPath => XDSL => DslModel`（loader，**被动**——只按坐标组装结构）‖ `DslModel => arguments => scope => Result`（运行时，外部参数独立施加）。对应 `generic-delta-composition.md` 的 `loadComponentModel` + 特征向量 `App = (工作流, 报表, 权限, ...)`。
- 与 dsh 差异：dsh 配置层也是 loader（`composeEntries`/`renderConfigDump`），但加载后 `boot()` 直接 mount 成活对象（立即激活 fiber），没把"静态 model"与"运行时参数"分离成独立两段；可逆计算 loader 明确输出静态 DslModel，运行时是独立第二阶段——这正是"被动模式"精确含义。
- **被动模式第二层含义（用户补充）**：依赖追踪 + 自动缓存失效——Loader 内置基于依赖的缓存，任何 Delta 文件修改后相关缓存自动失效并重算静态 model（`decoding-reversible-computation.md` 智能缓存）。dsh 的 `watchUserPatches` 也有缓存失效，但重组须重新激活整棵插件树（活资源 teardown）；可逆计算的失效只重算静态结构、运行时独立，代价远低。

### 修正（重大）：dsh 双层架构——配置层即标准可逆计算，差异在粒度

- 用户三点纠正：(1) plugin 本身是**粗粒度边界**（revertible effects 以 plugin 为单元整体回退）；(2) 可逆计算引入领域结构坐标系，是**非常细粒度的 delta**；(3) dsh 的 YAML 覆盖配置层与 effect 系统**完全无关**，且**正是可逆计算的标准处理方案**。
- 据此重写对比文档 `2026-08-14-...comparison.md` §5.1/5.2/5.3/Conclusion/metadata：旧判断"dsh 没有分离结构/运行时空间""结构未分离"是**错误的**。dsh 实为**双层独立系统**：
  - **YAML 配置层**（声明式、离线）：`ConfigTree = ∅ ⊕ bundle₁ ⊕ bundle₂ ⊕ patches`，`composeEntries`/`renderConfigDump` 可不运行任何 effect 纯离线合并——这正是 `App = Delta x-extends Generator<DSL>`，与可逆计算同构。
  - **运行时 effect 层**（论文 revertible effects）：`boot()` 在配置合并后才 mount/激活/disposer。
- 真正差异是**粒度谱系与逆元完整性**：plugin 整体（粗，revertible effects 边界）→ 配置行/entry（dsh patch 按 id）→ 领域坐标系节点（可逆计算 XDef，细粒度 delta）。dsh 配置层缺结构化逆元（无 remove/deep-merge），可逆计算有。论文 §3 只形式化了运行时层，未覆盖配置层。

### 分析：Cordis 论文 _A Programming Paradigm for Spatiotemporal Composability_ 精读

- 论文形式化核心：**revertible effects** = effect 类型 `Γ→Γ×(Γ→Γ)`（context 变换 + 显式 inverse）；effects 生活在 **monoid（单群）** 下；可撤销用**左逆（left inverse）** `g∘f`（单向），twisted composition `(f₁,g₁)∘(f₂,g₂)=(f₁∘f₂,g₂∘g₁)`。**关键：用 monoid + 左逆，非群**——与可逆计算 `explanation-of-delta.md` "实际差量空间不是真正群"论断同构。

### 分析：DeepSeek Harness 与可逆计算的思想异同

- 新增分析文档 `ai-dev/analysis/2026-08/2026-08-14-deepseek-harness-vs-reversible-comparison.md`，对比外部项目 `~/ai/deepseek-harness`（dsh / Cordis）与 Nop 可逆计算理论。
- 核心结论：两者共享"组合性/非侵入扩展/层叠覆盖"等工程共鸣，但"可逆"层次根本不同——**dsh = 运行时生命周期可逆（reversible effects，时间维度，注册⇄注销）**；**可逆计算 = 结构层可逆（reversible computation，空间/结构维度，合并⇄分解，差量含逆元）**。
- 三个决定性差异：(1) 可逆计算差量**含逆元**（`-F`、`x:override="remove"`），dsh 无（patch 仅替换/插入整行，无代数减法）；(2) 可逆计算在**标准化结构层（XDSL）**做代数运算，dsh 在**运行时对象层**做生命周期回滚；(3) **可逆计算把结构空间分离出来，运行时空间可独立处理**（`docs/theory/generic-delta-composition.md`：`modelPath => XDSL => DslModel => args => scope => Result`，DSL 动态更新独立于状态空间数据迁移），dsh 未分离这两个空间（结构即被消费，HMR 重组须处理活资源一致性）。
- 可借鉴：Nop 可吸收 dsh 在运行时可逆副作用（disposer / scope unwind / teardown-to-quiescence，见 `docs/defensive-patterns.md`）上的精细化经验，作为结构层差量之外的运行时层补充；Nop IoC 当前偏传统 bean 管理，运行时可逆副作用系统化程度低于 Cordis。
