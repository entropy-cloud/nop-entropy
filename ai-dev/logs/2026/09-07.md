## 17:00 调研纯 Java Tree-sitter runtime 移植可行性 + 下载参考仓库

- 背景：Nop 平台目前依赖 JNI/FFM 才能用 Tree-sitter 生态（200+ grammar）。用户提出想做纯 Java runtime 移植，目标：单 JAR 分发，零 native 依赖，跨平台含 Android/GraalVM。
- 下载：
  - 在 `~/sources/treesitter/` 下建立源码仓库集（`scripts/download-github.sh` + `download-all.sh` + `verify-downloads.sh`）
  - 17 个仓库全部下载完成：
    - 上游：`tree-sitter`（C runtime + CLI + `lib/binding_web` WASM/JS）
    - 重写参考：`gotreesitter`（纯 Go，206 grammar，~726k LOC）、`tree-sitter-rust-rewrite`（HerringtonDarkholme，~78k）、`tree-sitter-c2rust`（c2rust 翻译，~71k）
    - Java binding 对比：`java-tree-sitter`（FFM）、`tree-sitter-ng`（JNI）、`seart-group-java-tree-sitter`、`kotlin-tree-sitter`、`jtreesitter-type-gen`
    - Node binding：`node-tree-sitter`
    - 工具实例：`graft`（用 gotreesitter 的 VCS）、`stacklit`（代码索引）
    - 5 个 grammar：`tree-sitter-{json,java,javascript,typescript,python}`
  - 脚本特性：指数退避（5s→60s）× 80 次重试；同目标目录锁文件防并发 rm -rf；支持 GIT_TOKEN 提速率
- 脚本踩坑：
  - Bash 中 `GROUPS` 是 shell builtin 变量，会被预填当前用户的 group IDs → 改名为 `SELECTED`
  - array literal 中加 `|| true` 是语法错误
  - 并发跑 17 个 git clone 时，旧 process 的 `rm -rf` 会杀掉新 process 的成功 clone → 改为串行 + 锁文件
- 关键澄清（用户提到的"JS/TS 实现"）：
  - **没有"纯 JS runtime 重写"先例**。所有 JS/TS 实现都依赖 C 编译产物（WASM/NAPI）。
  - 现有 JS/TS 实现：`web-tree-sitter`（WASM 包装）、`tree-sitter-cli`（Rust + WASM 调用）、`node-tree-sitter`（C++ N-API）

  - `2026-09-07-pure-java-tree-sitter-feasibility.md` — 路线对比（A 纯 Java / B JNI 增强 / C 混合）+ 阶段化路线图
  - `2026-09-07-tree-sitter-runtime-architecture.md` — runtime 12 个子模块的 C/Go 对照表 + 移植设计点
- 结论（open，待用户决策）：
  - 推荐 **路线 C 混合**：短期用 `tree-sitter-ng` 解决需求；长期按 gotreesitter 模式渐进做纯 Java runtime
  - gotreesitter 的 `cmd/ts2go`（≈1800 LOC）证明 parse table 抽取 + 纯语言 runtime 完全可行
  - 关键风险：GLR 实现细节、external scanner VM、GC 压力（ast-grep 教训：早期 arena 内存爆炸）
