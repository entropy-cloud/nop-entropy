### 2026-09-06 时序敏感测试彻底修复（7处根因修复 + 连续3轮全量clean全绿）

- **背景**：合并后全量 `-T 1C` 构建在不同模块随机 flaky。逐一定位根因后全部根治，不是加大重试掩盖。
- **根因清单与修复**：
  1. **TestJobWorkerScanner$Inner**（确定性失败，master 遗留）：Inner 两个用例漏注 `capacityProvider` → scanBatch 在容量检查处 NPE 被 onScanFailed 吞掉 → 任务永不处理。连带修复两个实现缺陷：① DefaultJobExecutionContextBuilder 固定用 execution-failed 错误码掩盖 NopException 具体码（JOB_INVOKER_RETURNED_NULL 丢失）→ 保留 err instanceof NopException 的错误码；② executeTask 无 fire 终态守卫 → CANCELED fire 的任务在置 RUNNING 前检查，终态则回滚 WAITING 跳过执行。
  2. **TestRocksDBIncrementalRestoreAndBenchmark**（master 遗留，本机 ratio 3.2-5.2 超阈值 3.0）：state=20000 太小（约 5MB，SST 常驻页缓存），full scan 仅 ~19ms，incremental 的固定开销（RocksDB checkpoint 创建 + SST 全量 SHA-256）占比过大 → 物理上必然慢。state 20000→100000 后 incremental 优势显现（实测 ratio 0.167），测试耗时仍仅 1.5s。**这不是性能回归，是基准参数违背测试自身注释声明的"Large state"设计意图**。
  3. **TestSuspendContract.asyncSuspendInSequential/Selector_propagates**：`task.execute()` 返回时 executor 包装的挂起 promise 可能尚未完成（suspend 步骤在 globalWorker 排队），未完成 ASYNC 的 nextStepName=null 使 `isSuspend()` 判 false。DEBUG 输出捕获实锤（`async=true done=false`）。修复：execute 后 `ret.isAsync()` 则 `sync()` 等待完成值再断言。
  4. **TestEtlTaskStateStoreAtomicWrite**：reader 的 `while(writer.isAlive())` 在 writer 先于 reader 首轮调度完成时零执行，readCount==0。改 do-while 保证至少一轮（竞态不涉及被测语义）。
  5. **TestS1CdcRecoveryE2E / TestS1CdcPipelineE2E**：2PC sink 的 commit 在下一 checkpoint 周期（interval=100ms），finishLinger=600ms 仅 6 个周期，负载下 checkpoint executor 被抢占 commit 推迟到秒级 → run 1 断言时 alice alert 未提交。linger 600→3000ms（30 周期）。其余 5 个 S2/Parallel2Pc E2E 同参数统一加固。
  6. **TestReplayableCdcSourceFunction.offsetCheckpointAndResumeSkipConsumedPrefix**：cancel 与最后一条 5ms pacing 竞态，consumed==specs.size() 是合法结果（cancel 无法撤销已 accept 的事件），原断言 `consumed < specs.size()` 判 false。放宽为 `<=` 并对 resumed 空集跳过下标断言。
  7. **TestLazyLoadOrmModel.testConcurrentAddAndTopoRebuildKeepsAllEntities**：adder.join(5000) 超时不检查 isAlive，负载下 adder 未完成 put 即继续 → 与最终重建竞态丢实体。改为 join 超时后循环检查 isAlive 继续等待（保证 happens-before）。
  8. **ShellConcurrencyEdgeCaseTest.testPipelineStagesRunConcurrently**：共享 executor 被同 JVM 其他测试占满时 stage2 的 supplyAsync 排队超 500ms 窗口。stage1 sleep 500→2000ms、future.get 5→15s（窗口加宽不削弱"stage1 未完成时 stage2 已启动"的断言语义）。
