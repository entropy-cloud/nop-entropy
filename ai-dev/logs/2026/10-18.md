### mdxquery（主子表维度对齐）审计 + 全量修复（ad-hoc）

用户问 `io.nop.orm.mdx` 实现是否有需要改进修正的地方。先按选择修了 3 个 Blocker，随后用户指示「该修改的就修改」，把其余确认成立的缺陷一并修掉。

- **背景**：`MdxQueryExecutor`/`MdxQuerySplitter`/`MdxQueryBean` 仅 3 个文件，自 2017 年起几乎未改动（git log 仅 2 条）。入口为 `OrmTemplateImpl.java:441/446/451`，服务 `findListByQuery`、`IEntityDao.selectFieldsByQuery`、sql-lib `<query>`、xlib `DoFindListByMdxQuery`。`nop-code` 有 11 处生产调用点。唯一测试 `TestMdxQuery`（nop-auth，5 例）全部走 ORM 关联属性路径，**从未覆盖 `QueryBean.joins` 显式 JOIN 路径**。

**第一批（3 个 Blocker）**

- **B1 `getSubQuery(QuerySourceBean)` 维度字段从不回写**：原代码 `setDimFields(source.getDimFields())` 后又用局部变量算出回落 dimFields 喂给 `addDimFields`，bean 里始终是 `null`，`split()` 的 `dimFieldsMatch` 随即拿 `null` 比对主表维度，必抛 `nop.err.orm.dim-fields-mismatch` → 未显式声明 dimFields 的显式 JOIN 100% 失败。改为同一个值同时驱动 `addDimFields` 与 `setDimFields`。
- **B2 `QuerySourceBean.getConditions()` 全仓零消费者**：`QueryBean.addJoin` 在 `query.dimFields` 未预设时（常态）走 conditions 分支，等于把 `leftJoin/rightJoin/innerJoin` 声明的关联键整个丢弃。新增 `resolveSubDimFields`，conditions 分支按**主表维度顺序**（而非声明顺序）取配对 `rightField`。`leftJoin("Sub","d","deptId","dept_id")` 这条公开 API 从此可用。
- **B4 `getMainQuery` 属性拷贝不完整**：14 个属性只拷 7 个，`distinct`/`leftJoinProps`/`disableLogicalDelete`/`name` 全丢。实测 `select distinct o.deptName ... left join o.parent` → `select o.deptName,o.deptId`。**线上影响**：`SysDaoNamingService.java:139` `getServices()` 依赖 `SELECT DISTINCT` 去重服务名。
- **B1 附带发现的缺口**：`getNonAggFields` 回落对「子表字段全是聚合字段」返回空 → 无维度可用。改为抛 `nop.err.orm.query-no-dim-fields`（已存在、语义准确、无需新增 i18n），而非原先误导性的「维度个数不匹配」。

**第二批（其余确认成立的缺陷）**

- **M5 关联属性子表维度顺序错位**：`getSubQuery(alias,...)` 中 `mainQuery.getDimFields().indexOf(join.getLeftProp())` 算出的 `idx` 被丢弃，子表维度按 `rel.getJoin()` 顺序追加。`rel.getJoin()` 会被重排为**关联目标实体**的主键顺序（`OrmModelInitializer.java:473-485`），主表维度默认是**本实体**主键顺序，两者不一致时位置键对不上，子表数据全部静默丢失（只打 `nop.orm.mdx-sub-query-row-not-match` 日志，不抛异常）。改为 `dimFields.set(idx, rightProp)` 逐位定位。
- **M2 主/子表 label 碰撞静默覆盖**：主表和子表字段写入同一个 `Map<String,Object>`，而 `QueryFieldBean.getLabel()` 不含 owner。`mainField("deptName")` 与 `subField("d","deptName")` label 都是 `deptName`；`.count()` 两侧都是 `count(x)`。子表值覆盖主表值且无任何提示。新增 `ERR_ORM_QUERY_DUPLICATE_FIELD_LABEL`，在 `splitFields` 阶段检测并报错（alias 可消除）。**未改 `QueryFieldBean.getLabel()` 加 owner 前缀**——那是 nop-api-core 公共 API 且属破坏性变更（改变结果 map 的 key）。
- **M1 主表重复维度值被吞**：`agg==false` 时 `getMainQuery` 不加 GROUP BY，`dimFields` 不唯一则多行共享同一维度键，而 `dimIndex.put()` 无条件覆盖 → 子表值只回填到最后一行，其余行子字段静默为空。`dimIndex` 改为 `Map<维度值, List<行>>`，回填到所有匹配行。
- **M3 NULL 维度值污染 SQL**：维度键原先把 NULL 转成 `""`，再塞进过滤条件。数值列会直接报错（`in ('')` 对 bigint 是 `invalid input syntax`）；字符列则永远匹配不到 NULL；而复合维度分支的 `eq(col, "")` 又会被 `StringHelper.isEmptyObject` 改写成 `is null` —— **同一语义在两条分支上行为相反**。改为 `buildDimValue` 保留 `null`，`buildDimFilter` 用 `isNull` 表达，两条分支一致。
- **M4 IN 列表撞硬上限**：维度过滤按主表行数展开，`SQL.spreadParams` 在超过 `nop.core.sql.in-list-max-size`（默认 1000）时全局拦截抛 `nop.err.sql.in-list-too-large`，且此时主查询已执行完、结果被丢弃。改为按上限切片后 `OR` 合并。同时主表结果为空时跳过全部子查询。
- **m2 调用方 `QueryBean` 被就地改写**：`getMainQuery` 透传 `groupBy` 引用，而 `addGroupField` 会就地 append（实测调用方 `[deptType]` 变成 `[deptType, deptName]`）；`split()` 回写 `sourceName`；`findFirst` 把 `limit` 永久改成 1。分别改为复制列表 / 局部变量 / `query.cloneInstance()`。
- **m1 `expression`/`formula`/`aggregates` 静默忽略**：这三个属性在 MDX 通道无任何消费方，SQL 里也不出现。新增 `ERR_ORM_QUERY_UNSUPPORTED_FIELD_ATTR` 显式报错。
- **m3 `query.fields == null` NPE**：`splitFields` 与 `newDataSetMeta` 直接遍历 `getFields()`。改用 `CollectionHelper.toNotNull`。sql-lib `<query>` 不写 `<fields>` 可达。
- **死代码**：`splitFields` 中从未被读取的 `map` 局部变量已删除。

**审计中被证伪的一条（重要）**

独立审计子 agent 断言「`o.<refPropName>.<dimField>` 属性路径只在 EQL 编译器中存在，本通道不会展开，会产出 `Unknown column`」。实测证伪：在 `getSubQuery` 里据此加的「未覆盖维度字段直接抛 mismatch」把 `TestMdxQuery.testAggMainField2` 打成失败。抓取实际执行 SQL 显示 `DaoQueryHelper` 产出的 `select count(o.deptId),o.group.name from NopAuthGroupDept as o group by o.group.name` 会被 **EQL 编译器改写成** `select count(o.DEPT_ID) as c1, t1.NAME as c2 from NOP_AUTH_GROUP_DEPT as o join NOP_AUTH_GROUP as t1 on (o.GROUP_ID = t1.GROUP_ID) and (t1.DEL_FLAG = 0) group by t1.NAME`。即属性路径展开是这条通道的既有能力，合成逻辑是有意设计。已回退该处改动，**只保留按主表下标定位的顺序修复**（M5 仍然成立且与此无关）。
