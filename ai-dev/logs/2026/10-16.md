### 修复编译与单元测试：3 处竞态型 flaky + 1 处失效依赖（nop-cli-core VFS 冲突）

- **起点**：`git status` 干净（HEAD `f1b1ab1`），`./mvnw clean install -DskipTests -T 1C` 退出 0——**编译本身无问题**；红的是 `./mvnw test -T 1C`。按"修一项重跑全量"迭代，暴露 4 个独立根因（后 3 个因前一个修好后模块不再被 fail-fast 跳过才显形）。
- **根因 1（flaky，快 profile 断路器）**：`nop-lint-graphql` 的 `TestNopLintBizModel` 两处正向断言跑的是**未过滤的全库**（59 条 java 规则）。fast profile 每文件软预算仅 20ms（`LintProfile.FAST_FILE_BUDGET_MS`），pattern stage 单独超预算即触发 `RuleSetRunner` 断路器，按加载顺序（`RuleSetLoader.scanPaths` 对完整 VFS 路径字典序）中止其后所有规则——`exception/no-raw-exception.rule.yml` 排在 `antipattern/*` 之后，于是 `total()` 归 0。失败运行日志实证：`nop.lint.budget.breaker:ruleId=antipattern/print-stack-trace,patternNanos=25532249`。修法：把两处正向断言改为**钉住单条规则**（`List.of("nop/no-raw-exception")`）——断路器是 design 11 §5 的既定降级面，不是可断言的不变量；`ruleWhitelistNarrowsTheDiagnostics` 改为 0（`no-empty-catch`）vs ≥1（`no-raw-exception`）的对照，收窄主张反而更强。
- **根因 2（flaky，脚本真实时钟预算）**：`nop-lint-core` 的 `TestBudgetDegradeLadder.fastSliceExhaustionSkipsScriptsAndReportsPatternLayer` 的时钟程序把 match 1 的 slice 读数编成 `t0+9ms`，而 `xscriptBudgetMs()` 在 fast 下还会再 `min(剩余 slice)`，于是脚本被**意外夹到 1ms 真实时钟预算**（日志实证 `budgetMs=1`）。脚本内 deadline 按 plan R2 Minor C 刻意走 `System.nanoTime()`，满载时首次执行（含类加载）必然超时 → 该 match 被当非匹配、丢掉自己的 diagnostic，`diagnostics.size()` 从 2 变 1。修法：match 1 读到整段 slice（10ms，符合注释本意），并把断言从"下标定位"改为**按 message 定位被跳过 match 的 pattern-layer 结果**（skip 路径无条件上报，是该测真正要钉的那一半），补 `executed + skipped == 2` 的两 match 分流断言，不再断言依赖真实时钟的 match 1 结果。
- **根因 3（真缺陷，非竞态）**：`nop-cli-core` 全部 10 个测试（`io.nop.cli.*` / `io.nop.converter.*`）报 `nop.err.core.resource.duplicate-vfs-resource`，路径 `/nop/ai/prompts/advisor/long-term-memory.prompt.yaml`。查因：commit `5567495220`（2026-10-13 12:22，WI17 nop-ai-skills 拉平）把 deepwiki/translate 的 prompt 资源迁进 `nop-ai-core` 并解散该模块、移除 bom 条目，但 `nop-runner/nop-cli-core/pom.xml` 与 `nop-bom/pom.xml` 里 `nop-ai-translate` 两处残留未清。`~/.m2` 中该 jar 建于迁移**之前**（10-13 08:04），仍带同一批 `_vfs` 路径，两 jar 撞路径即 fail-closed。该 jar **零 class**（纯资源包），不可能被代码依赖。按用户裁定移除这两处失效依赖（cli-core 依赖 + bom 条目），注释记因由。
- **根因 4（flaky，调度器基线采样）**：`nop-job-local` 的 `TestLocalJobScheduler.testFireNow` `expected 1 but was 2`。原代码用 `awaitIdle`（只判 `running == null`）取基线，但首次触发是 `now+1ms` 排程的，尚未进入执行时 `awaitIdle` 立即返回、基线采到 0，满载下那次迟到的自动触发落地后多出一次调用。修法：改按触发次数等（`awaitFireCount(..., 1, 2s)`，其 `fireCount` 在 `handleResult` 中与 `running=null` 同临界区自增）再 `awaitIdle`，并新增 `assertEquals(1, baseline)` 钉住"自动触发是 fireNow 前唯一一次调用"。
