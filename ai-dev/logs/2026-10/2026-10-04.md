### nop-orm / EQL 能力盘点与边界裁定

- **性质**：ad-hoc 分析 + 决策记录，无 plan（分析结论本身不产生代码改动）。
- **做了什么**：对 `nop-persistence/nop-orm`、`nop-orm-eql`、`nop-dao` 做能力盘点，逐条读 live code 核实"功能缺失"类判断，产出两份文档：
  - `ai-dev/design/nop-orm-scope-and-non-goals.md`（新）——裁定**不实现**的能力：对象继承映射、二级表、隐式 m2m 连接表、Savepoint、ORM 层 PS 缓冲、XA/2PC、Criteria API。核心理由：nop-orm 实体形态在编译期由 codegen 完全确定（无字节码增强、无代理），L1 身份键 `(entityName, id)` 依赖这一确定性；继承映射需要运行期决定实体真实类型，与该约束正面冲突。m2m 关联表本质是普通实体，显式建模后可复用字典/租户/逻辑删除/审计/数据权限/审批/GraphQL 全套平台能力。
  - `ai-dev/plans/2307-eql-live-defect-and-dead-surface-remediation.md`（新，draft）——收敛已核实的 EQL live defect 与死表面。
- **关键事实（LATERAL）**：`SqlSubqueryTableSource.lateral` 被解析且影响语义分析（`compile/EqlTransformVisitor.java:601-608` 放宽作用域），但两个输出器都不打印 `LATERAL`（`sql/AstToEqlGenerator.java:666-673`）→ 编译出缺少关键字的 SQL。这是本轮最实质的正确性缺陷。
- **关键事实（集合 flush）**：`JdbcCollectionPersistDriver.flushCollectionChange` 空方法体是**设计意图**（集合成员增删由 `CascadeFlusher` 级联保存子实体表达），但"子实体无指向 owner 的反向外键属性"时无任何诊断信号，属 Plan 2307 Phase 5 的显式失败改造项，不是缺陷。
- **纠错记录**：初判"事务隔离级别未实现"经复核**成立**——`ITransactionTemplate` / `ITransaction` 均无隔离级别 API，全仓无 `Connection#setTransactionIsolation` 调用；已在 design 文档登记为 G1 gap（非 non-goal）。初判"`NOT EXISTS` 不可用"经复核**不成立**——该语义经通用 `NOT` 前缀可达，且 NOT 优先级已在 plan 2257 修正并有回归测试。
- **纠错记录（第二轮，用户指出）**：初判把"二级表"整条列为 non-goal 是**错的**——nop-orm 的 **alias 机制**已承担该职责：`<alias propPath>` 支持三种形态（关联表列投影 / `kvTable="true"` 纵表扩展属性表 / 组件内路径），且经 `internalGetAliasValue/internalSetAliasValue` → `BeanTool.getComplexProperty/setComplexProperty` 确认**整条属性路径可读可写**（初稿误标为"只读"）。`kvTable` 机制可把**任意**既有纵表（含历史系统属性表）按 owner key 反转成横表类型化属性，并获得类型化读写、`batchLoadProps` 批量预取、租户与审计能力——覆盖面强于 JPA `@SecondaryTable`（后者要求扩展表由框架设计）。design 文档的准确表述改为"不实现 **JPA 形态的**二级表"，理由收窄为"字段到表的映射不得在运行期才决定"。
- **顺带修掉的 owner-doc bug**：`docs-for-ai/` 此前**完全没有** alias / `kvTable` 扩展属性机制的文档（只有 `cross-module-entity-reference.md` 顺带提到 `<alias notGenCode>`），而该机制在 `nop-sys`、`nop-wf`、`nop-dyn` 均已使用。已在 `orm-model-design.md` 新增"跨表属性：alias 与扩展属性表（`kvTable`）"一节，含"在 EQL 中使用 alias"小节。
- **补记（第三轮，用户指出）**：alias 在 **EQL 语法中同样可用**——`EqlTransformVisitor.resolveColName` 在真实字段查找失败后回落到 `model.getAliasPropPath(name)`（`compile/EqlTransformVisitor.java:1441-1466`），再交给与手写属性路径**完全相同**的 `resolvePropPath` 隐式 JOIN 逻辑（`:799`），因此 `o.collegeName` 与 `o.simsCollege.collegeName` 编译产物等价；`TestEqlExtFields` 已覆盖纵表 alias 在投影/算术表达式/WHERE/ORDER BY 中的用法。约束：`OrmEntityModel.getAliasPropPath` 仅接受 `IEntityAliasModel`，故 `<compute>` 属性不能当列名用于 EQL。测试覆盖缺口（关联表投影 alias 在 EQL 中无 focused 测试）已登记为 plan 2307 的 non-blocking follow-up——两条路径共用同一段代码，无独立实现分支。

### Plan 2307 对抗性审查后重写

- **性质**：计划审查闭环（两轮独立子 agent，可执行性审查 `ses_efb32c9a4ffeoYsOshkYeIboKC` +逐条事实核查 `ses_efb32c998ffeOweifjfbOuzIjc`）。
- **结果**：初版Current Baseline 的 11 条 defect 中**5 条被证伪、3 条需修正、2 条部分成立**。计划已整体重写，编号体系 D1–D11 换成 V1–V9（仅保留经核验成立者），并新增 Phase 0（生成链路与回归基线固化）、Phase 7（owner doc 语法清单表格化）。
- **被证伪的断言（我写错的）**：
  - 「递归 CTE 因 `SELECT *` 锚点 CCE」——裸 `*` 是 `selectAll` 标志且已在 `EqlTransformVisitor.java:300-308` 展开；链式 UNION 已由 `SqlUnionSelect.java:30-32` 的 `getProjections()` override 处理。两条均不可达。
  - 「`SqlExistsExpr.not` 是死字段」——**错**，`CollectionOperatorTransformer.java:430` 有 `setNot(true)`（`_none` → NOT EXISTS 降级），是活字段。这是我连续第二轮对外表述中的错误。
  - 「`IJdbcTemplate.exists*` 全部抛异常是live defect」——接口default 确实抛，但 `JdbcTemplateImpl.java:469-540` 五个全部 `@Override` 且为真实现（方言模板优先 + `DatabaseMetaData` 回落）。降级为契约清理。
  - 「子实体无 refProp 时集合变更无 SQL」——`OrmEntitySet.java:496-501,156-161` 回落 `bindOwnerProps` 按 `<join>` 写 FK，移除走 orphan 判定 → DELETE。
  - 「`CROSS JOIN` 缺失不构成缺口」——方向对但危害被低估：实测 `select 1 from a cross join b` **解析成功**并输出 `from a as cross join b`（`cross` 被吃成别名），是静默错误输出而非语法拒绝。升级为 V2。
- **修正后的真实缺陷**：V1 LATERAL 解析但不输出（最实）；V2 CROSS JOIN 静默误解析为别名；V3 `SqlCollectionAccessExpr` 无printer 且主节点都不输出（实测 `where coll[x > 1].count() > 2` → `where collx > 1 > 2`）；V4 `SqlCommit/Rollback` 编译产物为空串；V5 `nullsFirst` printer 悬挂字段（`collate` 是纯死字段，两个输出器都不打印）；V6 三处未判空无条件强转（`AstToSqlGenerator:546`、`EqlCompiler:93-99`、`SqlSelect:70-71`）；V7 `ICollectionPersistDriver.flushCollectionChange` 整个接口方法零调用点；V8 `<upsertHandler>` 无消费方；V9 `NATURAL`/`USING` 零引用死 token（`CROSS` 的非保留字登记是有意设计，且 `mysql.dialect.xml:23` 已列入保留字表，不可移除）。
- **移出本计划**：`EqlASTOptimizer/Processor` 死表面——删除文件无效（`//__XGEN_FORCE_OVERRIDE__` 每次构建覆盖），须改 `nop-kernel/nop-codegen` ast 模板，该模板同时服务 XLang，属跨模块 codegen 变更，按 AGENTS.md Protected Areas 需独立 plan。
- **补上的初版缺失**：生成链路（g4/AST 模型 → 再生成产物 → `./mvnw install -pl nop-persistence/nop-orm-eql -DskipTests`）、2256 已固化的跨模块回归清单（初版只列 3 个 persistence 模块，漏 4 个下游消费模块）、Minimum Rules #22/#23/#24 的 Exit Criteria 条目、`check-plan-checklist` 与 import 顺序门槛、初版两条**不可满足**的 Exit Criteria（"所有 AST 节点都有printer" 不可满足——`SqlProgram`/`SqlColumnName`/`SqlAlias` 等设计上就没有 printer）。
