### 2026-07-25（Plan async-snapshot-pipeline 异步两阶段 Snapshot Pipeline）

- Plan `2026-07-25-2200-1-async-snapshot-pipeline` 完成：把 coordinator 侧 checkpoint 持久化（`storeCheckPoint` + `storeEpochManifest`）从 ACK 线程同步执行卸载到专用 persist executor，ACK 线程提交后立即返回，存储 I/O 不再阻塞 abort/timeout/trigger bookkeeping。收口 G30/G44，为 Stage 19 多并发 checkpoint 建立 async-persist 前置。
- 改动范围：
  - `CheckpointConfig` 新增 `asyncSnapshotEnabled`（默认 true）+ `asyncSnapshotThreadPoolSize`（默认 1）。
  - `CheckpointCoordinator.completePendingCheckpoint` 重构为三段模型：段 1（ACK 线程持锁，CAS + 构建不可变快照 + 提交 persist task）→ 段 2（persist executor 线程不持锁，storeCheckPoint + storeEpochManifest）→ 段 3a/3b（persist executor 线程重新获取 monitor，成功走 forceComplete/DURABLE→commit，失败走 FAILED+finishCommit(false)）。`asyncSnapshotEnabled=false` 时保留改造前同步行为（段 1+2+3a 全在 synchronized 方法内）。
  - N1：`acknowledgeTask` 入口加 status guard，async 窗口期间重复 ACK 返回 false（对齐 sync 语义）。N2：persist executor 懒创建（不绑 startCheckpointScheduler/stopCheckpointScheduler 可重启周期），仅在终态 `shutdown()` 关闭。N3：`shutdown()` 中 persist executor `awaitTermination(5s)` 对齐 trigger scheduler 纪律。
- 关键不变量保持：§12 不变量 5（manifest durable 前不 commit）—— `notifyParticipantsFinishCommit(true)` 在 `forceComplete`(DURABLE) 之后；§13.2 触发线程安全 —— 段 3a/3b 重新获取 monitor，`decrementPendingCheckpointCount` 与 `tryTriggerPendingCheckpoint` 的并发数检查仍同在 monitor 内。
- 诚实声明收益边界：当前 task 侧仅支持单 checkpoint 对齐，本 plan 解除的是「coordinator ACK 线程被存储 I/O 阻塞」；「checkpoint N+1 trigger 在 N 完成前即可生效」需 Stage 19。
