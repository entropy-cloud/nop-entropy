# 2026-08-17

### 2026-08-17（bridgic-amphibious 0.2.0 重构分析 + nop-ai-agent 深度对比）

- **做了什么**：
  - **bridgic-amphibious 0.2.0 重构梳理**：8 月 4 日 release 的核心改动是 "多 framework-owned context 类 + 大量隐式字段" → **OTAContext（small-loop，framework-owned）+ Context（big-loop，free-form）双段不变式**（commit `fe5af6c refactor(amphibious): rebuild the cognitive layer on the OTA context model` + `14c2dd1` + `6c356e2`）；同步集成 LiteLLM（commit `b6a2244`）。本次分析在 `agent-survey/` 目录下新建（**此前对 bridgic 无任何调研记录**）。
  - **架构核心点定位**：
    - **OTAContext 双段不变式**：framework-owned OTAContext 携带 `user_input + ota_record + tools`，自由 Context 仅 fields + overridable summary。`OTAContext.tool` 类装饰器显式声明工具，subclass 通过 `__init_subclass__` 继承，**框架不自动注入任何工具**。
    - **OTARecord `extra="allow"`**：per-round 折叠模式，`obs_result/think_result/action_result` setter 写到最新 record；hook 可向当前 record 折叠自定义字段（如 `permission_result`），无需子类化。
    - **AmphibiousFSM** (`_AmphiState`)：显式 FSM dataclass 字段（workflow_gen / agent_gen / scope / agent_mode_stack / consecutive_failures / step_index）；`yield ActionCall/HumanCall/LLMCall/EnterAgent/ThinkUnit/ThinkAgent/RETURN` 七种协作原语；scope rules 在 `_dispatch_step` 中验证；`AMPHIFLOW` 模式 = workflow-first + step-level fallback（bounded 内联 recovery sub-run + `_shape_fallback_value` 把恢复结果 mapped 成失败 step 返回类型）+ full fallback（连续失败超阈值时关闭 workflow_gen 全切 agent）。
    - **CognitiveWorker / AgentWorker 对称 peer**：内进程思考（持有 BaseLlm，对话 `BaseLlm.aselect_tool/achat/astructured_output/astream` 四协议） vs 外部 CLI 委派（持有 `BaseAgent` = ClaudeCodeAgent / CodexAgent + in-process FastMCP HTTP host 桥接项目工具）；统一 ThinkResult `{step_content, tool_calls}` 数据契约，`tool_calls` 为空即为 finish（无显式 finish flag）；对称 override hook：`observation / thinking / before_action / after_action` + `_DELEGATE` sentinel。
    - **`_DELEGATE` sentinel**：Worker hook 返回它 = 转交 agent 层 hook；返回具体值 = 覆盖。
    - **`agent_done` MCP signal tool**（in-process FastMCP host 暴露）：外部 CLI 必须调用一次触发 `done_signal` 完成事件；race against process exit / timeout；stdout/stderr 内容丢弃（只有 MCP 调用能出数据）。
    - **`_run_think_agent` fresh-instance 隔离**：每次 ThinkAgent 都新建 OTAContext 实例（sub_goal = item.goal or parent.ota_ctx.user_input；tools = `_filter_tools(parent_ota.tools, expose_tools)` 构造期 narrowing）+ 创建 `decision_channel: asyncio.Queue` + consumer task 跑 `_run_action_call` against fresh sub-context + `_DELEGATION_DONE` sentinel 关闭 consumer。父 OTAContext 永不 mutate。
  - **与 nop-ai-agent 当前设计的对比要点**：
    - **循环模型**：bridgic yield-driven coroutine FSM（`_AmphiState` 显式 FSM）vs nop `ReActAgentExecutor` while 双层（reactLoop + sustainLoop）。**核心差异**：bridgic 把"模式切换 + 恢复"统一到一个 FSM；nop 把这些分散到 lifecycle hooks + sustainer + reliability 子系统。
    - **Context 模型**：bridgic 双段不变式（OTAContext 4 字段 + Context 用户态；OTARecord `extra="allow"`）vs nop `AgentExecutionContext` ~25 字段（用户态与框架态混合）。**对 nop 的最直接可借鉴点**。
    - **Sub-agent 委派**：bridgic 提供"内 LLM 思考（CognitiveWorker）+ 外 CLI 委派（AgentWorker）"对称 peer；nop call-agent 仅同进程 fork session。
    - **错误恢复**：bridgic step-level fallback + full fallback + cycle safety bound（简单 ~100 行 _amphiflow）vs nop 显式容错栈（重试 + 熔断 + 三通道故障转移 + checkpoint journal + 60s 守护 + DB 接管锁）。**复杂度差异**：bridgic 框架级 fallback；nop 运维级 reliability。
    - **DSL**：bridgic ASL（Python-native 装饰器 + TrackingNamespace）vs nop XLang + agent.xdef + plan.xdef。两者不在同一抽象层。
    - **HITL**：bridgic `@human_channel` 类装饰器（多通道）+ `HumanCall` yield + 内置 `request_human_tool`（任何 OTAContext 均可声明）vs nop 无显式 HITL（仅 steering queue + skill hooks）。
  - **对 nop-ai-agent 的可借鉴点（P0/P1/P2 分级）**：
    - **P0 拆分 AgentExecutionContext**：把 framework-owned vs user-owned 二分；引入 OTARecord 等价物 + `extra="allow"` 模式。
    - **P0 AmphibiousFSM 的 step-level fallback + EnterAgent 模式切换原语**：先实现 step-level fallback（与现有 IToolCallRepairer + LlmCallCoordinator 分工需明确），全 fallback + mode switch 为 successor。
    - **P1 CognitiveWorker / AgentWorker 对称 peer 抽象**：抽取 `ICognitiveWorker` 接口（现有 ReActAgentExecutor 迁移为 `DefaultCognitiveWorker`）；预留 `IAgentWorker`（未来 sub-CLI-agent 用）。
    - **P2 OTAContext.tool 显式声明**：引入 `ToolSlot` 抽象替代 `@Tool` 反射扫描（与现有 IToolManager 兼容）。
    - **P3 agent_done MCP signal 模式**：仅在将来需要 sub-CLI-agent 时参考。
  - **不可借鉴 / 价值有限的点**：Python yield-driven FSM 协作接口（Java 没有原生等价物）、In-process MCP host（nop 不需要出进程）、ASL（不同抽象层）、OTARecord fold-on-write setter API（Java setter 更显式可读性反而下降）、AgentTrace workdir 持久化（nop checkpoint journal 已更强）。

### 2026-08-17（同日二次 review：HITL oracle backend 修正）

- **做了什么**：
  - 用户指出"HITL 不是有 ask-oracle 工具吗？人不是一个高智能体吗？ask-oracle 的形式下直接接入 human channel 不行吗"——这个观察完全正确，**我前面的 §6.1.7 建议方向是错的**。
  - **原错误方向**：建议加 `@human_channel` 类装饰器 + `HumanCall` yield 原语 + 内置 `request_human_tool`，等于在已有完美形态 `ask-oracle` 旁边**再造一个并行的 HITL 机制**。

  - **具体实现**：
    1. 引入 `IOracleBackend` SPI（`CompletionStage<String> ask(question, options, timeoutMs)`）
    2. 已实现 `AiAgentOracleBackend`（当前占位 stub）+ `NoOpOracleBackend` shipped 默认（与 P2-MA1-011 fast-fail 一致）
    3. future：`HumanChannelOracleBackend` / `SlackOracleBackend` / `FeishuOracleBackend`
    4. `ORACLE_CHANNEL` 环境变量决定 backend
    5. 与 `skill` 工具协同：`skill(action="list")` 列出可用 oracle backend 描述
  - **与 steering queue 语义区分**：steering = 任意外部 message 注入主消息流（plan 220）；ask-oracle HITL = 决策点暂停 + 等特定形式回复。互补不互斥。
