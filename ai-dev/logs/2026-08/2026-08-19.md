### 2026-08-19（nop-job REST Worker：异步执行 + 进度查询 + 日志上报补充分析）

- **做了什么**：用户指出同步 RPC 超时无法支撑长任务，要求异步执行 + 进度查询 + 日志上报，整体补充分析并更新对比报告：
  - **异步模型确立**：HTTP RPC 读超时是硬约束，长任务必须"启动即返回句柄 + 轮询进度"。`RemoteDispatchScanner` 改为两段式：认领段（WAITING remote 任务 → RUNNING → `startJob` 立即返回）＋轮询段（`fetchRunningTasks` 按分区游标轮询 `getJobStatus`，终态写回）。**远程任务句柄 = DB task 的 jobTaskId（零映射）**；轮询责任按分区隔离、无 in-memory 状态，崩溃后 TimeoutChecker worker-liveness 链兜底。
  - **`TaskStatusBean` 采用**（`nop-kernel/nop-api-core/.../beans/task/TaskStatusBean.java`）：平台级异步任务状态契约（RUNNING/SUCCESS/FAILURE/CANCELLED/TIMEOUT/NOT_FOUND + error + details），直接作为 `getJobStatus` 返回类型，details 承载中间进度，建立了与 nop-job task-status 的固定映射表。
  - **对方案 B 的修正**：`RpcJobInvoker` 的同步 `invokeAsync` 语义与异步模型不兼容，不改造/不下沉（DB 模式继续用），改新建 `IRemoteTaskClient`（start/status/cancel）——"复用平台 RPC 通道"结论不变，复用对象调整为 `IRpcServiceInvoker` + `ApiRequest`/`TaskStatusBean` 契约。
  - **日志上报**：平台无任务执行日志设施（nop-sys 仅 NopSysChangeLog）。设计：coordinator 开放 `NopJobTaskLogBizModel.reportTaskLog` 批量端点 + 新表 `nop_job_task_log`（ORM 变更标注 plan-first）；worker 上报地址零配置——`startJob` 请求头下发 `nop-log-report-url`；worker 侧轻量 client + 可选 logback appender；上报失败不影响任务执行。

### 2026-08-19（nop-job REST Worker 模式设计草案）

- **做了什么**：调研并设计了 nop-job 第三种 worker 模式（REST 模式）——worker 零数据库依赖、只暴露 REST 服务，coordinator 照常写 DB，新增 RemoteDispatchScanner 扫描 DB 中已归因任务并通过 HTTP 远程调用分派。与现有 DB 扫描模式并存（`workerInstanceId` 归因 + `fire.dispatchMode=remote` 双条件隔离）。
  - 分析了 `~/sources/PowerJob`（心跳注册 + server push + TaskTracker 自治）与 `~/sources/snail-job`（client 内置 gRPC server + server push + 结果回调）的 worker 接收任务模式（两个 explore subagent 报告），吸收结论：复用 nop-job 既有 `IDiscoveryClient` 服务发现而非引入心跳协议；同步请求-响应而非异步回调；不引入 gRPC/消息队列。
  - 关键架构决策：新增模块 `nop-job-worker-rest`（依赖仅 nop-job-api + nop-biz，不含 nop-job-dao，从依赖层面保证零数据库）；coordinator 侧不新增模块（RemoteJobTaskBuilder + RemoteDispatchScanner + IRemoteWorkerClient 放入 nop-job-coordinator，新增 nop-http-api 依赖）；新增 `JobTaskRequest` DTO（nop-job-api）；错误语义复用现有三层超时模型（连接失败→FAILED 显式失败，HTTP 超时→留 RUNNING 由 TimeoutChecker 回收）。
