## Verified controls

1. **Permission context propagation (no escalation)**: a task flow started from a
   `@BizMutation` runs under the caller's `IServiceContext` — `TaskFlowManagerImpl.newTaskRuntime`
   (L92-101) passes `svcCtx` into `TaskRuntimeImpl` (L60-82), which exposes it as
   `VAR_SVC_CTX` in the eval scope and to every `ITaskStepRuntime`. Steps that follow the
   documented pattern (`stepRt.getServiceContext()` → `I*Biz` calls) are subject to the
   original caller's identity in downstream auth checks. Job/scheduler-driven executions
   pass `svcCtx=null` → system context (`ContextProvider.getOrCreateContext()`), i.e. no
   spoofed user identity is invented. Cancel propagation parent→child runtime verified
   (L150-159).
2. **Step input validation**: mandatory inputs are enforced at binding time
   (`TaskStepExecution` — `ERR_TASK_MANDATORY_INPUT_NOT_ALLOW_EMPTY`); per-input
   `<schema>` (schema.xdef ref) and per-step `<validator>` (`ValidatorTaskStepWrapper`)
   are supported; GraphQL-side args generated from task `<input>` definitions carry
   types/mandatory into the API layer (xbiz binding per owner doc).
3. **Retry semantics bounded**: `RetryTaskStepWrapper` delegates to nop-retry
   `IRetryPolicy` (declarative, bounded); no unbounded or self-amplifying retry loop in
   the executor wrappers. Async wrapper `ExecutorTaskStepWrapper` enforces the
   cancel/timeout termination invariant (spotbugs style hit on unused `whenComplete`
   return dispositioned — completion is handled by the inner lambdas, no state loss).
4. **No log-side secret exposure from the engine**: the `dump` attribute on
   `<input>`/`<output>` is parsed but has no consumer — the task engine itself never logs
   step input/output values (fails safe; see F-WF-02-3 note).
5. **Trust boundary is config, not user input**: step bodies (`<invoke bean method>`,
   `<script>`, `customType` xlib tags, XPL `<source>`) can invoke arbitrary container
   beans/code, but only from `*.task.xml` models loaded from VFS; runtime request data
   only fills declared input variables. No path was found where request-controlled
   strings are re-parsed as code (inputs bind via `IEvalAction` expressions defined in
   the model, evaluated against scope values).

## Explicit no-finding statements

- No permission escalation in step execution: task runtime propagates the caller's
  service context; steps cannot elevate identity (no API on `ITaskStepRuntime` mints a
  user context).
- No user-controlled code injection into the executor layer: bean names, method names and
  scripts come exclusively from the (config-trust) task model, not from request data.
- Input mandatory/type validation is enforced before step body execution; unbound
  mandatory inputs fail with `ERR_TASK_MANDATORY_INPUT_NOT_ALLOW_EMPTY`.
- QA static analysis (existing target reports, parsed only): checkstyle 17 style
  warnings, pmd 0, spotbugs 1 STYLE finding (ExecutorTaskStepWrapper:40) — none
  security-relevant. No QA reports exist for nop-wf/nop-job (gap recorded for main session).
- Secret sweep clean: only empty datasource `password:` placeholder in demo
  `nop-task/nop-task-app/.../application.yaml:28`; zero `@cfg:` secrets in module Java.
