## Verified defenses on the request-facing path

1. **Field-name whitelist before interpolation**:
   `FilterBeanToSQLTransformer.visitCompareOp` (nop-kernel/nop-core,
   FilterBeanToSQLTransformer.java:84-95) validates `owner`, `name`, AND `valueName`
   via `validateVarName` → `StringHelper.isValidPropPath`
   (Java-identifier-start + Java-identifier-part + single dots —
   StringHelper.java:1999-2012) BEFORE any `.append(name)`/`.sql(name)` interpolation
   (L100-168). SQL metacharacters (space, quote, semicolon, parenthesis, `=`)
   cannot pass the validator.
2. **All callers enable validation**: every main-code construction passes
   `checkVarName=true` (DaoQueryHelper.java:210, FilterSqlHelper.java:27; default
   constructors also default true — FilterBeanToSQLTransformer.java:66-71).
3. **Values are parameterized**: filter values go through `.param(...)` /
   `eqEx/gt/lt/in` builder methods (marker-based parameter rendering), never string
   concatenation. LIKE wildcards are added around the parameter, not by splicing
   user text into SQL text (L160-168).
4. **QueryBean → SQL is whitelist-guarded end to end**: `DaoQueryHelper`
   enforces `checkFieldName` (isValidPropPath), `checkOwnerName`
   (isValidSimpleVarName), `checkFuncName` (isValidSimpleVarName) on fields,
   group-by, order-by, and aggregate function names
   (DaoQueryHelper.java:102-118, 165-176, 191-243). Source names/entities come from
   `query.getSourceName()` resolved against entity model space.
5. **SQL builder separates identifiers from values structurally**:
   `SQL.SqlBuilder` (nop-kernel/nop-core/lang/sql/SQL.java:204+) extends the
   marked-string builder; `param()` (L421) creates value markers rendered as `?`
   with bound parameters at execution; dialects `unescapeSQLName` for table names
   during generation (GenSqlHelper.java:610-616).
6. **EQL compile-time identifier resolution**: EQL compiles entity/prop references
   against the ORM entity model (typed AST, SqlColumnName construction) — expression
   identifiers cannot introduce arbitrary SQL text.

## Findings

| ID | Severity | Anchor | Description | Remediation suggestion |
|---|---|---|---|---|
| F-C4-1 | LOW | FilterBeanToSQLTransformer.java:60-64, 78-81; SQL.java SqlBuilder `append`/`sql` methods | Field-name validation lives in the transformer (caller-side, `checkVarName` constructor flag) rather than at the render boundary: `SqlBuilder.append(name)`/`.sql(name)` interpolate whatever they receive. | F-C4-2 | LOW (owner-doc drift) | docs-for-ai/02-core-guides/tenant-model.md:84 | The guide's illustrative comment `// dao().executeNativeSql("...")` uses a **fictional API name** — no such method exists anywhere in the codebase (real entry points: `IOrmSession.executeUpdate/executeQuery/executeStatement(SQL)`). The doc's semantic claim (native SQL bypasses EQL compile-time filtering) is accurate; only the example name is wrong. This drift already misled one audit plan draft into anchoring a sweep on the nonexistent method (caught in adversarial review). | Phase 3 doc fix: replace the pseudocode name with the real `IOrmSession` API in tenant-model.md. Recorded as owner-doc drift per plan rules (not silently edited during the audit phase). |

## Explicit no-finding statements

- No SQL injection path found on the request-facing QueryBean/FilterBean transform
  (validated identifiers + parameterized values, verified at source level).
- No raw string concatenation of user input into executable SQL found in the three
  module groups (all concatenation sites are metadata/constants/config-trust).
- `executeNativeSql` does not exist as an API (documentation pseudocode,
  tenant-model.md:84) — sweep anchored on real entry points instead.
