# AI-04 — LLM Response Handling & Secret-Hygiene Audit

> Mission: security-audit (roadmap item 6, deliverable AI-04)
> Date: 2026-09-19. Severity labels: CRITICAL/HIGH/MEDIUM/LOW + P0-P3.
> Scope: no credential/key material logged, echoed in responses, or leaked on error
> paths — `ChatOptions.accountKey` serialization, chat logging/redaction
> (`DefaultChatLogger`/`ChatLogHelper`), dialect key transport, failover metrics
> observability, persistence defaults, error-response construction.
> Boundary: credential STORAGE is item 3 (CRED-01..04); this report owns response-side
> and diagnostics-side handling only.
> Method: full read of DefaultChatLogger/ChatLogHelper/ChatServiceImpl/dialects/
  FailoverMetricsImpl; JDK empirical verification of the redaction regex behavior
  (`_tmp/security-audit/RedactCheck.java`); secret sweep + `_gen` spot + `@cfg`
  inventory (Phase 1, see `_tmp/security-audit/ai-inventory.md`).

## Verified controls

1. **`accountKey` (raw backup-account API key) never serializes**: `@JsonIgnore` on
   `ChatOptions.accountKey/accountBaseUrl` with copy()/merge() carrying them only
   in-memory (nop-ai-api/.../ChatOptions.java); `ModelClassCandidate.toString()` masks
   the key as `***` (nop-ai-core/.../routing/ModelClassCandidate.java:98-101).
   `ApiRequest.getProperties()` (the gateway per-request channel) is `@JsonIgnore` —
   property-borne keys are neither serialized nor logged by default serializers.
2. **Keys travel by headers, never URL**: all five dialects authenticate via
   `setHeaders` (OpenAI/Responses: bearer or configured header; Anthropic/Gemini:
   `x-api-key`); `GeminiDialect.buildUrl` explicitly documents the header choice over
   the query param (:263-278). No `ARG_URL` error params found in nop-ai-core — failed
   request diagnostics do not embed the URL (hence not a query-borne key).
3. **Log-path traversal blocked**: `ChatLogHelper` restricts the caller-supplied
   sessionId (embedded in the log file path) to `[A-Za-z0-9_-]+` — same allow-list as
   the agent's `SessionIds.requireValidIdentifier` (:19-23, 66-80).
4. **Secret sweep clean**: no hardcoded key/secret literals in nop-ai main code or
   `_vfs` resources; `_gen` (90 files) contains only the structural `_LlmAccountModel`
   apiKey field, no values (Phase 1 inventory §4).
5. **Error paths carry parsed, classified errors**: non-2xx responses are normalized by
   `dialect.parseErrorResponse` into `ChatResponse` with `errorClassification` (streaming
   errors recover `ARG_BODY/ARG_HTTP_STATUS/ARG_RESPONSE_HEADERS` params internally for
   classification, ChatServiceImpl:443-463) — raw provider bodies are not echoed as
   response payloads; gateway degraded responses surface the exception message only
   (AiGatewayFailoverInterceptor.degradedErrorResponse).

## Findings

| ID | Severity | Anchor | Description | Remediation suggestion |
|---|---|---|---|---|
| F-AI4-1 | HIGH (P1) | nop-ai/nop-ai-gateway/src/main/java/io/nop/ai/gateway/failover/FailoverMetricsImpl.java:44-128 (every counter/timer uses tag `"account", nvl(accountKey)`); producers: AiGatewayFailoverInterceptor.java:200,253-266,298-299,325,424,443-445 + ChatServiceFailoverAdapter.java:208-220,259-260,287-288; default wiring ai-gateway-defaults.beans.xml:181-187 (ioc:default=true, non-optional refs :226-228/:265-267); key semantics: ModelClassCandidate.java:50-53 ("备用账号 apiKey 直配值") | **Raw backup-account API key exported as a metrics label.** `IFailoverMetrics` receives the candidate's `accountKey` — which IS the literal backup-account API key — and `FailoverMetricsImpl` (production default bean) emits it verbatim as the micrometer tag `account` on ~10 metric families (switch/resubscribe/takeover/request-success/request-failure/concurrency-acquire/release/degraded/stream-element + request.duration timer). Every failover to a backup account therefore publishes a live credential to the observability plane (Prometheus scrapes, `/actuator/metrics`, dashboards, long-term TSDB retention) — readable by anyone with metrics access, no auth required at the metrics endpoint in typical setups. The codebase's own `ModelClassCandidate.toString()` masks this exact value, confirming its secret status. Primary accounts are unaffected (null key → empty tag); backup-account keys (typically the more quota-rich ones) are exposed. | Replace the tag with a non-secret account identifier (account ref/id from config, or a stable hash), keeping the raw key out of observability entirely; add a test asserting no metric tag ever equals a configured key. |
| F-AI4-2 | MEDIUM (P2) | nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/service/DefaultChatLogger.java:34-70 (CREDENTIAL_PATTERNS[2] = `sk-[A-Za-z0-9]{20,}` — no capturing group — replaced with `"$1: ***REDACTED***"`) | **Credential redaction is broken for OpenAI-style keys (crash, not leak).** The file-log redaction loop applies `replaceAll("$1: ***REDACTED***")` to all three patterns, but pattern 3 has no group 1. Empirically verified on the local JDK (evidence `_tmp/security-audit/RedactCheck.java`): any content matching `sk-` + 20+ alphanumerics throws `java.lang.IndexOutOfBoundsException: No group 1` from `Matcher.replaceAll`. Consequences when `redact-credentials=true` (default) and a real `sk-` key appears in request/response content (user pasted key, or model echoed one): the log write aborts BEFORE `writeText` (so the key is not persisted — fail-closed by accident) and the exception propagates out of `logRequest` through `ChatServiceImpl.callAsync/callStream`, failing the whole LLM call (availability defect). The pattern that exists precisely to redact real OpenAI keys never succeeds — the control is non-functional. No test covers `DefaultChatLogger` redaction behavior (TestChatLogHelper covers path building only). | Use a group-less replacement (`"***REDACTED***"`, as the console path `redactIfNeeded` already does) for pattern 3, or add a capturing group; add `TestDefaultChatLogger` asserting sk- content is redacted in the written file (and that logging never throws). |
| F-AI4-3 | LOW (P3) — deployment constraint | nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/AiCoreConfigs.java:34-37 (`nop.ai.persist.exchange-encrypt` default false); DefaultChatLogger.java:51-63 (console INFO logs full request/response content when `logMessage` enabled) | **Chat content at rest unencrypted by default; full-content console logging opt-in.** `AiChatExchange` persistence defaults to plaintext (documented legacy-compat choice); `DefaultChatLogger` writes full conversation content to the normal INFO log whenever a model enables `logMessage`. Both are deployment decisions, not defects — chat transcripts may contain user secrets pasted into prompts. | Item-9 deployment hardening: enable `nop.ai.persist.exchange-encrypt` (with a real key, plan-328 constraint applies); restrict `logMessage` models and `nop.ai.service.log-dir` permissions. |

## Explicit no-finding statements

- No key material in URLs, error params, or `toString()` outputs of the routing model
  (controls 1-2; the ONE raw-key surface is the metrics tag, F-AI4-1).
- Response/error payloads surfaced to callers contain provider-parsed messages and
  status codes, not key material; stream error classification params stay internal.
- Secret sweep + `_gen` spot clean (Phase 1 §4); `redact-credentials` default true and
  the console redaction path (group-less replacement) is functionally correct.
- Chat log file paths cannot traverse out of the log dir (session-id allow-list).
