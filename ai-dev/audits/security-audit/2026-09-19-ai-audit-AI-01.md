> Date: 2026-09-19. Auditor: ZCode session (plan 2026-09-18-2342-8, Phase 2).
> Severity labels: CRITICAL/HIGH/MEDIUM/LOW and P0/P1/P2/P3 (P0=CRITICAL … P3=LOW).
> Scope: transparent account/provider switching on failover (agent `LlmCallCoordinator`
> + core `AccountChain`/`ProviderFailoverChain` + gateway `AiGatewayFailoverInterceptor`/

> channel/scan-login gateway surface (`ChannelLoginApiBizModel`, `ChannelLoginScanProcessor`,

## Verified controls

1. **Fail-loud, forward-only switching**: `AccountChain` and `ProviderFailoverChain` are
   per-execution cursors (no oscillation); exhaustion fails loud (design §6.9) — no silent
   degradation; `MAX_FALLBACK_STEPS=16` bounds cycles (LlmCallCoordinator.java:915,
   checkFallbackStepCap).
2. **No cross-account credential residue in the switching logic itself**:
   `doProviderFailover` explicitly clears `accountKey`/`accountBaseUrl` on provider switch
   (LlmCallCoordinator.java:577-578) — a new provider always starts from its primary
   account. `ChatOptions.accountKey/accountBaseUrl` are `@JsonIgnore`
   (nop-ai-api/.../ChatOptions.java) so the raw key never serializes into request bodies,
   logs, or audit JSON.
3. **Provider chain is server-configured, not client-influenced**: chains resolve from
   config files only (`{provider}.llm.xml <accounts>` via `LlmConfigHelper.resolveAccountChain`,
   `_default.llm-failover.xml` via `resolveFailoverChain`; LlmCallCoordinator.java:75-84).
   In the gateway interceptor, the router is built from `primaryProvider` (server config,
   `nop.ai.service.default-llm`) + client body `model` only
   (AiGatewayFailoverInterceptor.java:541-553); `accountKey` travels the per-request
   property channel whose map is `@JsonIgnore` on `ApiRequest.getProperties()`
   (verified io/nop/api/core/beans/ApiRequest.java:54-57) — not client-injectable, not
   forwarded to the provider.
4. **Scan-login identity hardening (audit ai-rest D5, verified live)**:
   `ChannelLoginScanProcessor` fails closed when the provider asserts no server-side
   identity (ERR_CHANNEL_LOGIN_NO_SERVER_IDENTITY, :93-101) and cross-checks
   `ticketOwnerId == binding.platformUserId` (:119-126) — a caller-forged `open_id`
   cannot select another user's binding. Ticket = `"fs_bind_" + UUID.randomUUID()`
   (unguessable), single-use, 5-min TTL, server-side map
   (FeishuBindProvider.java:88-146). Access code minted via purpose-isolated
   `generateAccessCode` (AUTH-01 provider).
5. **Channel messaging**: outbound `sendToUser` resolves bindings by server-side userId
   only (ChannelMessageServiceImpl.java:268-304); no cross-user addressing from message
   content. `ChannelSessionStoreImpl` keys strictly on (channelType, channelId) with
   explicit not-found; inbound transport is the Feishu Stream long-connection
   (FeishuConnector over `FeishuClient`), not a public unauthenticated webhook.

## Explicit no-finding statements

- No client-controllable path sets `provider`, `accountKey`, `accountBaseUrl` or the
  failover chains: options carrier is `@JsonIgnore`-guarded, properties map is
  `@JsonIgnore`, chains are config-file only.
- The agent-side switch path rebuilds `ChatOptions` copies (never mutates the original),
  and provider switch clears account identity (control 2).
- `ModelClassCandidate.toString()` masks `accountKey` as `***` (raw-key handling elsewhere
  is owned by AI-04).
- Channel session mapping cannot be re-keyed by message content; inbound group messages
  are `@bot`-filtered; rate limit 3000/min default on the connector.
- No cross-account state in `ConcurrencyRegistry`/`ThresholdBreaker` beyond keyed counters.
