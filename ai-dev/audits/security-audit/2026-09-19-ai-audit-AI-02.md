# AI-02 — Tool-Call Sandboxing Audit (toolkit + sandbox seams + HTTP/SSRF)

> Mission: security-audit (roadmap item 6, deliverable AI-02)
> Date: 2026-09-19. Severity labels: CRITICAL/HIGH/MEDIUM/LOW + P0-P3.
> Scope: toolkit executor permission model (engine Layers 1-4 + builder defaults),
> `LocalToolFileSystem` path confinement, BOTH sandbox seams (toolkit `IBashSandbox`
> family + agent `ISandboxBackend` family), Http executor SSRF posture (plan-336
> boundary), and `nop-ai-shell` unwired-library disposition.
> Method: full read of the sandbox families, `LocalToolFileSystem`, SSRF guards,
> `HttpRequestExecutor`/`BashExecutor`, engine dispatch/wiring (`AgentToolDispatcher`,
> `ReActAgentExecutorBuilder`, `AgentSecurityConsultation`, security package defaults);
  `check-ai-tool-executor-boundary.mjs` (PASS); in-repo consumer greps.

## Verified controls

1. **Invariant checker green**: `node ai-dev/tools/check-ai-tool-executor-boundary.mjs`
   → PASS (31 executor instances, `LocalToolFileSystem.isPathAllowed` wired into
   `resolveFile`, zero inventory gaps; log `_tmp/security-audit/ai-boundary-checker.log`).
2. **`LocalToolFileSystem` confinement is real** (nop-ai-toolkit/.../fs/LocalToolFileSystem.java):
   every operation funnels through `resolveFile` → `isPathAllowed`, which canonicalizes
   BOTH sides (`getCanonicalPath` — resolves `..`, symlinks) and checks segment-boundary
   prefix (`StringHelper.pathStartsWith`, Windows separator normalized :52-54); absolute
   paths outside workDir rejected; unresolvable paths (IOException) → deny (fail-closed).
3. **Bash fail-closed default**: `BashExecutor` refuses every call when `sandbox == null`
   (BashExecutor.java:91-96, NO_BACKEND_ERROR); shipped wiring
   `ai-toolkit-defaults.beans.xml:38` registers the bare executor (no sandbox) — bash is
   disabled by default; host execution requires explicit `HostBashSandbox` opt-in, Docker
   isolation via `DockerBashSandbox`. No implicit fallback anywhere.
4. **Backend isolation quality**: both backends share `BashSandboxPaths.validateWorkingDirectory`
   (rejects `..`, non-real paths, denies when `allowedBaseDirs` empty) BEFORE launch;
   Docker backend is argv-based (no shell interpolation into the `docker` CLI),
   `--network none` default (egress deny), `--cpus`/`--memory` limits, env keys validated
   (`^[A-Za-z_][A-Za-z0-9_]*$`), wall-time kill + `docker kill`/`rm -f` cleanup, exit-code
   classification. Host backend honestly documents what it cannot enforce (cpu/mem/network).
5. **SSRF two-stage guard** (HttpRequestExecutor + GraphqlQueryExecutor): pre-flight
   `SsrfAddressGuard.validateHost` (scheme allowlist http/https, blocked-hosts set incl.
   cloud metadata, encoded-IP literal normalization) + authoritative resolution-time
   `SsrfGuardDnsResolver` immediately before send (ALL addresses of a multi-answer set
   checked — DNS-rebinding fail-closed; IP literals re-checked; unresolved → deny).
   Default-wired as the executors' `IDnsResolver`.
6. **Engine permission model (builder defaults, ReActAgentExecutorBuilder.java:630-632)**:
   `DefaultToolAccessChecker` hard-denies `bash/write-file/delete-file/move-file/patch-file/
   apply-delta/http-request/graphql-query` (the dangerous toolkit surface) even before
   Layer 2; `DefaultPathAccessChecker` denies traversal, sensitive prefixes
   (~/.ssh, ~/.aws, /etc, /root, …), sensitive filenames (id_rsa, .env*), and
   symlink-resolved real-path evasion (fail-closed on unresolvable); `DefaultPermissionMatrix`
   channel × security-level with OPERATOR bypass; `DefaultApprovalGate` +
   denial ledger + post-denial guard; per-agent `workDir`/path-root/path-rule clamping
   parent ∩ child for sub-agents (`AgentToolPlanResolver.computeEffective*`).
7. **File tools in the default engine are fail-closed**: `AgentToolDispatcher
   .prepareDispatchContext` passes `fileSystem = null`
   (nop-ai-agent/.../AgentToolDispatcher.java:126-135) and file executors return
   "File system not available" on null fs (ReadFileExecutor.java:29-32). The only in-repo
   production `LocalToolFileSystem` producer is the operator CLI
   (`CliCallToolsCommand.java:68-76`, workDir = explicit `-d` or CWD).

## Explicit no-finding statements

- `LocalToolFileSystem` callers cannot escape workDir (canonical + segment-prefix check,
  fail-closed on resolution errors); `glob`/`grep` base paths go through the same jail.
- Default shipped assembly denies the dangerous tool set twice (no sandbox wired AND
  `DefaultToolAccessChecker` hard deny-list); enabling bash is a two-step explicit opt-in.
- No shell-injection into the Docker backend: argv-only `ProcessBuilder`, env keys
  pattern-validated, container name UUID-based.
- `HostBashSandbox`/`NoOpSandboxBackend` never fall back to each other or hide failures;
  destructive-command regex and dangerous-env-var blocklist exist as defense-in-depth
  (documented as non-primary).
- SSRF: no scheme smuggle (http/https only), blocked-hosts set covers known metadata
  endpoints, IP-literal encodings normalized before verdict.
