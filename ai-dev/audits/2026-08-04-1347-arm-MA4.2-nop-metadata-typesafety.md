### [P3-MA4-102] MinAcc/MaxAcc 缺非 Comparable 守卫——与同包两个比较器防御模式不一致，可触发 CCE

- **文件**: `nop-metadata/nop-metadata-service/src/main/java/io/nop/metadata/service/query/AggregationContext.java:329-369`
- **证据片段**:
  ```java
  public static final class MinAcc extends MemAggAccumulator {
      private Comparable<Object> min;
      @Override
      @SuppressWarnings("unchecked")
      public void accumulate(Object v) {
          if (v == null) return;
          Comparable<Object> c = (Comparable<Object>) v;   // 无 instanceof 守卫
          if (!hasValue || c.compareTo(min) < 0) { min = c; hasValue = true; }
      }
  }
  // 对照：MemoryFilterEvaluator.java:245-250（同模块防御写法）
  if (a instanceof Comparable && b.getClass().isInstance(a)) {
      return ((Comparable) a).compareTo(b);
  }
  ```
- **严重程度**: P3
- **现状**: 跨库内存聚合 MIN/MAX 路径对传入值直接强转 `Comparable<Object>` 无守卫；同包 MemoryOrderByComparator/MemoryFilterEvaluator 对同样的值比较做了 `instanceof Comparable` + 类型一致守卫并回退字符串比较。
- **风险**: 外部表列值为非 Comparable 类型（如 byte[]、自定义对象）时 MIN/MAX 聚合抛 CCE → 500，而 SQL 路径处理同样查询不崩溃；与代码库自身防御模式不一致。
- **建议**: 复用 `MemoryFilterEvaluator.compareValues` 守卫逻辑（或抽公共 helper）：`v instanceof Comparable` 才强转，否则显式抛带上下文的 `ERR_AGGR_*` 错误码。
- **信心水平**: 确定（机制无守卫必可抛 CCE）；触发需 byte[] 等列参与 min/max，为边角场景
- **误报排除**: 值来源虽是动态 SQL 行（可豁免 Object），但比较语义在模块内已被另两处实现为"类型守卫+回退"——此处缺守卫是与自身契约不一致，不是平台边界要求。
- **复核状态**: 未复核
- **修复归属**: MR2（低风险小改动）

### [P3-MA4-103] Quality checkpoint 内部 summary Map 契约：同文件内一半读取有守卫、一半无守卫强转

- **文件**: `nop-metadata/nop-metadata-service/src/main/java/io/nop/metadata/service/entity/NopMetaQualityCheckpointBizModel.java:172, 281, 290`
- **证据片段**:
  ```java
  // executeCheckpoint 内（有守卫，安全）：
  Object affectedTableIds = summary.get("affectedTableIds");
  if (affectedTableIds instanceof List) { dto.setAffectedTableIds((List<String>) affectedTableIds); }
  // triggerAutoScoring 内（无守卫，同一调用链同一 key）：
  List<String> affectedTableIds = (List<String>) summary.get("affectedTableIds");   // :281
  List<Map<String, Object>> errors = (List<Map<String, Object>>) summary.get("errors"); // :290
  ```
- **严重程度**: P3
- **现状**: executor（MetaQualityCheckpointExecutor:170-177）与 biz model 之间以 `Map<String,Object>` summary 隐式契约传递；读侧一半 instanceof 守卫、一半裸强转，同一 key 两种读法并存。
- **风险**: 未来改 key 类型/删 key → 裸强转处 CCE，契约漂移时错误出现在调用链深处而非契约边界。当前两端同模块且 key 恒被设置，无运行时故障。
- **建议**: 最小改动——281/290/172 三处补 instanceof 守卫对齐 182-192；结构性方案——executor 返回值换成已存在的 `CheckpointExecutionResultDTO`。
- **信心水平**: 确定（契约漂移风险真实；当前无故障）
- **误报排除**: 非 JSON/XDSL 动态边界——summary 的 key 集合与值类型由同模块 Java 代码固定写入，完全可静态类型化，属"内部 Map 传参"反模式。
- **复核状态**: 未复核
- **修复归属**: 非阻塞（MR2 顺手项）

### [P3-MA4-104] 对账 details 行强转无 instanceof 守卫（顶层 List 检查后即裸转元素）

- **文件**: `nop-metadata/nop-metadata-service/src/main/java/io/nop/metadata/service/entity/NopMetaReconciliationResultBizModel.java:81-82, 117-118, 138-150`
- **证据片段**:
  ```java
  List<Object> details = parseDetailsOrThrow(result);   // 仅校验顶层是 List
  checkRowIndex(resultId, rowIndex, details.size());

  Map<String, Object> row = (Map<String, Object>) details.get(rowIndex);  // 元素类型未校验
  ```

- **严重程度**: P3
- **现状**: details 是用户可编辑的落库 JSON（`result.getDetails()`），confirmMatch/batchConfirmMatches 对元素裸强转 Map 无元素级类型检查；模块内其他 JSON 读取（NopMetaQualityCheckpointBizModel:334、MetaContractChecker:378）均先 `instanceof Map`。

- **信心水平**: 确定（机制）；触发需非本模块写入的 details 数据
- **误报排除**: 非平台边界——details 是自有落库 JSON，schema 由同模块 ReconciliationExecutor 写死，读取端本可静态定型为 `List<Map<String,Object>>`，且与模块自身 instanceof 惯例不一致。
- **复核状态**: 未复核
- **修复归属**: 非阻塞（MR2 顺手项）
