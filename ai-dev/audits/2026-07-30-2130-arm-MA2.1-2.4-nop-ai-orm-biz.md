# MA2.1+MA2.4 — ORM Model & BizModel Audit: nop-ai

> Date: 2026-07-30
> Scope: 21 entities + 21 BizModels (nop-ai-dao + nop-ai-service)
> Checker: houyi sub-agent

## Summary
- Total findings: 11
- P0: 1 — Dual ORM source file drift (nop-ai.orm.xml vs ai-gen.orm.xml)
- P1: 4 — Missing audit props, version type conflict, relation refPropName mismatch, empty DAO beans
- P2: 4 — Missing displayName on to-one relations, prototype missing displayName, minimal error codes, unused domain
- P3: 2 — VARCHAR(65536) limit edge case, line-break inconsistency

**Health assessment**: The ORM model and BizModel wiring is structurally sound — all 21 entities have retention classes extending `_gen`, all 21 BizModels extend `CrudBizModel`, all 21 implement their interface, all 21 are registered in `_service.beans.xml`. The critical concern is the dual ORM source (`ai-gen.orm.xml` vs `nop-ai.orm.xml`) which is drifting and could cause codegen inconsistencies. The agent runtime entities (Session, SessionMessage, etc.) have several minor displayName gaps. No P0 issues found in the BizModel layer.

## Findings

### P0-MA2-01: Dual ORM model source files with divergent definitions
- **Files**: `nop-ai/model/nop-ai.orm.xml` (1403 lines) vs `nop-ai/model/ai-gen.orm.xml` (364 lines)
- **Priority**: P0 (critical — codegen source ambiguity)
- **Description**: There are two ORM model source files defining the same entities with conflicting schemas:
  1. **Dict naming conflict**: `nop-ai.orm.xml` uses `ai/message-type`, `ai/project-language` (namespace-prefixed); `ai-gen.orm.xml` uses `message_type`, `project_language` (underscore, unprefixed)
  2. **Dict value conflict**: `ai/message-type` (nop-ai) has `valueType="int"` with values 10–80 and codes USER/ASSISTANT/COMPACTION/SHELL/SYNTHETIC/SYSTEM/AGENT_SWITCHED/MODEL_SWITCHED; `message_type` (ai-gen) has `value` "002","003" and codes USER/TOOL — these are fundamentally incompatible
  3. **Entity scope**: `nop-ai.orm.xml` has 21 entities; `ai-gen.orm.xml` has only 14 (missing: NopAiSession, NopAiSessionMessage, NopAiSessionInput, NopAiSessionContext, NopAiTodo, NopAiEvent, NopAiTestResult — the entire agent runtime group)
  4. **Entity naming**: `nop-ai.orm.xml` uses `name="io.nop.ai.dao.entity.NopAiProject"` (FQN) with `className` attribute; `ai-gen.orm.xml` uses `name="NopAiProject"` (short)
  5. **Column completeness**: `ai-gen.orm.xml` omits all version/audit columns (version, created_by, create_time, updated_by, update_time)
- **Impact**: If `ai-gen.orm.xml` is ever used for code generation, it will produce incomplete entities missing audit columns with incompatible dict references. The dict clash (`message_type` with values 002/003 vs `ai/message-type` with values 10-80) would cause silent data corruption if both models are deployed concurrently.
- **Recommendation**: Decide on a single canonical ORM source. If `ai-gen.orm.xml` is a legacy/design artifact, archive or remove it. If it serves a different purpose (e.g., simplified codegen), clearly document the distinction and ensure it never overrides `nop-ai.orm.xml`.

### P1-MA2-02: NopAiProject missing audit propagation attributes
- **File**: `nop-ai/model/nop-ai.orm.xml:117-118`
- **Priority**: P1 (important — ORM auto-audit disabled for root entity)
- **Description**: `NopAiProject` entity definition lacks `createTimeProp="createTime"`, `createrProp="createdBy"`, `updateTimeProp="updateTime"`, `updaterProp="updatedBy"`. All other 20 entities have these attributes. While the entity does have explicit `created_by`, `create_time`, `updated_by`, `update_time` columns, the absence of entity-level audit props means the ORM will not auto-populate these fields during insert/update, risking constraint violations or stale data.
- **Impact**: Inserts/updates on `NopAiProject` through ORM may fail with NOT NULL constraint violations if the caller doesn't explicitly set audit fields. This is the root aggregation entity — highest data integrity risk.
- **Recommendation**: Add `createTimeProp="createTime" createrProp="createdBy" updateTimeProp="updateTime" updaterProp="updatedBy"` to the `NopAiProject` entity element.

### P1-MA2-03: NopAiRequirement version column type mismatch with versionProp
- **File**: `nop-ai/model/nop-ai.orm.xml:344,357-358`
- **Priority**: P1 (important — optimistic locking may fail)
- **Description**: Entity `NopAiRequirement` declares `versionProp="version"` (entity-level, line 344), which instructs the ORM to use the `version` column for optimistic locking. However, the `version` column is defined as `stdDataType="string" stdSqlType="VARCHAR"` (lines 357-358). Optimistic locking requires a numeric type (`int`/`long`/`Integer`/`Long`). This is also semantically wrong: the column is labeled "当前版本" (current version) and holds a string version identifier (like "1.0.0"), not a numeric lock counter.
- **Impact**: Optimistic locking on `NopAiRequirement` will fail at runtime with type conversion errors, or silently not work. Concurrent modifications to the same requirement record will not be detected, leading to lost updates.
- **Recommendation**: Add a dedicated `nanoLock` column (integer, domain="version") for optimistic locking, or remove `versionProp="version"` if manual versioning is intended. The `version` string column should not serve dual purposes.

### P1-MA2-04: NopAiSessionContext to-one relation references wrong refPropName
- **File**: `nop-ai/model/nop-ai.orm.xml:1275` (also `nop-ai/model/nop-ai.orm.xml:1051`)
- **Priority**: P1 (important — bidirectional relation broken)
- **Description**: `NopAiSessionContext` defines `<to-one name="session" ... refPropName="context">` (line 1275), but the matching property in `NopAiSession` is `<to-many name="contexts" ...>` (line 1051, plural `contexts`). The `refPropName` should be `"contexts"`, not `"context"`.
- **Impact**: The ORM will not correctly wire the bidirectional relationship. The `NopAiSessionContext.session` to-one will not properly track back to its owning session's `contexts` collection. GraphQL queries navigating `session -> contexts` or `sessionContext -> session` may return partial or empty results.
- **Recommendation**: Change line 1275 from `refPropName="context"` to `refPropName="contexts"`.

### P1-MA2-05: _dao.beans.xml is empty — no interface Biz bean registrations
- **File**: `nop-ai/nop-ai-dao/src/main/resources/_vfs/nop/ai/beans/_dao.beans.xml:1-5`
- **Priority**: P1 (important — interface Biz beans not registered at DAO layer)
- **Description**: The DAO-layer beans file is empty (only schema declarations, no bean elements). All 21 `INopAi*Biz` interfaces are registered via `BizProxyFactoryBean` only in `_service.beans.xml`. According to Nop platform conventions, `_dao.beans.xml` should ideally register the DAO-layer interface beans. While the service-layer `BizProxyFactoryBean` registrations create functional beans (they use `ioc:type="io.nop.ai.biz.INopAiXxxBiz"` with `ioc:force-lazy-property="true"`), the DAO beans file being empty is anomalous and may indicate incomplete codegen or a missing setup step.
- **Impact**: If any component depends on DAO-layer bean scanning or expects DAO-layer beans to be present (e.g., for custom DAO extensions), they will be missing. The service-layer proxy may compensate, but this bypasses the intended layering.
- **Recommendation**: Investigate whether the empty `_dao.beans.xml` is intentional. If DAO-layer beans are genuinely not needed, add a comment explaining why. If they are needed, add bean definitions mirroring the service-layer pattern or regenerate.

  - `NopAiSession.parentSession` (line 1033): no displayName, no refDisplayName

  - `NopAiSessionMessage.parentMessage` (line 1151): no displayName
  - `NopAiSessionInput.session` (line 1217): no displayName
  - `NopAiSessionContext.session` (line 1275): no displayName
  - `NopAiTodo.session` (line 1344): no displayName
  - `NopAiEvent.session` (line 1394): no displayName

### P2-MA2-08: NopAiErrors.java has only 1 error code for 21 entities
- **File**: `nop-ai/nop-ai-service/src/main/java/io/nop/ai/service/NopAiErrors.java:1-13`
- **Priority**: P2 (minor — code quality/defer)
- **Description**: `NopAiErrors.java` defines a single error code (`ERR_AI_SESSION_ID_REQUIRED`). For a module with 21 entities and complex business logic (session context management, test execution, model pricing), this is very minimal. Only `NopAiChatResponseBizModel.summarizeByModel()` uses custom error codes; all other BizModels rely on generic CRUD error handling.
- **Impact**: Debugging domain-specific business rule violations is harder without specific error codes. Generic errors lack the context needed for targeted error handling.
- **Recommendation**: Define error codes incrementally as business logic is added, particularly for session lifecycle, todo validation, and model pricing operations.

### P2-MA2-09: `boolFlag` domain defined but never used
- **Files**: `nop-ai/model/nop-ai.orm.xml:110`
- **Priority**: P2 (minor — dead definition)
- **Description**: The domain `boolFlag` with `stdSqlType="BOOLEAN"` is defined in the `<domains>` section but never referenced by any column. Boolean columns like `is_active`, `success` use `stdDataType="boolean"` directly instead of `domain="boolFlag"`.
- **Impact**: None functional, but the unused domain adds noise to the model.
- **Recommendation**: Either remove the unused `boolFlag` domain, or apply it to boolean columns (`is_active`, `success`) for consistency.

### P3-MA2-10: VARCHAR(65536) exceeds MySQL's VARCHAR limit
- **Files**: `nop-ai/model/nop-ai.orm.xml:592,594,654,729,800` (5 occurrences)
- **Priority**: P3 (info/deferred — database-dependent)
- **Description**: Columns `system_prompt`, `user_prompt`, `response_content`, `content` (GenFile), `content` (GenFileHistory) use `precision="65536"` with `stdSqlType="VARCHAR"`. MySQL's VARCHAR maximum is 65535 characters. On MySQL, this would cause a DDL error. On PostgreSQL and Oracle, VARCHAR(65536) may be treated as CLOB or succeed depending on configuration.
- **Impact**: DDL generation may fail on MySQL. On other databases, behavior is implementation-specific. If the columns genuinely need >64KB, CLOB is the correct SQL type.
- **Recommendation**: Change `stdSqlType` to `CLOB` for these columns (they already have `stdDomain="json"` or `ui:control="textarea"` which is consistent with CLOB usage elsewhere). Alternatively, set precision to 65535 to stay within MySQL limits.

### P3-MA2-11: Inconsistent line-break style in entity definitions
- **Files**: Various — `nop-ai/model/nop-ai.orm.xml`
- **Priority**: P3 (info/deferred — stylistic)
- **Description**: Some entity elements break attributes across lines while others keep them on a single line. Example: `NopAiProject` keeps all attributes on two lines (lines 117-118), while most other entities use 3-4 lines with one attribute per line. This is purely cosmetic but makes model diffing harder.
- **Impact**: None functional.
- **Recommendation**: Standardize formatting when doing other model changes (not worth a dedicated cleanup).
