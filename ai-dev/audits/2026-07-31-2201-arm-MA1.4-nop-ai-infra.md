## 发现明细

### [P1-MA1-017] nop-ai-maven 模块名与实际内容不符

- **模块**: `nop-ai/nop-ai-maven`
- **文件**: `pom.xml:13`（`<artifactId>nop-ai-maven</artifactId>`）
- **严重程度**: **P1**
- **现状**: 核心功能是无 Maven 依赖的 Delta VFS；README 明确说明"本工具不依赖 Maven API"；零 `org.apache.maven.*` import。
- **风险**: 查找 VFS 工具的开发者不会找到此模块；期望 Maven 集成的开发者会失望。
- **建议**: 重命名为 `nop-ai-delta-vfs` 或类似；或明确文档说明核心是 VFS 而非 Maven。
- **信心水平**: 高

### [P1-MA1-018] nop-ai-codegen 零生产 Java 代码 — 结构边界违规

- **模块**: `nop-ai/nop-ai-codegen`
- **文件**: 模块根目录
- **严重程度**: **P1**
- **现状**: `src/main/java/` 不存在；仅有 `src/test/java/` 下的 `NopAiCodeGen.main()` 启动类和 `postcompile/gen-orm.xgen` 脚本。生成的 JAR 无生产类。
- **风险**: 对 nop-ai-codegen 的依赖获得空 JAR；启动类 `main()` 在 test 目录无法在打包后执行。
- **建议**: (a) 将 main() 移到 src/main/java；(b) 转换为 Maven plugin；(c) 合并到父模块或 nop-ai-dao/service。
- **信心水平**: 高

### [P1-MA1-019] postcompile 脚本引用不存在的 ORM 模型文件

- **模块**: `nop-ai/nop-ai-codegen`
- **文件**: `postcompile/gen-orm.xgen:4-6`
- **严重程度**: **P1**
- **现状**: 路径 `../../model/nop-ai.orm.xml` 指向不存在的文件。搜索 nop-ai/ 目录树未找到该文件。
- **风险**: 执行 NopAiCodeGen.main() 或触发 postcompile 将失败。
- **建议**: 更新路径指向 ORM 模型实际位置（如 `../nop-ai-dao/src/main/resources/_vfs/nop/ai/orm/`），或创建模型文件。
- **信心水平**: 高

### [P2-MA1-020] dsl-orm 硬编码包名 app.demo.*

- **模块**: `nop-ai/nop-ai-dsl-orm`
- **文件**: `GptOrmModelParser.java:49`
- **严重程度**: **P2**
- **现状**: `entityModel.setClassName("app.demo." + StringHelper.simpleClassName(name))` — 生成的实体类始终在 `app.demo.*` 包下。
- **风险**: 实际项目中使用此解析器时生成的类包名错误。
- **建议**: 使基础包可配置。
- **信心水平**: 高

### [P2-MA1-021] nop-ai-maven pom.xml 包含死依赖

- **模块**: `nop-ai/nop-ai-maven`
- **文件**: `pom.xml:21-43`
- **严重程度**: **P2**
- **现状**: 声明了 `nop-api-core`、`nop-core`、`maven-resolver-api`、`maven-resolver-util`，但全模块零 import。
- **风险**: 误导性依赖图；无谓引入传递依赖。
- **建议**: 移除未使用的依赖声明。
- **信心水平**: 高

### [P2-MA1-022] nop-ai-codegen pom.xml 包含多余重型依赖

- **模块**: `nop-ai/nop-ai-codegen`
- **文件**: `pom.xml:17-34`
- **严重程度**: **P2**
- **现状**: 声明 `nop-ooxml-xlsx`、`nop-orm`、`nop-graphql-core`、`nop-xlang-debugger`，但零生产 Java 代码，启动类仅使用 nop-api-core/nop-codegen/nop-commons/nop-core。
- **风险**: 构建传递依赖膨胀。
- **建议**: 移除非必要的依赖或改为 test scope。
- **信心水平**: 中

### [P3-MA1-023] gateway 测试与生产代码比 >2:1

- **模块**: `nop-ai/nop-ai-gateway`
- **文件**: 测试和生产代码
- **严重程度**: **P3**
- **现状**: 生产代码 87 行，测试 185 行（213%）。
- **风险**: 低 — 测试全部有效，反映了转换器的薄。
- **建议**: 无需行动，除非模块增长。
- **信心水平**: 高

### [P3-MA1-024] gateway 隐式传递依赖

- **模块**: `nop-ai/nop-ai-gateway`
- **文件**: `pom.xml`
- **严重程度**: **P3**
- **现状**: 使用 nop-core 和 nop-api-core 的类但未在 pom.xml 中直接声明。
- **风险**: 若传递链变更则破裂。
- **建议**: 添加显式依赖声明。
- **信心水平**: 中

### [P3-MA1-025] dsl-orm 薄模块可能与 nop-ai-coder 重叠

- **模块**: `nop-ai/nop-ai-dsl-orm`
- **文件**: 全模块（~191 行生产代码，4 文件）
- **严重程度**: **P3**
- **现状**: dsl-orm 处理 ORM 特定的 DSL 解析；nop-ai-coder 处理更广泛的代码生成。边界不清晰。
- **建议**: 记录边界或考虑合并。
- **信心水平**: 中

### [P3-MA1-026] maven 测试辅助方法重复

- **模块**: `nop-ai/nop-ai-maven`
- **文件**: `DeltaVirtualFileSystemTest.java:193-219` / `DeltaWorkspaceReaderTest.java:178-221`

### [P3-MA1-028] DeltaWorkspaceReader 打破封装直接访问 VFS 内部
