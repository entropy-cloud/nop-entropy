# MA2.5: D11 XMeta vs BizModel Alignment — nop-ai Module

**Date**: 2026-07-31 03:53  
**Auditor**: ARM (Phase 2 follow-up)  
**Module**: `nop-ai`  
**Scope**: 21 ORM entities, 21 BizModels, 42 xmeta files (generated + retention)

---

## Executive Summary

The nop-ai module shows strong structural consistency across its 21 entities, BizModels, and xmeta pairs. All retention xmeta files are empty delta shells extending generated xmeta — zero drift between retention and generated layers. All BizModels are plain `CrudBizModel<T>` extensions with no `@BizLoader` annotations. One custom `@BizQuery` (`summarizeByModel`) returns a `@DataBean` DTO.

**4 findings identified**: 1 P1 (security), 1 P1 (data-integrity risk), 1 P2 (design inconsistency), 1 P3 (cosmetic).

---

## Findings

### P1-MA2-023: NopAiModel.apiKey — sensitive credential field exposed without access restrictions

| Field | Value |
|-------|-------|
| **File** | `nop-ai/nop-ai-meta/src/main/resources/_vfs/nop/ai/model/NopAiModel/_NopAiModel.xmeta` |
| **Lines** | 38–41 |
| **Severity** | **P1** — Security |

**Evidence** (xmeta snippet):
```xml
<prop name="apiKey" displayName="API密钥" propId="5" queryable="true" sortable="true" insertable="true" updatable="true">
    <schema type="java.lang.String" precision="100"/>
</prop>
```

The `apiKey` field stores third-party AI model API credentials. It is:
- `queryable="true"` — exposed in list/filter queries
- `sortable="true"` — can be used as sort key
- `insertable="true"` / `updatable="true"` — can be written via API
- NOT marked `internal="true"`, `published="false"`, or `ui:show="X"`
- Has no masking or encryption indication in the ORM model or xmeta

For comparison, the `id` field (line 22–25) correctly has `internal="true" ui:show="X"`.

**ORM source**: `nop-ai/model/nop-ai.orm.xml` lines 298–299:
```xml
<column code="api_key" displayName="API密钥" name="apiKey" precision="100" propId="5" stdDataType="string"
        stdSqlType="VARCHAR"/>
```

**Risk**: API credentials exposed in GraphQL query results and filterable by end-users. An attacker could enumerate/apiKey values through sort/query operations.

**Recommendation**: Add `internal="true"` (or `published="false"`) to the xmeta `apiKey` prop to exclude it from default query responses. Consider adding `ui:show="X"` to hide it from UI auto-rendering. In the retention xmeta (`NopAiModel/NopAiModel.xmeta`), override the prop:
```xml
<prop name="apiKey" internal="true" queryable="false" sortable="false"/>
```

### P1-MA2-024: NopAiProject — duplicate to-many relations `context`/`contexts` mapping to NopAiSessionContext

| Field | Value |
|-------|-------|
| **File** | `nop-ai/nop-ai-meta/src/main/resources/_vfs/nop/ai/model/NopAiSession/_NopAiSession.xmeta` |
| **Lines** | 148–153 (`contexts`), 172–177 (`context`) |
| **Severity** | **P1** — Data integrity |

**Evidence** (xmeta):

`contexts` (line 148–153):
```xml
<prop name="contexts" displayName="上下文快照" ext:kind="to-many" internal="true" ext:joinLeftProp="id"
      ext:joinRightProp="sessionId" lazy="true" published="false">
    <schema><item bizObjName="NopAiSessionContext"/></schema>
</prop>
```

`context` (line 172–177):
```xml
<prop name="context" ext:kind="to-many" internal="true" ext:joinLeftProp="id" ext:joinRightProp="sessionId"
      lazy="true" published="false">
    <schema><item bizObjName="NopAiSessionContext"/></schema>
</prop>
```

Both use `ext:joinLeftProp="id"` and `ext:joinRightProp="sessionId"` — i.e., they represent the **same database relationship**.

**ORM source**: `nop-ai/model/nop-ai.orm.xml` line 1275:
```xml
<to-one name="session" refEntityName="io.nop.ai.dao.entity.NopAiSession" refPropName="context">
```
And lines 1049–1055:
```xml
<to-many displayName="上下文快照" name="contexts" refEntityName="io.nop.ai.dao.entity.NopAiSessionContext"
         refPropName="session"> ... </to-many>
```

The child's `to-one` declares `refPropName="context"`, which auto-generates a reverse `to-many` named `context`. The parent then *also* explicitly declares a `to-many name="contexts"`. The result: two separate `OrmEntitySet` instances in the generated Java class (`_context` and `_contexts`) pointing to the same table data.

**Generated Java**: `_gen/_NopAiSession.java` lines 1512–1560:
- Line 1512: `_contexts = new OrmEntitySet<>(..., PROP_NAME_contexts, ...)`
- Line 1552: `_context = new OrmEntitySet<>(..., PROP_NAME_context, ...)`

**Risk**: Two independent in-memory entity sets for the same FK relationship. Modifying one set (e.g., adding via `getContext().add(...)`) will **not** be reflected in the other (`getContexts()`). This can cause subtle data loss or desynchronization bugs during cascade saves. Additionally, `context` has no `displayName`, making it less discoverable in documentation/UI.

**Recommendation**: Align the `refPropName` in `NopAiSessionContext.session`'s `to-one` with the explicit collection name:
- In `nop-ai.orm.xml` line 1275, change `refPropName="context"` to `refPropName="contexts"`, OR
- Remove the explicit `to-many name="contexts"` and rename the remaining one to `context` with proper `displayName`

Then regenerate and remove the duplicate Java field.

### P2-MA2-025: NopAiProject — missing ORM audit auto-prop attributes

| Field | Value |
|-------|-------|
| **File** | `nop-ai/model/nop-ai.orm.xml` |
| **Lines** | 117–118 (NopAiProject entity element) |
| **Severity** | **P2** — Design inconsistency |

**Evidence**:

Compare the entity element for NopAiProject (lines 117–118):
```xml
<entity className="io.nop.ai.dao.entity.NopAiProject" displayName="AI项目"
        name="io.nop.ai.dao.entity.NopAiProject"
        registerShortName="true" tableName="nop_ai_project" ext:icon="folder-kanban">
```
**No** `createTimeProp`, `createrProp`, `updateTimeProp`, or `updaterProp` attributes.

vs. every other entity in the same file (e.g., NopAiProjectRule, lines 190–193):
```xml
createTimeProp="createTime" createrProp="createdBy" updateTimeProp="updateTime" updaterProp="updatedBy"
```

Count: 20 out of 21 entities have these 4 attributes; only NopAiProject lacks them.

**Consequence in generated xmeta** (`_NopAiProject.xmeta`, lines 50–65):
```xml
<prop name="createdBy" ... insertable="true" updatable="true">  <!-- NOT insertable="false" -->
<prop name="createTime" ... insertable="true" updatable="true">
<prop name="updatedBy" ... insertable="true" updatable="true">
<prop name="updateTime" ... insertable="true" updatable="true">
```

All other 20 entities have `insertable="false" updatable="false"` for these audit columns.

**Risk**: Users can manually set `createdBy`/`createTime`/`updatedBy`/`updateTime` on NopAiProject via API. Inconsistent with the rest of the module. If this is intentional (e.g., to preserve timestamps from external data sources), it should be documented explicitly.

**Recommendation**: Either:
- **If intentional**: Add the 4 audit attributes to NopAiProject entity element to match the other entities. Use the retention xmeta to override `insertable`/`updatable` to `true` for specific use cases.
- **If accidental**: Add the 4 attributes and regenerate:
  ```xml
  createTimeProp="createTime" createrProp="createdBy" updateTimeProp="updateTime" updaterProp="updatedBy"
  ```

### P3-MA2-026: All 21 retention xmeta files are empty delta shells — no custom overrides

| Field | Value |
|-------|-------|
| **File** | All files under `nop-ai-meta/src/main/resources/_vfs/nop/ai/model/NopAi*/NopAi*.xmeta` |
| **Severity** | **P3** — Minor / Monitoring |

**Evidence**: Every retention xmeta file has identical structure:
```xml
<?xml version="1.0" encoding="UTF-8" ?>
<meta x:schema="/nop/schema/xmeta.xdef" xmlns:x="/nop/schema/xdsl.xdef" x:extends="_NopAi*.xmeta">
    <props/>
</meta>
```

All 21 files confirmed via audit scan. Zero customization — no field-level permission overrides, display adjustments, UI hints, or computed fields.

**Risk**: Low. This is acceptable for freshly codegen'd modules. However, as the module matures, the empty shells provide no extension points for UI customization or field-level access control without editing generated files (which is prohibited by project convention).

**Recommendation**: As feature requirements emerge (e.g., hiding `apiKey`, adding computed fields, setting field-level roles), use the retention xmeta for overrides rather than editing generated `_*.xmeta` files. This finding serves as a baseline for future audits.
