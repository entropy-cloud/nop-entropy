# MA6.4 — Vector Store / Embedding Data Isolation Audit

> **Auditor**: AI Agent (open-ended adversarial review)
> **Date**: 2026-07-31
> **Plan Reference**: `ai-dev/plans/2026-07-31-0000-3-arm-ma5-ma6-audit.md` Phase 8
> **Scope**: nop-ai-core `IVectorStore` / `IEmbeddingModel` + nop-ai-agent memory adapters
> **Methodology**: `ai-dev/skills/open-ended-adversarial-review-prompt.md` (adversarial review)

## Executive Summary

The vector store and embedding subsystem has a structural isolation problem: **the core API abstraction (`IVectorStore`) has zero concrete implementations**, the embedding model interface has no authentication or tenant context, and the agent-layer memory adapters — which form the only working vector/embedding path — have per-session isolation but no multi-tenant safeguards. Meanwhile, the rest of the nop-ai-agent codebase (DB stores, session management, team management) has been systematically retrofitted with `TENANT_ID` columns and `ITenantResolver` integration (plan 232/L4), but the vector store and embedding APIs were never included in that retrofit.

---

### [AR-1] IVectorStore API — dead abstraction with zero implementations

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/vectorstore/IVectorStore.java:29-90`
- **Evidence**:
  ```java
  public abstract class IVectorStore<T extends VectorData> {
      public abstract VectorStoreResult store(List<T> vectorDataList, VectorStoreOptions options);
      public abstract VectorStoreResult delete(Collection<Object> ids, VectorStoreOptions options);
      public abstract List<T> search(VectorQueryBean wrapper, VectorStoreOptions options);
      // ... more abstract methods
  }
  ```
  There is not a single class in the entire codebase that `extends IVectorStore` or `implements IVectorStore`. A `grep` for `extends IVectorStore`, `implements IVectorStore`, and `new.*VectorStore` all return **zero hits**. The `nop-ai-rag` module — the presumed home for concrete implementations (FAISS / pgvector / Milvus) — is an empty shell with only a `pom.xml` and a prebuilt `target/` JAR but **no source files**.
- **Severity**: P2
- **Status**: The `IVectorStore` API defines the sole nop-ai-core vector storage contract (store/delete/update/search with `VectorStoreOptions`). No implementation exists anywhere in the codebase. The `nop-ai-rag` module was set up with a `pom.xml` but has zero Java source. This means the abstraction is dead code — no production vector store integration has been built, so all vector store isolation analysis is speculative.
- **Risk**: Anyone implementing `IVectorStore` from scratch has no reference implementation, no contract tests, and no tenant isolation guidance from the API. If multiple implementations appear independently (one per module), they will likely have inconsistent isolation semantics.
- **Recommendation**: Either (a) remove the `IVectorStore` abstraction if it is not planned for the current release, or (b) define a `tenantId` parameter contract in `VectorStoreOptions` before any implementation is written. Add contract tests in `nop-ai-core/src/test/` that verify tenant isolation for any future implementation.

### [AR-2] VectorStoreOptions has no tenantId field — no tenant isolation contract at the API level

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/vectorstore/VectorStoreOptions.java:30-117`
- **Evidence**:
  ```java
  @DataBean
  public class VectorStoreOptions extends Metadata {
      private String collectionName;
      private String indexName;
      private List<String> partitionNames;
      private EmbeddingOptions embeddingOptions;
      // NO tenantId field
  }
  ```
  The `Metadata` superclass (at `nop-ai-core/.../support/Metadata.java:24`) provides an arbitrary `Map<String, Object> metadata` — but there is no typed `tenantId` field, no documentation that tenant context should be stored as metadata, and no `ITenantResolver` integration. Compare this to every DB table class in nop-ai-agent (e.g., `AiAgentSessionTable.COL_TENANT_ID`, `AiAgentMessageTable.COL_TENANT_ID`, `NopAiChatResponseTable.COL_TENANT_ID`) which explicitly defines a `TENANT_ID` column.
- **Severity**: P1
- **Status**: The entire DB-backed half of the codebase (sessions, messages, teams, usage, locks, daemon coordination) has been systematically retrofitted with `TENANT_ID` columns and `ITenantResolver`-based SQL injection (via `TenantSql.whereTenant`). The vector store options API has **no equivalent**. This is a systematic exclusion from the multi-tenant retrofit.
- **Risk**: When a concrete `IVectorStore` implementation is finally written, it will have no tenant isolation contract at the API level. The implementor must independently discover and apply the tenant isolation pattern, which will likely be missed. Result: vectors from tenant A will be returned in searches from tenant B.
- **Recommendation**: Add a typed `tenantId` field to `VectorStoreOptions`, document that implementations MUST filter by tenant context, and add a `withTenantId(String)` convenience method mirroring the existing `partitionName(String)` pattern.

### [AR-3] IEmbeddingModel has no authentication / tenant context parameters

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/embedding/IEmbeddingModel.java:10-22`
- **Evidence**:
  ```java
  public interface IEmbeddingModel {
      CompletionStage<VectorData> embedAsync(AiDocument doc, EmbeddingOptions options);
      CompletionStage<List<VectorData>> embedAllAsync(List<AiDocument> docs, EmbeddingOptions options);
  }
  ```
  `EmbeddingOptions` (at `EmbeddingOptions.java:6-16`) only has a `model` field — no `apiKey`, `tenantId`, `authToken`, or any authentication/authorization parameter. A production implementation wrapping a paid LLM embedding API would need to embed API keys in the implementation class itself (no way to pass them per-request).
- **Severity**: P1
- **Status**: If a real embedding model implementation (e.g., OpenAI / Cohere / HuggingFace API wrapper) were written against this interface, there would be no way to:
  - Pass an API key per-request (forcing the implementation to hardcode or read from a shared config)
  - Associate the embedding with a tenant context
  - Authorize or audit which user/tenant issued the embedding request
- **Risk**: API key management is pushed into the implementation layer with no contract-level guidance. Different implementations will handle keys differently (hardcoded, config file, env var), creating a security inconsistency. Embedding API calls cannot be attributed to any tenant.
- **Recommendation**: Add an extensible auth/context mechanism to `EmbeddingOptions` (or create an `EmbeddingRequest` envelope that includes credentials + tenant context). At minimum, add a `tenantId` field to `EmbeddingOptions` for audit attribution.

### [AR-4] Agent-layer vector/embedding adapters have per-session but no tenant isolation

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/memory/IVectorAdapter.java:38-44`, `IEmbeddingAdapter.java:44-50`, `AdapterBackedAiMemoryStore.java:56-304`, `InMemoryVectorAdapter.java:38-104`
- **Evidence**:
  ```java
  // IVectorAdapter — per-session, no tenant scope
  public interface IVectorAdapter {
      void index(String itemKey, double[] vector);
      List<String> search(double[] queryVector, int topK);
      void remove(String itemKey);
  }
  ```
  The `AdapterBackedMemoryStoreProvider` (at `AdapterBackedMemoryStoreProvider.java:35-80`) has two construction modes:
  1. **Shared adapters**: `new AdapterBackedMemoryStoreProvider(storage, embedding, vector)` — all sessions share the SAME adapter instances
  2. **Per-session factories**: `new AdapterBackedMemoryStoreProvider(factory)` — each session gets its own adapters
  
  The shared-adapter mode (mode 1) **completely bypasses isolation** — all sessions share the same `InMemoryVectorAdapter` map and `InMemoryStorageAdapter` map. Mode 2 (per-session factory) provides session-level isolation but has **no tenant-level isolation**: two sessions belonging to different tenants but having different session IDs are correctly isolated, but if a session ID is leaked/guessed, there is no tenant boundary check. The `IVectorAdapter` and `IStorageAdapter` interfaces have no `tenantId` parameter, unlike the DB-backed stores which all use `ITenantResolver`.
- **Severity**: P1
- **Status**: The shared-adapter mode (mode 1) is used in the production wiring path (`DefaultAgentEngine.Builder` → `AdapterBackedMemoryStoreProvider` constructor with explicit adapters). When adapters are shared, the `InMemoryVectorAdapter.map` and `InMemoryStorageAdapter.map` are a single `ConcurrentHashMap` shared across ALL sessions. Any session can `search()` against vectors indexed by any other session.
- **Risk**: In multi-tenant deployments using the shared-adapter construction (the default when adapters are explicitly provided), every session's vector data is visible to every other session. Memory items stored by tenant A are searchable by tenant B. The per-session factory mode is safe, but the API's dual-mode nature is a footgun — the simpler (and implicitly encouraged) construction is the less secure one.
- **Recommendation**: Deprecate the shared-adapter constructor of `AdapterBackedMemoryStoreProvider`. Require the per-session `StoreFactory` pattern for production use, where each session gets its own isolated adapter instances. Alternatively, add `tenantId` to `IVectorAdapter`/`IStorageAdapter` so implementations can filter by tenant.

### [AR-5] EmbeddingModelBasedClassifier has no authorization — any caller can classify any text

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/classifier/EmbeddingModelBasedClassifier.java:35-98`
- **Evidence**:
  ```java
  public class EmbeddingModelBasedClassifier implements ITextClassifier, IDocumentClassifier {
      private final IEmbeddingModel embeddingModel;
      private final Map<String, List<VectorData>> exampleEmbeddingsByLabel;
      private final EmbeddingOptions embeddingOptions;

      public ClassificationResult classifyDocument(AiDocument document) {
          VectorData textEmbedding = embeddingModel.embed(document, embeddingOptions);
          // ... compares against exampleEmbeddingsByLabel
      }
  }
  ```
  The classifier stores `exampleEmbeddingsByLabel` as a `Map<String, List<VectorData>>` computed at construction time from `EmbeddingExampleConfig`. There is no tenant context, no authorization check, and no isolation between classifiers for different tenants. The example embeddings (which may contain sensitive labeled data) are shared across all callers who hold a reference to the classifier. The `EmbeddingOptions` passed to the embedding model has no tenant context (see AR-3).
- **Severity**: P2
- **Status**: The `EmbeddingExampleConfig.getExampleEmbeddings()` method (at `EmbeddingExampleConfig.java:50-53`) calls `embeddingModel.embedAll(docs, embeddingOptions)` at construction time to pre-compute example embeddings. If the example documents contain tenant-specific content, the classifier leaks that content's embeddings to any caller. The classifier also passes the same `EmbeddingOptions` (with no tenant context) — so even if the embedding model implementation were tenant-aware, the classifier cannot propagate tenant identity.
- **Risk**: Classification labels and example embeddings could leak across tenants. A classifier trained on tenant A's labeled data could be used by tenant B's caller. The embedding API calls from classification are not attributable to any tenant.
- **Recommendation**: Add a `tenantId` context parameter to `ITextClassifier.classifyText()` and `IDocumentClassifier.classifyDocument()`. Refactor `EmbeddingExampleConfig` to compute example embeddings lazily per tenant rather than eagerly at construction.

### [AR-6] nop-ai-rag module is an empty shell — no production vector store exists

- **Severity**: P3
- **Status**: The `nop-ai-rag` module exists as a placeholder — presumably intended to hold production vector store implementations (FAISS, pgvector, Milvus) — but has never been populated. Code in `nop-ai-agent` (e.g., `InMemoryVectorAdapter.java:35`) comments reference "a real vector-store implementation (wrapping nop-ai-core IVectorStore against FAISS / pgvector / Milvus) is an explicit successor", confirming this is known and deferred.
- **Risk**: Low (nothing depends on it yet). However, when the module is eventually populated, the implementor must independently discover the tenant isolation patterns documented in this audit. The empty module is a code smell — someone may start adding implementations without understanding the isolation requirements.
- **Recommendation**: Either remove the empty module to avoid confusion, or add a README documenting the required tenant isolation contract and linking to this audit report.

### [AR-7] Memory store adapters are not integrated with ITenantResolver, unlike all other DB stores

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/memory/` (all 17 files)
- **Evidence**: Compare the memory store adapters with any DB-backed store:
  - `DBSessionStore.java:178` uses `TenantSql.whereTenant(AiAgentSessionTable.COL_TENANT_ID)`
  - `DBMessageService.java:350` uses `TenantSql.whereTenant(AiAgentMessageTable.COL_TENANT_ID)`
  - `DbTeamManager.java:353` uses `TenantSql.whereTenant(AiAgentTeamTable.COL_TENANT_ID)`
  - `DbUsageRecorder.java:139` writes `COL_TENANT_ID`
  
  But in `InMemoryStorageAdapter.java:44`, `InMemoryVectorAdapter.java:42` — zero tenant awareness:
  ```java
  // InMemoryStorageAdapter
  private final Map<String, AiMemoryItem> items = new ConcurrentHashMap<>();
  
  // InMemoryVectorAdapter
  private final Map<String, double[]> index = new HashMap<>();
  ```
  Neither class has an `ITenantResolver` field, neither filters by tenant, neither has a `tenantId` column or map key prefix. The `IStorageAdapter` and `IVectorAdapter` interfaces define no tenant parameter.
- **Severity**: P1
- **Status**: The entire DB-backed layer has been systematically retrofitted with tenant isolation via `ITenantResolver` + `TenantSql`. The memory store adapters — which are the default shipped wiring (`InMemoryMemoryStoreProvider` is the engine default) and the functional reference for the adapter-backed store — have **zero tenant awareness**. This is a systematic gap in the tenant isolation retrofit.
- **Risk**: In a multi-tenant deployment, the shipped default `InMemoryMemoryStoreProvider` stores all tenants' memory items in a shared `ConcurrentHashMap<String, InMemoryAiMemoryStore>` keyed by `sessionId`. If session IDs are predictable or not universally unique, tenant A's session could resolve to a store pre-populated by tenant B's earlier session with the same ID. The `AdapterBackedAiMemoryStore` with shared adapters (mode 1, AR-4) has the same issue at the vector index level.
- **Recommendation**: Add `ITenantResolver` to `InMemoryStorageAdapter`, `InMemoryVectorAdapter`, and `InMemoryAiMemoryStore`. At minimum, prefix in-memory map keys with the resolved `tenantId` when non-null. Document in the `IStorageAdapter` and `IVectorAdapter` contracts that implementations MUST respect tenant isolation.

## Blind Spot Self-Assessment

This audit was limited to code inspection of the vector store and embedding APIs in `nop-ai-core` and the memory adapters in `nop-ai-agent`. The following were not assessed:
- The `nop-ai-rag/target/` precompiled JAR contents (no source available) — there may be classes inside that we could not review
- Cross-session vector index pollution through shared threads (race conditions in `InMemoryVectorAdapter`)
- The MCP (Model Context Protocol) modules — excluded per roadmap scope, but they may contain additional vector store integrations
- Third-party vector store clients (e.g., Pinecone, Weaviate, Qdrant) — none exist in the codebase yet
