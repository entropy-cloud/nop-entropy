## 框架级隔离机制确认（基线）

- 每个测试类 `beforeAll` 生成唯一 UUID 的 ORM H2 库（`NopTestConfigProcessor.java:39`，无 DB_CLOSE_DELAY → 容器每方法 restart 关闭连接池时库被丢弃，方法间 ORM 数据基本隔离）
- 外置 H2 库（`jdbc:h2:mem:xxx;DB_CLOSE_DELAY=-1`）JVM 级存活，跨类共享 ← 风险点
- 每类 `afterAll` 重置时钟 + destroy（`NopJunitExtension.java:64-68`）；`beforeAll` 每类 `AppConfig.getConfigProvider().reset()`（:31）→ 配置类间隔离由框架保证

## 16-05 交叉复核（TestCheckpointActionDispatcherConcurrency）

| 项 | 登记状态（16-05：并发测试无共享状态验证） | Live 核验结果 |
|----|------------------------------------------|--------------|
| 共享状态验证 | "no shared-state verification" | **实质准确**：测试确在 :75-78/:117-121 断言 `collected.size()==threadCount*repeats`，但 collected 是测试自己每线程私有 summary 的累加（:44 synchronizedList + :52 add）；SUT（null 依赖的 dispatcher）无任何共享可变状态（CheckpointActionDispatcher.java:77-88 仅实例字段，null 注入下无外部 I/O），断言只验证测试自身累加器，不触及 SUT 共享态 |
| 线程/屏障/线程内断言 | — | 4×4（ExecutorService 4 线程）与 8×1；无 start 屏障但线程数=池大小 → 重叠近必然；latch.await(15s/10s) 有界；线程内断言 errs.size()!=2 → failures++（:54-57） |
| 自身竞态 | — | 无：AtomicInteger + synchronizedList + CountDownLatch 全线程安全 |
| 对其他测试隔离 | — | 无 static、无容器依赖（纯 JUnit）、无顺序依赖 |

**裁决（16-05）**：**真测试但浅（P3）**——真实起线程、有界等待、线程内断言、死锁/异常冒烟有效，非空洞测试；但 javadoc 声称"验证并发操作产生一致的最终状态"（:27-28）言过其实：串行执行同样全绿，未触达 SUT 任何共享状态（无 shared state 可验证），只覆盖失败路径。登记维持（不是"无共享状态验证"的缺陷升级，而是文档过度宣称 + 覆盖局限），定级 P3 非 P1。
