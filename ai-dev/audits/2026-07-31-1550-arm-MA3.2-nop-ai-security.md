7. **P2-MA3-026**: No permission/role attributes (`rights`/`roles`) in any xbiz action definition.

## Findings

### [D13-1] P1-MA3-020: BizModel methods lack `@Auth` permission annotations

- **File**: `nop-ai/nop-ai-service/src/main/java/io/nop/ai/service/entity/NopAiChatResponseBizModel.java`
- **Line range**: 58–65
- **Evidence**:
  ```java
  @Override
  @BizQuery
  public List<ModelUsageSummary> summarizeByModel(@Name("sessionId") String sessionId, IServiceContext context) {
      if (StringHelper.isBlank(sessionId)) {
          throw new NopException(ERR_AI_SESSION_ID_REQUIRED).param(ARG_SESSION_ID, sessionId);
      }
      return orm().findAll(buildSummarySql(sessionId), ROW_MAPPER);
  }
  ```
  Also applies to `FileToolBizModel` (15 methods) and `SequentialThinkingBizModel` (3 methods) — all lack `@Auth`.

- **Severity**: P1
- **Current state**: Zero `@Auth` annotations exist on any nop-ai BizModel method. The `@Auth` annotation exists in the framework (`io.nop.api.core.annotations.directive.Auth`) and is used extensively in other modules (nop-code: 60+ usages, nop-auth: 11+ usages). The nop-ai module group has zero usages across 18+ BizModel methods.
- **Risk**: Every custom GraphQL query/mutation (file read/write, shell execution, token usage aggregation, thought processing) is publicly accessible without authentication or authorization checks. If `nop-ai` is deployed in a multi-tenant or authenticated context, any user can invoke any tool.
- **Suggestion**: Add `@Auth(permissions = "NopAiModel:query")` or equivalent on each BizModel method. At minimum, the `FileToolBizModel` (which exposes file read/write/delete) and `BashExecutor` callers should be permission-gated. Consider adding a module-level permission prefix convention (e.g., `NopAi*`) following nop-code's pattern.
- **Confidence**: High — confirmed by full grep of nop-ai Java, xbiz, and XML sources; zero `@Auth`/`rights`/`roles` hits.
- **False-positive exclusion**: Not a platform convention gap. Other modules (nop-code, nop-auth) demonstrate the expected pattern. The `@Auth` annotation is a runtime, not build-time, constraint — no compiler error for missing it.

### [D13-2] P1-MA3-021: Sensitive `apiKey` field unrestricted in xmeta

- **File**: `nop-ai/nop-ai-meta/src/main/resources/_vfs/nop/ai/model/NopAiModel/_NopAiModel.xmeta`
- **Line range**: 38–41
- **Evidence**:
  ```xml
  <prop name="apiKey" displayName="API密钥" propId="5" queryable="true" sortable="true" insertable="true"
        updatable="true">
      <schema type="java.lang.String" precision="100"/>
  </prop>
  ```
  The field has no `internal="true"`, no `maskPattern`, no `ui:show` restriction, and is `queryable="true" sortable="true"`.

- **Severity**: P1
- **Current state**: `apiKey` stores API credentials for LLM providers. It is fully exposed through the GraphQL layer — queryable, sortable, insertable, updatable. Any authenticated user can read, list, sort, and modify all stored API keys. There is no mask pattern or storage encryption indicated.
- **Risk**: Credential leakage — API keys stored in plaintext are enumerable via GraphQL queries. An attacker with any GraphQL access can extract all provider API keys and use them to invoke LLM services at the project's expense, or pivot to the provider's other services.
- **Suggestion**: Set `internal="true"` in xmeta to hide from default GraphQL selection. Consider `maskPattern="***"` for logging/display. For write operations, use a separate input DTO that never echoes the value back. Evaluate encryption-at-rest for the `apiKey` column (AES-256 or KMS).
- **Confidence**: High — the xmeta property is clearly identifiable as a credential with no restrictions.
- **False-positive exclusion**: This is not a field where internal/protected semantics would break GraphQL functionality (unlike primary keys). The `baseUrl` field (which is not sensitive) has the same unrestricted pattern, which is acceptable; `apiKey` is categorically different.

### [D13-3] P1-MA3-022: Absolute path bypass in `LocalFileOperator.resolveFile()`

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/file/LocalFileOperator.java`
- **Line range**: 70–76
- **Evidence**:
  ```java
  private File resolveFile(String path) {
      if (path.contains("..") || path.contains(":")) {
          throw new NopException(ERR_FILE_INVALID_PATH)
                  .param(ARG_PATH, path);
      }
      return path.isEmpty() ? baseDir : new File(baseDir, path);
  }
  ```
  On Unix: `new File(new File("/nop/projects"), "/etc/passwd")` returns `/etc/passwd`, not `/nop/projects/etc/passwd`.

- **Severity**: P1
- **Current state**: The `resolveFile` method only blocks `..` (directory traversal) and `:` (Windows drive letters). It does not check for absolute paths starting with `/`. On Unix/Linux/MacOS, `java.io.File` treats a path starting with `/` as absolute, ignoring the parent baseDir. This means all file read/write/glob/delete operations in `LocalFileOperator` can escape the `baseDir` sandbox by passing an absolute path.
- **Risk**: Arbitrary file read/write outside the intended workspace. `FileToolBizModel` exposes this through `readFiles`, `saveFile`, `mergeFile`, `delete`, `glob`, `grep` — all of which accept user-controlled `filePath` parameters. An attacker could read `/etc/passwd`, write to arbitrary paths, or delete system files.
- **Suggestion**: Add an explicit check for absolute paths:
  ```java
  if (new File(path).isAbsolute()) {
      throw new NopException(ERR_FILE_INVALID_PATH).param(ARG_PATH, path);
  }
  ```
  Alternatively, use `FileHelper.getAbsoluteFile(baseDir)` + manual path resolution that rejects root-anchored paths.
- **Confidence**: High — the code logic is clear and the behavior of `java.io.File` with absolute paths is well-defined.
- **False-positive exclusion**: This is a real path traversal vulnerability, not a false alarm. The `..` check shows awareness of path traversal but misses the absolute-path vector. The `:` check (for Windows) shows partial defense-in-depth.

### [D13-4] P2-MA3-023: `DefaultCommandChecker` is a no-op

- **File**: `nop-ai/nop-ai-shell/src/main/java/io/nop/ai/shell/checker/DefaultCommandChecker.java`
- **Line range**: 5–11
- **Evidence**:
  ```java
  public class DefaultCommandChecker implements ICommandChecker {

      @Override
      public String check(SimpleCommand command, ICommandCheckContext context) {
          return null;
      }
  }
  ```
  Used in `ShellCommandExecutor` (line 38: `private final ICommandChecker checker;`) with no default replacement — when `checker` is null, the `checkAst` call is skipped (line 69: `if (checker != null)`).

- **Severity**: P2
- **Current state**: The `ICommandChecker` interface exists and `ShellCommandExecutor` supports it, but the default implementation (`DefaultCommandChecker`) returns `null` for every command (null means "allowed"). Furthermore, the `ShellCommandExecutor` constructor at line 57–59 (`ShellCommandExecutor(ShellCommandRegistry, IToolFileSystem)`) passes `null` for the checker, so the entire command-filtering path is disabled by default.
- **Risk**: Any command that reaches the shell executor (including arbitrary commands from AI agent tool calls) executes without any allowlist/denylist filtering. The `ShellCommandExecutor` can execute registered internal commands + external OS commands via `ExternalCommandAdapter`.
- **Suggestion**: Either (a) make `DefaultCommandChecker` implement a reasonable default deny-list/allow-list (e.g., reject `rm -rf`, `mkfs`, `dd`, etc.), or (b) wire the `ShellCommandExecutor` with a non-null checker by default in the IoC configuration, or (c) document explicitly in design docs that a production deployment MUST supply a custom `ICommandChecker`.
- **Confidence**: High — code is clear and unambiguous.
- **False-positive exclusion**: The interface exists for a reason (command filtering). Having a no-op default is a known anti-pattern. This is not a platform convention — it's a missing security control.

### [D13-5] P2-MA3-024: `BashExecutor` runs arbitrary shell commands with no validation

- **File**: `nop-ai/nop-ai-toolkit/src/main/java/io/nop/ai/toolkit/tools/BashExecutor.java`
- **Line range**: 32–48
- **Evidence**:
  ```java
  private AiToolCallResult doExecute(AiToolCall call, IToolExecuteContext context) {
      try {
          String command = call.childText("command", "");
          // ...
          ProcessBuilder pb = new ProcessBuilder();
          if (isWindows()) {
              pb.command("cmd", "/c", command);
          } else {
              pb.command("sh", "-c", command);
          }
  ```
  The command string comes directly from the AI tool call (`call.childText("command", "")`) with zero validation, sanitization, or allowlist checking.

- **Severity**: P2
- **Current state**: `BashExecutor` is a registered AI tool that accepts arbitrary `command` text from the LLM and passes it to `sh -c`. There is no sandboxing, no command allowlist/denylist, no argument validation, and no path restriction. The `timeoutMs` and `workingDir` are the only controls applied. Compare with `DockerSandboxBackend` in nop-ai-agent which has proper validation (`validateHostPath`, `validateEnvironmentVariableKey`, `allowedBaseDirs`).
- **Risk**: An LLM (or attacker-injecting via the LLM) can execute arbitrary shell commands on the host with the application's privileges. This includes file deletion, network access, process manipulation, and credential exfiltration.
- **Suggestion**: At minimum, (a) add a command allowlist or denylist, (b) validate arguments for dangerous patterns (`rm -rf`, `> /dev/sda`, etc.), (c) consider routing through `DockerSandboxBackend` for isolation, (d) restrict execution to within a configurable workspace directory, (e) add `@Auth` permission annotation to the tool's BizModel entry point.
- **Confidence**: High — the code path is straightforward and the lack of validation is clear.
- **False-positive exclusion**: This is not a convention issue — it is a missing security control on an intentionally dangerous operation. The nop-ai-agent sandbox infrastructure (`ISandboxBackend`, `DockerSandboxBackend`) exists but is not used by `BashExecutor`.

### [D13-6] P2-MA3-025: Zero `DataAuth` usage across all nop-ai modules

- **Evidence**: Full grep of `nop-ai/**/*.{java,xml,xmeta,xbiz}` for `DataAuth`, `IDataAuth`, `dataAuth` — zero results.
- **Severity**: P2
- **Current state**: The Nop platform's `DataAuth` mechanism for row-level/column-level data access filtering (via `IDataAuth` interface and filter decorators) is not used anywhere in any nop-ai module. All CRUD operations through `CrudBizModel` inheritance have no data-scoping filters.
- **Risk**: In a multi-tenant or multi-user deployment, users can access any entity instance regardless of ownership. For example, `NopAiSession` records are not scoped to the current user — a user could query or modify sessions belonging to other users. No built-in filtering for `createdBy` or project-scoped access.
- **Suggestion**: Implement `DataAuth` filter configurations per entity, or at minimum add filter conditions in xbiz `query`/`find` actions that scope by `createdBy` (or equivalent tenant/project ID). The `NopAiProjectConfig`, `NopAiSession`, and `NopAiModel` entities are high-priority candidates.
- **Confidence**: Medium — the absence of DataAuth may be acceptable if the deployment model is single-user or if access control is handled at a higher layer (API Gateway, network). However, the audit cannot confirm such an external control, and the module provides zero internal data isolation.
- **False-positive exclusion**: DataAuth is an elective framework feature, not mandatory. However, in modules that store user-owned data (sessions, projects, API keys), its absence is notable. This is flagged at P2 because multi-tenancy readiness is a real concern.

### [D13-7] P2-MA3-026: No permission/role attributes in any xbiz action definition

- **Evidence**: Full grep of `nop-ai/**/*.xbiz` for `rights=`, `roles=`, `permissions=`, `auth` — zero results. All 42 xbiz files.
- **Severity**: P2
- **Current state**: Every xbiz action (standard CRUD: `save`, `update`, `delete`, `find`, `get`, `batchDelete`, `batchModify`, etc.) inherits from `CrudBizModel` without any `rights` or `roles` attribute override in the xbiz XML. No custom action defines permission requirements either.
- **Risk**: In the Nop platform, xbiz-level `rights`/`roles` attributes provide declarative action-level access control. Without these, all CRUD operations on every nop-ai entity are accessible to any user with GraphQL access. Combined with D13-1 (no `@Auth` in Java) and D13-6 (no DataAuth), the entire module group has no declarative or programmatic access control.
- **Suggestion**: Add `rights="NopAiModel:query"` (and variants) to xbiz action definitions following the pattern from other modules. For example:
  ```xml
  <action name="find" rights="NopAiModel:query"/>
  <action name="save" rights="NopAiModel:save"/>
  ```
- **Confidence**: High — grep confirms zero attribute usage.
- **False-positive exclusion**: While `CrudBizModel` provides default implementations, the permission attributes are still required for access control — they are not inherited from the Java class. Other Nop modules (nop-code, nop-auth) demonstrate the pattern.
