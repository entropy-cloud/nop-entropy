## Executive Summary

This audit examined the `nop-ai` module group (20+ submodules) for Delta Customization compliance following Nop platform conventions. The overall assessment is **satisfactory but with actionable findings**.

**Positive highlights**:
- `x:extends` is used correctly and consistently across all retention file types (`.xmeta`, `.xbiz`, `.view.xml`, `.orm.xml`, `.action-auth.xml`, `.i18n.yaml`, `module-meta.json`)
- All `_`-prefixed generated files are properly separated from retention files
- No hand-edits to generated files were found in production source directories
- `x:gen-extends` and `x:post-extends` patterns are correctly applied in generated files
- The `_service.beans.xml` correctly uses `x:extends` to inherit from `/nop/biz/defaults/service-base.beans.xml`
- Page `.view.xml` files correctly reference `_gen/_*.view.xml`

**Critical issues found**:
- **9 orphaned snake_case dict files** in `nop-ai-meta` — stale leftovers from a naming-inconsistent period, not referenced anywhere, content substantially different from their kebab-case counterparts (P1)
- **Dual-sourced dict definitions** — same dicts defined inline in ORM AND as standalone YAML files, creating maintenance burden (P2)
- **Missing zh-CN i18n for nop-ai-web** (P2)
- **No production `_delta/` directories** across all nop-ai modules (P3, expected for framework)

### P1-D06-018: Orphaned snake_case Dict Files in nop-ai-meta

| Field | Value |
|-------|-------|
| **Severity** | P1 |
| **File** | `nop-ai/nop-ai-meta/src/main/resources/_vfs/dict/ai/` |
| **Type** | Dead code / stale files |

**Files affected** (9 files total):

| Orphaned snake_case file | Established kebab-case counterpart |
|---|---|
| `config_type.dict.yaml` | `config-type.dict.yaml` |
| `file_format.dict.yaml` | `file-format.dict.yaml` |
| `message_type.dict.yaml` | `message-type.dict.yaml` |
| `model_provider.dict.yaml` | `model-provider.dict.yaml` |
| `module_type.dict.yaml` | `module-type.dict.yaml` |
| `project_language.dict.yaml` | `project-language.dict.yaml` |
| `requirement_type.dict.yaml` | `requirement-type.dict.yaml` |
| `rule_type.dict.yaml` | `rule-type.dict.yaml` |
| `status_type.dict.yaml` | `status-type.dict.yaml` |

**Evidence**:

1. **Naming violation**: Nop convention mandates kebab-case for all resource paths. These files use snake_case.

2. **Unreferenced**: Grep across the entire `nop-ai/` tree for `ai/message_type`, `ai/config_type`, etc. returns zero matches in XML/YAML files. The ORM model only references kebab-case dict names (e.g., `ext:dict="ai/message-type"`).

3. **Draft/incomplete content**: File timestamps show snake_case files are dated **Mar 25** while kebab-case files are dated **Jun 8**, suggesting the snake_case were early drafts never cleaned up. Content comparison shows substantial differences:
   - `message_type.dict.yaml`: valueType empty, only **2 options** (002, 003), description: "对话消息的角色类型"
   - `message-type.dict.yaml`: valueType `int`, **8 options** (10–80), description: empty
   - `config_type.dict.yaml`: valueType empty
   - `config-type.dict.yaml`: valueType `string`

4. The 9 kebab-case counterparts are correctly defined, referenced, and contain the proper data.

**Risk**: Dead files waste developer attention and create confusion about which file is authoritative. If accidentally referenced, they would load incomplete/wrong dict definitions (e.g., `message_type` has only 2 message types vs the 8 in `message-type`).

**Recommendation**: **Delete** all 9 snake_case `*_type.dict.yaml` files. They are unreferenced, unmaintained, and dangerous if discovered by auto-loading logic.

### P2-D06-019: Dual-Sourced Dict Definitions (ORM + Standalone Files)

| Field | Value |
|-------|-------|
| **Severity** | P2 |
| **Modules** | `nop-ai-dao` (ORM), `nop-ai-meta` (standalone dicts) |
| **Type** | Maintenance burden / potential drift |

**Evidence**:

Same dict names are defined in two separate places:

**Source A** — ORM embedded dicts in `nop-ai-dao/src/main/resources/_vfs/nop/ai/orm/_app.orm.xml` lines 17–108:
```xml
<dicts>
    <dict label="消息类型" name="ai/message-type" valueType="int" ...>
        <option code="USER" value="10"/>  <!-- 8 options -->
    </dict>
    <dict label="文件格式" name="ai/file-format" valueType="string" ...>
        <option code="TEXT" value="001"/>  <!-- 2 options -->
    </dict>
    <!-- ... 13 dicts total -->
</dicts>
```

**Source B** — Standalone dict files in `nop-ai-meta/src/main/resources/_vfs/dict/ai/`:
- `message-type.dict.yaml`, `file-format.dict.yaml`, `config-type.dict.yaml`, `model-provider.dict.yaml`, `project-language.dict.yaml`, `requirement-type.dict.yaml`, `rule-type.dict.yaml`, `status-type.dict.yaml`, `session-status.dict.yaml`, `todo-status.dict.yaml`, `todo-priority.dict.yaml`, `input-delivery.dict.yaml`, `event-type.dict.yaml`, `compaction-type.dict.yaml`, `module-type.dict.yaml`

The ORM defines 14 dict names inline. The standalone directory defines 15 dict files (13 overlap with ORM, 2 are ORM-only: `compaction-type`, `event-type`).

**Risk**: These two sources must be manually kept in sync. If the ORM's inline dicts are updated (e.g., a new option added to `ai/message-type`), the standalone dict file must be updated separately or drift occurs. Currently they are aligned, but there's no automated mechanism enforcing consistency.

**Recommendation**: Choose one authoritative source:
- **Option A (recommended)**: Keep dicts in ORM only and generate standalone dict files via codegen during build, or remove standalone files and let runtime resolve dicts from ORM definitions.
- **Option B**: Keep standalone dicts as authoritative and remove inline dicts from ORM (ORM can still reference by name). This is cleaner but requires ORM codegen changes.
- **Minimum**: Add a build-time validation that checks standalone dict YAML content matches ORM `<dicts>` section.

### P2-D06-020: Missing zh-CN i18n for nop-ai-web

| Field | Value |
|-------|-------|
| **Severity** | P2 |
| **File** | Missing: `nop-ai-web/src/main/resources/_vfs/i18n/zh-CN/` |
| **Type** | Incomplete localization |

**Evidence**:

`nop-ai-meta` has complete i18n locale pairs:
```
nop-ai-meta/src/main/resources/_vfs/i18n/en/  ← "x:extends" + _ files
nop-ai-meta/src/main/resources/_vfs/i18n/zh-CN/  ← "x:extends" + _ files
```

`nop-ai-web` has only English:
```
nop-ai-web/src/main/resources/_vfs/i18n/en/  ← exists
nop-ai-web/src/main/resources/_vfs/i18n/zh-CN/  ← MISSING
```

The English i18n for web (`nop-ai-web.i18n.yaml` using `"x:extends": _nop-ai-web.i18n.yaml`) defines labels for `site.resource.*.displayName` entries including all permission labels and menu labels. Without a zh-CN counterpart, Chinese UI users see English labels for the action-auth defined resources.

**Risk**: Incomplete Chinese localization for the web module. All menu items, permission labels, and resource names under the `nop-ai` admin site will appear in English when the system locale is set to zh-CN.

**Recommendation**: Create `nop-ai-web/src/main/resources/_vfs/i18n/zh-CN/` with:
- `_nop-ai-web.i18n.yaml` containing Chinese translations matching the English keys
- `nop-ai-web.i18n.yaml` using `"x:extends": _nop-ai-web.i18n.yaml`

### P3-D06-021: No Production `_delta/` Directories in nop-ai Modules

| Field | Value |
|-------|-------|
| **Severity** | P3 |
| **Modules** | All 20+ nop-ai submodules |
| **Type** | Missing customization infrastructure (expected) |

**Evidence**:

```
$ find nop-ai -type d -name "_delta"
nop-ai/nop-ai-agent/src/test/resources/_vfs/_delta
nop-ai/nop-ai-agent/target/test-classes/_vfs/_delta
```

Only *test-resource* delta directories exist (in `nop-ai-agent` for test agent config overriding). Zero production `_delta/` directories across all nop-ai submodules.

**Assessment**: For a **framework module group** like `nop-ai`, this is the expected state. Framework modules are the base layer; downstream projects/application modules create their own `_delta/` directories when they need to override `nop-ai` behavior. The absence of production deltas here confirms the nop-ai group is properly positioned as a foundational layer.

**However**, there are two risks:
1. If a nop-ai submodule needs internal delta customization between its own submodules (e.g., `nop-ai-web` customizing `nop-ai-core`), no mechanism exists.
2. New developers may not understand where to put their overrides.

**Recommendation**: 
- Document this as an explicit design decision in `docs-for-ai/01-repo-map/module-groups.md`
- If any nop-ai module requires first-party delta overrides (e.g., for different deployment variants), create `_delta/default/` with clear documentation
