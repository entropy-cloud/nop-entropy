### [D09-1 / P1-MA3-1] AiCoreErrors: `ERR_AI_RESULT_INVALID_NUMBER` description has `value={name}` instead of `value={value}`

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/AiCoreErrors.java:66-67`
- **Evidence**:
  ```java
  ErrorCode ERR_AI_RESULT_INVALID_NUMBER =
          define("nop.err.ai.service.result-invalid-number", "大语言模型返回的结果不是数字:name={name},value={name}", ARG_NAME, ARG_VALUE);
  ```
- **Severity**: P1
- **Status**: The error code description template references `{name}` twice but defines `ARG_VALUE` as a separate parameter. The second placeholder should be `{value}` to match `ARG_VALUE`. When both `ARG_NAME` and `ARG_VALUE` are passed via `.param()`, the rendered message will incorrectly show `value={name}` instead of `value={actualValue}`.
- **Risk**: Confusing error messages when a non-numeric value is encountered; the actual value is lost from the message and replaced by the parameter name. This complicates debugging and AI-powered repair loops that parse error output.
- **Suggestion**: Change the second `{name}` to `{value}` in the description string: `"大语言模型返回的结果不是数字:name={name},value={value}"`.
- **Confidence**: Certain (template clearly mismatches ARG_* constants).
- **False-positive exclusion**: Not a generated file; hand-written ErrorCode definition. Not a formatting/style issue — it's a correctness bug where the rendered message will produce wrong output.
- **Review status**: Unreviewed

### [D09-2 / P1-MA3-2] BizModel public API uses IllegalArgumentException instead of ErrorCode mode

- **File**: `nop-ai/nop-ai-tools/src/main/java/io/nop/ai/tools/sequential_thinking/service/SequentialThinkingBizModel.java:51-68`
- **Evidence**:
  ```java
  @BizMutation
  public ThoughtAnalysis processThought(@RequestBean ProcessThoughtRequest request, IServiceContext ctx) {
      ...
      if (thought == null || thought.trim().isEmpty()) {
          throw new IllegalArgumentException("Thought cannot be empty");
      }
      if (request.getThoughtNumber() <= 0) {
          throw new IllegalArgumentException("Thought number must be positive");
      }
  ```
- **Severity**: P1
- **Status**: BizModel with `@BizMutation` annotation (public GraphQL API endpoint) throws bare `IllegalArgumentException` instead of using ErrorCode mode. Per the two-tier strategy, BizModel public API must use `NopException + ErrorCode + .param()`.
- **Risk**: This exception bypasses the framework's structured error response pipeline; the client receives a generic 500 without a proper error code, i18n, or structured param context. Other modules calling this BizModel cannot programmatically match on the error.
- **Suggestion**: Define an ErrorCode (e.g., `ERR_AI_TOOLS_INVALID_THOUGHT`) and throw `new NopException(ERR_...).param(...)`. Or at minimum use `NopAiException` (available via transitive dep on `nop-ai-api`).
- **Confidence**: Certain.
- **False-positive exclusion**: This is not a false positive — BizModel methods are the canonical example of tier-1 (public API / GraphQL) and must use ErrorCode mode per `docs-for-ai/02-core-guides/error-handling.md`. This is not an internal implementation detail.
- **Review status**: Unreviewed

### [D09-3 / P2-MA3-1] nop-ai-shell module: widespread IllegalArgumentException (100+ instances), no logger, no exception class

- **File**: `nop-ai/nop-ai-shell/src/main/java/io/nop/ai/shell/commands/ShellCommandRegistry.java:35-62` (representative sample)
- **Evidence**:
  ```java
  public void registerCommand(IShellCommand command) {
      if (command == null) {
          throw new IllegalArgumentException("Command cannot be null");
      }
      String name = command.name();
      if (name == null || name.trim().isEmpty()) {
          throw new IllegalArgumentException("Command name cannot be null or empty");
      }
  ```
- **Severity**: P2
- **Status**: The entire `nop-ai-shell` module uses bare `IllegalArgumentException` for all error conditions (100+ instances across 10+ files). No SLF4J logger is defined anywhere in the module. No module-level exception class is used. The module depends on `nop-ai-toolkit` which depends on `nop-ai-api`, so `NopAiException` is available via transitive dependency.
- **Risk**: `IllegalArgumentException` bypasses the Nop exception framework: no ErrorCode integration, no i18n, no structured error response. The shell module's errors cannot be programmatically caught or distinguished at system boundaries. No logging means silent failures.
- **Suggestion**: Replace all `IllegalArgumentException` with `NopAiException` (from `io.nop.ai.api.exceptions`). All messages are already in English, which is correct. Add SLF4J logger to the module and log errors before throwing.
- **Confidence**: Certain.
- **False-positive exclusion**: The module is internal implementation (so string-based NopAiException is acceptable per tier-2), but bare `IllegalArgumentException` is not NopException-compatible. This is not a style preference — it's a structural gap that prevents framework-level error handling.
- **Review status**: Unreviewed

## Noteworthy — Not Findings (excluded)

1. **AiCoreErrors.java Chinese descriptions**: All ErrorCode descriptions in AiCoreErrors use Chinese. Per `docs-for-ai/02-core-guides/error-handling.md`, `ErrorCode.define()` descriptions use Chinese for i18n. This is correct, not a finding.

2. **No Logs.java / ILogFactory pattern**: Unlike modules like `nop-auth` or `nop-core`, nop-ai modules do not follow the `Logs.java` / `ILogFactory` pattern for logger definitions. They use direct `LoggerFactory.getLogger()` instead. This is acceptable for non-framework modules and is not flagged.

3. **SandboxException pattern**: `SandboxException` extends `NopAiAgentException` and provides only `(String)` constructors (no `ErrorCode` constructor). This is intentional — sandbox failures are domain-specific internal exceptions that carry a `SandboxFailureReason` enum, not ErrorCodes. Acceptable.

4. **MCP modules excluded**: `nop-ai-mcp-server`, `nop-spring-mcp-server`, `nop-spring-mcp-server-support` were excluded per audit scope.

## Positive Observations

1. **NopAiException** in `nop-ai-api` is correctly designed with all four constructors (String, String+cause, ErrorCode, ErrorCode+cause) — matches the documented pattern in `error-handling.md`.

2. **NopAiAgentException** in `nop-ai-agent` has the same correct constructor pattern.

3. **nop-ai-core (AiCoreErrors.java)**: Well-organized ErrorCode interface with clear ARG_* constant conventions and `nop.err.ai.*` namespace prefix. Most ErrorCodes include appropriate context parameters.

4. **nop-ai-agent (session package)**: The session persistence layer correctly wraps all `IOException` with `NopAiAgentException(message, cause)`, preserving the exception chain. Good pattern.

5. **LocalFileOperator.java**: Correctly uses `NopException` with `ERR_FILE_*` ErrorCodes from `nop-commons.CommonErrors` — follows the tier-1 ErrorCode pattern for cross-module file operation API.

6. **Exception chain preservation**: All `NopAiAgentException(cause)` and `NopException(errorCode, cause)` usages in nop-ai-agent and nop-ai-core correctly preserve the original cause.

## Blind spots and limitations

- Only static code analysis was performed; runtime exception paths were not traced.
- The `nop-ai-web` module was not deeply inspected (no Java source — primarily XView/XMeta).
- The `nop-ai-rag` module had minimal exception code and was given a lighter review.
- Generated files (`_*` prefix) were excluded per audit scope.
