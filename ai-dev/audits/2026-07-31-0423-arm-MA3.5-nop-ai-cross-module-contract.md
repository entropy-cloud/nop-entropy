### P1-MA3-01: nop-ai-agent depends on core-internal `ChatOptionsModel`

**File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/engine/AgentExecutionContext.java:26`  
**Lines**: 11 (import), 26 (field declaration), 97-99 (assignment from AgentModel)

```java
// AgentExecutionContext.java:11
import io.nop.ai.core.model.ChatOptionsModel;

// AgentExecutionContext.java:26
private ChatOptionsModel chatOptionsModel;

// AgentExecutionContext.java:97-99
ChatOptionsModel chatOptions = agentModel.getChatOptions();
if (chatOptions != null)
    ctx.setChatOptionsModel(chatOptions);

// ReActAgentExecutor.java:3658
private ChatOptions buildChatOptions(ChatOptionsModel model, List<ChatToolDefinition> toolDefs) {
```

**Evidence** (15 references in agent module): AgentExecutionContext, ReActAgentExecutor, and PipelineCompactor all reference `io.nop.ai.core.model.ChatOptionsModel` directly. Additionally, `_gen/_AgentModel.java:40` declares a `@Prop` field typed as `io.nop.ai.core.model.ChatOptionsModel`, baking this dependency into generated code.

**Severity**: P1  
**State**: Open — active production code  
**Risk**: Any change to `ChatOptionsModel` (package rename, field type change, removal) breaks agent compilation. Compiler does not catch this because the dependency compiles fine — it is a coupling debt, not a compile error.  
**Suggestion**: Either (a) move `ChatOptionsModel` to `nop-ai-api` as a public DTO, or (b) have the agent convert from `ChatOptions` (api) to its own internal options representation instead of referencing core's model class directly.  
**Confidence**: High (95%)  
**False-positive exclusion**: This is not an api-core model generated file (`_gen/` prefix) — it is a hand-coded model class (`ChatOptionsModel.java`) that the agent module directly imports. The dependency is structural, not generated.

### P1-MA3-02: nop-ai-agent depends on core-internal `ILlmDialect` and `LlmDialectFactory`

**File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/engine/CalibratedTokenEstimator.java:4-6`  
**Lines**: 34-35 (field types), 39 (constructor parameter)


**Evidence**: `CalibratedTokenEstimator` imports three core-internal classes (`ILlmDialect`, `LlmDialectFactory`, `ApiStyle`) from `nop-ai-core.dialect` and `nop-ai-core.model`. These are implementation detail classes, not public API.

**Severity**: P1  
**State**: Open

**Confidence**: High (90%)  
**False-positive exclusion**: These are not generated classes — they are hand-written implementation interfaces and factories in core's dialect package. The agent should not reference them directly.

### P2-MA3-03: nop-ai-tools uses deprecated `IAiChatFunctionTool` / `IAiChatToolSet` from core

**File**: `nop-ai/nop-ai-tools/src/main/java/io/nop/ai/tools/graphql/GraphQLToolProvider.java:3-8`  
**Lines**: 3-8 (imports), method signatures

```java
// GraphQLToolProvider.java:3-8
import io.nop.ai.core.api.tool.DefaultAiChatFunctionTool;
import io.nop.ai.core.api.tool.DefaultAiChatToolSet;
import io.nop.ai.core.api.tool.IAiChatFunctionTool;
import io.nop.ai.core.api.tool.IAiChatToolSet;
import io.nop.ai.core.api.tool.ToolSpecification;
import io.nop.ai.core.api.tool.ToolSpecificationLoader;
```

**Evidence**: Production code in `nop-ai-tools` depends on deprecated interfaces `IAiChatFunctionTool` and `IAiChatToolSet` (annotated `@Deprecated` with "Please use the new AI API instead") and their concrete implementations (`DefaultAiChatFunctionTool`, `DefaultAiChatToolSet`). The `GraphQLToolSetFactoryBean` also imports `DefaultAiChatToolSet` and `IAiChatToolSet`.

**Severity**: P2

**Suggestion**: Migrate `GraphQLToolProvider` and `GraphQLToolSetFactoryBean` to the non-deprecated API (`nop-ai-api`'s `IToolDefinition` + `nop-ai-toolkit`'s `IToolExecutor`/`IToolManager`).  
**Confidence**: High (95%)  
**False-positive exclusion**: The `@Deprecated` annotation on the source interface is explicit and unambiguous. This is not a generated file issue.

### P2-MA3-04: Misleading `@Deprecated` — `IAiChatService` still backbone of nop-ai-core

**File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/chat/IAiChatService.java:14-15`  
**Lines**: 14-15 (deprecation annotation)

```java
// IAiChatService.java:14-15
@Deprecated
public interface IAiChatService {
    IAiChatSession newSession(AiChatOptions options);
    IAiChatSession getSession(String sessionId);
    CompletionStage<AiChatExchange> sendChatAsync(Prompt prompt, AiChatOptions options, ICancelToken cancelToken);
}
```

**Evidence**: Three core interfaces (`IAiChatService`, `IAiChatSession`, `IAiChatFunctionTool`) are annotated `@Deprecated` but:
- `DefaultAiChatService` implements `IAiChatService` and is the primary chat service implementation in core
- `AbstractAiChatSession` implements `IAiChatSession` and is the base for all session implementations
- `DefaultAiChatFunctionTool` implements `IAiChatFunctionTool` and is the primary function tool implementation
- `IAiChatToolSet` (also not marked `@Deprecated`) depends on `IAiChatFunctionTool`
- `AiCommand` uses `IAiChatService` and `IAiChatFunctionTool` directly

The deprecation message says "Please use the new AI API instead" but `IChatService` from `nop-ai-api` has a completely different interface shape (`callAsync(ChatRequest, ICancelToken)` vs `sendChatAsync(Prompt, AiChatOptions, ICancelToken)`). There is no migration path or adapter.

**Severity**: P2  
**State**: Open  
**Risk**: Future readers will be confused about which API to use. If someone removes these deprecated interfaces thinking they are truly unused, the entire nop-ai-core module breaks.  
**Suggestion**: Either (a) remove the `@Deprecated` annotation and accept these as stable internal interfaces, or (b) actually migrate all internal users to the new API and add an adapter layer, then mark for removal.  
**Confidence**: High (95%)  
**False-positive exclusion**: This is not a "deprecated but kept for compatibility" scenario — the deprecated interfaces are the primary working implementation. The deprecation is misleading.

### P2-MA3-06: Duplicate DTO patterns — `ChatOptions` (api) vs deprecated `AiChatOptions` (core)

**Files**:
- `nop-ai/nop-ai-api/src/main/java/io/nop/ai/api/chat/ChatOptions.java`
- `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/chat/AiChatOptions.java`

```java
// ChatOptions (api) — non-deprecated, ~516 lines
public class ChatOptions {
    private String sessionId, provider, model;
    private Float temperature, topP;
    private Integer topK, maxTokens;
    // ... 14 more fields
}

// AiChatOptions (core) — @Deprecated, ~442 lines
@Deprecated
public class AiChatOptions extends ExtensibleBean {
    private String sessionId, provider, model, seed;
    private Float temperature, topP;
    private Integer topK, maxTokens, contextLength;
    // ... 20+ fields (subset overlap with ChatOptions + extra fields)
}
```

**Evidence**: Both classes model the same concept (LLM chat options) with significant field overlap. `AiChatOptions` is marked `@Deprecated` but still has fields not present in `ChatOptions` (e.g., `seed`, `contextLength`, `workMode`, `botId`, `conversationId`, `userId`, `disableCache`, `streamListener`, `enabledTools`, `enableCognitivePrompt`, `enableMetaPrompt`, `enableSystemPrompt`). Conversely, `ChatOptions` has fields not in `AiChatOptions` (e.g., `tools`, `toolChoice`, `responseFormat`).

**Severity**: P2  
**State**: Open  
**Risk**: Feature drift — new fields added to one may not be added to the other. Developers must maintain two parallel DTOs for the same concept.  
**Suggestion**: Consolidate all options into a single `ChatOptions` in `nop-ai-api` and remove `AiChatOptions` from core. Add any missing fields to the api class.  
**Confidence**: Medium (80%) — consolidation would be a significant refactor  
**False-positive exclusion**: This is not a false-positive issue — two classes modeling the same concept with overlapping fields is a known maintainability antipattern. The deprecated annotation on one without a clear migration path confirms the incomplete state.

### P3-MA3-07: nop-ai-agent imports `AiCoreErrors` from core

**File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/reliability/LlmErrorClassifier.java:3`  
**Line**: 3 (import), 124 (reference)

```java
// LlmErrorClassifier.java:3
import io.nop.ai.core.AiCoreErrors;

// LlmErrorClassifier.java:124
Object value = ((NopException) error).getParam(AiCoreErrors.ARG_HTTP_STATUS);
```

**Evidence**: `LlmErrorClassifier` references `AiCoreErrors.ARG_HTTP_STATUS` to extract HTTP status from NopExceptions thrown by the chat service. This is a cross-module dependency on core's error code constants.

**Severity**: P3  
**State**: Open  
**Risk**: If `ARG_HTTP_STATUS` constant name changes or is removed, the classifier silently returns `null` (degrading classification accuracy) rather than failing to compile.  
**Suggestion**: Either (a) expose the constant via a public method in `nop-ai-api`, or (b) have the chat service attach the HTTP status in a more standard way (e.g., standard exception property) so classifiers don't need to know the constant name.  
**Confidence**: Medium (85%)  
**False-positive exclusion**: This is a cross-module reference to a core-internal error constant. It works currently but is fragile.

**Total findings**: 7 (2 × P1, 4 × P2, 1 × P3)

**Healthy contract chains**:  
- `nop-ai-api` → `nop-ai-agent` (IChatService + ChatMessage hierarchy): clean  
- `nop-ai-api` → `nop-ai-toolkit` (IToolDefinition → AiToolModel): clean  
- `nop-ai-toolkit` → `nop-ai-agent` (IToolExecutor/IToolManager): clean  
- `nop-ai-toolkit` → `nop-ai-core` or `nop-ai-api` → `nop-ai-core`: zero imports (correct separation)

**Broken contract chains**:  
- `nop-ai-core` → `nop-ai-agent`: 5 leaked internal classes (ChatOptionsModel, ILlmDialect, LlmDialectFactory, ApiStyle, AiCoreErrors)  
- `nop-ai-core` → `nop-ai-tools`: 3 leaked internal classes (IAiChatFunctionTool, IAiChatToolSet, IFileOperator)  
- `nop-ai-core` → `nop-ai-coder`: 1 leaked internal class (IFileOperator)

**Architecture pattern violation**: The `nop-ai-core` module was intended to be an internal engine, but its internal APIs (model classes, dialect interfaces, error constants, file operator services) leak into `nop-ai-agent`, `nop-ai-tools`, and `nop-ai-coder`. The `nop-ai-toolkit` is the only consumer module that correctly isolates itself from `nop-ai-core`.

**Recommendation**: Establish a hard rule that `nop-ai-agent`, `nop-ai-tools`, and `nop-ai-coder` may only depend on `nop-ai-api` and `nop-ai-toolkit` for contracts. Any class from `nop-ai-core` that is needed externally should be promoted to `nop-ai-api` or `nop-ai-toolkit`.
