# MA6.2 — Agent Orchestration Security Audit (nop-ai-agent / nop-ai-toolkit / nop-ai-shell)

> **Auditor**: opencode adversarial-review
> **Date**: 2026-07-31
> **Plan ref**: `ai-dev/plans/2026-07-31-0000-3-arm-ma5-ma6-audit.md` Phase 6
> **Methodology**: `ai-dev/skills/open-ended-adversarial-review-prompt.md`
> **Scope**: ToolExecutor input validation, SSRF, instruction injection defense, sandbox bypass, path traversal

---

## Summary

7 findings across 3 modules. Two SSRF vectors with no URL validation, a path-access check that is silently bypassed in the actual file operations, and five additional tool-level input validation gaps. The engine's `DefaultToolAccessChecker` blocks the highest-risk tools (`bash`, `http-request`, `write-file`, etc.) at Layer 1, but every one of those tools lacks per-executor input validation, making them a single `AllowAllToolAccessChecker` wiring mistake away from being fully exploitable.

## Findings

### [AR-1] HttpRequestExecutor — no URL whitelist or SSRF defense

- **File**: `nop-ai/nop-ai-toolkit/src/main/java/io/nop/ai/toolkit/tools/HttpRequestExecutor.java:44-81`
- **Evidence**:
  ```java
  // Line 44-45: URL accepted verbatim from AI tool call — no validation
  String url = call.attrText("url", "");
  // Line 60: directly set on request
  HttpRequest request = new HttpRequest();
  request.setUrl(url);
  ```
- **Severity**: P1
- **Status**: No URL whitelist, no internal-IP blocklist, no scheme restriction. Any URL (including `http://169.254.169.254/`, `http://localhost:8080/internal-api`) is executed.
- **Risk**: SSRF to cloud metadata endpoints, internal services, and unauthenticated internal APIs. An attacker who can influence the LLM's tool-call arguments (prompt injection) can probe or exploit internal infrastructure.
- **Recommendation**: Add a configurable URL allowlist/blocklist. Deny private IP ranges (RFC 1918), link-local, and loopback by default. Require explicit opt-in for internal URLs. Apply at the executor level, not just at `DefaultToolAccessChecker` (which can be replaced with `AllowAllToolAccessChecker`).
- **Confidence**: certain
- **Found via**: Model attacker perspective

### [AR-2] GraphqlQueryExecutor — SSRF via endpoint URL

- **File**: `nop-ai/nop-ai-toolkit/src/main/java/io/nop/ai/toolkit/tools/GraphqlQueryExecutor.java:38-66`
- **Evidence**:
  ```java
  // Line 39: default is localhost, caller-supplied endpoint is not validated
  String endpoint = call.attrText("endpoint", "http://localhost:8080/graphql");
  // Line 51: directly set
  request.setUrl(endpoint);
  ```
- **Severity**: P1
- **Status**: Default endpoint is localhost (already an SSRF), and no validation is applied to user-supplied endpoints. Same `IHttpClient.fetchAsync` path as `HttpRequestExecutor`.
- **Risk**: Identical SSRF risk as AR-1 — attacker-controlled endpoints can target any reachable HTTP server.
- **Recommendation**: Same as AR-1: URL whitelist/blocklist at the executor level. Additionally, do not default to `localhost` — require explicit configuration.
- **Confidence**: certain

### [AR-3] LocalToolFileSystem — `isPathAllowed()` not called by file operations (path check silent bypass)

- **File**: `nop-ai/nop-ai-toolkit/src/main/java/io/nop/ai/toolkit/fs/LocalToolFileSystem.java:52-61,152-155,197-211,214-230,233-251`
- **Evidence**:
  ```java
  // isPathAllowed() exists but is NEVER called inside the executor's
  // readText/writeText/delete/move/copy/glob/grep methods.
  // Each method calls resolveFile(path) directly without a permission check:

  // writeText (line 152-155):
  public void writeText(String path, String content, boolean append) {
      File file = resolveFile(path);  // no isPathAllowed() call
      FileHelper.writeText(file, content, ...);
  }

  // delete (line 197-211):
  public void delete(String path, boolean recursive, boolean force) {
      File file = resolveFile(path);  // no isPathAllowed() call
      ...
  }

  // resolveFile (line 52-61) does not enforce workDir boundary:
  private File resolveFile(String path) {
      File file = new File(path);
      if (file.isAbsolute()) return file;  // absolute paths pass through!
      ...
  }
  ```
- **Severity**: P1
- **Status**: `isPathAllowed()` exists on the interface but is never called by the tool file system's own operations. Absolute paths are passed through `resolveFile()` without any workDir boundary check. The permission check is entirely caller-side (e.g., the engine's path access checker), but the file system itself enforces nothing.
- **Risk**: Any code path that constructs a `LocalToolFileSystem` but does not independently call `isPathAllowed()` before each operation will silently allow operations on any path the JVM can access. Additionally, if the engine's `DefaultPathAccessChecker` is replaced with `AllowAllPathAccessChecker`, file tools can read/write anywhere.
- **Recommendation**: Each file operation method in `LocalToolFileSystem` should internally enforce the workDir boundary (reject absolute paths and `..` traversal that escape workDir) rather than relying entirely on the caller. Alternatively, remove `isPathAllowed()` from the interface if it is always bypassed, to avoid misleading future integrators.
- **Confidence**: certain
- **Found via**: Code path detective

### [AR-4] BashExecutor — arbitrary command execution with environment variable injection

- **File**: `nop-ai/nop-ai-toolkit/src/main/java/io/nop/ai/toolkit/tools/BashExecutor.java:32-113,119-135`
- **Evidence**:
  ```java
  // Line 34: command taken verbatim from AI tool call
  String command = call.childText("command", "");
  // Line 52-53: environment variables injected verbatim — no validation
  Map<String, String> processEnv = pb.environment();
  processEnv.putAll(env);
  // Line 47: arbitrary shell execution
  pb.command("sh", "-c", command);
  ```
- **Severity**: P1 (mitigated by `DefaultToolAccessChecker` deny list — P0 if `AllowAllToolAccessChecker` is used)
- **Status**: The executor performs zero input validation on the command string or environment variable names/values. Environment variables can override `PATH`, `LD_PRELOAD`, `IFS`, or inject malicious values. Currently blocked at `DefaultToolAccessChecker` Layer 1, but the executor itself offers no defense-in-depth.
- **Risk**: If `DefaultToolAccessChecker` is downgraded to `AllowAllToolAccessChecker` (which is a supported configuration and triggers only a WARN log, not a hard block), an attacker gains arbitrary OS command execution. The env injection risk is independent: a `PATH` override could hijack commands even without arbitrary command execution.
- **Recommendation**: (1) Reject or sanitize environment variable keys that start with `-` or contain shell metacharacters (mirror `DockerSandboxBackend.validateEnvironmentVariableKey`). (2) Add a configurable command allowlist/blocklist at the executor level. (3) Strip dangerous env vars (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `SHELLOPTS`, etc.).
- **Confidence**: certain

### [AR-5] DefaultCommandChecker — unconditionally allows all shell commands (no restriction by default)

- **File**: `nop-ai/nop-ai-shell/src/main/java/io/nop/ai/shell/checker/DefaultCommandChecker.java:5-10`
- **Evidence**:
  ```java
  public class DefaultCommandChecker implements ICommandChecker {
      @Override
      public String check(SimpleCommand command, ICommandCheckContext context) {
          return null;  // null = no rejection, ALL commands allowed
      }
  }
  ```
- **Severity**: P2
- **Status**: The `ShellCommandExecutor` calls `checkAst()` before executing any command, but the shipped default `ICommandChecker` returns null (allow) for every command. No built-in implementation rejects dangerous commands like `rm -rf /`, `dd`, `mkfs`, or commands that modify system configuration.
- **Risk**: If `ShellCommandExecutor` is wired with the default checker (which is the only shipped implementation), all shell commands including destructive ones are allowed. The system depends entirely on the caller to provide a restrictive checker.
- **Recommendation**: Provide a built-in `DefaultCommandChecker` that blocks at minimum: `rm -rf /`, `dd`, `mkfs.*`, `shutdown`, `reboot`, `init`, and commands mutating `/etc/`, `/boot/`, `/sys/`. Make the allow-null behavior an explicit opt-in (`AllowAllCommandChecker`).
- **Confidence**: certain

### [AR-6] No production IContentGuardrail implementation (no content safety filtering)

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/guardrail/NoOpContentGuardrail.java:5-20`
- **Evidence**:
  ```java
  // The only implementation of IContentGuardrail
  public final class NoOpContentGuardrail implements IContentGuardrail {
      @Override
      public GuardrailResult check(GuardrailDirection direction,
                                    String content, AgentExecutionContext ctx) {
          return GuardrailResult.PassResult.instance();  // always pass
      }
  }
  ```
- **Severity**: P2
- **Status**: The engine has a hook point for content safety (`IContentGuardrail`) but the shipped default is a no-op. There is NO production implementation in the entire `nop-ai` module set. The engine logs an INFO line acknowledging this gap but provides no path to a built-in implementation.
- **Risk**: LLM-generated content (tool call arguments, responses) is never checked for malicious instructions, prompt injection payloads, or harmful content before being passed to tool executors or stored in chat history. A prompt injection that tricks the LLM into generating dangerous tool arguments will reach the executor without interception.
- **Recommendation**: Ship at minimum a basic content guardrail that blocks known prompt injection patterns, sensitive command patterns, and restricted path patterns. Make the NoOp default emit a WARN (not INFO) to make the gap more visible.
- **Confidence**: certain

### [AR-7] DefaultToolAccessChecker denys tools by hardcoded name list — no per-tool input validation in executors

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/security/DefaultToolAccessChecker.java:7-27` and all tool executors in `nop-ai/nop-ai-toolkit/src/main/java/io/nop/ai/toolkit/tools/`
- **Evidence**:
  ```java
  // DefaultToolAccessChecker blocks by tool name only:
  private static final Set<String> DENIED_TOOLS = Set.of(
      "bash", "write-file", "delete-file", "move-file",
      "patch-file", "apply-delta", "http-request", "graphql-query"
  );
  ```
- **Severity**: P2
- **Status**: The Layer 1 security model relies entirely on `DefaultToolAccessChecker` blocking tools by name. No individual executor validates its own inputs for safety (e.g., `ReadFileExecutor` doesn't restrict path access, `WriteFileExecutor` doesn't check whether the directory is safe, `CopyFileExecutor` doesn't validate source/target). The path access checker (`DefaultPathAccessChecker`) provides a second layer, but it only covers path-based tools — not tools like `bash`, `http-request`, or `graphql-query`.
- **Risk**: Defense-in-depth is single-dimensional: tool name blocking + path checking. A bypass of either (e.g., downgrading the checker, adding a new dangerous tool that's not on the deny list, or a tool name mismatch) leaves no per-executor safety net. The architectural assumption is that all dangerous tools are explicitly known and blocked by name, which is brittle.
- **Recommendation**: Add executor-level input validation contracts. Each `IToolExecutor` should validate its own inputs against a configurable policy (e.g., `@ToolPolicy(allowedParams=..., maxLength=..., allowedPatterns=...)`). This makes the security model compositional rather than centralized.
- **Confidence**: likely

## Blind Spot Self-Assessment

This review likely missed:
- **MCP module risks** — excluded per roadmap scope; MCP-triggered tool dispatch may introduce different injection vectors.
- **Race conditions in multi-turn tool dispatch** — the `ReActAgentExecutor` dispatch loop processes tool calls sequentially, but concurrent sessions sharing filesystem state were not tested.
- **Side-channel information leakage via tool error messages** — several executors include file paths and operation details in error messages returned to the LLM, which could leak system topology.
- **Team tool ACL bypass** — `NoOpTeamAclChecker` is the default; this was noted but not deeply audited.
- **Memory store isolation** — `IAiMemoryStore` implementations were not checked for cross-tenant data leakage.
