## 发现清单

### [MA7.3-01] 全量 UK 零物化：DDL 模板 gate 在 `constraint` 属性上，nop-metadata 69 个 UK 全部被静默跳过（MA6.6-001 根因纠正 + RACE 前提证伪）（P2）

- **文件**: `nop-persistence/nop-orm/src/main/resources/_vfs/nop/orm/xlib/ddl/ddl.xlib:81-82`；`nop-kernel/nop-xdefs/src/main/resources/_vfs/nop/schema/orm/entity.xdef:206-208`（`constraint="string"` 可选属性，缺省 null）；`nop-metadata/model/nop-metadata.orm.xml`（**69 个 `<unique-key`，0 个 `constraint=` 属性**——主 agent 实读核实）；对照 `nop-auth/model/nop-auth.orm.xml:176,286`（`constraint="UK_NOP_AUTH_*"` 显式声明，证明该属性是 UK 发射激活条件）；方言 ddl_*.xlib 全部 `x:extends="ddl.xlib"`；`nop-orm/.../DdlSqlCreator.java:71-76`（createTable → XLang 模板生成）；`initialize/DataBaseSchemaInitializer.java:59-66`（initDatabaseSchema 共用同一 DdlSqlCreator）
- **证据片段**:
  ```xml
  <!-- ddl.xlib:81-88 —— 无 constraint 名 → 整个 UK 被跳过 -->
  <c:for var="uniqueKey" items="${table.uniqueKeys}">
      <c:if test="${uniqueKey.constraint}">
          ... constraint ${uniqueKey.constraint} unique (${columns.join(',')})
  ```
  ```xml
  <!-- nop-metadata.orm.xml:299 —— 69/69 个 UK 均无 constraint 属性（rg 实证 0 命中） -->
  <unique-key name="UK_NOP_META_MODULE_ID_VER" columns="moduleId,moduleVersion" .../>
  ```
- **严重程度**: **P2**
- **现状**: 主 agent 实证：`rg -c '<unique-key' nop-metadata/model/nop-metadata.orm.xml` = **69**；`rg -n 'constraint='` 同文件 = **0**。DDL 模板 `TableUniqueConstraints` 仅在 `uniqueKey.constraint` 非空时发射约束 → 所有 DDL 生成路径（deploy/sql 快照 与 initDatabaseSchema）都零 UK 发射（DdlSqlCreator 是两条路径的公共实现，方言 xlib 均 extends ddl.xlib）。对比 nop-auth 显式 constraint 可物化，证明机制本可用。运行时实证（子 agent 实跑 TestNopMetaModuleBizModel 11/11 PASS）：同一导入在 delta+full 两张图各建一条 NopMetaTable，产生 (metaModuleId, tableName) 重复对——若 UK 物化则每次导入必失败，测试通过证明 UK 确实未物化。
- **风险**: (1) **MA6.6 RACE 终局定论（watch-only）的前提被证伪**——"并发重复 INSERT 被 UK 拦截（完整性保住）"在运行时不存在：并发 upsertExternalTable 两线程均查无候选 → 双双 INSERT → 无 UK → 重复行真实落库；(2) P2-MA6.6-001 判定根因不是"DDL 快照过期"——重新生成快照不会修复，必须改模型（69 个 UK 补 constraint 属性，plan-first）或改模板缺省行为；(3) 双重存储设计与已声明的 UK_NOP_META_TABLE_MODULE_NAME 不相容——即使补 constraint，导入也会立刻失败，需同时裁决 NopMetaTable UK 列集合（如加 isDelta 维度）或表去重。此影响面同时牵动 MA7.4-02（重复血缘边无 UK 兜底）。
- **建议**: 归 MR3：①裁定 DDL 模板 constraint 缺省策略（缺省用 name 或强制显式）；②nop-metadata 69 个 UK 补 constraint 属性（model-first，Protected Area plan-first）；③同步裁决 NopMetaTable 双重存储与 UK 的相容性；④修复后回归 TestNopMetaModuleBizModel + MA6.6 closure audit 复核 RACE 裁定在新证据下的成立性（本审计不重新裁决 RACE，只登记证据）。
- **信心水平**: 高（模板 gate + xdef 缺省 + 69/0 计数 + 同生成器双路径 + 方言 extends + 测试实证六点闭环）
- **修复归属**: MR3（新发现，P2-MA6.6-001 根因纠正与归属更新）

### [MA7.3-02] 导入无大小/数量上限：全量读入 + 无界实体数单事务落库（P3）

- **文件**: `NopMetaModuleBizModel.java:172,560-566`（readText 无大小限制）；`persistModelGraph :291-356`（逐条 save 无数量上限）；orm.xml:451-453（sourceContent mediumtext 16MB）
- **证据片段**:
  ```java
  try (InputStream in = resource.getInputStream()) {
      return new String(in.readAllBytes(), StandardCharsets.UTF_8);   // 无上限
  ```
- **严重程度**: P3
- **现状**: 导入文件大小、实体数、字段数均无守卫；全部写入 @BizMutation 单事务。深度有守卫（XNodeParser maxDepth=50），大小无守卫。
- **风险**: 超大 orm.xml → 内存峰值 + 巨型事务（连接占用/锁竞争）；超列精度时 fail-close 回滚整批。
- **建议**: 加文件大小上限配置（如 nop.metadata.import.max-size）与实体/字段数上限；或导入分片提交。
- **信心水平**: 高
- **修复归属**: MR3（新发现）

### [MA7.3-03] 重复表名/实体名无应用层防护：UK 不物化时静默累积重复行（P3）

- **文件**: `NopMetaModuleBizModel.java:291-356`；`nop-metadata.orm.xml:579-582,708,1315`
- **严重程度**: P3
- **现状**: 导入前无重复检测。若 UK 物化 → fail-close（安全失败）；当前 UK 未物化（MA7.3-01）→ 同文件内重复 entityName/tableName 静默落库。跨导入的重复由版本化隔离（新 moduleVersion）缓解，但同版本内重复无防护。
- **风险**: 目录数据质量；下游 findExternalTables/entity 查询返回重复行。
- **建议**: 导入前 Java 层按 (moduleId, tableName)/(ormModelId, entityName) 预检去重或显式报错（与 MA7.3-01 修复联动）。
- **信心水平**: 高
- **修复归属**: MR3（新发现）

### [MA7.3-04] syncExternalTables 的 schemaPattern 无标识符校验（与 AR-01 三执行器修复不一致）（P3）

- **文件**: `NopMetaDataSourceBizModel.java:172,190` → `ExternalTableStructureReader.java:58-68,154-160`；对照 `MetaCatalogCollector.java:164-172`（AR-01 已修复）
- **严重程度**: P3
- **现状**: 3 个执行器（MetaTableProfiler:557-565 / MetaQualityRuleExecutor:670-685 / MetaCatalogCollector:164-172）的 schema 均已走 validateIdentifier（AR-01 修复，MA6.6 复核 PASS）；唯独同步扫描入口缺失。JDBC DatabaseMetaData 调用为参数化 API → 无 SQL 注入面，但 `%`/`_` 通配符可放大扫描范围（schemaPattern="%" → 全 schema），且与模块内既定标识符纪律不一致。
- **风险**: 低（无注入），行为不一致 + 通配符放大扫描面（DoS/越界扫描）。
- **建议**: 同步入口复用 validateIdentifier（保留 null/空串=不过滤语义）；JDBC 通配符转义或文档化。
- **信心水平**: 高
- **修复归属**: MR3（新发现）

### [MA7.3-05] 导入链可达 x:gen-extends XPL 执行面（特权文件场景代码执行）（P3）

- **文件**: `nop-kernel/nop-xlang/src/main/java/io/nop/xlang/xdsl/XDslExtender.java:299-307,340-359`；`DslNodeLoader.java:35-44`；`NopMetaModuleBizModel.java:171`
- **严重程度**: P3（威胁模型受限）
- **现状**: importOrmModel 解析链对带 `<x:gen-extends>` 的 orm.xml 会编译并执行内嵌 XPL 脚本（平台 DSL 既定能力）。**触发前提：攻击者须能将文件写入 VFS**——本模块无文件写入端点（import path 仅读既有 VFS 文件），仅特权/开发侧可达。x:extends 路径解析经 VFS canonical 门禁（无穿越）。xdef 结构校验不限制 x:gen-extends 的 XPL 内容。
- **风险**: 若未来增加 VFS 上传/导入端点或 VFS 被第三方污染，该面升为 RCE。当前为设计继承面。
- **建议**: 文档化该面（import 仅限可信文件）；若新增上传路径需剥离 x:gen-extends/import 能力。
- **信心水平**: 高（链路代码实证）
- **修复归属**: MR3 记录项 / 文档化

### [MA7.3-07] 外部结构扫描无表/列数量上限（JDBC 元数据 DoS 面）（P3）

- **文件**: `ExternalTableStructureReader.java:64-96,98-118`
- **严重程度**: P3
- **现状**: schemaPattern=null 时扫描目标库全部表 + 每表全部列，无上限（与 AR-09 lineage maxEdges 上限修复的模块内纪律不一致）；单表 getColumns 失败（SQLException）会中断整批扫描（无 per-table 隔离，与 upsert 阶段的 per-table try/catch 不对称）。

- **建议**: 上限配置（maxTables/maxColumns）+ readColumns per-table 错误隔离。
- **信心水平**: 高
- **修复归属**: MR3（新发现）

## 总评

**导入引擎的 XML 解析面在结构上是安全的**：Nop 自研字符扫描解析器（非 SAX/DOM）使 XXE、外部实体、billion-laughs 结构性免疫，深度守卫（50）与 xdef 全量校验在线，VFS canonical 路径门禁阻断穿越，导入不注册运行时 ORM——本审计未发现 P0/P1。

**真正的风险集中在数据一致性层**：旗舰发现 MA7.3-01 证明 nop-metadata 全部 69 个 UK（含 RACE 依赖的 UK_NOP_META_TABLE_MODULE_NAME）在所有 DDL 路径零物化——不仅纠正了 P2-MA6.6-001 的根因判定（模板 constraint gate 而非快照过期），更证伪了 RACE 终局裁定"完整性由 UK 保住"的运行时前提，并暴露双重存储设计与已声明 UK 的模型级不相容（三者必须联动修复）。其余为一致的 P3 纪律面。整体判断：结构安全面 PASS，一致性/防护面存在 1 项 P2 需要 MR3 联动修复。

## 盲区自评

- 并发 upsert 重复行落库未用双线程 H2 场景实测（结论基于 UK 零物化的必然推演）
- deploy/sql 快照 UK 发射未对其他模块（如 nop-sys/nop-job）抽样——模板 gate 是平台级行为，影响面可能超出 nop-metadata
- x:gen-extends XPL 能力边界未验证；未排查平台其他 VFS 写入端点使该面可被低权限触达
- initDatabaseSchema 的 H2 方言分支未逐行核对（主路径 gate 已覆盖）
- manifest content 未来消费方未审计（当前写后无人读）
