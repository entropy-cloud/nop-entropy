## 发现清单

### [MA7.1-01] queryAggregation HAVING 叶子 name 未命中白名单时原样透传 → HAVING 子句 SQL 注入（P0）

- **文件**: `query/AggregationHelper.java:292-294`（nameResolverFor 原始透传）+ `FilterToSqlTranslator.java:270-278`（requireField 跳校验）+ 消费点 `AggregationHelper.java:573-574,603-604`、`ExternalExternalJoinAggregationProcessor.java:87-89`、`MixedSameDbJoinAggregationProcessor.java:113-114`、`EntityAggregationProcessor.java:138-139,228-229`、`EntityEntityJoinAggregationProcessor.java:123-124` + 入口 `NopMetaTableBizModel.java:249-255`
- **证据片段**:
  ```java
  // AggregationHelper.java:291-294 —— 非标识符 name 原样返回，直接进入 SQL 文本
  return name -> {
      if (!FilterToSqlTranslator.IDENTIFIER_PATTERN.matcher(name).matches()) {
          return name;                       // ← 无白名单校验、无 nameToExpr 解析
      }
      ...
  };
  // FilterToSqlTranslator.java:270-278 —— fieldResolver 命中后不再校验
  if (fieldResolver != null) {
      String resolved = fieldResolver.apply(name);
      if (resolved == null || resolved.isEmpty()) { throw ...; }
      return resolved;                        // 无 validateIdentifier
  }
  // 消费：AggregationHelper.java:573-577 —— 直接拼入 HAVING
  FilterToSqlTranslator.TranslatedFilter hf = ctx.filterTranslator().translate(having, nameResolverFor(...));
  sql.append(" HAVING ").append(hf.getSql());
  ```
- **严重程度**: P0
- **现状**: 攻击者提交 `having = {type:"gt", name:"(SELECT COUNT(*) FROM mysql.user WHERE user='root' AND SUBSTRING(password,1,1)='a')", value:1}`（无 `expr` attr → `preprocessHavingArithmetic` 直通，MetaAggregationExecutor.java:169-184 仅处理 expr attr 与非空子节点）。叶子 name 含 `(`/空格 → 不匹配 `^[A-Za-z_][A-Za-z0-9_]*$` → nameResolverFor 原样返回 → 拼入 SQL 成为比较左操作数：`HAVING (SELECT ...) = ?`（value 正常绑定，无需注释技巧）。分组是否保留即布尔盲注 oracle。可执行路径均为裸 JDBC：`ExternalAggregationProcessor`（external 表恒走，withConnection + executeJdbcQuery）、`ExternalExternalJoinAggregationProcessor:131`、`MixedSameDbJoinAggregationProcessor:167`、`EntityAggregationProcessor` bypass-EQL 路径（:242，temporal 维度或 expression measure 存在即触发）。EQL 路径（via-EQL entity/entity-entity JOIN）经 orm executeQuery 由 EQL 编译器解析，payload 大概率 parse-fail，视为受约束（未实测）。
- **风险**: 与已修复的 AR-01（schemaPattern 注入，P0）同类同量级，且权限门槛更低——AR-01 需 mutation 权限，本注入只需 `NopMetaTable:query` 级别 `@BizQuery` 权限，只读用户即可对目标数据源账户执行任意 SELECT（information_schema 枚举、mysql.user 盲注等）。与 MA7.3-01（UK 零物化）叠加时，盲注可利用性不受唯一键约束影响。
- **建议**: `nameResolverFor` 移除原始透传分支——非标识符 name 一律走 `nameToExpr` 解析，未命中即抛 `ERR_AGGR_HAVING_UNKNOWN_NAME`；`preprocessHavingArithmetic` 的 expr 路径产物应显式标记（如 HAVING_EXPR_ATTR 结果直通标志）与原始用户 name 区分；补回归测试：having 叶子 name 含 `(SELECT ...` 类 payload 在 external 聚合路径必须显式失败（错误码而非 SQL 执行）。
- **信心水平**: 确定（代码路径完整实证：透传 → 无校验 → HAVING 拼接 → 裸 JDBC 执行 → GraphQL 入口无拦截）
- **修复归属**: **MR3（新发现；P0 即时通道——本报告与 arm-index P0 追踪表显式登记，MR3 R3.0 展开器硬输入）**

### [MA7.1-02] custom_sql 关键字黑名单可绕过（多词条目子串匹配 + 空白/反引号变体 + 关键字缺项）（P2）

- **文件**: `quality/MetaQualityRuleExecutor.java:73-82,320-333`
- **证据片段**:
  ```java
  private static final Set<String> CUSTOM_SQL_FORBIDDEN_KEYWORDS = unmodifiableSet(
          ";", "UNION",
          "INTO OUTFILE", "INTO DUMPFILE",          // ← 含空格的精确子串
          "LOAD DATA", "LOAD_FILE", "CALL", "EXEC", "EXECUTE", "SHUTDOWN",
          "DROP", "TRUNCATE", "ALTER", "CREATE", "GRANT", "REVOKE",
          "INFORMATION_SCHEMA", "MYSQL.USER", "MYSQL.SCHEMAS");
  static void validateCustomSqlSandbox(String sql, ...) {
      String upper = sql.trim().toUpperCase();
      for (String keyword : CUSTOM_SQL_FORBIDDEN_KEYWORDS) {
          if (upper.contains(keyword)) { throw ...; }   // contains 子串匹配
      }
  }
  ```
- **严重程度**: P2
- **现状**: 维度 13-03 的"唯一防御"（注释自述白名单是唯一可控注入面收口）存在系统性绕过且 fail-open：①空白/注释变体：`INTO\tOUTFILE`、`INTO  OUTFILE`、`INTO/**/OUTFILE` 均不命中 `contains("INTO OUTFILE")`，custom_sql 是顶层语句直接执行（querySingleValue 无子查询包装），文件写入语句可原样执行；②反引号/空白点限定名：`` SELECT * FROM `mysql`.`user` `` → 大写后为 `MYSQL`.`USER` 不命中 `MYSQL.USER`；③缺项：`COPY`（PG 服务端文件写）、`PG_READ_FILE`/`PG_LS_DIR`、MySQL UDF `SYS_EXEC` 不在黑名单；④反噬（fail-closed 方向）：单词条目子串匹配 → 字符串字面量含 `UNION` 被误拒。
- **风险**: 黑名单宣传的"禁多语句/跨表/文件 IO"防护可被廉价变体击穿；实际危害受限于数据源账户权限与服务器配置（MySQL 8 默认 secure_file_priv=NULL 禁写、allowMultiQueries 已禁），但"唯一防御"声明不成立；与 MA7.1-01 同权限面叠加时危害面扩大（规则配置者→数据源账户任意 SELECT）。
- **建议**: 改 token 级解析（分词后逐 token 精确匹配 + `INTO` 后接 `OUTFILE/DUMPFILE` 双 token 序列检测）；拒绝反引号/双引号限定符与 `/*!...*/` 可执行注释；按 ruleType 对 custom_sql 做语法白名单或结构解析。
- **信心水平**: 确定（三个绕过向量均为 SQL 词法常识 + 匹配逻辑直接可证）
- **修复归属**: MR3（新发现；维度 13-03 本体首个绕过实证——MA3.3 仅核 connectionConfig 写侧未覆盖黑名单本体）

### [MA7.1-03] ExpressionMeasureValidator 关键字黑名单条目失效（含空格条目永远无法命中）+ 语句关键字缺失（P3）

- **文件**: `field/ExpressionMeasureValidator.java:64-91,476-496`（分词器 :381-439）
- **证据片段**:
  ```java
  // KEYWORD_BLACKLIST 含 "SET TRANSACTION"；FUNCTION_BLACKLIST 含 "INTO OUTFILE","INTO DUMPFILE"
  // scanBlacklist（:478-495）对 token 流逐 token 匹配——"INTO OUTFILE" 永远无法等于单个 token → 死条目
  if (tok.type == TokenType.IDENTIFIER) { if (KEYWORD_BLACKLIST.contains(tok.text)) throw ...; }
  else if (tok.type == TokenType.FUNCTION_CALL) { if (FUNCTION_BLACKLIST.contains(tok.text)) throw ...; }
  ```
- **严重程度**: P3
- **现状**: 三个含空格条目（SET TRANSACTION / INTO OUTFILE / INTO DUMPFILE）是死代码；SELECT/FROM/UNION/INTO/OUTFILE 等语句关键字完全缺失（当前消费上下文均为标量表达式位置，`SUM((SELECT ...))` 类 payload 属语法错误不可直接利用，HAVING 算术路径另有 substituteAndValidateHavingExpr 兜底——不可达但防御声明与实现不符）。
- **风险**: 若未来任一消费点把 fragment 提升到语句级上下文（如直接嵌入 SELECT 列表），缺失的 SELECT/UNION/INTO 即构成注入入口。防御机制失效但当前不可达。
- **建议**: 删除死条目或改双 token 序列检测；把 SELECT/FROM/UNION/INTO/OUTFILE/DUMPFILE/DATA/TABLE/FILE 纳入黑名单（表达式上下文拒绝无功能损失）；补 tokenizer 单测断言 `1 INTO OUTFILE` 类输入被拒。
- **信心水平**: 确定（分词/匹配逻辑逐行可证；不可利用性为静态推断）
- **修复归属**: MR3（新发现）

### [MA7.1-04] 跨库内存路径 LIKE 语义与 SQL LIKE 不一致 + 用户值正则元字符致 PatternSyntaxException（P3）

- **文件**: `query/MemoryFilterEvaluator.java:108-117`
- **证据片段**:
  ```java
  case FilterBeanConstants.FILTER_OP_LIKE: {
      String s = String.valueOf(rowVal);
      String pattern = String.valueOf(literal).replace("%", ".*").replace("_", ".");
      return s.matches(pattern);          // literal 中其他正则元字符未转义
  }
  ```
- **严重程度**: P3
- **现状**: 跨库内存 HAVING 的 LIKE 把 SQL LIKE 值直接当 Java 正则：`[`/`(`/`\` 等值字符触发 `PatternSyntaxException`（unchecked，绕过 ErrorCode 体系）；同一查询在 SQL 路径与内存路径语义分叉（如 `a[b]` 两侧结果不一致）。无注入能力，纯求值正确性/健壮性缺陷。
- **建议**: 转义用户输入中的正则元字符后再替换 `%`/`_`；异常包成 NopMetadataException（对齐模块 ErrorCode 体系）。
- **信心水平**: 确定
- **修复归属**: MR3（新发现）

## 总评

实质新发现是 **MA7.1-01（P0）**：聚合 HAVING 翻译的 `nameResolverFor` 对非白名单叶子 name 原样透传，配合 4 处裸 JDBC 执行路径构成与已修复 AR-01 同类的 SQL 注入，且权限门槛更低（@BizQuery 只读权限），是"防御集中在 WHERE/列名/schema，唯独漏掉 HAVING resolver 回退分支"的典型白名单覆盖盲区——修复成本低（移除透传分支），建议 MR3 优先。custom_sql 黑名单（MA7.1-02）确认可绕过，实际危害受限于目标 DB 账户权限与服务器配置。AR-01 家族修复、绑定顺序、join 标识符校验全部验证在位；sourceSql 直执行面维持"已知显式风险、子查询包装、SELECT-only"既定结论，无新绕过。

## 盲区自评

- EQL 路径（entity via-EQL、entity-entity JOIN）对 payload 是否实际 parse-fail 未实证（未运行测试）
- HAVING 注入在各方言（H2/MySQL/PG）的实际执行语义未实测
- 驱动对注释内 `?` 的计数行为未实测（不影响主利用路径，仅影响 `--` 变体）
- custom_sql 实际危害依赖 MySQL secure_file_priv/FILE 权限/服务器配置，仓库无法验证
- 权限面推断（`NopMetaQualityRule:create` vs `NopMetaTable:query` 的角色授予数据）为代码级推断
