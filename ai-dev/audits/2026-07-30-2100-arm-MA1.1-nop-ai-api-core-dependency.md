# 审计报告：nop-ai-api / nop-ai-core — 依赖图与模块边界 + API 表面积与契约一致性

**审计 ID**：ARM-MA1.1-MA1.2  
**日期**：2026-07-30  
**审计人**：大禹（结构审计）  
**范围**：nop-ai-api（`/nop-ai/nop-ai-api/`）、nop-ai-core（`/nop-ai/nop-ai-core/`）  
**维度**：D01-依赖图与模块边界、D03-API 表面积与契约一致性  

---

## 摘要

本次审计覆盖 nop-ai 子系统最底层的两个模块（api + core），评估依赖合规性、模块职责边界、API 接口稳定性与契约完备性。

**总发现数**：9（P0=0, P1=2, P2=5, P3=2）

| 严重度 | 数量 | 关键主题 |
|--------|------|---------|
| P0 | 0 | — |
| P1 | 2 | 废弃并行 API 未清理；nop-diff 未使用依赖 |
| P2 | 5 | 实现类在 API 模块中；接口默认方法依赖具体类；UnsupportedOperationException default 方法；第三方版权文件；nop-dao 依赖合理性 |
| P3 | 2 | ChatOptions 膨胀；包命名歧义 |

---

## 发现明细

### 发现 1 — `nop-diff` 依赖未使用（P1）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-core/pom.xml:52` |
| **严重程度** | **P1** |
| **现状** | nop-ai-core 声明了 `<artifactId>nop-diff</artifactId>` 依赖，但全模块 `src/main/java` 中无任何 `import io.nop.diff.*` 引用。文件 diff 功能通过自定义实现的 `FileDiff` / `FileDiffGenerator`（内含 Myers Diff 算法）完成，未使用 nop-diff 模块的任何类型。 |
| **风险分析** | 无用依赖增加构件体积、传递依赖冲突风险、构建时间。当其他模块升级 nop-diff 时可能对本模块产生不必要的影响。 |
| **修复建议** | 从 `nop-ai-core/pom.xml` 中移除 `nop-diff` 依赖声明。如果运行时确需（例如其他模块通过传递依赖引入），可确认后完全移除。 |

### 发现 2 — 废弃并行 API 体系未清理（P1）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/chat/IAiChatService.java:15`（及同包下的 IAiChatSession、IAiChatFunctionTool、IAiChatToolSet、AiChatOptions、AiChatExchange、AiMessage 体系、ToolCall、AiChatUsage） |
| **严重程度** | **P1** |
| **现状** | 存在两套完整的、职责重叠的聊天服务 API：<br>— **新版**：`IChatService`（`nop-ai-api`，使用 `ChatRequest`/`ChatResponse`/`ChatOptions`/`ChatMessage` 体系）<br>— **旧版（`@Deprecated`）**：`IAiChatService`（`nop-ai-core`，使用 `Prompt`/`AiChatExchange`/`AiChatOptions`/`AiMessage` 体系）<br><br>两套 API 均未标注 `@Deprecated(forRemoval=true)`。旧版 `DefaultAiChatService` 仍有完整实现（622 行），且被其他模块引用。旧版类型数量约 15+ 个接口/类，几乎与新版类型一一对应，维护负担翻倍。 |
| **风险分析** | 1. 新人容易混淆两套 API，选错接口引入技术债务。<br>2. 两套类型体系同步修改成本高（更改一个概念需要改两套）。<br>3. 未标注 `forRemoval=true` 意味着编译器不产生警告，消费者可能持续依赖旧 API。<br>4. 迁移进度不可见——无迁移截止日期或计划文档。 |
| **修复建议** | 1. 在旧版接口/类上标注 `@Deprecated(forRemoval=true)` 并添加 `@deprecated` javadoc 标签说明替代类路径。<br>2. 创建 `ai-dev/plans/` 下的迁移计划，列出所有旧 API 消费者并安排迁移窗口。<br>3. 设置目标版本移除旧 API（如 3.0.0），在 RELEASE-NOTES 中声明。 |

### 发现 3 — `NopAiException` 实现类在 API 模块中（P2）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-api/src/main/java/io/nop/ai/api/exceptions/NopAiException.java:1` |
| **严重程度** | **P2** |
| **现状** | `NopAiException extends NopException` 是一个具体异常实现类，位于 `nop-ai-api` 模块中。按模块职责约定，API 模块应包含纯接口、DTO 数据类、常量——不应包含实现类。 |
| **风险分析** | 1. API 消费者隐式依赖了异常类型的实现细节（构造函数参数、序列化 UID）。<br>2. 异常层次结构变更时影响所有消费者，违反"面向接口编程"原则。<br>3. nop-ai-core 中的 `AiCoreErrors` 已经定义了错误码常量——消费者应通过 `NopException(ErrorCode)` + `param()` 构造异常，不需要直接扩展 NopException。 |
| **修复建议** | 将 `NopAiException` 移至 `nop-ai-core` 模块。在 API 模块中保留零实现类原则。如确有 API 层需要异常工厂，提供一个 `static` 方法在 `AiCoreErrors` 接口中或单独的错误码接口。 |

### 发现 4 — `ILlmDialect.estimateTokens()` 默认方法依赖具体类 `AbstractLlmDialect`（P2）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/dialect/ILlmDialect.java:161-163` |
| **严重程度** | **P2** |
| **现状** | `ILlmDialect` 接口的 `default` 方法 `estimateTokens()` 直接调用 `AbstractLlmDialect.estimateTokensBaseline()` 静态方法。这使得接口强依赖于一个具体抽象类：<br><br>`default long estimateTokens(List<ChatMessage> messages) {`<br>`    return AbstractLlmDialect.estimateTokensBaseline(messages);`<br>`}` |
| **风险分析** | 1. 违反依赖倒置原则——接口不应依赖具体类。<br>2. 任何实现 `ILlmDialect` 的类必须保证 `AbstractLlmDialect` 在类路径上，即使该实现类并不继承 `AbstractLlmDialect`。<br>3. 难以单独测试 `ILlmDialect` 的默认行为。 |
| **修复建议** | 将 `estimateTokensBaseline()` 提取到一个独立的工具类（如 `TokenEstimationHelper`）或直接内联到接口的 default 方法中。这样接口只依赖自身，消除对具体实现的编译时依赖。 |

### 发现 5 — `ILlmDialect` 含 `UnsupportedOperationException` 默认方法（P2）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/dialect/ILlmDialect.java:170-172` |
| **严重程度** | **P2** |
| **现状** | `parseRequestBody()` 默认方法直接抛出 `UnsupportedOperationException`：<br><br>`default ChatRequest parseRequestBody(Map<String, Object> body) {`<br>`    throw new UnsupportedOperationException("parseRequestBody");`<br>`}`<br><br>同时 `buildResponse()` 和 `buildStreamChunk()` 虽然提供了 OpenAI 格式的默认实现，但并非所有方言都能正确使用这些默认值。 |
| **风险分析** | 1. 违反 Liskov 替换原则——调用者无法安全地在任意 `ILlmDialect` 实例上调用 `parseRequestBody()`。<br>2. 运行时才暴露的接口设计缺陷，编译器无法提前发现。<br>3. `buildResponse()` 和 `buildStreamChunk()` 的默认实现在 OpenAI 格式之外可能产生不合预期的输出。 |
| **修复建议** | 将 `parseRequestBody()` 改为抽象方法（强制所有方言实现），或将其提升到独立的 SPI 接口（如 `ILlmDialectReverse`）中以分离关注点。对于 `buildResponse()`/`buildStreamChunk()`，考虑类似的方案。 |

### 发现 6 — `IVectorStore` / `VectorData` 携带第三方 Agents-Flex 版权头（P2）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/vectorstore/IVectorStore.java:1-15`<br>`nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/support/VectorData.java:1-15` |
| **严重程度** | **P2** |
| **现状** | `IVectorStore`（抽象类）和 `VectorData` 类包含 Apache License 2.0 版权标头，版权归属为 "Agents-Flex (fuhai999@gmail.com)"。这些文件属于从外部项目引入的衍生代码，但未经适配器/包装层封装，直接作为 nop-ai-core 的核心类型使用。 |
| **风险分析** | 1. 许可证合规风险——Apache 2.0 代码需要保留版权声明和免责声明，当前虽有保留但缺少修改说明标注。<br>2. 代码演进后难以追踪外部依赖边界，修改时可能无意中违反原始许可条款。<br>3. 引入外部代码不应是 nop-ai-core 的实现策略——应通过接口抽象 + 适配器模式来处理。 |
| **修复建议** | 1. 在 COPYRIGHT 文件中或每个文件头部添加修改声明（如 "Modified from Agents-Flex original"）。<br>2. 考虑重构：用纯粹的 `IVectorStore` 接口（而非抽象类）取代，将 Agents-Flex 实现作为可选适配器放在单独的模块或分包中。<br>3. 或统一用 Nop 自己的 VectorData 类型包装外部数据，减少直接依赖。 |

### 发现 7 — `nop-dao` 在 nop-ai-core 中的必要性存疑（P2）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-core/pom.xml:26-28` |
| **严重程度** | **P2** |
| **现状** | nop-ai-core 声明了对 `nop-dao` 的直接依赖。但在 `src/main/java` 全目录搜索 `import io.nop.dao.*` 无匹配结果。nop-ai-core 的持久化仅通过 `IAiChatExchangePersister` 实现文件 IO（基于 `IResource`），不需要 ORM/DAO 层的数据库操作。 |
| **风险分析** | 1. 非必要的 `nop-dao` 依赖将整个 ORM/持久化框架带入 nop-ai-core 的传递依赖树，增加了消费者的类路径重量。<br>2. 对于仅使用 nop-ai-api + nop-ai-core 做纯 LLM 调用的场景（不需要数据库），此依赖是不合理的。 |
| **修复建议** | 审查 nop-ai-core 是否在运行时确实需要 `nop-dao`（例如通过 `nop-xlang` 或 `nop-http-client-jdk` 的传递依赖）。如果确认不需要，则将 `nop-dao` 从 `<dependencies>` 中移除，或改为 `<optional>true</optional>`。 |

### 发现 8 — `ChatOptions` 类膨胀（P3）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-api/src/main/java/io/nop/ai/api/chat/ChatOptions.java`（516 行） |
| **严重程度** | **P3** |
| **现状** | `ChatOptions` 作为一个 @DataBean 同时包含 Builder 内部类（90+ 行）、`copy()`、`merge()` 以及一系列链式辅助方法。类似的，废弃版本的 `AiChatOptions` 也有 `cloneInstance()` 和 `update()` 方法。两个功能重叠的 Options 类各自维护了不同形状的基础设施代码。 |
| **风险分析** | 1. Data bean 膨胀超过 500 行，违反单一职责原则。<br>2. Builder 模式内部实现增加了维护成本且与 Lombok/@DataBean 的构建模式不一致。<br>3. `copy()` 与 `merge()` 方法需要随着字段变更同步维护，容易遗漏。 |
| **修复建议** | 1. 考虑使用 Nop 平台的 `ExtensibleBean` 继承机制来减少手动字段维护。<br>2. 或将 Builder 提取到单独的文件（`ChatOptionsBuilder.java`）。<br>3. 使用 `@DataBean` 的自动生成能力替代手写 getter/setter/constructor。 |

### 发现 9 — `io.nop.ai.core.api.*` 包名造成 API/内部类混淆（P3）

| 字段 | 值 |
|------|-----|
| **文件** | `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/api/`（整个目录树） |
| **严重程度** | **P3** |
| **现状** | nop-ai-api 模块使用 `io.nop.ai.api.*` 作为根包；nop-ai-core 模块中有一组废弃/内部的 API 类放在 `io.nop.ai.core.api.*` 下。新手开发者很容易误认为 `io.nop.ai.core.api.chat.IAiChatService` 是稳定 API，而实际上它已被标记为 `@Deprecated`。 |
| **风险分析** | 包名中的 "api" 暗示其为公共 API 层，与实际的废弃/内部状态矛盾，造成可发现性误导。 |
| **修复建议** | 在旧版 API 完全移除前，将 `io.nop.ai.core.api.*` 下的废弃类迁移到 `io.nop.ai.core.legacy.*` 或 `io.nop.ai.core.deprecated.*`，以清晰表达其状态。终极方案是完成迁移后完全移除。 |
