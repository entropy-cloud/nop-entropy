## 4. FieldSelectionBean

### Standard CrudBizModel
All inherited CRUD methods accept `FieldSelectionBean selection` as a parameter:
```java
public PageBean<T> findPage(QueryBean query, FieldSelectionBean selection, IServiceContext context)
public T get(@Name("id") String id, FieldSelectionBean selection, IServiceContext context)
public T findFirst(QueryBean query, FieldSelectionBean selection, IServiceContext context)
```

### Custom Method  
`summarizeByModel()` does **not** accept `FieldSelectionBean`. The method returns `List<ModelUsageSummary>` and always returns all fields of the DTO. This means GraphQL clients cannot request a subset of fields.

### Risk
Low — the DTO has only 7 fields and aggregate queries typically need all fields. However, on large datasets the `responseContent`-style fields (not present here, but in similar patterns) could be bandwidth-intensive. The current `ModelUsageSummary` DTO has no large text fields, so the practical impact is minimal.

**Verdict: ⚠️ ADVISORY** — See Finding MA2-028.

## 6. RPC vs GraphQL Path Support

### Framework Behavior
Nop GraphQL engine automatically exposes every `@BizQuery`/`@BizMutation` annotated method via two URL conventions:

| Path | Example | Type |
|------|---------|------|
| `/r/{bizObjName}__{method}` | `/r/NopAiKnowledge__findPage` | REST |
| `/q/{bizObjName}__{method}` | `/q/NopAiKnowledge__findPage` | GraphQL |

### Configuration
- `nop-ai-app/src/main/resources/application.yaml` enables `graphql.schema-introspection.enabled: true` and `smallrye-graphql.ui.always-include: true`
- All standard CrudBizModel operations are automatically available at both paths
- Custom `summarizeByModel` is exposed at `/r/NopAiChatResponse__summarizeByModel` and `/q/NopAiChatResponse__summarizeByModel`

### Verification
The Nop framework's `GraphQLEngine` (in `nop-graphql-core`) handles path routing without module-specific configuration. No custom GraphQL resolvers or REST controllers exist in `nop-ai` — all routing is declarative.

**Verdict: ✅ PASS** — Both /r/ and /q/ paths supported for all operations.

## 7. Security Annotations

### Auth Configuration
- `_nop-ai.action-auth.xml` (generated) defines `:query` and `:mutation` permissions for all 21 entities
- `nop-ai.action-auth.xml` extends the generated file with `<site id="main"/>`
- `app.action-auth.xml` extends `nop-ai.action-auth.xml`
- `app.data-auth.xml` uses `<auth-gen:GenFromModules/>` for data-level auth

### @Auth Usage in Entity BizModels
- **Zero `@Auth` annotations found** in any of the 21 entity BizModel `.java` files
- The CrudBizModel base class does **not** add `@Auth` annotations to inherited CRUD methods — auth is enforced by the action-auth framework at the permission level (i.e., the `FNPT:NopAiXxx:query` and `FNPT:NopAiXxx:mutation` permission checks)
- The custom `summarizeByModel()` method lacks `@Auth`, meaning it has no explicit permission guard beyond whatever the framework's default auth policy applies

### Finding — Missing @Auth on Custom @BizQuery

**Finding ID**: **P2-MA2-027**  
**Severity**: P2 (Moderate)  
**File**: `nop-ai-service/src/main/java/io/nop/ai/service/entity/NopAiChatResponseBizModel.java`, line 59  
**Interface**: `nop-ai-dao/src/main/java/io/nop/ai/biz/INopAiChatResponseBiz.java`, line 15  

```java
// INopAiChatResponseBiz.java line 15
@BizQuery
List<ModelUsageSummary> summarizeByModel(@Name("sessionId") String sessionId, IServiceContext context);

// NopAiChatResponseBizModel.java lines 59-65
@Override
@BizQuery
public List<ModelUsageSummary> summarizeByModel(@Name("sessionId") String sessionId, IServiceContext context) {
    // ...
}
```

**Description**: The `summarizeByModel()` custom query method is exposed as a GraphQL query via `@BizQuery` but has no `@Auth` annotation to restrict access. The generated action-auth config defines `FNPT:NopAiChatResponse:query` and `FNPT:NopAiChatResponse:mutation` permissions, but `summarizeByModel` is a custom method that doesn't fall under the standard `:query` umbrella generated for CRUD `findPage`/`findList`.

**Risk**: Any authenticated user can call `summarizeByModel()` on any session's data. While the method validates that `sessionId` is not blank, it does not check whether the caller has permission to access the session's billing data. This could lead to unauthorized access to token usage and estimated cost data across sessions.

**Recommendation**: Add `@Auth(permission = "NopAiChatResponse:query")` to the method — either in the interface or the implementation class:

```java
@Override
@BizQuery
@Auth(permission = "NopAiChatResponse:query")
public List<ModelUsageSummary> summarizeByModel(@Name("sessionId") String sessionId, IServiceContext context) {
```

## 8. Additional Advisory — FieldSelectionBean on Custom Method

**Finding ID**: **P3-MA2-028**  
**Severity**: P3 (Low / Advisory)  
**File**: `nop-ai-service/src/main/java/io/nop/ai/service/entity/NopAiChatResponseBizModel.java`, line 60  

```java
public List<ModelUsageSummary> summarizeByModel(@Name("sessionId") String sessionId, IServiceContext context) {
```

**Description**: The `summarizeByModel()` method does not accept `FieldSelectionBean selection` as a parameter. In the Nop framework, `@BizQuery` methods that return entities or data beans should accept `FieldSelectionBean` to allow GraphQL clients to select only the fields they need. The current implementation always returns all 7 fields of `ModelUsageSummary`.

**Risk**: Low. `ModelUsageSummary` is a small DTO (7 fields: modelId, aiProvider, aiModel, totalPromptTokens, totalCompletionTokens, callCount, totalDurationMs, estimatedCost) with no large text/blob columns. The bandwidth impact of always returning all fields is negligible. However, this deviates from the Nop best practice pattern and could become a concern if the DTO grows.

**Recommendation**: (Optional) Add `FieldSelectionBean selection` to the method signature for future-proofing:

```java
@Override
@BizQuery
@Auth(permission = "NopAiChatResponse:query")
public List<ModelUsageSummary> summarizeByModel(@Name("sessionId") String sessionId,
                                                  FieldSelectionBean selection,
                                                  IServiceContext context) {
```

This would require wrapping the return value with selection-aware handling, e.g., using `context.getSelectionCollector()` or passing `selection` to the framework's result processing.
