## Findings

### P2-MA3-001: nop-ai-core declares compile-scope nop-dao dependency (Rule 3 layer violation)

- **File**: `nop-ai/nop-ai-core/pom.xml:25-28`
- **Severity**: P2
- **Current state**: `nop-ai-core` declares `nop-dao` as a compile-scope (default) dependency. No `import io.nop.dao.*` statement found in any Java, XPL, or XML file under `nop-ai-core/src/main` or `nop-ai-core/src/test`. The dependency is effectively unused at compile time.
  ```xml
  <!-- nop-ai-core/pom.xml -->
  <dependency>
      <groupId>io.github.entropy-cloud</groupId>
      <artifactId>nop-dao</artifactId>
  </dependency>
  ```
  Source files in `nop-ai-core/src/main/java/io/nop/ai/core/` import only:
  - `io.nop.ai.api.*` (from nop-ai-api, correctly declared)
  - `io.nop.ai.core.*` (own module)
  - `io.nop.api.core.*` (framework)
  - `io.nop.commons.*` (framework)
  - `io.nop.core.*` (framework)
  - `io.nop.xlang.*` (framework)
  
  Zero references to `io.nop.dao.*`.

- **Risk**: This violates layered architecture rule #3 ("core层只依赖api和框架核心，不依赖dao"). The unused dependency introduces unnecessary transitive coupling. If `nop-dao` were ever removed or refactored, this module would be unaffected, making the dependency misleading for maintainers. It also obscures the true module boundary of `nop-ai-core`.

- **Suggestion**: Remove the `nop-dao` dependency from `nop-ai-core/pom.xml` if no runtime classpath need can be demonstrated. If it is somehow needed at runtime (e.g., by XPL templates loaded at runtime), add a comment documenting the runtime requirement or change to `<scope>provided</scope>`.

- **Confidence**: High (90%). Exhaustive search of all source files under `nop-ai-core/src` found zero references. If runtime reflection / XPL-based class loading is the reason, it should be documented.

- **False-positive exclusion**: The calibration list specifically exempts `nop-api-core`, `nop-commons`, `nop-core`, `nop-xlang`, `nop-markdown` as "stable transitive deps not needing declaration." `nop-dao` is not in that list and is architecturally significant as a persistence-layer module. This is not a case of "declaring necessary transitive deps" (which is good practice) — it is a direct violation of the core→dao prohibition.

### P3-MA3-002: nop-ai-codegen declares compile-scope dependencies without main source evidence

- **File**: `nop-ai/nop-ai-codegen/pom.xml:26-33`
- **Severity**: P3
- **Current state**: `nop-ai-codegen` declares `nop-graphql-core` and `nop-xlang-debugger` as compile-scope dependencies. The module has **no main source code** (only `src/test/java/io/nop/ai/codegen/NopAiCodeGen.java`). No references to `io.nop.graphql.*` or `io.nop.xlang.debugger.*` were found in any file under `nop-ai-codegen/src/main`.
  ```xml
  <!-- nop-ai-codegen/pom.xml lines 26-33 -->
  <dependency>
      <groupId>io.github.entropy-cloud</groupId>
      <artifactId>nop-graphql-core</artifactId>
  </dependency>
  <dependency>
      <groupId>io.github.entropy-cloud</groupId>
      <artifactId>nop-xlang-debugger</artifactId>
  </dependency>
  ```
  The only test source (`NopAiCodeGen.java`) imports only `XCodeGenerator`, `MavenDirHelper`, and core initialization classes — none from these two modules.

- **Risk**: These dependencies may be needed at **runtime** by the codegen XPL scripts (in `postcompile/` or via `XCodeGenerator.runPostcompile`). If so, they should be either scoped as `provided` or documented with a comment explaining the runtime requirement. If genuinely unused, they bloat the dependency graph and increase build time.

- **Suggestion**: Investigate whether `nop-graphql-core` and `nop-xlang-debugger` are actually required at runtime for the codegen script execution. If yes, add a comment in `pom.xml` explaining the runtime dependency and consider changing to `<scope>provided</scope>`. If no, remove them.

- **Confidence**: Medium (70%). It is plausible that codegen XPL tasks load GraphQL model classes reflectively. The audit cannot fully verify runtime codegen classpaths without executing the build.

- **False-positive exclusion**: This is not about "unused but harmless" declarations — it's about potentially over-broad compile-scope deps that violate the principle of minimal dependency surface. If they are confirmed runtime deps, the fix is scope documentation, not removal.

### P3-MA3-003: nop-ai-rag is an empty module with no code or dependencies

- **Severity**: P3
- **Current state**: The `nop-ai-rag` module has:
  - A `pom.xml` with **zero dependencies** (no internal or external deps)
  - No `src/` directory (no Java, no resources, no templates)
  - Only build artifacts (`target/`) and IDE config files (`.classpath`, `.project`, `.settings`)
  
  ```xml
  <!-- nop-ai/nop-ai-rag/pom.xml (entire file) -->
  <?xml version="1.0" encoding="UTF-8"?>
  <project ...>
      <modelVersion>4.0.0</modelVersion>

          <maven.compiler.source>21</maven.compiler.source>
          <maven.compiler.target>21</maven.compiler.target>
          <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
      </properties>
  </project>
  ```

- **Risk**: This is a dead module. It adds Maven build time (module discovery, artifact creation) with zero delivered value. It may confuse maintainers who expect RAG (Retrieval-Augmented Generation) functionality to exist here.

- **Suggestion**: Either (a) remove the module from `nop-ai/pom.xml` and `nop-ai-rag/` entirely, or (b) populate it with the planned RAG implementation. If the module was created as a placeholder for future work, add a `README.md` or comment in pom explaining the intent.

- **Confidence**: High (95%). Directory inspection confirms no source code exists. The only other possibility is generated output in `target/`, but generated artifacts without source are meaningless.

- **False-positive exclusion**: This is not a "looks not elegant" complaint. An empty module with zero deps is a concrete build-time cost with no benefit. The plan explicitly targets module structure quality.

### P3-MA3-004: nop-ai-meta has no compile-scope internal dependencies (all test scope)

- **File**: `nop-ai/nop-ai-meta/pom.xml:15-27`
- **Severity**: P3
- **Current state**: The `nop-ai-meta` module declares both `nop-ai-codegen` and `nop-ai-dao` with `<scope>test</scope>` only. It has no compile-scope dependencies on any `nop-ai-*` module. The module contains only `precompile/`, `postcompile/` XGen scripts, `_templates/` JSON templates, and no Java source code in main scope.
  ```xml
  <!-- nop-ai/nop-ai-meta/pom.xml lines 15-27 -->
  <dependencies>
      <dependency>
          <artifactId>nop-ai-codegen</artifactId>
          <groupId>io.github.entropy-cloud</groupId>
          <version>${nop-entropy.version}</version>
          <scope>test</scope>
      </dependency>
      <dependency>
          <artifactId>nop-ai-dao</artifactId>
          <groupId>io.github.entropy-cloud</groupId>
          <version>${nop-entropy.version}</version>
          <scope>test</scope>
      </dependency>
  </dependencies>
  ```
  The `exec-maven-plugin` is configured with `<classpathScope>test</classpathScope>`, which confirms the XGen scripts intentionally run on the test-scope classpath.

- **Risk**: Low — this is a deliberate design choice for a template-only metadata module. However, it is architecturally unusual: the module produces XMeta files that reference entity definitions from `nop-ai-dao`, yet the compile-time dependency chain does not reflect this dependency. If another module depends on `nop-ai-meta` at compile scope (as `nop-ai-service` and `nop-ai-web` do), they must also have `nop-ai-dao` in their classpath to resolve the generated XMeta references, which they do.

- **Suggestion**: No code change needed. Consider documenting in the pom.xml with a `<comment>` that the test-scope pattern is intentional for the codegen-driven meta module. Alternatively, if any Java source is ever added to `nop-ai-meta/src/main`, the deps must be moved to compile scope.

- **Confidence**: High (90%). The test-scope classpath pattern for `exec-maven-plugin` is a known Nop convention for codegen-only modules.

- **False-positive exclusion**: This finding explicitly is **not** calling for a code change; it is documenting an architectural anomaly. The plan requires documenting all boundary deviations, and this one is significant enough to record.

### P3-MA3-005: nop-ai-dao contains I*Biz interfaces but does not depend on nop-ai-api

- **File**: `nop-ai/nop-ai-dao/pom.xml`
- **Severity**: P3
- **Current state**: `nop-ai-dao` defines 21 `INopAi*Biz` interfaces in package `io.nop.ai.biz` (e.g., `INopAiChatRequestBiz`, `INopAiSessionBiz`). These interfaces extend `ICrudBiz<T>` from `io.nop.orm.biz` (in `nop-orm` module). The module does not declare a dependency on `nop-ai-api`. The `nop-ai-api` module defines GraphQL API interfaces (`NopAi*Api`) and DTO beans, but the CRUD biz interfaces are independent.
  
  ```java
  // nop-ai-dao/src/main/java/io/nop/ai/biz/INopAiChatRequestBiz.java
  package io.nop.ai.biz;
  import io.nop.orm.biz.ICrudBiz;
  import io.nop.ai.dao.entity.NopAiChatRequest;
  
  public interface INopAiChatRequestBiz extends ICrudBiz<NopAiChatRequest> {
  }
  ```
  
  The pom.xml dependencies are only `nop-api-core` and `nop-orm`:
  ```xml
  <!-- nop-ai/pom.xml -->
  <dependencies>
      <dependency>
          <groupId>io.github.entropy-cloud</groupId>
          <artifactId>nop-api-core</artifactId>
      </dependency>
      <dependency>
          <groupId>io.github.entropy-cloud</groupId>
          <artifactId>nop-orm</artifactId>
      </dependency>
      <!-- nop-ai-codegen is test-only -->
      <dependency>
          <artifactId>nop-ai-codegen</artifactId>
          <scope>test</scope>
      </dependency>
  </dependencies>
  ```

- **Risk**: Low. The `I*Biz` interfaces in the dao module is a standard Nop platform pattern — they are CRUD contracts tied to ORM entities, not public API. The calibration explicitly excludes this as a finding (`"I*Biz接口放在dao模块（代码生成的DAO层CRUD契约，绑定DAO实体）"` is not a problem). However, the structural layering is non-standard: in a typical business module, the api layer would expose service interfaces, and dao would only expose entities and repositories.

- **Suggestion**: No change needed. Document this as an accepted Nop platform convention.

- **Confidence**: High (95%) — confirmed by the calibration list.

- **False-positive exclusion**: This is noted as a structural observation, not a violation. The calibration explicitly says this is NOT a problem.
