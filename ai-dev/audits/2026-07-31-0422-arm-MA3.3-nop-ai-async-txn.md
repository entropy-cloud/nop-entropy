## Findings

### Finding P3-MA3-001: `SequentialThinkingBizModel.clearHistory()` annotated `@BizQuery` but performs file mutation

- **File**: `nop-ai/nop-ai-tools/src/main/java/io/nop/ai/tools/sequential_thinking/service/SequentialThinkingBizModel.java`
- **Lines**: 98–102
- **Evidence**:
```java
    @BizQuery
    public void clearHistory(IServiceContext ctx) {
        String sessionId = AiToolsHelper.makeChatSessionId(ctx);
        storage.clearHistory(sessionId);
    }
```
`storage.clearHistory()` (ThoughtStorage.java:88–95) acquires a `ReentrantLock` and writes an empty list to a JSON session file — a mutation of persistent state.

- **Severity**: P3
- **State**: Present in current code
- **Risk**: The `@BizQuery` annotation signals to clients and code-generators that this operation is read-only and idempotent. A client calling `GET /r/SequentialThinking__clearHistory` would not expect the request to delete state. Moreover, `@BizQuery` does not wrap a transaction (correct for file operations), but the semantic contract of the annotation is violated. This could mislead code-generators (e.g., typed API generation) that use `@BizQuery`/`@BizMutation` to determine HTTP method binding.
- **Suggestion**: Change annotation to `@BizMutation`. The method performs a write (clearing history); `@BizMutation` is the correct annotation for mutations regardless of storage backend.
- **Confidence**: High
- **False-positive exclusion**: This is not a "query returning ORM entity" pattern (per Nop Platform Common Calibration, `BizModel` returning ORM entity is standard). This is a semantic mismatch between the annotation's documented contract (`@BizQuery` = read-only) and the actual behavior (file write). The Nop docs explicitly state: "`@BizQuery` = query/mutationless read, `@BizMutation` = write operation." Also notable: `processThought` in the same file is correctly annotated `@BizMutation`.

### Finding P3-MA3-002: `SubmissionPublisher` in `ChatServiceImpl.callStream()` — closed on terminal signals, but unbounded `request(Long.MAX_VALUE)`

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/service/ChatServiceImpl.java`
- **Lines**: 161–192
- **Evidence**:
```java
        SubmissionPublisher<ChatStreamChunk> publisher = new SubmissionPublisher<>();
        // ...
        eventPublisher.subscribe(new Flow.Subscriber<>() {
            @Override
            public void onSubscribe(Flow.Subscription subscription) {
                subscription.request(Long.MAX_VALUE);
                // ...
            }
            @Override
            public void onError(Throwable throwable) {
                publisher.closeExceptionally(throwable);
            }
            @Override
            public void onComplete() {
                publisher.close();
            }
        });
```
`SubmissionPublisher` is constructed with the default `maxBufferCapacity` (Flow.defaultBufferSize()). Requesting `Long.MAX_VALUE` means no backpressure — the upstream `IServerEventResponse` publisher pushes all chunks without demand control.

- **Severity**: P3
- **State**: Present in current code
- **Risk**: In theory, a very fast upstream publisher + slow downstream consumer could cause the `SubmissionPublisher`'s internal buffer to overflow, dropping chunks or throwing `IllegalStateException`. In practice, for LLM streaming use cases (single request, bounded response, SSE over HTTP), the risk is low — the upstream is rate-limited by network I/O. However, this pattern is not robust against a pathological upstream or if the publisher is reused.
- **Suggestion**: Consider using a bounded request pattern (e.g., `subscription.request(1)` followed by `request(1)` after each `onNext`) to enable backpressure, or document in a comment why unbounded demand is safe for this specific use case (e.g., "SSE stream capped by network I/O — no unbounded upstream possible"). No urgent action required.
- **Confidence**: Medium
- **False-positive exclusion**: This is not a general `@BizQuery`/`@BizMutation` pattern issue — it's a specific reactive streams backpressure concern. The risk is minimal in practice but represents a deviation from the Reactive Streams spec's recommendation against unbounded demand.
