### [MA7.5-01] cron job 首次 checkpoint 级执行错误后永久死亡，且配置修复后无法复活（P1）

- **文件**: `quality/MetaQualityCheckpointScheduler.java:202-212`（executeScheduledCheckpoint）；平台链 `nop-job-local/.../BeanMethodJobInvoker.java:57-65` → `nop-job-core/.../LocalJobScheduler.java:277-296,84-90`；`JobFireResult.java:62-67`
- **证据片段**:
  ```java
  // BeanMethodJobInvoker —— 捕获任何异常返回 ERROR result
  } catch (Exception e) {
      return CompletableFuture.completedFuture(JobFireResult.ERROR(...));
  }
  // LocalJobScheduler.handleResult —— ERROR → FAILED 态，scheduleNext 永不调用
  if (result.isErrorResult()) { job.state.internal = InternalState.FAILED; return; }
  // addJob(allowUpdate=true) update 分支 —— 仅 WAITING/SUSPENDED 重排程，FAILED 不复活
  ```
- **严重程度**: P1
- **现状**: `executeScheduledCheckpoint` 直调 raw executeCheckpoint，后者在配置级错误路径抛异常（不落入 per-rule catch）：`ERR_CHECKPOINT_NOT_ACTIVE`（:105-109）、`ERR_CHECKPOINT_ACTION_NOT_SUPPORTED`（:112）、**`ERR_CHECKPOINT_NO_RULES`**（:116-120，validations 引用规则被删/validations JSON 畸形→parseValidations 静默空集）、`ERR_CHECKPOINT_NOT_FOUND`（直接改库删除）、`ERR_CHECKPOINT_RULE_TARGET_TABLE_NOT_FOUND`。异常经 invoker → JobFireResult.ERROR → FAILED 态 → 不再调度。用户修好配置后 save → registerCheckpoint → addJob(allowUpdate=true) 仅对 WAITING/SUSPENDED 重排程 → **FAILED 不复活**。唯一恢复手段 = 重启 JVM（init() 全量重注册）。
- **风险**: 任一配置笔误/规则误删/直接改库，该检查点的定时质量检查永久静默停止（仅日志留一次 ERROR），告警链路全断且修复配置无效。模块 javadoc（scheduler:60-66）把"转 JobFireResult.ERROR"当作显式化特性宣传，未意识到 ERROR 语义是终止任务。
- **建议**: (a) executeScheduledCheckpoint 内 try/catch，把 checkpoint 级业务错误转为 LOG.error + 返回正常 summary（附 errors），让 job 存活；(b) 或依赖调度器复活路径；(c) 至少把 NO_RULES 等配置错误改为"登记 + 不抛"。
- **信心水平**: 高（模块→invoker→scheduler 全程源码链追踪）
- **修复归属**: **MR3（新发现）**

### [MA7.5-03] cron 改为非法值后旧 job 残留——旧调度继续触发、新配置永不上线（P2）

### [MA7.5-04] 调度器副作用处于业务事务内：save/delete 回滚产生僵尸 job / 调度静默丢失（P2）

- **文件**: `entity/NopMetaQualityCheckpointBizModel.java:224-262`（save 后 register / delete 前 unregister）
- **严重程度**: P2
- **现状**: save→register 在事务提交前注册 job：外层事务回滚 → job 指向不存在的 checkpoint → 首个 cron 触发抛 CHECKPOINT_NOT_FOUND → 经 MA7.5-01 链路 job 死亡。delete→unregister 在删除提交前移除 job：删除回滚 → 检查点仍在但 cron job 已永久移除（重启才恢复）——调度静默丢失且无日志。
- **风险**: 低概率（事务回滚）但后果与 MA7.5-01 叠加（一次性杀死调度或静默丢调度），无恢复手段。
- **建议**: 注册/移除延迟到事务提交后（afterCommit listener 或独立事务触发）；或记录"预注册/预移除"待回滚回补。
- **信心水平**: 高
- **修复归属**: **MR3（新发现）**

## 总评

可靠性面出现**一个 P1 结构性缺陷**（MA7.5-01）和四个 P2：整个 cron 调度链（模块 scheduler → BeanMethodJobInvoker → LocalJobScheduler）在"JobFireResult.ERROR 终止任务"的平台上没有任何存活策略——任何 checkpoint 级配置错误（尤其 NO_RULES）会一次性、永久性杀死定时质量检查，且修复配置无法复活（重启除外）。这是此前 MA3.4/MA6.x 各轮都未跨模块追踪到的一跳（模块 javadoc 甚至把该行为当作"显式化"特性）。叠加效应显著：MA7.5-07（静默空 validations）→ MA7.5-01（job 死亡）；MA7.5-03（旧 job 残留）→ 过期调度继续触发。**修复优先级建议：MA7.5-01 应先于一切**。事件面（MA7.5-08/09/10）总体健康：脱敏链完整、零消费者无投递风险、fail-close 设计裁定维持；唯一实质残留是 dispatcher javadoc 过期与兜底列名缺口（均 P3）。

- 平台行为（FAILED 死亡、WAITING 门、fireNow-running）基于源码逐行推断，未用运行实验验证；TestMetaQualityCheckpointScheduler 仅覆盖成功/空 cron/PAUSED 路径

- 多实例部署形态未核实
