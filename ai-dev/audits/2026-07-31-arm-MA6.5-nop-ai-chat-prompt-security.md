# MA6.5 — Chat History & Prompt Security Audit (nop-ai)

**Date**: 2026-07-31
**Scope**: nop-ai-core (service, persist, api/messages) + nop-ai-agent (session stores, engine)
**Methodology**: Open-ended adversarial review (ai-dev/skills/open-ended-adversarial-review-prompt.md)
**Auditor**: Phase 9 (MA6.5) of audit plan 2026-07-31-0000-3-arm-ma5-ma6-audit.md

## Findings

### [AR-1] User message content shipped to LLM without input sanitization

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/engine/DefaultAgentEngine.java:2279`
- **Evidence**:
  ```java
  ctx.addMessage(new ChatUserMessage(request.getUserMessage()));
  ```
  The `request.getUserMessage()` is a raw `String` from the external caller. It is placed directly into a `ChatUserMessage` object without any sanitization, content-filtering, or prompt-injection detection before being sent to the LLM.
- **Severity**: P1
- **Status**: No input validation, sanitization, or content guardrail check is applied to the user message before it enters the conversation history and is subsequently sent to the LLM. The `IContentGuardrail` exists in the wiring but is opt-in (default `NoOpContentGuardrail`).
- **Risk**: Direct prompt injection: a user can embed instructions in their message that override the system prompt, instruct the LLM to exfiltrate data, or hijack tool-calling behaviour. Because the guardrail is no-op by default, this is a live vulnerability on any deployment that does not explicitly wire a guardrail.
- **Recommendation**: Make `IContentGuardrail` mandatory (fail-closed if not wired) and apply it to user messages before they enter the conversation context. At minimum, add a system-level guardrail that strips/rejects known injection patterns before the message reaches the LLM.

### [AR-2] DefaultAiChatExchangePersister writes full conversation history to disk in plain text

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/persist/DefaultAiChatExchangePersister.java:123-127`
- **Evidence**:
  ```java
  public String serialize(AiChatExchange exchange) {
      StringBuilder sb = new StringBuilder();
      writeExchange(sb, exchange);
      return sb.toString();
  }
  ```
  The serialized output includes the complete `Prompt` (all messages including system/user/assistant content, tool definitions, variables, metadata) + the response + usage data. The file format is markdown with embedded JSON, written via `ResourceHelper.writeText(resource, ...)` with no encryption.
- **Severity**: P1
- **Status**: Every `AiChatExchange` call (deprecated `IAiChatService` path) that is persisted via `DefaultAiChatExchangePersister` writes the full user prompt, system instructions, tool definitions, variables, and model response as plaintext to the configured storage directory. The persister is the default implementation (`s_instance` singleton).
- **Risk**: Users may inadvertently include sensitive information (PII, credentials, internal business data) in their chat messages. This data is persisted indefinitely on the filesystem with no encryption, access control, or retention policy. An attacker who gains filesystem access can read the entire conversation history of every user.
- **Recommendation**: Add at-rest encryption for persister output. Implement a retention/rotation policy. Consider transparently redacting or blocking known sensitive patterns (e.g., API keys, bearer tokens) before persistence.

### [AR-3] ChatLogger logs full request/response content verbatim

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/service/DefaultChatLogger.java:26-34`
- **Evidence**:
  ```java
  public void logRequest(ChatRequest request) {
      ChatMessage message = request.getLastMessage();
      LOG.info("request:role={},content=\n{}", message.getRole(), message.getContent());
      if (isValidLogDir()) {
          IResource resource = getResource(request, "-request.yaml");
          ResourceHelper.writeText(resource, JSON.serialize(request, true));
      }
  }
  ```
  Both the logger SLF4J output and the file-based log capture include the **full message content** with no truncation, redaction, or PII filtering. This includes user messages, system instructions, and tool definitions.
- **Severity**: P2
- **Status**: Activated by config `CFG_AI_SERVICE_LOG_MESSAGE` (default `false`, but trivially enabled). When enabled, every request and response is written as a pretty-printed JSON YAML file to the log directory, plus logged via SLF4J at INFO level where it may be captured by a centralized log aggregator.
- **Risk**: If chat logging is enabled (e.g., for debugging in staging or production), all user conversations are written to disk and/or log aggregation systems with zero access control or redaction. Sensitive information in chat messages becomes available to anyone with log access.
- **Recommendation**: Never log message content at INFO level by default. When file logging is enabled, add a configurable content redaction filter (regex patterns for credentials, tokens, etc.). Implement log rotation with expiry.

### [AR-4] DBSessionStore persists full message history in unencrypted SESSION_DATA CLOB

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/session/DBSessionStore.java:280-333`
- **Evidence**:
  ```java
  public void save(AgentSession session) {
      ...
      String json = SessionFileWriter.serialize(session);
      ...
      ps.setString(4, json);
      ...
  }
  ```
  The `SessionFileWriter.serialize()` (line 110-133 of `SessionFileWriter.java`) creates a `LinkedHashMap` with all session fields including `messages` (full `List<ChatMessage>` with user/assistant/system content) and serializes to JSON. This JSON is stored in the `SESSION_DATA` CLOB column in the `ai_agent_session` table with no column-level encryption.
- **Severity**: P1
- **Status**: The `session.json` / DB CLOB stores every single user message, tool call, and tool response as part of `AgentSession.messages`. This is the primary crash-recovery mechanism, so it is written frequently (after every tool call, every checkpoint, every save). No encryption-at-rest is applied to the DB column.
- **Risk**: A database dump or SQL injection attack exposes the complete conversation history for every user session. Combined with AR-6 (no prompt-injection guard), an attacker who controls the DB can inject crafted session data that, when restored, executes malicious prompts.
- **Recommendation**: Add column-level encryption for `SESSION_DATA`. Consider separating the user message content into a separate encrypted store rather than bundling everything into the session aggregate. Implement a TTL for session data in the DB.

### [AR-5] No cross-session access control on legacy IAiChatSession

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/service/AbstractAiChatSession.java:36-38`
- **Evidence**:
  ```java
  public List<AiMessage> getActiveHistoryMessages() {
      return messages;
  }
  ```
  The `AbstractAiChatSession` stores messages in a plain `List<AiMessage>` field. The `IAiChatSession.getActiveHistoryMessages()` returns all messages without any authorization check. There is no binding between the session and the calling user identity.
- **Severity**: P1
- **Status**: The legacy `IAiChatSession` interface (used by `DefaultAiChatService.newSession()`) provides no mechanism for session ownership, user binding, or access control. Any caller with a `sessionId` can access the full message history. The `IAiChatService.getSession(sessionId)` method is documented as `@Deprecated(forRemoval=true)` but still present in the interface.
- **Risk**: If the legacy `IAiChatService` path is used, a malicious caller can enumerate or guess session IDs (which are UUIDs, but may be leaked through other channels) and read any user's conversation history. No authentication is required at the session access layer.
- **Recommendation**: Add explicit session-to-user ownership tracking. Validate that the requesting identity matches the session owner before returning `getActiveHistoryMessages()`. Since the interface is deprecated for removal, prioritize migration to the new `DefaultAgentEngine` + `ISessionStore` path where tenant isolation exists.

### [AR-6] System prompt assembly concatenates untrusted content without segregation

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/engine/DefaultAgentEngine.java:2448-2470`
- **Evidence**:
  ```java
  String systemPrompt = null;
  if (agentModel.getPrompt() != null) {
      systemPrompt = agentModel.getPrompt().getSource();       // from config — trusted
  }
  String memorySection = buildBudgetedMemorySection(session.getSessionId()); // from data — less trusted
  if (memorySection != null) {
      if (systemPrompt == null || systemPrompt.isEmpty()) {
          systemPrompt = memorySection;
      } else {
          systemPrompt = systemPrompt + "\n\n" + memorySection;
      }
  }
  ...
  ctx.addMessage(new ChatSystemMessage(systemPrompt));
  ```
  The budgeted memory section (loaded from `IAiMemoryStore`, which may contain user-originated content from prior interactions) is **concatenated directly** into the system prompt string. There is no delimiter, separator, or role distinction between the trusted agent model prompt and the potentially-untrusted memory content.
- **Severity**: P1
- **Status**: Memory content (which is ultimately derived from user messages and LLM responses in prior conversation turns) is injected into the system prompt with no privilege boundary. An attacker who controls the conversation history can influence the system prompt in subsequent turns.
- **Risk**: Classic prompt injection persistence path: user sends "Ignore your instructions" → it gets stored in memory → memory is concatenated into the system prompt of the next turn → the LLM overrides its original instructions. This is a cross-turn prompt injection amplification vector.
- **Recommendation**: Never concatenate user-derived content into the system prompt. Instead, keep memory in a separate user-role or tool-role message that appears after the system prompt. The LLM architecture inherently gives system messages higher priority over user messages, so this separation creates a natural privilege boundary.

### [AR-7] Response cache stores prompt-response pairs indefinitely with no TTL

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/persist/DefaultAiChatResponseCache.java:41-45`
- **Evidence**:
  ```java
  public void saveCachedResponse(AiChatExchange exchange) {
      IResource resource = getCacheResource(exchange.getPrompt(), exchange.getChatOptions());
      chatExchangePersister.save(resource, exchange);
  }
  ```
  Cached exchanges are persisted to the filesystem with a path derived from provider/model/prompt-name/hash. No TTL, expiry, or eviction policy is enforced. Once written, a cached response stays on disk forever.
- **Severity**: P2
- **Status**: The cache is intended to avoid redundant LLM calls for identical prompts. However, there is no mechanism to expire cached entries. If the cache directory is not manually cleaned, old cached exchanges accumulate indefinitely. Cached exchanges include full request and response content.
- **Risk**: (a) Storage growth unbounded over time. (b) Old cached responses may contain obsolete or incorrect information that gets replayed. (c) Sensitive information in cached exchanges persists beyond its useful lifetime.
- **Recommendation**: Implement TTL-based cache eviction (configurable per-provider/model). Add a cache entry timestamp and expire entries older than a configurable duration. Consider not persisting the full exchange but only an opaque cached response token.

### [AR-8] AgentSession.forkSession inherits all parent messages without sanitization

- **File**: `nop-ai/nop-ai-agent/src/main/java/io/nop/ai/agent/session/FileBackedSessionStore.java:273-276`
- **Evidence**:
  ```java
  if (inheritContext) {
      child.appendMessages(parent.getMessages());
      child.setPlanId(parent.getPlanId());
      child.setMetadata(parent.getMetadata());
  }
  ```
  `forkSession()` copies the entire parent message history (including every user, assistant, system, and tool message) into the child session without any filtering, sanitization, or privilege re-validation. This is identical in `InMemorySessionStore.forkSession()` and `DBSessionStore.forkSession()`.
- **Severity**: P2
- **Status**: When `inheritContext=true`, the child session receives the complete parent conversation history verbatim. If the parent was a high-privilege agent or contained sensitive data in its context, the child agent (which may have different tool permissions or a different agent model) inherits all of it unconditionally.
- **Risk**: Sensitive data spills across agent boundaries. A child agent with fewer security restrictions inherits the full context of its parent, potentially including data the child should not have access to. The inherited messages are persisted in the child's session store as well.
- **Recommendation**: When forking with `inheritContext=true`, apply a permission-based filter to messages before copying: only messages that the child agent is authorized to see should be inherited. At minimum, add a configurable message-filtering hook to `forkSession()`.

### [AR-9] ChatLogHelper session paths use unsanitized sessionId from request

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/service/ChatLogHelper.java:15-21`
- **Evidence**:
  ```java
  static String makeSessionId(ChatRequest request) {
      String sessionId = request.makeOptions().getSessionId();
      if (sessionId == null) {
          ...
          sessionId = prefix + '-' + StringHelper.generateUUID();
          request.getOptions().setSessionId(sessionId);
      }
      return sessionId;
  }
  ```
  When a `sessionId` is provided by the caller (via `request.makeOptions().getSessionId()`), it flows directly into a filesystem path without validation or sanitization. The returned sessionId is used in `ChatLogHelper.getSessionResource()` to construct a `FileResource`.
- **Severity**: P1
- **Status**: If the caller provides a `sessionId`, it is used directly in `makeSessionId()` without any path-traversal validation (unlike the nop-ai-agent `FileBackedSessionStore` which has `SessionIds.requireContainedPath`). The `ChatLogHelper` in nop-ai-core does not validate the sessionId.
- **Risk**: A malicious caller or prompt injection that controls the `ChatRequest.options.sessionId` can perform path traversal when chat logging is enabled, writing log files to arbitrary filesystem locations. This is a limited write-what-where primitive.
- **Recommendation**: Add path-traversal validation to `ChatLogHelper.makeSessionId()` (reuse the `SessionIds.requireValidIdentifier` pattern from nop-ai-agent). Sanitize the sessionId to `[A-Za-z0-9_-]` before constructing any filesystem path.

## Total Assessment

The nop-ai modules have a clear **prompt injection persistence chain**: user input (AR-1) → stored verbatim in session messages (AR-2, AR-4) → loaded into memory → concatenated into system prompt on next turn (AR-6). This is the highest-risk finding cluster because it is a built-in amplification loop rather than a configuration mistake.

The DBSessionStore and FileBackedSessionStore have good path-traversal guards and tenant isolation logic, but the legacy `nop-ai-core` side (`ChatLogHelper`, `DefaultAiChatExchangePersister`, `DefaultChatLogger`) has none of these guards. This is a two-tier security posture: the new agent engine is well-guarded, but the old legacy APIs remain unhardened.

There is also a systematic absence of content-layer security: no input sanitization, no output filtering, no PII redaction, no encryption at rest. These are all declared out-of-scope or future-work in the plans but from a deployment perspective they are live risks.

## Qualitative Risk Ranking (by likelihood × impact)

1. **Prompt injection persistence chain** (AR-1 → AR-6): likely, high impact
2. **Plaintext conversation storage** (AR-2, AR-4): certain, medium impact (requires FS/DB access)
3. **Path traversal via log helper** (AR-9): unlikely but high impact if exploited
4. **Unlimited cache persistence** (AR-7): certain, low impact
5. **Unrestricted fork inheritance** (AR-8): conditional on multi-agent usage, medium impact
6. **Verbose logging** (AR-3): conditional on config, medium impact
7. **No session access control** (AR-5): conditional on legacy API usage, medium impact
