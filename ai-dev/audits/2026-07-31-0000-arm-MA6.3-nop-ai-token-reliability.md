## Findings

### [AR-1] ChatServiceImpl has no timeout — LLM calls can hang indefinitely

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/service/ChatServiceImpl.java:198-213`
- **Evidence**:
  ```java
  private HttpRequest buildHttpRequest(LlmModel config, String provider, String model,
                                        ChatRequest request, boolean stream, ILlmDialect dialect) {
      HttpRequest httpRequest = new HttpRequest();
      httpRequest.setMethod("POST");
      httpRequest.setUrl(dialect.buildUrl(baseUrl, config.getChatUrl(), apiKey));
      dialect.setHeaders(httpRequest, apiKey, config.getApiKeyHeader());
      Map<String, Object> body = dialect.buildBody(request, config, modelConfig, model, stream);
      httpRequest.setBody(JsonTool.serialize(body, false));
      return httpRequest;  // ← no timeout set anywhere
  }
  ```
- **Severity**: P1
- **Status**: `ChatServiceImpl.buildHttpRequest()` creates an `HttpRequest` with zero timeout configuration. The `requestTimeout` field exists on `ChatOptions` (line 75 of `ChatOptions.java`) but is never read by `ChatServiceImpl`. The deprecated `DefaultAiChatService.initHeaders()` (line 285-289) does apply it, but that class is `@Deprecated`. The replacement `ChatServiceImpl` silently drops the timeout. The `ReActAgentExecutor` has its own `llmTimeoutMs` wrapper in `callChatWithTimeout()` (line 2356), but this only protects ReAct-loop callers — direct `IChatService.callAsync()` users get no timeout.
- **Risk**: A permanently hung LLM provider connection blocks the thread indefinitely. In production, this can exhaust the HTTP client connection pool and cascade into full service unavailability. No connect timeout means a TCP connection to an unresponsive host can block for minutes (kernel default ~127s).
- **Recommendation**: Apply the `requestTimeout` from `ChatOptions` (or a config-default) to the `HttpRequest` — at minimum a connect timeout (e.g. 10s) and a read timeout (e.g. 60s). The `buildHttpRequest` method should call `httpRequest.timeout(timeoutMs)` before returning.
- **Confidence**: High

### [AR-2] Default retry policy and circuit breaker are both pass-through — zero resilience out of the box

- **File**: `nop-ai-agent/src/main/java/io/nop/ai/agent/reliability/NoRetryPolicy.java:23-41` + `AlwaysClosed.java:33-72` + `ReActAgentExecutor.java:431-432`
- **Evidence**:
  ```java
  // ReActAgentExecutor.java:431-432
  this.retryPolicy = retryPolicy != null ? retryPolicy : NoRetryPolicy.noRetry();
  this.circuitBreaker = circuitBreaker != null ? circuitBreaker : AlwaysClosed.alwaysClosed();
  ```
  ```java
  // NoRetryPolicy.java:38-40
  public RetryOutcome shouldRetry(RetryContext context) {
      return RetryOutcome.stop();  // never retry
  }
  ```
  ```java
  // AlwaysClosed.java:48-50
  public boolean allowCall(String modelKey) {
      return true;  // always allow, never trip
  }
  ```
- **Severity**: P1
- **Status**: The out-of-box agent configuration has zero retry resilience and zero circuit-breaking. Every transient LLM failure (e.g. a 5-second OpenAI 503 spike) immediately terminates the entire ReAct loop. The functional implementations (`StandardRetryPolicy`, `ThresholdBreaker`) exist and are well-designed but are entirely opt-in via `DefaultAgentEngine.setRetryPolicy()` / `setCircuitBreaker()`. This is an explicit pass-through designed for zero-regression, but the runtime consequence is that any production deployment that forgets to register functional policies gets zero failure tolerance.
- **Risk**: Transient infrastructure failures cascade into user-visible failures. A 30-second provider outage can fail hundreds of concurrent agent sessions. The retry loop infrastructure (classification, backoff, context) is fully wired but inert because the policy defaults to "never retry".
- **Recommendation**: Change the shipped default to `StandardRetryPolicy` (with conservative defaults: 2 retries, 1s base delay, 30s cap). Keep the circuit breaker as `AlwaysClosed` (opting-in to circuit-breaking requires more deployment awareness). Document explicitly that `NoRetryPolicy` / `AlwaysClosed` are the defaults and what the operational impact is.
- **Confidence**: High — this is a deliberate design choice but a dangerous default for any generic deployment.

### [AR-3] Token counting is provider-agnostic and imprecise — no per-provider tokenizer

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/dialect/ILlmDialect.java:165-182` + `nop-ai-core/src/main/java/io/nop/ai/core/api/tokenizer/ITokenCountEstimator.java:1-9` + `nop-ai-agent/src/main/java/io/nop/ai/agent/engine/CalibratedTokenEstimator.java:66-71`
- **Evidence**:
  ```java
  // ILlmDialect.java:169-182 — default estimation, same for ALL providers
  static long estimateTokensDefault(List<ChatMessage> messages) {
      long total = 0;
      for (ChatMessage msg : messages) {
          total += PER_MESSAGE_TOKEN_OVERHEAD;  // 4
          String content = msg.getContent();
          if (content != null) {
              total += content.length() / CHARS_PER_TOKEN;  // chars/4
          }
      }
      return total;
  }
  ```
  ```java
  // CalibratedTokenEstimator.java:70-71 — same baseline for every ApiStyle
  public long estimateTokens(List<ChatMessage> messages) {
      long base = dialect.estimateTokens(messages);  // always chars/4
      return Math.round(base * factor);  // one EMA factor for all ApiStyles
  }
  ```
  ```java
  // ITokenCountEstimator.java — the only other tokenizer interface, has 0 implementations
  public interface ITokenCountEstimator {
      int estimate(String text);
      int estimateForMessage(AiMessage message);
  }
  ```
- **Severity**: P2
- **Status**: The `ITokenCountEstimator` interface (in `nop-ai-core/api`) has zero implementations across all nop-ai modules. Every token count in the system (context window tracking, compaction triggers) ultimately uses `chars/4` — a rough heuristic that doesn't account for any provider's actual tokenizer. OpenAI uses `cl100k_base` / `o200k_base`, Anthropic uses their own tokenizer, Gemini uses SentencePiece — all produce different token counts for the same text, yet the Nop platform estimates identically. The `CalibratedTokenEstimator` EMA customization mitigates this somewhat but uses a single factor per `ApiStyle`, not per model.
- **Risk**: Token-based context compaction fires at the wrong threshold: the compaction trigger uses `DEFAULT_TRIGGER_TOKEN_PERCENT = 0.8` of `DEFAULT_MAX_CONTEXT_TOKENS = 128000` (line 185-187 of `ReActAgentExecutor.java`). With a 4x underestimation (MAX_FACTOR=4.0), the actual context could be 4× the estimate before compaction fires, causing provider `context_length_exceeded` errors.
- **Recommendation**: Implement at least the most common tokenizer (OpenAI's `tiktoken` / `o200k_base` via a library call) as a drop-in `ITokenCountEstimator`. Add a provider-specific estimation override in each dialect's `estimateTokens()` method. At minimum, document the estimation error margin prominently so compaction trigger tuning is informed.
- **Confidence**: High

### [AR-4] Usage recording is NoOp by default — no token metering without explicit wiring

- **File**: `nop-ai-agent/src/main/java/io/nop/ai/agent/usage/NoOpUsageRecorder.java:20-40` + `ReActAgentExecutor.java:426`
- **Evidence**:
  ```java
  // ReActAgentExecutor.java:426
  this.usageRecorder = usageRecorder != null ? usageRecorder : NoOpUsageRecorder.noOp();
  ```
  ```java
  // NoOpUsageRecorder.java:35-39
  public void record(UsageRecord record) {
      // No-op: the pass-through default persists no per-call usage data.
  }
  ```
- **Severity**: P2
- **Status**: Every LLM call in the ReAct loop constructs a `UsageRecord` with prompt/completion tokens, provider, model, timing, etc. — and then silently discards it because `NoOpUsageRecorder` is the default. The `DbUsageRecorder` implementation exists (raw JDBC to `nop_ai_chat_response` table) but requires explicit wiring via `engine.setUsageRecorder(new DbUsageRecorder(dataSource))`. There is no operational alert or log warning when usage recording is inactive.
- **Risk**: No LLM call cost tracking, no billing data, no usage analytics, no audit trail of LLM consumption. If a compliance requirement demands usage records, the system silently fails to produce them. No feedback loop to detect unexpected token consumption until the provider bill arrives.
- **Recommendation**: Log a WARN-level message at agent startup when no `IUsageRecorder` is registered (or when `NoOpUsageRecorder` is in use). Consider shipping a default SimpleUsageRecorder that writes to a structured log (SLF4j MDC or JSON log line) so token usage is at least observable without a DB. Document the wiring path prominently.
- **Confidence**: High

### [AR-5] StandardRetryPolicy exponential backoff has no jitter — thundering herd risk

- **File**: `nop-ai-agent/src/main/java/io/nop/ai/agent/reliability/StandardRetryPolicy.java:131-148`
- **Evidence**:
  ```java
  private long computeBackoff(int attempt) {
      if (baseDelayMs == 0) {
          return 0L;
      }
      long delay = baseDelayMs;
      for (int i = 0; i < attempt && delay < maxDelayMs; i++) {
          long next = delay << 1;
          if (next < delay) { break; }  // overflow guard
          delay = next;
      }
      return Math.min(delay, maxDelayMs);  // pure deterministic backoff
  }
  ```
- **Severity**: P2
- **Status**: The exponential backoff is purely deterministic: every failed attempt at the same attempt-count computes `min(baseDelayMs * 2^attempt, maxDelayMs)` with zero randomization. When multiple ReAct loops share a provider and experience simultaneous failures (e.g. a provider returns 429 for all concurrent requests), every loop will retry at identical timestamps, recreating the load spike at each backoff step.
- **Risk**: Deterministic backoff transforms a transient rate-limit spike into a sustained thundering herd: all retries synchronize on the same schedule, compounding the provider load at each retry wave. This defeats the purpose of exponential backoff in a concurrent deployment.
- **Recommendation**: Add full jitter: `delay = random(0, min(baseDelayMs * 2^attempt, maxDelayMs))`, or at minimum capped jitter: `delay = min(baseDelayMs * 2^attempt, maxDelayMs) / 2 + random(0, min(baseDelayMs * 2^attempt, maxDelayMs) / 2)`. This is a well-established best practice (AWS, Google, all major SDKs implement jitter in their retry backoff).
- **Confidence**: High

### [AR-6] Simple in-memory rate limiting with no multi-tenant quota management

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/service/ChatServiceImpl.java:240-258` + `nop-ai-core/src/main/java/io/nop/ai/core/service/DefaultAiChatService.java:105-118`
- **Evidence**:
  ```java
  // ChatServiceImpl.java:240-258
  private void checkRateLimit(String provider, LlmModel config) {
      if (config.getRateLimit() == null) return;
      IRateLimiter rateLimiter = rateLimiters.computeIfAbsent(provider, k -> {
          return createRateLimiter(config.getRateLimit());
      });
      rateLimiter.acquire();  // single global token bucket per provider
  }
  ```
- **Severity**: P2
- **Status**: Rate limiting is a single in-memory `DefaultRateLimiter` (flat token bucket) per provider string, keyed in a `ConcurrentHashMap`. There is no per-user quota, no per-tenant isolation, no per-session cap, no cross-JVM coordination, and no distinction between burst and sustained rate limits. The `DefaultRateLimiter` is a simple rate limiter from `nop-commons` — it provides `acquire()` blocking but no `tryAcquire()`, so hitting the rate limit blocks the calling thread rather than failing fast with a retryable error.
- **Risk**: A single aggressive user/agent can consume the entire per-provider rate budget, starving all other concurrent users. No burst allowance means occasional traffic spikes are flatly rejected rather than absorbed. The blocking `acquire()` can hold agent worker threads under load, increasing latency for all sessions.
- **Recommendation**: Expose a `tryAcquire()` path that returns immediately when the rate limit is exceeded, allowing the ReAct loop to FALLBACK or backoff rather than blocking. Add per-tenant quota configuration. For production deployments, document that cross-JVM coordination (e.g. Redis-based distributed rate limiter) is a required extension.
- **Confidence**: High

## Assessment

### Strengths
- The **LlmErrorClassifier** (`nop-ai-agent/.../reliability/LlmErrorClassifier.java`) is well-designed — it unwraps the cause chain correctly (CompletionException, ExecutionException, SocketTimeoutException) and classifies by HTTP status code with clear rationale.
- The **ThresholdBreaker** (`nop-ai-agent/.../reliability/ThresholdBreaker.java`) is a clean three-state circuit breaker with proper locking, lazy cooldown (no background timers), and per-model-key isolation — the implementation quality is high.
- The **RetryContext** / **RetryOutcome** / **RetryDecision** data model is minimal and well-specified.
- The **DbUsageRecorder** uses raw JDBC (no ORM dependency) and handles the `modelId`-null case as graceful degradation.

### Most Critical Direction
1. **AR-1 (P1)** — The missing `requestTimeout` in `ChatServiceImpl` is the highest-impact finding: it can cause total connection pool exhaustion in production. This is a single-line fix (`httpRequest.timeout(...)`) with outsized impact.
2. **AR-2 (P1)** — The pass-through defaults for retry and circuit-breaker should be reconsidered for production workloads. At minimum, `StandardRetryPolicy` should be the shipped default.
3. **AR-5 (P2)** — The missing jitter in `StandardRetryPolicy.computeBackoff()` is a correctness issue in concurrent deployments — it defeats the purpose of backoff under concurrent load.

### Blind Spots
This audit did not:
- Test the actual HTTP client implementation (`IHttpClient`) to verify that `HttpRequest.timeout()` is correctly wired end-to-end.
- Audit the `DefaultRateLimiter` implementation in `nop-commons` for correctness under high concurrency.
