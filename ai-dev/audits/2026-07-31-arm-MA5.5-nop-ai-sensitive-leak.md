## Findings

### [AR-1] Hardcoded JWT encryption key in application.yaml (production app config)

- **File**: `nop-ai/nop-ai-app/src/main/resources/application.yaml:6`
- **Evidence**:
  ```yaml
  nop:
    auth:
      jwt:
        enc-key: 380732e8bdf34857974d97d3da3036e6
  ```
- **Severity**: P1
- **Status**: The JWT token encryption key `380732e8bdf34857974d97d3da3036e6` is hardcoded in a production application configuration file. This key is static and identical across all deployments.
- **Risk**: Any attacker with access to this public repository can forge valid JWT tokens. All deployed instances using this default key are vulnerable to authentication bypass.
- **Recommendation**: (1) Remove hardcoded key from source; (2) Load from `nop.auth.jwt.enc-key` environment variable or external secret store; (3) Rotate the key for any production deployment that has used the default.
- **Confidence**: certain

### [AR-2] Plaintext MySQL password in tools/application.yaml (active, not commented)

- **File**: `nop-ai/nop-ai-coder/tools/application.yaml:14`
- **Evidence**:
  ```yaml
  nop:
    datasource:
      driver-class-name: com.mysql.cj.jdbc.Driver
      jdbc-url: jdbc:mysql://127.0.0.1:3306/dev?useUnicode=true&characterEncoding=utf-8&useSSL=true&serverTimezone=UTC
      username: nop
      password: nop-test
  ```
- **Severity**: P1
- **Status**: Active MySQL datasource configuration in `nop-ai-coder/tools/application.yaml` contains a plaintext password `nop-test`. This is NOT commented out (unlike the sibling H2 block above it).
- **Risk**: Credential exposed in source code repository. Anyone with repo access can connect to any instance using these default credentials.
- **Recommendation**: Use `nop.datasource.password` environment variable or externalized config. Remove file from VCS or replace with H2 default.
- **Confidence**: certain

### [AR-3] API key embedded in Gemini request URL (leaks via any URL logging)

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/dialect/GeminiDialect.java:66-72`
- **Evidence**:
  ```java
  public String buildUrl(String baseUrl, String chatUrl, String apiKey) {
      String url = StringHelper.appendPath(baseUrl, chatUrl);
      if (!StringHelper.isEmpty(apiKey)) {
          url = url + (url.contains("?") ? "&" : "?") + "key=" + apiKey;
      }
      return url;
  }
  ```
- **Severity**: P1
- **Status**: Gemini API requires the key as a URL query parameter (`?key=...`). The full URL (with embedded API key) flows into `httpRequest.setUrl()` and is subsequently transmitted. Any error handler, access log, HTTP client debug log, or proxy that records the full URL will capture the API key in plaintext.
- **Risk**: Credential leakage through URL logging, HTTP referrer headers, browser history (if proxied), or error diagnostics.
- **Recommendation**: (1) Add `@Sensitive` annotation or URL-sanitizing wrapper around the `apiKey` query parameter; (2) Mask `key=` value in `toString()`/error messages; (3) If possible, switch to x-api-key header (Gemini supports it as alternative).
- **Confidence**: certain

### [AR-4] API key serialized in NopAiModelOutputBean (API response exposure)

- **File**: `nop-ai/nop-ai-api/src/main/java/io/nop/ai/api/beans/NopAiModelOutputBean.java:84-94`
- **Evidence**:
  ```java
  private String _apiKey;

  @PropMeta(propId=5)
  public String getApiKey(){
      return _apiKey;
  }

  public void setApiKey(String value){
      this._apiKey = value;
  }
  ```
- **Severity**: P1
- **Status**: `NopAiModelOutputBean` (a `@DataBean` GraphQL response DTO) exposes the API key as a serialized field with `propId=5`. This means any GraphQL query selecting `apiKey` on the `NopAiModel` entity will return the API key to the caller. The corresponding ORM entity `_NopAiModel` also stores `apiKey` as a plaintext column.
- **Risk**: Unauthorized users could retrieve LLM provider API keys through GraphQL introspection and queries. If multi-tenant, one tenant could read another's API key.
- **Recommendation**: (1) Mark field as `@PropMeta(propId=5, excludeFromAuth=false)` — actually remove it from the output bean entirely; (2) Store API keys in a separate encrypted secrets table, never in the main entity; (3) Use server-side-only config loading (existing `LlmConfigHelper` pattern) rather than database-stored keys.
- **Confidence**: certain

### [AR-5] API key stored as plaintext VARCHAR in database

- **File**: `nop-ai/nop-ai-dao/src/main/java/io/nop/ai/dao/entity/_gen/_NopAiModel.java:167`, `nop-ai/model/nop-ai.orm.xml:299`
- **Evidence**:
  ```xml
  <column code="api_key" displayName="API密钥" name="apiKey" precision="100"
          propId="5" stdDataType="string" .../>
  ```
  ```java
  private java.lang.String _apiKey;
  ```
- **Severity**: P2
- **Status**: The `NopAiModel` ORM entity persists the API key as a plaintext `VARCHAR(100)` column with no encryption-at-rest. The DB column is named `api_key` in the `nop_ai_model` table.
- **Risk**: Database dump, backup, or DBA access exposes all LLM provider API keys. No tenant isolation on the key storage. No encryption, no masking, no HSM.
- **Recommendation**: (1) Implement column-level encryption (AES-256-GCM with key rotation); (2) Or move API keys to a dedicated secrets table with access control; (3) Or follow the existing `LlmConfigHelper` file-based secret pattern instead of storing keys in the entity.
- **Confidence**: certain

### [AR-6] Example JWT bearer token in tool definition XML

- **File**: `nop-ai/nop-ai-toolkit/src/main/resources/_vfs/nop/ai/tools/http-request.tool.xml:95`
- **Evidence**:
  ```xml
  <auth type="bearer">
      <token>eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...</token>
  </auth>
  ```
- **Severity**: P2
- **Status**: The `http-request` tool definition includes an example call with a JWT bearer token. While this is a truncated/fake JWT (`...` suffix), it creates a dangerous pattern of embedding bearer tokens in tool definition examples and documentation.
- **Risk**: Developers copy-pasting examples into production usage may hardcode tokens. Also, this normalizes credential-in-config anti-pattern.
- **Recommendation**: (1) Remove the `<auth>` block from the example entirely; (2) If an auth example is needed, use placeholder text like `<token>YOUR_BEARER_TOKEN_HERE</token>` with a strong comment about never hardcoding.
- **Confidence**: certain

### [AR-7] Commented-out MySQL credentials in application.yaml files (credential sprawl)

- **File**: Multiple files
  - `nop-ai/nop-ai-app/src/main/resources/application.yaml:28-32`
  - `nop-ai/nop-ai-coder/src/test/resources/application.yaml:4-8`
  - `nop-ai/nop-ai-skills/nop-ai-translate/src/test/resources/application.yaml:4-8`
- **Evidence**:
  ```yaml
  #    driver-class-name: com.mysql.cj.jdbc.Driver
  #    jdbc-url: jdbc:mysql://127.0.0.1:3306/dev?useUnicode=true&characterEncoding=utf-8&useSSL=true&serverTimezone=UTC
  #    username: nop
  #    password: nop-test
  ```
- **Severity**: P2
- **Status**: Three application.yaml files contain commented-out MySQL datasource blocks with the same hardcoded credentials (`nop`/`nop-test`). While commented-out, they normalize credential exposure in source and create a risk of accidental uncommenting.
- **Risk**: If a developer uncomments the wrong block in a deployment environment, the well-known `nop-test` password becomes active. Also signals credential hygiene neglect.
- **Recommendation**: Remove all commented-out credential blocks from committed config files. The canonical H2 config is sufficient for source-level dev.
- **Confidence**: likely

### [AR-8] getApiVersion() uses wrong config constant (copy-paste bug)

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/service/DefaultAiChatService.java:261-263`
- **Evidence**:
  ```java
  private String getApiVersion(String llmName) {
      String apiVersionKey = StringHelper.replace(CONFIG_VAR_LLM_API_KEY, PLACE_HOLDER_LLM_NAME, llmName);
      return AppConfig.var(apiVersionKey, "");
  }
  ```
- **Severity**: P2
- **Status**: This method is supposed to read the API version from config (`nop.ai.llm.{llmName}.api-version`), but it uses `CONFIG_VAR_LLM_API_KEY` instead of `CONFIG_VAR_LLM_API_VERSION`. It constructs the wrong config key name (`...api-key` instead of `...api-version`). Not a direct credential leak but a copy-paste error that makes `getApiVersion` always return empty string.
- **Risk**: Azure OpenAI deployments (which require an `api-version` parameter) will silently fail to load the version, breaking API calls.
- **Recommendation**: Change to use `CONFIG_VAR_LLM_API_VERSION`.
- **Confidence**: certain

### [AR-9] Hardcoded test API key in dialect unit tests

- **File**: `nop-ai/nop-ai-core/src/test/java/io/nop/ai/core/dialect/TestAnthropicDialect.java:139`
- **Evidence**:
  ```java
  dialect.setHeaders(httpRequest, "test-api-key", null);
  assertEquals("test-api-key", httpRequest.getHeaders().get("x-api-key"));
  ```
- **Severity**: P3
- **Status**: Unit test uses a hardcoded string `"test-api-key"` as a test API key. While this is not a real credential, it creates a copyable pattern that may be replicated into production code or CI configs.
- **Risk**: Low — only test code, no real secret exposed. But the pattern is contagious: a developer searching for "how to set API key" might find this test and emulate it with a real key.
- **Recommendation**: (1) Use a `@Value`-injected test property or constant; (2) Or add a clear comment that test keys must never be real credentials.
- **Confidence**: likely

### [AR-10] Error handler omits HTTP response body (missed opportunity for credential leak)

- **File**: `nop-ai/nop-ai-core/src/main/java/io/nop/ai/core/service/ChatServiceImpl.java:120-124`
- **Evidence**:
  ```java
  if (response.getHttpStatus() != 200) {
      throw new NopException(ERR_AI_SERVICE_HTTP_ERROR)
              .param(ARG_LLM_NAME, provider)
              .param(ARG_HTTP_STATUS, response.getHttpStatus());
  }
  ```
- **Severity**: P3
- **Status**: When an LLM provider returns HTTP error, the error handler does NOT include the response body. The error code `ERR_AI_SERVICE_HTTP_ERROR` only logs `llmName` and `httpStatus`. This is good practice (avoids leaking LLM error details), but the same handler in `DefaultAiChatService` also omits the body. Conversely, if someone later "improves" this by adding the response body, they could accidentally leak the API key (which Gemini puts in the URL, or which appears in certain provider error messages).
- **Risk**: Low currently, but regression risk if developers add body to error messages without sanitizing credentials.
- **Recommendation**: (1) Add a `SanitizeResponseBody()` utility if error body logging is ever needed; (2) Document that LLM response bodies must never be logged raw.
- **Confidence**: interesting guess

## Assessment

### Key Risk Vectors

1. **Hardcoded JWT key** (`AR-1`): The most critical finding — it's in a production-facing config, used for authentication, and is fully static.
2. **API key in GraphQL response** (`AR-4`): The `NopAiModelOutputBean` design means API keys are accessible via GraphQL queries. Combined with database plaintext storage (`AR-5`), any user with model query access can retrieve all configured LLM provider keys.
3. **Gemini URL credential leak** (`AR-3`): Protocol-enforced key-in-URL pattern creates unavoidable leakage surface through any URL-logging infrastructure.
4. **Credential sprawl** (`AR-2`, `AR-7`): Multiple config files contain the same `nop-test` MySQL password, creating risk surface across test and production configs.

### Positive Practices Observed

- The `LlmConfigHelper.resolveApiKey()` method reads from `AppConfig.var()` and falls back to a file-based secret directory — good separation of credentials from code.
- Error messages in `AiCoreErrors` do NOT include the API key value (they use `{llmName}` and `{httpStatus}`).
- `IChatLogger` interface could filter if implemented correctly — but no audit of its implementation was done here.

### What Could Be Missed

- Runtime secret injection (env var, Docker secrets, K8s secrets) — these are external to source code scan.
- Third-party MCP modules (excluded from scope per plan).
- Log aggregator configs (ELK, Datadog, etc.) that might ingest credential-carrying fields.
- The actual `IChatLogger` implementations — if they log the full HTTP request/response, they may leak credentials.
