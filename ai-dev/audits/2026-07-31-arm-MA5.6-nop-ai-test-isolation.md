# MA5.6 — Test Isolation Audit: nop-ai

> Audit Date: 2026-07-31
> Auditor: AI (openended-adversarial-review-prompt.md)
> Scope: All `nop-ai/*/src/test/java/`
> Methodology: Open-ended adversarial review focused on shared mutable state, ordering dependencies, and cross-contamination between tests.

---

## Findings

### [AR-1] CoreInitialization lifecycle race across 40+ test classes

- **File**: Multiple files (see breakdown below)
- **Evidence**: Each test class independently manages `CoreInitialization` lifecycle via `@BeforeAll/@AfterAll`:

```java
// Appears in 40+ test classes across nop-ai-agent, nop-ai-gateway, nop-ai-service, etc.
@BeforeAll
static void init() {
    CoreInitialization.initializeTo(CoreConstants.INITIALIZER_PRIORITY_REGISTER_COMPONENT);
}

@AfterAll
static void destroy() {
    CoreInitialization.destroy();
}
```

`CoreInitialization` is a static-state singleton (lines 42-49 of `CoreInitialization.java`):
```java
private static List<ICoreInitializer> initializers;
private static int initializationLevel = -1;
private static boolean initialized;
private static long initializeBeginTime;
private static volatile boolean suspended;
private static Map<String, Object> bootstrapConfig = null;
private static List<Runnable> cleanups;
```

When test class A's `@AfterAll destroy()` fires, it tears down this global state. If test class B has not yet run its `@BeforeAll init()` (or is in the middle of execution when class A finishes), B will find `CoreInitialization` in a broken state. JUnit 5 does not guarantee test class execution order.

**Affected classes (non-exhaustive, >=40 files)**:

| Module | Count | Example files |
|--------|-------|---------------|
| nop-ai-agent | ~35 | `TestSmartModelRouterWiring`, `TestSmartModelRouterFallback`, `TestModelRouterInReActLoop`, `TestCallAgentExecutor`, `TestSendMessageExecutor`, `TestWorkingMemoryEndToEnd`, etc. |
| nop-ai-gateway | 1 | `AiDialectBackendMessageConverterTest` |
| nop-ai-service | 1 | `TestNopAiChatResponseSummarizeByModel` |
| nop-ai-coder | 1 | `TestAiCoderHelper` |
| nop-ai-dsl-orm | 1 | `TestGptOrmModelParser` |

- **Severity**: **P1**
- **Status**: Every test class independently calls `CoreInitialization.initializeTo()` and `CoreInitialization.destroy()` in `@BeforeAll/@AfterAll`, creating a cross-class-lifecycle race condition.
- **Risk**: Intermittent CI failures when test classes run in different orders or when parallel class execution is enabled (`junit.jupiter.execution.parallel.enabled=true`). One class's `destroy()` can de-initialize the framework before another class's tests complete.
- **Recommendation**: Replace per-class `@BeforeAll init/@AfterAll destroy` with a shared `TestExecutionListener` or JUnit 5 `LauncherInterceptor` that initializes once per test run and tears down once after all tests complete. Alternatively, use `@NopTestConfig` (already available in the project) which handles lifecycle correctly.

### [AR-2] Shared static mutable state in TestWorkingMemoryEndToEnd

- **File**: `nop-ai/nop-ai-agent/src/test/java/io/nop/ai/agent/tool/TestWorkingMemoryEndToEnd.java:84-85`
- **Evidence**:

```java
private static final AtomicReference<IAiMemoryStore> firstStoreSeen = new AtomicReference<>();
private static final AtomicInteger storeObservationCount = new AtomicInteger(0);
```

These static fields are mutated by test execution (e.g., `firstStoreSeen.compareAndSet(null, observed)`) and are never reset between test methods. If test ordering changes or tests are parallelized, `firstStoreSeen` from test method A leaks into assertion context of test method B.

- **Severity**: **P2**
- **Status**: Static test infrastructure fields mutated during test execution without `@BeforeEach` reset.
- **Risk**: Non-deterministic test failures when test ordering changes or under parallel execution. A passing test could be dependent on the prior test having populated (or not populated) these static fields.
- **Recommendation**: Replace static fields with instance fields + `@BeforeEach` initialization, or reset the static fields in `@BeforeEach`.

### [AR-4] Temp directory accumulation via deleteOnExit (resource leak)

- **File**: Multiple locations in `nop-ai-shell` and `nop-ai-maven`
- **Evidence**:

```java
// ShellCommandExecutorTest.java (nop-ai-shell), CdCommandTest.java, etc.
Path tempDir = Files.createTempDirectory("shell-test");
tempDir.toFile().deleteOnExit();

// DeltaVirtualFileSystemTest.java (nop-ai-maven)
Path basePath = Files.createTempDirectory("vfs-base-");
Path deltaPath = Files.createTempDirectory("vfs-delta-");
```

The `deleteOnExit()` hook only cleans up temp directories when the JVM exits. Over multiple test runs within the same JVM session (or across CI builds without cleanup), these accumulate.

- **Severity**: **P3**
- **Status**: Temp directories created in `@BeforeEach` with `deleteOnExit()` instead of explicit `@AfterEach` cleanup.
- **Risk**: Disk space accumulation across continuous test runs. In CI environments with shared workspaces, old temp directories may persist.
- **Recommendation**: Replace `deleteOnExit()` with explicit `@AfterEach` cleanup that deletes the temp directory immediately after each test.

### [AR-5] PassThroughModelRouter singleton shared across test files

- **File**: `nop-ai/nop-ai-agent/src/test/java/io/nop/ai/agent/router/TestPassThroughModelRouter.java:94-98`
- **Evidence**:

```java
@Test
void passThroughFactoryReturnsSingleton() {
    IModelRouter a = PassThroughModelRouter.passThrough();
    IModelRouter b = PassThroughModelRouter.passThrough();
    assertSame(a, b);  // Tests assert singleton identity
}
```

`PassThroughModelRouter.passThrough()` returns a static singleton. While the class is currently stateless, this pattern means every test that exercises `PassThroughModelRouter` shares the exact same object instance. If any state is ever added (even logging counters, timing, etc.), all tests become coupled.

- **Severity**: **P3**
- **Status**: Stateless singleton tested for identity, no current state pollution, but latent coupling risk.
- **Risk**: If a future change adds observable state to `PassThroughModelRouter`, tests will show non-deterministic failures depending on execution order.
- **Recommendation**: Change `passThrough()` to return a new instance each call, or add a defensive comment preventing state addition to the singleton.

boolean isWin = System.getProperty("os.name").toLowerCase().contains("win");

- **Severity**: P3 (observation only, no action needed)
- **Status**: Read-only system property access, no pollution risk.

### [AR-7] Test shell executor uses `deleteOnExit` for temp dirs without cleanup on error

- **File**: `nop-ai/nop-ai-shell/src/test/java/io/nop/ai/shell/executor/ShellConcurrencyEdgeCaseTest.java:44-45`
- **Evidence**:

```java
Path tempDir = Files.createTempDirectory("shell-test");
tempDir.toFile().deleteOnExit();
```

Same pattern as AR-4 but in the concurrency edge case test. Also related: the `@BeforeEach` creates new temp dirs but the `LocalToolFileSystem` writes files into them. If `deleteOnExit` fails (e.g., the dir is non-empty because the test left files), temp files persist.

- **Severity**: **P3**
- **Status**: Temp directories with deferred cleanup, potential accumulation under failure conditions.
- **Risk**: Orphaned temp directories on CI systems.
- **Recommendation**: Add `@AfterEach` cleanup that recursively deletes the temp directory regardless of test outcome.

### Top 3 concerns

1. **AR-1 (P1)**: The `CoreInitialization` lifecycle pattern is the single highest-risk isolation defect. With 40+ test classes each managing global state lifecycle, intermittent CI failures are almost guaranteed when tests run in non-deterministic order or parallel mode.
2. **AR-2/AR-3 (P2)**: Static mutable test infrastructure fields that are never reset create hidden test-ordering dependencies. These are ticking time bombs for parallel test execution.
3. **AR-4/AR-7 (P3)**: Temp directory accumulation is a low-priority but real operational concern for long-running CI pipelines.

### Blind spots

- This audit did not verify whether JUnit 5 parallel execution is enabled in the nop-ai pom.xml files. If enabled, all findings become one severity level higher.
- This audit did not check for shared global caches in `VirtualFileSystem` or `ReflectionManager` that CoreInitialization manages — those are framework-level concerns but could be triggered differently by different test orders.
