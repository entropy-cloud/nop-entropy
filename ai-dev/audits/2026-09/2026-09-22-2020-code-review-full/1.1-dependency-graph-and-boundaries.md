### P2-1.1-001 module-groups.md 未覆盖 10/47 root 模块（4 个全 docs-for-ai 零路由）

- **文件**: `docs-for-ai/01-repo-map/module-groups.md`；对照 root `pom.xml`（47 活跃 modules）
- **严重程度**: P2（真实维护成本：repo-map 是 AGENTS.md 指定的模块路由第一站）
- **现状**: 逐模块 grep 核对，10 个 root 模块在 module-groups.md 无专述：nop-bom、nop-cluster、nop-credential、nop-datav、nop-dev-tools、nop-format、nop-frontend-support、nop-migration、nop-search、nop-utils（nop-message/nop-treesitter/nop-utils 仅顺带提及，无本组行）。其中 **nop-bom、nop-datav、nop-dev-tools、nop-migration 在 docs-for-ai 全域（3500 文件）零提及**（datav 为 150 main/81 test 的 S/A 级组，完全无路由）；nop-cluster/format/frontend-support/message/search/utils 仅散见于 reusable-modules-overview/source-anchors 等，无模块级入口。
- **风险**: AI/新人按 AGENTS.md 路由（「模块分组和依赖关系见 module-groups.md」）找不到这 10 组的职责、子模块与入口文档；模块结构变更时无 owner doc 承接，漂移无告警。
- **建议**: module-groups.md 补齐 10 行（最小职责一句话 + 指向既有散落文档）；datav/dev-tools/migration 另建 03-modules 页或至少在 INDEX.md 挂路由；nop-bom 作为纯版本管理模块显式标注「非功能组」。归 R1.0 的 doc-sync 批次。

### P2-1.1-002 业务组间 service/core 实现级 compile 耦合 13 条

- **文件**: 各组 pom.xml（逐条坐标见下）；对照规则 `docs-for-ai/02-core-guides/architecture-principles.md` §二（跨模块经 `I*Biz` 接口、不直接绑定实现类）
- **严重程度**: P2（跨模块边界债：无 Maven 环、DAG 成立、同仓同版发布，故不判 P1；但方向与平台「契约依赖」收敛指引不一致）
- **现状**: 口径 =「业务样板 + 可复用业务」13 组（auth/job/task/wf/sys/report/rule/batch/dyn/file/retry/tcc/metadata）内部的 compile 级跨组模块边，合计 49 条（closure audit 独立复算确认）。分解：**21 条** `*-app` 源 → 外部 `-service`/`-web` 装配边（app 源合计 22，另 1 条 app 源边目标为非 service/web 层；装配边合法，Nop app 聚合模式）+ **28 条非装配边** = **13 条实现级耦合**（下表，pom 坐标经独立 closure audit 逐条实证）+ **15 条 `-dao`/`-api`/`-meta` 契约面收敛边**（方向合规，非发现）。13 条实现级耦合：
  - `nop-auth/nop-auth-service/pom.xml` → nop-sys-service（认证服务依赖系统服务实现）
  - `nop-batch/nop-batch-biz/pom.xml`、`nop-batch-dsl/pom.xml`、`nop-batch-exp/pom.xml` → nop-report-core（×3）
  - `nop-batch/nop-batch-dsl/pom.xml` → nop-task-core
  - `nop-dyn/nop-dyn-service/pom.xml` → nop-report-core
  - `nop-metadata/nop-metadata-service/pom.xml` → nop-wf-core、nop-wf-service（实现级依赖他组 service，最重）
  - `nop-rule/nop-rule-web/pom.xml` → nop-auth-service、nop-auth-web（web→外部 web，唯一 web 级耦合）
  - `nop-task/nop-task-ext/pom.xml` → nop-rule-core
  - `nop-wf/nop-wf-scheduler/pom.xml:26` → nop-job-local（closure audit 第二轮补入）
  - `nop-job/nop-job-retry-adapter/pom.xml:21` → nop-retry-engine（closure audit 第二轮补入）
  - 同模式扩展面（在上述 13 组口径之外，性质相同，一并列给 R1.0）：`nop-ai-coder`→nop-task-core/nop-report-core、`nop-ai-agent`→nop-task-core、`nop-ai-core`→nop-rule-core、`nop-ai-gateway`→nop-integration-feishu、`nop-code-service`→nop-graph-core/nop-ai-rag、`nop-datav-service`→nop-ai-toolkit、`nop-dyn-service`→nop-ai-dsl-orm
- **风险**: 单边升级/拆分被他组实现拖绊；契约面与实现面耦合使 I*Biz 替换/分层重构成本上升；rule-web→auth-web 在 web 层横向耦合放大前端契约漂移面。
- **建议**: R1.0 逐条裁定——收敛到目标组 `-dao`/`-api`（I*Biz 契约）依赖，或显式登记豁免理由（如 batch→report/task 为 DSL 内嵌编排的既定设计）。metadata→wf-service 与 rule-web→auth-web 为 closure audit 点名的 P1 再裁候选，优先复审。

### P2-1.1-003 【已撤回——closure audit 证伪】~~`INopBatch*Biz` 双模块重复定义~~

- **严重程度**: 不适用（初版判 P2，证伪撤回）
- **撤回理由**: 独立 closure audit（agent_2dfe253d）以 find/grep 实证：4 个 `INopBatch*Biz` 接口**仅定义于 nop-batch-dao**（`nop-batch/nop-batch-dao/src/main/java/io/nop/batch/biz/`），nop-batch-biz 全模块（含编译产物）零定义。初版「双模块重复定义/AMBIGUOUS=4」是 beans 扫描器按**包名**归属模块造成的假象——包 `io.nop.batch.biz` 确实横跨 batch-biz/batch-dao 两模块（biz 放常量/工具类、dao 放 codegen 的 I*Biz 契约），但接口定义唯一。同包跨模块是平台 codegen 标准布局（deep-audit 校准「I*Biz 接口放 dao 模块」的同族形态），不构成缺陷。
- **方法学登记**: 包名→模块归属映射对「同包跨模块」布局会产生 AMBIGUOUS 假象；后续复用 `_tmp/fcr-1.1-scan.py` 时，AMBIGUOUS 条目必须先做 FQCN 磁盘定位再判定（本仓已有先例记录，供 6.x 反模式扫描项参考）。
