## 二、三子模块深审节

### 2.1 nop-lint-js——适配面合格 + 两真实缺陷 + tsc 桥零装配状态注记

**A.1 语言适配表与 CLI 扩展（合格）**：

- `TypeScriptLanguage` / `TsxLanguage`（`nop-lint/nop-lint-js/src/main/java/io/nop/lint/js/TypeScriptLanguage.java:22-93`、`TsxLanguage.java:19-90`）：恒等 pattern 预处理（`$` 为合法 ECMAScript IdentifierPartChar，`$VAR`/`$$$ARGS` 天然 lex 为单标识符——javadoc 论证 + 双 grammar 端到端测试背书）；`SHARED` 静态 adapter 单例避免 ServiceLoader 重复构造重复解码 grammar blob；`suppressionProvider()` 保持契约缺省 null（v1 纯注释抑制路径），与 design 09 §3.1「缺省 null」一致。
- ServiceLoader 注册面：`META-INF/services/io.nop.lint.core.lang.LintLanguage` 双行注册 ✓；与 core `LanguageRegistry.discoverDefaults`（`engine/LanguageRegistry.java:45-53`）的消费链闭合；id 归一（trim+lowercase）与 `TargetScanner` 表一致。
- CLI 扩展核对：`TargetScanner` 显式表（`cli/TargetScanner.java:50-55`）`ts→typescript`、`tsx→tsx` 与 design 03 §2.4 item 19 增注逐字一致；`.mts`/`.cts` 显式不入表（javadoc 在档）；表外扩展名与未注册语言均进 skipped 分桶显式计数（`classify` :156-165），不会静默忽略，也不会因 `.ts` 文件在 nop-lint-js 缺席时炸 run（scan 期 `languageIds.contains` 判定 → skip，非 lint 期 abort——与 design「不静默」口径自洽）。
- **资源归属注意点（非缺陷）**：grammar blob 实际由 `nop-treesitter/src/main/resources/grammars/{typescript,tsx}/*.bin` 携带，nop-lint-js 自身 resources 只有 ServiceLoader 文件；`Language.fromClasspath("/grammars/...")` 跨模块共享 classpath 路径。运行时模块集 = nop-lint-js + nop-treesitter，pom 依赖经 nop-lint-core 传递获得（必要传递依赖不算问题）。

**A.2 JS 规则执行面（tsc 桥）——fail-visible 质量高，两真实缺陷**：

- 协议层 `TscProtocol`（`tsc/TscProtocol.java`）：newline-JSON 帧、ready 握手校验 typescript 绑定（:71-82）、`decode` 坏帧→BAD_FRAME 不吞（:41-47）、`isOk`/`intValue`/`errorOf`/`resultOf` 全部结构化失败——「Nothing on this level returns a silent null」成立。
- 进程层 `NodeTscBridge`（`tsc/NodeTscBridge.java`）：懒 spawn（`isAvailable` 无副作用探针 :79-81）、per-query deadline（:245-265）、有限重启（`handleProcessFailure` :267-275，预算 2）、终态 EXHAUSTED 永不无限重试、correlation id 校验（:167-172）、结构化 error frame 不杀进程（:175-177）。整体 fail-visible 质量高。
- L2 适配 `TscTypeResolver`（`tsc/TscTypeResolver.java`）：`TscQueryException`/`TscBridgeUnavailableException` → `TypeResolutionException` 的映射完整（引擎据此 degrade 规则，绝不伪造 L1 答案），与 design 06 §5.3 方案 A、design 11 §3 懒原则/§5 降级阶梯一致。
- **两处真实缺陷**：P2-4.6-002（resolver 重启后不重绑 project）与 P3-4.6-001（慢死旧进程迟到帧污染下一次握手）。
- **生产装配缺席（状态注记，P3-4.6-003）**：引擎 L2 通道存在（`LintEngine` 构造族 `typeResolver` 参数 + `l2Ready` gate + `TypeQuerySupport` 注入链），但全部生产装配点（`CheckRunner.java:196-198` 仅传 DeepResolvers；Mojo/GraphQL BizModel 用 2 参构造 typeResolver=null）均不注入 `TscTypeResolver`；全仓 `new TscTypeResolver` 仅测试（复核 grep 证实仅 7 处全在测试）。roadmap item 20 `done` 的消费面 = RuleTester L2 套件 + 引擎 gate，生产运行 type 规则恒 degrade。

**A.3 错误处理两档策略（维度 09）——字面合规，基类偏离一处**：

- 模块内部档：`NopLintJsException extends RuntimeException` + 全英文消息，无裸 RuntimeException throw（grep 证实，仅 catch RuntimeException 一处 :220），无中文消息，无 System.out/err。字面合规。
- **基类偏离**：core 同族 `NopLintException extends NopException`（javadoc 明写理由「keeping the free-form English message reachable through the framework's structured error response path」），同仓 `NopAiException`/`StreamException` 家族均挂平台异常链；`NopLintJsException` 直接 extends RuntimeException 脱离该链——P3-4.6-002。
- 测试面（维度 16 视角）：协议矩阵经 `FakeTscPeer` 全真进程测试（握手/坏帧/超时回收/崩溃重启/预算耗尽/tsconfig 失效，`NodeTscBridgeTest` 9 例 + `TscProtocolTest` + `TscTypeResolverTest` 6 例）；真实 Node+tsc e2e（`TestTscBridgeReal` 3 例，环境缺失显式 skip 非 silently green——roadmap item 20 环境契约兑现）。缺口：resolver 层「重启 × project 状态」交互零覆盖（P2-4.6-002 的伴生测试缺口），且 `FakeTscPeer` 不建模 NO_PROJECT 使该缺口在现替身下不可补（复核补强）。

#### P2-4.6-001〔原维度09-01〕checkFile 表外扩展名/无扩展名路径触发 NPE，击穿模块 message-mode 错误面契约

- **文件**: `nop-lint/nop-lint-graphql/src/main/java/io/nop/lint/graphql/NopLintBizModel.java:128-133`（触发点）、`:307-309`（NPE 点）
- **证据片段**:
  ```java
  String extension = dot < 0 ? TargetScanner.NO_EXTENSION
          : name.substring(dot + 1).toLowerCase(Locale.ROOT);
  String languageId = TargetScanner.languageIdForExtension(extension);
  List<CompiledRule> selected = rt.select(languageId, rules);   // languageId == null
  // Runtime.select:
  List<CompiledRule> forLanguage = compiledByLanguage.getOrDefault(languageId, List.of());
  ```
- **严重程度**: P2（复核**维持 P2 高位**）
- **现状**: `TargetScanner.languageIdForExtension` 对无扩展名文件（`NO_EXTENSION="(none)"`）与一切表外扩展名（`.mts`/`.cts`/`.json` 等）返回 null；`Runtime.select` 把 null 传给 `compiledByLanguage.getOrDefault(null, ...)`。`compiledByLanguage` 是 `Map.copyOf` 产物，JDK 不可变 Map 对 null key 探针抛 NPE（本机 JDK 21 实测：`Map.copyOf(...).getOrDefault(null, …)` → `java.lang.NullPointerException`，`get(null)` 同炸）。
- **风险**: 任何指向工作目录/VFS 内无扩展名或表外扩展名文件的合法 `Lint__checkFile` 请求（如 `LICENSE`、`Makefile`、`x.json`）都以裸 NPE 形式逃逸 `@BizQuery`，GraphQL 层呈现为内部错误而非设计规定的 message-mode `NopLintException`（design 03 §2.3(c)「错误面 = message-mode NopLintException」）——错误面契约被击穿，AI 消费者拿到不可诊断的 500 型错误。测试面（`TestNopLintBizModel`）覆盖了大写扩展名但未覆盖无扩展名/表外扩展名分支。
- **建议**: `select()` 入口对 null/未知 languageId 显式抛 `NopLintException`（提示扩展名无法绑定语言），或在 checkFile 将 null 语言短路为「零规则 + 显式说明」的空结果；补无扩展名与 `.mts` 两例测试。
- **信心水平**: 确定（JDK 行为已实测复现，并经复核跨 JDK 版本独立复现）
- **误报排除**: 不是「扫描器 skip 分桶」语义——CLI `TargetScanner.classify` 对表外扩展名走 skipped 分桶从不进 select；只有 GraphQL checkFile 这一条路径把 null 带进不可变 map 查询。也非既有 C7 修复（大小写归一）的回归——归一只解决表内大小写，不解决表外 null。
- **复核修正注记**: 复核**保留 P2 高位**，完整触发链逐环亲读证实：(1) `NopLintBizModel.checkFile`:128-132 扩展名归一后调 `TargetScanner.languageIdForExtension`；(2) `TargetScanner.java:50-56` `EXTENSION_TO_LANGUAGE_ID = Map.of("java","java","ts","typescript","tsx","tsx","xml","xml","xbiz","xml")` 表内仅 5 键，`languageIdForExtension`:73-74 查表 miss 返回 null（`NO_EXTENSION="(none)"`:43 同样 miss）；(3) `Runtime.select`:308 `getOrDefault` 而 `compiledByLanguage = Map.copyOf(compiled)`（:298）；(4) **JDK 行为独立复现**（复核本机 JDK 26.0.1）：`Map.copyOf(...).getOrDefault(null, …)` → NPE、`get(null)` → NPE——初审 JDK 21 实测结论**跨版本成立**。**与「任意文件读」既住裁定的关系（复核重点）**：两者正交且互不削弱——安全边界在 `readControlled`:196-205（首段含 `:` 先于任何解析拒绝），NPE 发生在**已受控读取完成之后**，不是安全回归、不是 namespace 修复的漏洞回开；既住裁定复核为准确（`nop-kernel/nop-core/src/main/java/io/nop/core/resource/store/FileNamespaceHandler.java` buildFileResource(vPath, true) 仅在 `CFG_RESOURCE_ALLOWED_FILE_PATH_PATTERN` 非空时限制，:52-59，默认空 → 任意绝对路径放行；初审路径省略 `store/` 段，本终稿勘正）。测试缺口证实：`TestNopLintBizModel` 16 例含大写扩展名（:198 `checkFileResolvesUppercaseExtension`）但 grep 证实无无扩展名/`.mts`/`.json` 用例（测试例数初审记 13、复核实读 16，以复核为准）。**判级边界注记（不改变裁定）**：触发面为 P2×4 中最宽（无扩展名/表外扩展名的任意合法请求），可争议 P1；但 fail-loud（裸 NPE）而非 fail-wrong、无数据暴露、有 checkSource 旁路、无高概率回归、无跨模块边界错误，「错误面契约」是模块级而非平台核心契约 → 维持 P2，**建议 R1.0 排期最优先**。

#### P2-4.6-002〔原维度09-02〕TscTypeResolver 桥重启后不重绑 project：进程恢复但程序绑定永久丢失，重启预算形同虚设

- **文件**: `nop-lint/nop-lint-js/src/main/java/io/nop/lint/js/tsc/TscTypeResolver.java:107-118`、`tsc/NodeTscBridge.java:267-275`
- **证据片段**:
  ```java
  private NodeTscBridge bridge() {
      synchronized (lock) {
          if (bridge == null) { bridge = new NodeTscBridge(config); }
          if (!projectInitialized && defaultTsConfigPath != null) {
              bridge.initProject(defaultTsConfigPath);
              projectInitialized = true;          // 单向闸，永不复位
          }
          return bridge;
      }
  }
  // NodeTscBridge.handleProcessFailure: 崩溃/超时后 state=NEW，下次请求 spawn 新进程
  ```
- **严重程度**: P2（复核**维持 P2**）
- **现状**: 桥崩溃/超时后 `handleProcessFailure` 置 state=NEW 并在下一次请求时 spawn 全新 Node 进程（peer 端 `projects` program cache 为空）；但 `TscTypeResolver.projectInitialized` 已为 true，`bridge()` 永不再发 `initProject`——此后每次 type 查询都命中 peer 的 `NO_PROJECT` 结构化错误 → `TypeResolutionException` → 引擎把 type 规则降级。
- **风险**: 一次崩溃后，尽管桥 `isAvailable()` 仍为 true（state=NEW 可复活）且重启预算未耗尽，所有 L2 type 规则对该 resolver 生命周期内永久静默降级（仅 LOG.warn 计数）——「bounded restart 恢复服务」的机制承诺被 resolver 层单向闸抵消；对长时间驻留消费方（LSP/常驻服务）是从偶发降级退化为持续降级。
- **建议**: `NodeTscBridge` 以代际计数暴露「进程已更换」事实，resolver 在每代首查前重发 `initProject`；或 resolver 捕获 `NO_PROJECT` 错误码时复位 `projectInitialized` 重试一次（带上限）。
- **信心水平**: 确定（状态机推演逐行核对；`NodeTscBridgeTest` 的 restart 用例止步于 bridge 层，resolver 层零覆盖，见维度 16 伴生缺口）
- **误报排除**: 不是降级阶梯的正常行为——design 11 §5 的 EXHAUSTED 永久降级以「重启预算耗尽」为前提；本缺陷在预算未耗尽、桥已恢复 READY 的状态下使降级提前固化。

#### P2-4.6-003〔原维度02-01〕CheckMojo 声明 threadSafe=true，但生命周期依赖 JVM 级 CoreInitialization 全局 init/destroy 对——并行 reactor 下存在跨模块竞态

- **文件**: `nop-lint/nop-lint-maven-plugin/src/main/java/io/nop/lint/maven/CheckMojo.java:58`（`threadSafe = true`）、`:160-166` + `:189-192`（init/destroy 对）；`nop-kernel/nop-core/src/main/java/io/nop/core/initialize/CoreInitialization.java:54-56`（非原子 `isInitialized`）、`:158-206`（`destroy` 清 `initializers`/`initialized=false`/`GlobalCacheRegistry.clearAllCache()`）
- **证据片段**:
  ```java
  @Mojo(name = "check", defaultPhase = LifecyclePhase.VALIDATE, threadSafe = true)
  ...
  if (!CoreInitialization.isInitialized()) {          // 检查在 CoreInitialization 锁外
      CoreInitialization.initializeTo(REGISTER_COMPONENT);
      selfInitialized = true;
  }
  ... CheckRunner 管线 ...                             // 运行在锁外
  finally { if (selfInitialized) CoreInitialization.destroy(); }
  ```
- **严重程度**: P2（复核**维持 P2**，附触发面校准注记）
- **现状**: `threadSafe=true` 向 Maven 声明该 Mojo 可在 `-T` 并行 reactor 中并发执行；但 `CoreInitialization` 是类加载器级全局静态状态。交错：模块 A init（selfInitialized=true）→ 模块 B `isInitialized()` 读到 true → B 跳过 init（selfInitialized=false）→ A 管线完成 → A `destroy()`（initialized=false、initializers=null、全局缓存清空）→ B 继续在已拆除平台上跑 CheckRunner（规则加载经 VirtualFileSystem/全局缓存）。`initializeTo`/`destroy` 各自 synchronized 但「检查-使用-销毁」序列不在同一临界区。
- **风险**: `-T 1C` 等并行构建中间歇性失败（规则加载错/注册表空），且属 heisenbug；声明与实现不符还可能让后续使用者据此放心并发。单模块 `-pl` 与串行构建不触发，故非 P1。
- **建议**: 方案一：Mojo 不复用全局 skip/destroy 对——每次 execute 自持引用计数或按模块全量 init+destroy（接受成本）；方案二：`threadSafe=false` 让 Maven 串行化（与全局生命周期语义匹配，代价是放弃并行）；方案三：CoreInitialization 提供 acquire/release 配对 API。任一方案需同步修订 design 03 §2.1(f) 增注。
