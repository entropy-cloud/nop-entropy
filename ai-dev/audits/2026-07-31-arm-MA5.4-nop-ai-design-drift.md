## Findings

### P1 — High Regression Probability / Core Contract Drift

#### Finding P1-1: Bidirectional dialect conversion only implemented for OpenAI — gateway breaks on non-default config

- **Doc**: `ai-dev/design/nop-ai-gateway/01-architecture.md` §三 (lines 36-48)
- **Claim**: All four dialects (OpenAI, Anthropic, Gemini, Ollama) provide bidirectional conversion methods: `buildBody`→`parseRequestBody` (request), `parseResponse`→`buildResponse` (response), `parseStreamChunk`→`buildStreamChunk` (stream). The gateway `AiDialectBackendMessageConverter` relies on this symmetry to convert between arbitrary frontend/backend formats.
- **Code**: Only `OpenAiDialect` overrides `parseRequestBody()` (`nop-ai-core/dialect/OpenAiDialect.java:58`). `AnthropicDialect`, `GeminiDialect`, and `OllamaDialect` all fall through to the `ILlmDialect` default which throws `UnsupportedOperationException("parseRequestBody")` (`ILlmDialect.java:189-190`). The default `buildResponse`/`buildStreamChunk` produces OpenAI format — if `frontendLlm` is anything other than `openai`, the gateway throws at runtime.
- **Severity**: P1 — Core contract drift. The entire point of the gateway design (bidirectional conversion between arbitrary provider formats) is non-functional for 3 of 4 dialects. Default config (openai↔openai) works but any deviation breaks at runtime.
- **Remediation**: Implement `parseRequestBody` on `AnthropicDialect`, `GeminiDialect`, `OllamaDialect`, or document that only OpenAI→Provider (one-way) is currently supported and update the design doc accordingly.

### P2 — Real Maintenance Cost / Local Defect

#### Finding P2-1: DashScope (aliyun/Qwen) dialect advertised as known Provider but does not exist

- **Doc**: `ai-dev/design/nop-ai-agent/nop-ai-agent-llm-layer.md` §4.3 (line 141: "Provider | DashScope (阿里) | OpenAI 兼容 + Qwen 特有参数 | nop-ai-core ILlmDialect")
- **Claim**: DashScope (阿里云 Qwen) is a known Provider adapter implemented in `nop-ai-core` alongside OpenAI, Anthropic, Gemini, Ollama.
- **Code**: No `DashScopeDialect` or any aliyun/qwen-related class exists anywhere in `nop-ai-core/src/main/java/` or `nop-ai-core/src/main/resources/`. Grep for `DashScope`, `dashscope`, `aliyun`, `tongyi` returns zero results.
- **Severity**: P2 — Real maintenance cost. The design lists this as an implemented provider, misleading implementors. Adding DashScope later will require creating a new dialect class, SPI registration, and testing — this is at least half a day of work that the design implies is already done.
- **Remediation**: Either implement the DashScope dialect, or remove it from the design doc's Known Provider table and add a note that it is a future addition.

#### Finding P2-2: 4 pre-built content guardrails described in design — zero implemented

- **Doc**: `ai-dev/design/nop-ai-agent/nop-ai-agent-security-and-permissions.md` §5.2 (lines 404-411: "预构建 Guardrail (Layer 2 默认提供，可选启用)" lists `PromptInjectionGuardrail`, `UntrustedEnvelopeGuardrail`, `PIIDetectionGuardrail`, `ContentLengthGuardrail`)
- **Claim**: Four pre-built guardrails shipped as optional defaults in Layer 2, each with specific detection targets and execution modes (`off`/`report`/`enforce`).
- **Code**: Only `IContentGuardrail` interface (`nop-ai-agent/guardrail/IContentGuardrail.java`) and `NoOpContentGuardrail` exist. Grep for `PromptInjectionGuardrail`, `UntrustedEnvelopeGuardrail`, `PIIDetectionGuardrail`, `ContentLengthGuardrail` returns zero matches across all `nop-ai` source code. The engine (DefaultAgentEngine, ReActAgentExecutor) wires `IContentGuardrail` but defaults to NoOp — no shipped guardrail implementation is ever active.
- **Severity**: P2 — Real security gap. The design describes guardrails as "pre-built and optionally enabled", but the code has no actual guardrail logic (`NoOpContentGuardrail` passes everything). A deployer trusting the design's "Layer 2 pre-built guardrail" claim would have a false sense of content safety.
- **Remediation**: Implement at least `PromptInjectionGuardrail` (highest value), or update the design to mark all 4 guardrails as `successor`/`unimplemented` rather than "pre-built".

#### Finding P2-3: ISensitivePathProvider (Layer 4) referenced in design but absent from code

- **Doc**: `ai-dev/design/nop-ai-agent/nop-ai-agent-security-and-permissions.md` §4.3 (line 141: "敏感路径 denylist 可通过 XDSL 外部配置（未来，`ISensitivePathProvider` L4）")
- **Claim**: `ISensitivePathProvider` is a Layer 4 interface for external configuration of sensitive path denylists.
- **Code**: No `ISensitivePathProvider` or `SensitivePathProvider` class exists anywhere in `nop-ai-agent/src/main/java/`. The sensitive path patterns are hardcoded in `DefaultPathAccessChecker.SENSITIVE_PREFIX_PATTERNS` and `SENSITIVE_FILENAMES`. A deployer wanting to customize these must edit source code (no DSL/Delta mechanism).
- **Severity**: P2 — Real maintenance cost. The design promotes "XDSL 外部配置" as an explicit design goal (§2 design principle "渐进式增强"), but sensitive paths are hardcoded in Java. Adding new sensitive paths requires Java source changes and recompilation.
- **Remediation**: Implement `ISensitivePathProvider` or at minimum add a configurable path list via `nop-ai-core-config.xlsx` / `nop-ai.beans.xml`.

#### Finding P2-4: Pipeline execution only supports SimpleCommand — rejects all complex expressions

- **Doc**: `ai-dev/design/nop-ai-agent/04-tool-invocation.md` §四 — design describes pipeline as general command composition where all command types participate equally.
- **Doc**: `ai-dev/design/nop-ai-shell/03-executor-and-async.md` §2.5 — design shows `PipelineExpr` executing arbitrary `CommandExpression` nodes, including complex commands.
- **Code**: `ShellCommandExecutor.executePipeline()` (line 215-216): `if (!(cmdExpr instanceof SimpleCommand)) { return FutureHelper.success(new ExecutionResult(1, "", "Pipeline does not support complex commands yet")); }`. Pipelines containing logical expressions (`cmd1 && cmd2 | cmd3`), group expressions, or subshells are rejected at runtime.
- **Severity**: P2 — Real limitation that contradicts design. Any multi-stage pipeline with non-trivial AST nodes silently produces exit code 1 rather than executing.
- **Remediation**: Either implement support for complex command AST nodes in pipeline, or document this limitation explicitly (including the exit code 1 behavior) in `04-tool-invocation.md`.

#### Finding P2-5: `IApprovalChannel` referenced in design but absent from code

- **Doc**: `ai-dev/design/nop-ai-agent/nop-ai-agent-security-and-permissions.md` §6.1 (lines 483-487: "通道抽象为可插拔接口（`IApprovalChannel`）为后续功能化审批流增强")
- **Claim**: `IApprovalChannel` is an extensibility interface for approval delivery (Web UI, GraphQL Subscription, RPC polling).
- **Code**: No `IApprovalChannel` or `ApprovalChannel` class exists anywhere in `nop-ai-agent/src/main/java/`. There is no extensibility point for approval channels — `DefaultApprovalGate` and `AutoApproveGate` handle approval decisions synchronously in-memory with no abstraction for external notification.
- **Severity**: P2 — The design's "future functional approval flow" has no code foundation. Any implementor wanting to add human-in-the-loop approval must build both the gate logic and channel abstraction from scratch.
- **Remediation**: Either create the `IApprovalChannel` interface as a placeholder (even without implementations), or explicitly mark it as deferred in the design doc.

### P3 — Low Priority

#### Finding P3-1: IShellInput convenience methods defined in design but not on interface

- **Doc**: `ai-dev/design/nop-ai-shell/02-io-and-pipeline.md` §3.3 (lines 114-130: `IShellInput` specified with `readLine()`, `readAllText()`, `chunks()`, `lines()`)
- **Claim**: `IShellInput` interface provides 4 convenience methods alongside the core `read()` method.
- **Code**: `IShellInput.java` only has `read()`, `close()`, `isClosed()`. The convenience methods (`readLine()`, `readAllText()`, `lines()`, `chunks()`) live in `AbstractShellInput` instead. They are accessible but not part of the interface contract — any custom `IShellInput` implementation that doesn't extend `AbstractShellInput` won't inherit them.
- **Severity**: P3 — Low priority. The methods exist and work for the shipped implementations. But the design says they're part of the interface contract, which could mislead someone implementing `IShellInput` directly.
- **Remediation**: Either add the methods as `default` on `IShellInput` (delegating to `AbstractShellInput`'s implementations), or update the design doc to match.

#### Finding P3-2: IAiMemoryStore.readBudgeted() throws UnsupportedOperationException

- **Doc**: `ai-dev/design/nop-ai-agent/01-architecture-baseline.md` §四 memory table (line 76: "system-prompt 自动注入 ✅（plan 192）：`DefaultAgentEngine.buildBaseExecutionContext`（doExecute + resumeSession 共用）在每轮执行启动时经 `readBudgeted(budget)` 将非空 budgeted memory 追加到 system prompt 尾部")
- **Claim**: `readBudgeted` is a delivered capability used by the engine for budget-limited memory injection into system prompts.
- **Code**: `IAiMemoryStore.readBudgeted()` (line 15-17) throws `UnsupportedOperationException("readBudgeted requires Phase 2")`. The `InMemoryAiMemoryStore` extends `IAiMemoryStore` but does NOT override `readBudgeted()` — so any code calling it on `InMemoryAiMemoryStore` will also get UoE.
- **Severity**: P3 — The design claims this is "delivered ✅" but the default implementation throws. The engine may only call this through the `IAiMemoryStore` interface where custom implementations override it. But the shipped `InMemoryAiMemoryStore` does not, making this a documentation gap.
- **Remediation**: Implement `readBudgeted()` on `InMemoryAiMemoryStore`, or update the document to mark it as "Phase 2" rather than "delivered".

#### Finding P3-3: IShellInput.readAllText() only returns chunk text — may lose binary data

- **Doc**: `ai-dev/design/nop-ai-shell/02-io-and-pipeline.md` §3.3 (line 120: `readAllText()` reads all text)
- **Claim**: `readAllText()` reads all available text content.
- **Code**: `AbstractShellInput.readAllText()` (line 50) reads `ShellChunk` instances and concatenates text from `TextChunk` instances only, skipping `BinaryChunk` silently. The design acknowledges binary chunks exist (the `BinaryChunk` class exists) but `readAllText()` silently discards them without warning.
- **Severity**: P3 — Binary data in shell pipeline is currently unused (all built-in commands use text), but the silent data loss is a correctness trap for future binary command implementations.
- **Remediation**: Document the limitation or add a warning log when `BinaryChunk` is skipped.

### Design-Code Consistency Assessment

**Verdict**: **FAIL** (1 P1 + 5 P2 findings)

### Key Regression Risks
1. **Gateway deployment with non-OpenAI dialect fails at runtime** (P1-1) — the most actionable finding. Any production use of `nop-ai-gateway` with `frontendLlm=anthropic` or `backendLlm=gemini` crashes with `UnsupportedOperationException`.
2. **Content safety is not enforced** (P2-2) — despite the design's 4 pre-built guardrail descriptions, only `NoOpContentGuardrail` is wired. The "PROMPT" contribution type injects arbitrary text into system prompts with zero injection detection.
3. **Sensitive path management is hardcoded** (P2-3) — violating the design's own "渐进式增强" principle. No XDSL/Delta mechanism for customizing path denylists.

### Owner Boundary Observations
- The `nop-ai-gateway` design doc (`01-architecture.md`) is accurate about the module structure and data flow — the issue is that dialect implementations don't fulfill the contract, not that the design is wrong.
- The `nop-ai-shell` design docs are largely well-implemented — the `ShellChunk` model, `BlockingQueueShellOutput` pipeline, `CompletableFuture.supplyAsync` concurrency model, and `ICommandChecker` pre-check all match live code.
- `nop-ai-agent` security design is the most drifted area — it describes a comprehensive 4-layer security architecture with guardrails, approval channels, and sensitive path providers, but most of Layer 2-4 exists only as NoOp defaults with no shipped implementation.
