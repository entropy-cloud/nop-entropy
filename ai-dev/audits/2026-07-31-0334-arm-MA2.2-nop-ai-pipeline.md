## Findings

### P2-MA2-012: NopAiRequirement has string-typed version with `versionProp`

| Attribute | Value |
|-----------|-------|
| **File** | `nop-ai/model/nop-ai.orm.xml` lines 342–417 |
| **Severity** | P2 (Minor — compiles, but semantic concern) |
| **Evidence** | Line 344: `versionProp="version"` on entity element. Line 357–358: `version` column has `stdDataType="string"` and `stdSqlType="VARCHAR"` (NOT using the `domain="version"` domain which maps to INTEGER). |
| **Current State** | The `NopAiRequirement` entity defines `versionProp="version"` to track business version (e.g., "1.0.0", "2.1.0") as a string. The generated `_NopAiRequirement.java` compiles correctly with `String getVersion()`. No conflict with parent `DynamicOrmEntity` because it doesn't define `getVersion()`. |
| **Risk** | Other entities (NopAiSession, NopAiProject, etc.) use `domain="version"` (INTEGER) for `versionProp`. The Nop ORM framework may expect integer version for optimistic locking. A string-typed version with `versionProp` is non-standard: (1) The ORM cannot auto-increment a string version for optimistic lock; (2) `DynamicOrmEntity` property serialization may behave unexpectedly; (3) If the framework assumes `versionProp` implies `stdDataType="int"`, ORM flush could fail. |
| **Recommendation** | Either (a) rename the column to `req_version` and remove `versionProp` (use a separate business version field), or (b) add an integer `version` column with `domain="version"` for ORM locking alongside the string version field. If the string version is the canonical version for business purposes, `versionProp` should not be set on it — remove `versionProp="version"` from the entity definition. |

### P2-MA2-013: `_service.beans.xml` uses incorrect BizModel package path

| Attribute | Value |
|-----------|-------|
| **File** | `nop-ai-service/src/main/resources/_vfs/nop/ai/beans/_service.beans.xml` lines 8–159 |
| **Severity** | P2 (Minor — works at runtime but inconsistent) |
| **Evidence** | All 21 BizModel bean IDs follow pattern `io.nop.ai.service.entity.NopAiXxxBizModel` (e.g., line 8: `io.nop.ai.service.entity.NopAiProjectBizModel`). However, the actual BizModel classes do not exist in `nop-ai-service/src/main/java/io/nop/ai/service/entity/` — they exist in `nop-ai-dao/src/main/java/io/nop/ai/dao/entity/_gen/`. The `@BizModel` annotation is on the retention entity class in `nop-ai-dao/entity/`. The `_service.beans.xml` ID format `io.nop.ai.service.entity.NopAiXxxBizModel` appears to be the expected pattern for the generated BizModel wrapper, but no such classes exist. |
| **Risk** | At runtime, the `BizModel` registration via `@BizModel` on entity classes (e.g., `NopAiSession.java` line 7: `@BizObjName("NopAiSession")`) combined with `BizProxyFactoryBean` in `_service.beans.xml` creates the actual service beans. The BizModel bean IDs in `_service.beans.xml` are references to auto-generated classes that don't explicitly exist — they are created by the graphQL engine from entity annotations. If the Nop framework changes the discovery mechanism, these stale bean definitions could cause injection failures. |
| **Recommendation** | Either (a) remove the `BizModel` bean entries from `_service.beans.xml` if they are auto-discovered from `@BizObjName` annotations, or (b) ensure the `io.nop.ai.service.entity.NopAiXxxBizModel` classes are actually generated. Verify the intended service layering: if BizModels are discovered from entity annotations, the bean entries in `_service.beans.xml` may be vestigial. |

### P1-MA2-014: XDSL codegen output not verifiable for agent/toolkit tracks

| Attribute | Value |
|-----------|-------|
| **File** | `nop-ai-agent/precompile/gen-agent-xdsl.xgen` (lines 1–4), `nop-ai-toolkit/precompile/gen-toolkit-xdsl.xgen` (lines 1–7), `nop-ai-core/precompile/gen-ai-xdsl.xgen` (lines 1–5) |
| **Severity** | P1 (Major — codegen scripts exist but output unreachable) |
| **Evidence** | Three XDSL codegen scripts exist, each calling `codeGenerator.renderModel(schema, '/nop/templates/xdsl', '/', $scope)`. For agent: references `/nop/schema/ai/agent-plan.xdef` and `/nop/schema/ai/agent.xdef`. For toolkit: references `/nop/schema/ai/tool/tool-call.xdef`, `/nop/schema/ai/tool/tool.xdef`, `/nop/schema/ai/tool/call-tools.xdef`, `/nop/schema/ai/tool/call-tools-response.xdef`, `/nop/schema/ai/tool/available-skills.xdef`. For core: references `/nop/schema/ai/prompt.xdef`, `/nop/schema/ai/chat-options.xdef`, `/nop/schema/ai/llm.xdef`. **No generated `.xdef` or model files were found in these modules' `src/main/resources/_vfs/` directories.** The nop-ai-core module has hand-written `*.llm.xml` configs and `*.md` prompt files, but no files from the XDSL codegen. The nop-ai-agent and nop-ai-toolkit modules have hand-written `*.tool.xml` files but no codegen outputs. |
| **Risk** | (1) If the XDSL codegen is meant to produce default model instances from schema, those are missing — users must write them manually. (2) If the codegen runs during build (`precompile` phase via exec-maven-plugin), the outputs may be generated into `target/` or the project root but not committed to source. This makes the codegen results non-reproducible from source. (3) The `gen-ai-xdsl.xgen` and `gen-toolkit-xdsl.xgen` may be stale/unused, and the actual model configs are hand-maintained. |
| **Recommendation** | (a) Run the XDSL codegen scripts and commit the generated outputs to `src/main/resources/_vfs/` following the pattern used by ORM codegen. (b) If the codegen is obsolete, remove the `precompile/` scripts to avoid confusion. (c) Add a comment to each `.xgen` file explaining where its output goes and whether it's still active. |

### P2-MA2-015: `nop-ai-api/pom.xml` sets `java.version=11` instead of 21

| Attribute | Value |
|-----------|-------|
| **File** | `nop-ai-api/pom.xml` line 17 |
| **Severity** | P2 (Minor — consistent with standalone consumption, but inconsistent with project) |
| **Evidence** | Line 17: `<java.version>11</java.version>`. The parent project `nop-ai` inherits from `nop-entropy` which targets Java 21. No other nop-ai submodule overrides the Java version. |
| **Risk** | The `nop-ai-api` module is compiled for Java 11 bytecode, while the rest of the project uses Java 21. This is likely intentional (the API module is a lightweight published artifact for consumers who may be on older JDKs). However, if any API code uses Java 17+ features (records, sealed classes, text blocks, etc.), compilation will fail. Currently the API code uses only simple Java 8-11 syntax (interfaces, beans), so this is low risk. |
| **Recommendation** | Add a comment in `pom.xml` explaining why Java 11 is used (e.g., "Published API artifact — compiled for maximum compatibility"). Alternatively, remove the override to align with Java 21 if API consumers are guaranteed to be on JDK 21+. |

### P3-MA2-016: `gen-orm.xgen` uses relative filesystem path for second renderModel source

| Attribute | Value |
|-----------|-------|
| **File** | `nop-ai-codegen/postcompile/gen-orm.xgen` lines 5–6 |
| **Severity** | P3 (Minor — fragile path but currently correct) |
| **Evidence** | Line 5: `codeGenerator.withTargetDir("../nop-ai-dao/src/main/java").renderModel('../../nop-ai-dao/src/main/resources/_vfs/nop/ai/orm/app.orm.xml', '/nop/templates/orm-entity', '/', $scope)`. The first call (line 4) correctly uses a VFS-unavailable filesystem path to the source model. The second call uses an even deeper relative path to reach the generated `app.orm.xml`. |
| **Risk** | If the directory structure changes (e.g., module relocation, renaming), this relative path breaks silently. The Nop platform convention is to use VFS paths for model references (e.g., `/nop/ai/orm/app.orm.xml`). |
| **Recommendation** | Change the second renderModel source to use a VFS path: `renderModel('/nop/ai/orm/app.orm.xml', '/nop/templates/orm-entity', '/', $scope)`. The VFS resolves to the same file at runtime because `app.orm.xml` is on the classpath under `_vfs/nop/ai/orm/`. |

### P3-MA2-017: NopAiSessionContext uses `versionProp="revision"` — unconventional naming

| Attribute | Value |
|-----------|-------|
| **File** | `nop-ai/model/nop-ai.orm.xml` line 1231 |
| **Severity** | P3 (Cosmetic — intentional design but noteworthy) |
| **Evidence** | Line 1231: `versionProp="revision"`. The ORM model's `domains` section defines `version` domain as INTEGER. The actual column is named `revision` (line 1252) and uses `domain="version"` (INTEGER). This is the only entity that uses a non-`version` version property name. |
| **Risk** | None functional — the Nop ORM uses the value of `versionProp` as the column name, so `revision` is valid. However, it violates the principle of least surprise: developers expect `getVersion()`/`setVersion()` on entities. Instead, this entity has `getRevision()`/`setRevision()`. |
| **Recommendation** | Document the rationale for using `revision` instead of `version` in a comment (e.g., "Context snapshot version — semantically different from ORM optimistic lock version; named 'revision' to align with document versioning convention"). |

## Conclusions

The nop-ai generation pipeline is **substantially complete and well-structured**. All 6 ORM-based codegen tracks produce the expected artifacts for all 21 entities. Key strengths:

- **Full entity coverage**: Every entity has DAO, xmeta, page, i18n, service bean, and CRUD API artifacts
- **Consistent naming**: Entity names, biz names, and file names follow Nop conventions
- **Correct build order**: Module dependencies respect the generation pipeline sequence
- **Retention files present**: All `_gen/` files have corresponding retention files (`.java`, `.xmeta`, `.view.xml`, `.i18n.yaml`)

The three highest-priority issues are:

1. **P1-MA2-014**: XDSL codegen scripts for agent/toolkit/core are present but their output is uncommitted — unclear whether they are active or stale.
2. **P2-MA2-012**: `NopAiRequirement.version` string/versionProp mismatch could cause ORM issues if optimistic locking is triggered.
3. **P2-MA2-013**: Stale BizModel bean definitions in `_service.beans.xml` may cause confusion.

**Next audit recommendation**: Re-run after fixing P1-MA2-014 and P2-MA2-012 to verify the pipeline in a clean state.
