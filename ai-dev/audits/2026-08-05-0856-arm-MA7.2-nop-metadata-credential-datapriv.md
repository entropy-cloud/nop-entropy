### [MA7.2-01] AR-02 主机白名单可被 URL userinfo 旁路：extractHost 把用户名当 host（SSRF 回归缺口）（P1）

- **文件**: `connection/MetaDataSourceConnectionProcessor.java:269-286`（extractHost）；对照 `quality/CheckpointActionDispatcher.java:277-285`（extractWebhookHost 正确处理 userinfo）
- **证据片段**:
  ```java
  // MetaDataSourceConnectionProcessor.java:277-285 —— userinfo 未剥离
  String rest = jdbcUrl.substring(schemeEnd + 3);      // "user:pass@host:3306/db"
  String hostPort = end > 0 ? rest.substring(0, end) : rest;
  int colon = hostPort.indexOf(':');
  String host = colon > 0 ? hostPort.substring(0, colon) : hostPort;  // = "user" !!
  ```
- **严重程度**: P1
- **现状**: `validateJdbcUrl`（:220-254）对 `jdbc:mysql://user:pass@169.254.169.254:3306/db`：协议白名单通过 → 危险 token 无命中 → `extractHost` 返回 `"user"` → `isInternalHost("user")=false` → **放行**；而 MySQL/PostgreSQL 驱动文档均支持 userinfo 形式 URL，驱动实际连接目标是内网主机。IPv6 字面量同缺陷（`jdbc:mysql://[::1]:3306/db` → host=`"["`，loopback 校验失效）。对照 `redactJdbcUrl` 的 `CREDENTIAL_PATTERN`（:89-90）证明代码已意识到 userinfo 形式存在；webhook 侧 extractWebhookHost 明确剥离 userinfo——同 bug 类在 webhook 侧已修复，JDBC 侧遗漏。测试 `TestMetaDataSourceConnectionSecurity.java:111-147` 仅覆盖无 userinfo 的 URL。
- **风险**: AR-02 三项加固中"内网禁连"层被绕过：任何可建/测数据源的用户（action-auth 默认关）可对 169.254.169.254（云元数据）、10.x/192.168.x/172.16-31.x、localhost 发起 MySQL/PostgreSQL TCP 连接（内网扫描/内部库读取/时序侧信道）。"AR-02 已验证"的结论需在 host 元素上打补丁复核。
- **建议**: extractHost 在取 hostPort 前剥离 `...@`（与 webhook 实现对齐）；处理 IPv6 `[::1]`/`::ffff:` 段；补 userinfo/IPv6 回归测试。
- **信心水平**: 确定（代码逻辑实证；驱动对 userinfo 的接受基于 Connector/J/PostgreSQL 文档）
- **修复归属**: **MR3（新发现）**

### [MA7.2-06] redactJdbcUrl 覆盖缺口：仅剥 userinfo，URL query 内凭据（`?password=`/`?user=`）穿透"脱敏"参数（P3）

- **文件**: `MetaDataSourceConnectionProcessor.java:88-90,264-267`
- **证据片段**:
  ```java
  private static final Pattern CREDENTIAL_PATTERN = Pattern.compile("(://)([^:@/]+)(?::[^@/]*)?@");
  public static String redactJdbcUrl(String jdbcUrl) { return CREDENTIAL_PATTERN.matcher(jdbcUrl).replaceAll("$1"); }
  ```
- **严重程度**: P3
- **现状**: MySQL Connector/J 与 PostgreSQL 驱动支持 `?user=`/`?password=` URL 参数；`jdbc:mysql://host:3306/db?user=admin&password=s3cret` 经 redactJdbcUrl 后原样保留 → 错误消息"脱敏"参数里仍含明文密码（与 MA7.2-01 同源的 userinfo/query 处理盲区）。
- **建议**: redact 增加 query 参数 `(user|password|token|access_token|secret)=[^&]+` 替换为 `$1=***`；补单测。
- **信心水平**: 确定（正则行为实证；驱动参数支持基于文档）
- **修复归属**: MR3（新发现）

## withConnection 旁路面边界结论

- **裸 JDBC 旁路 = by design**（外部数据源不注册 ORM querySpace，行级 data-auth 对裸 JDBC 无适用对象）。访问门禁链 = requireEntity（含 checkDataAuth 行级检查）→ DISABLED 显式拒绝 → AR-02 URL/driver/超时加固 → 方言白名单（MySQL/PostgreSQL/H2）。
- **入口点枚举（14 处 withConnection，9 类）**: testConnection/syncExternalTables/collectCatalog、queryExternalData/querySqlData、executeQualityRulesForDataSource、MetaJoinExecutor（同库 JOIN + 跨库 fetchTableRows）、3 个外部聚合 Processor、TableReferenceExecutor（collectCatalogForTable/profileTable/单表质量规则）、SqlViewFieldTypeInferrer。全部为 external/sql 形态。
- **认证开关默认态（重确认）**: ApiConfigs.java:87-92 双开关默认 false；biz-defaults.beans.xml 注入默认 false；app/application.yaml 无覆盖 → 默认双关。
- **gap 点（MA7.2-02）**: 平台 SQL 级 data-auth 全平台零调用点（休眠）；entity 路径自定义查询跳过 CrudBizModel 的 appendFilter/checkDataAuthForList——行级 data-auth 若开启，标准 CRUD 表面受控而 metadata 自定义查询表面全裸。此为"ORM 行级 data-auth 本应适用却被跳过"的唯一边界点。

MA6.4 三项 P3 深挖结论全部为"维持 P3"，凭据脱敏主链路（storage→read→log→error 四环节）除错误路径回显外无新增绕过点，事件快照 REDACTED 链与 anti-hollow 测试复核在位。**但 AR-02 的"已修复且已验证"结论需修正**：主机白名单元素存在 userinfo/IPv6 解析旁路（MA7.2-01，P1），修复成本低（extractHost 剥离 `...@` + 处理 `[::1]` + 补测试），性质上是 SSRF 防护实质性缺口，应优先于 MR3 其余条目。withConnection 数据权限旁路基础结论（by design + 门禁链 + 双开关默认 false）复核成立，但边界比 MA3.3 描述更宽：entity 路径自定义查询同样跳过行级 data-auth（MA7.2-02），需与 MA3.3-01/02 同批部署收紧时一并处理。无 P0，默认配置下无直接可利用的越权读路径。
