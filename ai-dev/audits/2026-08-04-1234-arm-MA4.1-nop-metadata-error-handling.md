## 发现清单

### [P2-MA4-001] NopMetaTagLabelBizModel.getWfNameFromMeta catch-all 静默吞异常（09-02/03/06 家族 live 复核，维持 open → MR2）

- **文件**: `nop-metadata/nop-metadata-service/src/main/java/io/nop/metadata/service/entity/NopMetaTagLabelBizModel.java:106-112`
- **证据片段**:
  ```java
  private String getWfNameFromMeta() {
      try {
          Object val = bizObjectManager().getBizObject("NopMetaTagLabel")
                  .getObjMeta().getProp("wf:wfName");
          return val instanceof String ? (String) val : null;
      } catch (Exception e) {
          return null;
      }
  }
  ```
- **严重程度**: P2
- **现状**: `catch (Exception e)` 捕获**所有**异常后静默返回 null，无 LOG、无 rethrow。调用点 :87 `getWfNameFromMeta()` 拿到的 null 被当作"无工作流"处理，真实失败（meta 加载异常、bizObjectManager 异常）与"确实没有配置 wfName"无法区分。
- **风险**: 标签标注的 submitForApproval 路径在元数据层故障时静默降级为"不提交审批"，运维无凭据；违反 error-handling.md「丢弃异常前必须留证」硬约束（catch 位置既非系统边界也非 per-element 故障隔离）。
- **建议**: catch 后 `LOG.warn("getWfNameFromMeta failed for TagLabel ...", e)` 再返回 null（throwable 作末参数）。
- **信心水平**: 确定
- **误报排除**: 非误报——同文件 `trySubmitForApproval`（:115-123）对同类场景正确使用 `LOG.warn(..., e)`，本方法是同文件内唯一静默点，属遗漏而非有意设计。
- **复核状态**: 未复核
- **修复归属**: MR2（09-02/03/06 家族统一补 LOG）

### [P3-MA4-003] MetaQualityRuleExecutor:607/:714 catch 后 return null 无日志（fallback 语义，复核维持 open）

- **文件**: `nop-metadata/nop-metadata-service/src/main/java/io/nop/metadata/service/quality/MetaQualityRuleExecutor.java:600-607, 714`
- **证据片段**:

  } catch (SQLException ignore) {

  // :607 布尔读也失败 → return null（无 LOG）

- **严重程度**: P3
- **现状**: M0.3 候选清单登记的 `MetaQualityRuleExecutor:599,606` 实际 catch 行确认为 **600/607**（清单行号偏差已修正）；第 3 处静默（:714 NumberFormatException → return null）live 确认存在。三处均为"读数值→回退格式"的 fallback 语义（质量规则 SQL 结果解析），非错误传播路径。
