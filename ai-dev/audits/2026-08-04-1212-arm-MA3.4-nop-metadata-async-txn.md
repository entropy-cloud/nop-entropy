### [MA3.4-01] upsertExternalTable：schema 维度未进 DB UK——多 schema 同名表功能与模型冲突（RACE 复核新增 P2）

- **文件**: `entity/NopMetaDataSourceBizModel.java:435-474`；`nop-metadata/model/nop-metadata.orm.xml:1314-1316`
- **证据片段**:
  ```java
  // javadoc 421-434：幂等 upsert：按 (metaModuleId, schema, tableName) 复合键去重…
  // 「使同数据源不同 schema 同名表可区分、互不覆盖」

      table = tableDao.newEntity();
      ...
      tableDao.saveEntity(table);        // ← 第二个 schema 同名表 → UK 冲突
  }
  // orm.xml:1314-1316
  <unique-key name="UK_NOP_META_TABLE_MODULE_NAME" columns="metaModuleId,tableName" .../>
  ```
- **严重程度**: P2
- **现状**: 应用层去重键 (metaModuleId, schema, tableName) 与 DB UK (metaModuleId, tableName) 不一致。同名不同 schema 的表在第二次 INSERT 时**必然**违反 UK（非仅并发时）；`syncExternalTables` 的 per-table catch（196-203）把该表记入 errors，该功能实际不可用。对 14-02 RACE：UK 已阻止重复行（完整性保住，07-19 a8eefeecb 加入），但无 catch-duplicate+re-read，并发败者得 error 而非幂等更新。
- **风险**: 多 schema 数据源同步持续报错；并发同步错误表项噪音；文档承诺行为与模型矛盾。
- **建议**: UK 扩展为 (metaModuleId, metaSchema, tableName)（metaSchema 可空，需处理 null 语义）或修正 javadoc；RACE 缓解：catch duplicate-key → re-read → update。
- **信心水平**: 高（代码 + ORM 模型直接对证；git 历史确认 UK 于 a8eefeecb 加入、metaSchema 列于 d88ed2d60 加入，UK 从未含 schema）
- **误报排除**: 非生成文件（model/ 源模型）；非并发场景即可复现。
- **修复归属**: MR2（需 ORM 模型变更，plan-first 区域）

## 总评

事务/异步面整体纪律良好：资源关闭 100% 合规、事务边界无滥用、核心实体乐观锁覆盖齐全、cron 链逐跳错误隔离清晰。主要风险是"长事务 + 无重试 + 无重叠守卫"的组合：外部查询在 store 事务内执行（3 入口）、调度/手动执行可重叠、webhook 失败不重试——单个风险 P3，叠加起来是质量告警链路的可靠性面（与 MA3.1 的 xwf 不可用结论同链路，MA7.5 承接深挖）。RACE 复核有实质进展：UK 已阻止重复，但暴露了 schema 未进 UK 的模型级缺陷（P2），且并发败者语义仍非幂等——终局定论归 MA6.6。
