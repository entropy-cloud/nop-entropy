## 性能风险点清单

### [MA7.4-01] 69 个 UK 零落库：全模块唯一键在 DDL 中全部不物化（跨层一致性，P2，与 MA7.3-01 同根因）

- **文件**: `nop-metadata/model/nop-metadata.orm.xml`（69 个 `<unique-key`，0 个 `constraint=`）；`nop-kernel/nop-xdefs/.../orm/entity.xdef:206-208`；`nop-persistence/nop-orm/.../xlib/ddl/ddl.xlib:81-82`（`<c:if test="${uniqueKey.constraint}">` gate）；`nop-orm/.../DdlSqlCreator.java:71-76`；对比 `nop-auth/model/nop-auth.orm.xml:176,286`（显式 constraint 可物化）
- **严重程度**: P2（数据完整性；与 MA7.3-01 同一根因，本报告从血缘/性能视角交叉确认）
- **现状**: 主 agent 实证：69 个 unique-key 全部缺 constraint 属性；DDL 模板仅在 constraint 非空时发射 UNIQUE → deploy/sql 快照与 initDatabaseSchema 均零 UK 物化。ORM 运行时无 UK 检查（唯一消费者 DdlSqlCreator）。MA3.4-01/03/08 依赖的"UK 已阻止重复"保护全部落空；血缘重复边（MA7.4-02）无任何 DB 兜底。
- **风险**: 并发首同步静默产生重复 module 行；血缘重复边真实落库（无去重兜底）。
- **建议**: 归 MR3（与 MA7.3-01 联动：模型补 constraint 属性 plan-first + 模板缺省裁决 + NopMetaTable 双重存储与 UK 相容性裁决）。不重复注册 finding（详见 MA7.3 报告 MA7.3-01）。
- **信心水平**: 高
- **修复归属**: MR3（见 MA7.3-01）

### [MA7.4-02] 列级血缘同批重复键缺口：表达式内重复列引用产 2 条同键候选 → 重复 INSERT（P2）

- **文件**: `NopMetaLineageEdgeQueryAction.java:243-271`；`SqlColumnLineageExtractor.java:226-235`（表达式列引用提取）
- **证据片段**:
  ```java
  Map<String, NopMetaLineageEdge> existingEdgeMap = batchLoadExistingColumnParseEdgeMap(...);  // 预载
  for (int i = 0; i < resolvedCandidates.size(); i++) {
      String key = sourceId + "|" + c.getSourceColumn() + "|" + c.getTargetColumn();
      NopMetaLineageEdge existing = existingEdgeMap.get(key);      // 只查预载 map
      if (existing == null) { toSave.add(newEdge); }               // 同批重复键第二项也判 null
  }
  dao.batchSaveEntities(toSave);                                   // 重复 INSERT
  ```
- **严重程度**: P2
- **现状**: `a.x + a.x` 类表达式产生 2 条同键候选；`existingEdgeMap` 不含 toSave 内待插项 → 第二条同键候选同样走 INSERT。UK 未物化（MA7.3-01）时重复行真实落库，且无测试覆盖该场景。
- **风险**: 血缘图重复边（图查询 visited-set 缓解显示层，但数据层冗余累积）；无 DB 兜底。
- **建议**: 循环内维护 toSave 已见键集合去重；补重复列引用提取回归测试。
- **信心水平**: 确定
- **修复归属**: MR3（新发现）

### [MA7.4-03] queryTableData 无 limit 默认值/上限：全表拉入内存序列化（P2）

- **文件**: `NopMetaTableBizModel.java:196-219`（limit `@Optional` 直传）；`NopMetaTableQueryAction.java:91`；`MetaTableQueryExecutor.java:67-74`+`SqlPagination.java:67-81`
- **严重程度**: P2
- **现状**: limit 为 @Optional 且无默认值、无上限；全仓库无 max-page-size 兜底。GraphQL 调用省略 limit + 大表 → 全表拉入内存序列化（external 路径全量 JDBC 读取）。
- **风险**: 大表目录查询内存/IO 放大（DoS 面）。
- **建议**: limit 缺省给默认值（如 1000）+ 上限配置；分页路径统一兜底。
- **信心水平**: 确定
- **修复归属**: MR3（新发现）

### [MA7.4-04] 跨库 JOIN 合并产物无上限：单侧 ≤10K 时笛卡尔积最坏 10^8 行入内存（P2）

- **文件**: `MetaJoinExecutor.java:420-465`；`CrossDbJoinMerger.java:77-97`；`CrossDbInMemoryAggregationProcessor.java:69-82`；`CrossDbConfigHolder.java:5`
- **严重程度**: P2
- **现状**: 跨库 JOIN 单侧各 ≤10K（分页守卫），但合并产物（含聚合前内存行集）无上限；limit 仅在 groupBy 后截断。高基数重复 join 键时笛卡尔积最坏 10^8 行。
- **风险**: 跨库 join 聚合 OOM/GC 风暴。
- **建议**: 合并产物上限（如 maxMergedRows 配置）+ 聚合前预聚合/流式合并。
- **信心水平**: 很可能
- **修复归属**: MR3（新发现）

### [MA7.4-05] LineageTagPropagationProcessor N+1：sourceLabels 循环内重复查询 + 每标签走全量 biz 管线（P3）

- **文件**: `entity/LineageTagPropagationProcessor.java:136-153,160-198`；`NopMetaTagLabelBizModel.java:47-53`
- **严重程度**: P3
- **现状**: findDirectEdges 在 sourceLabels 循环内重复查询；每标签经 invoke("save") 走全量 biz 管线；全链在单个 @BizMutation 事务内。多 Manual 标签 + 深度 3 扇出（S=3,B=5 → ~1400 查询）。
- **风险**: 标签传播大图时事务时长/锁竞争。
- **建议**: 批量预载 edges + 直接 DAO 保存（跳过 biz 管线）。
- **信心水平**: 高
- **修复归属**: MR3（新发现）

### [MA7.4-06] 图查询默认载入 10 万边（~100MB 实体）+ 超限整功能 fail-closed（P3）

- **文件**: `NopMetaLineageEdgeQueryAction.java:395-402,418-426`（buildLineageGraph/buildTableNameIndex 全表扫描 LIMIT maxEdges+1）；`NopMetaLineageEdgeBizModel.java:37-44`（默认 100_000）
- **严重程度**: P3
- **现状**: 每次图 API 全表扫描（无 WHERE，LIMIT 100001）；默认上限 10 万 → 单次调用 ~100MB 实体；超限整功能 fail-closed（>10 万边图查询全部不可用）。
- **风险**: 边数 >10 万或高并发图查询时资源放大；超限无渐进降级。
- **建议**: 默认上限调低或按查询类型差异化；或图查询改为流式/分批。
- **信心水平**: 确定
- **修复归属**: MR3（新发现）

### [MA7.4-07] deleteMeasureParseEdges 逐实体 delete（N 条 DELETE）（P3）

- **风险**: measure 边多时每次重抽取语句数放大。

- **信心水平**: 确定

### [MA7.4-08] 检查点调度 init 全量扫描不翻页 + 显式 ruleIds 逐条 getEntityById（P3）

## 总评 + 盲区自评

**总评**: 最大发现是跨层一致性问题——ORM 模型 69 个 UK 全部缺 constraint 属性（对比 nop-auth 显式 constraint），DDL 生成器按 constraint 过滤，使 MA3.4 依赖的"UK 已阻止重复"保护全部落空（与 MA7.3 报告 MA7.3-01 同根因，从血缘/性能视角交叉确认）。历史修复质量高：**AR-25 已批量化（复核关闭）**、AR-09 防线有效且有测试锚定。其余风险集中在三个"无上限"（queryTableData 无默认 limit、跨库合并乘积、图查询 10 万默认载入），规模触发条件明确但需大表/高扇出才显现。

**盲区自评**: 未逐一核对 69 个 UK 的 ORM 层行为差异；未在 MySQL 实测 DDL；LineageTagPropagationProcessor 事务时长未实测；getLineagePath 大图最坏路径耗时未实测；nop-metadata-web 层是否统一带 limit 未检查（若 UI 恒带则 MA7.4-03 暴露面收窄）。
