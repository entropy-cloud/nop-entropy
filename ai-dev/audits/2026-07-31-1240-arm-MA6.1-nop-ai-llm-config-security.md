# MA6.1 — LLM Config Security Audit (nop-ai modules)

**Date**: 2026-07-31
**Scope**: nop-ai-core, nop-ai-api, nop-ai-dao, nop-ai-agent
**Methodology**: `open-ended-adversarial-review-prompt.md` — key management / credential path focus
**Perspective used**: Secret exposure detective (tracing API key through loading → using → logging → storing paths)

---

## Summary

Audit traced the complete lifecycle of LLM API keys across all nop-ai modules: how keys are configured (env/config var), resolved (`LlmConfigHelper.resolveApiKey`, `DefaultAiChatService.getApiKey`), transmitted (HTTP headers, URL query params), logged (`DefaultChatLogger`), and persisted (DAO entity). Found 8 real findings, including one P0 (API key in URL query parameter with no masking) and multiple P1 exposures through logging and API output beans.

---

### [AR-MA6.1-01] Gemini API key transmitted in URL query parameter (plaintext in URL)

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/dialect/GeminiDialect.java:66-71`
- **Evidence**:
  ```java
  public String buildUrl(String baseUrl, String chatUrl, String apiKey) {
      String url = StringHelper.appendPath(baseUrl, chatUrl);
      if (!StringHelper.isEmpty(apiKey)) {
          url = url + (url.contains("?") ? "&" : "?") + "key=" + apiKey;
      }
      return url;
  }
  ```
- **Severity**: P0
- **Status**: API key embedded directly in URL query parameter, visible in HTTP access logs, proxy logs, browser history (if proxied), and any URL logging infrastructure.
- **Risk**: Any component that logs/serializes the `HttpRequest` URL (including the HTTP client itself, network proxies, server-side access logs) will capture the full API key in plaintext. This is a systemic exposure that cannot be mitigated by masking headers or message bodies.
- **Recommendation**: (1) Add a comment / documentation that Gemini should use a limited-scope API key since it's URL-exposed. (2) Add URL redaction in `ChatServiceImpl.buildHttpRequest` to mask the `key=` parameter value before logging the request URL. (3) At minimum, add a security warning in the `gemini.llm.xml` config.
- **Confidence**: certain

### [AR-MA6.1-02] DefaultAiChatService.getApiVersion() reads wrong config key (reads API key instead of API version)

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/service/DefaultAiChatService.java:261-263`
- **Evidence**:
  ```java
  private String getApiVersion(String llmName) {
      String apiVersionKey = StringHelper.replace(CONFIG_VAR_LLM_API_KEY, PLACE_HOLDER_LLM_NAME, llmName);
      return AppConfig.var(apiVersionKey, "");
  }
  ```
  `CONFIG_VAR_LLM_API_KEY` = `"nop.ai.llm.{llmName}.api-key"` — should be `CONFIG_VAR_LLM_API_VERSION` = `"nop.ai.llm.{llmName}.api-version"`.
- **Severity**: P1
- **Status**: The `getApiVersion()` method reads the API key config variable instead of the API version variable. This means for LLMs that use `{api-version}` template in baseUrl (e.g., Azure), the actual API version would be the API key string value, or the API key value would be used for API version resolution — neither is correct.
- **Risk**: Runtime failure for Azure/other LLMs that depend on API version in URL template expansion, or silent usage of wrong value. The method is called from `getBaseUrl()` line 249 during URL template rendering.
- **Recommendation**: Replace `CONFIG_VAR_LLM_API_KEY` with `CONFIG_VAR_LLM_API_VERSION` on line 262.
- **Confidence**: certain

### [AR-MA6.1-03] NopAiModelOutputBean exposes apiKey in GraphQL/REST API response

- **File**: `nop-ai-api/src/main/java/io/nop/ai/api/beans/NopAiModelOutputBean.java:84-95`
- **Evidence**:
  ```java
  private String _apiKey;

  @PropMeta(propId=5)
  public String getApiKey(){
      return _apiKey;
  }

  public void setApiKey(String value){
      this._apiKey = value;
  }
  ```
- **Severity**: P1
- **Status**: The output bean has `apiKey` as a plain property with no masking, no `@JsonIgnore`, and no conditional visibility. Any API call that returns model configuration (including list/query operations) will return the plaintext API key to the caller.
- **Risk**: An unauthorized user or a user with read access to model configurations can retrieve all configured API keys via the standard GraphQL/REST API. This is a cross-user information disclosure vulnerability.
- **Recommendation**: (1) Add `@JsonInclude(JsonInclude.Include.NON_NULL)` alone is insufficient since the field will be non-null when set. Add `@JsonIgnore` on the getter and provide a masked accessor (e.g., `getMaskedApiKey()`) if frontend display is needed. (2) Alternatively, use a separate "secure" output bean that never includes the key.
- **Confidence**: certain

### [AR-MA6.1-04] DefaultChatLogger logs chat request/response content to SLF4J without sanitization

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/service/DefaultChatLogger.java:26-28, 38-40`
- **Evidence**:
  ```java
  public void logRequest(ChatRequest request) {
      ChatMessage message = request.getLastMessage();
      LOG.info("request:role={},content=\n{}", message.getRole(), message.getContent());
      ...
      ResourceHelper.writeText(resource, JSON.serialize(request, true)); // writes to disk
  }
  ```
- **Severity**: P1
- **Status**: Both SLF4J log output and file-based logging serialize user message content in plaintext. While the API key is not in the message body for most providers, the `ChatRequest` object serialized to disk contains the full request — and for Gemini via URL or for providers using `Authorization: Bearer` headers, the HttpRequest headers are not directly serialized here, but the `logMessage=true` default means many chat exchanges are persisted.
- **Risk**: (1) Sensitive user data in message content is logged to SLF4J (may go to log aggregation systems). (2) Full `ChatRequest`/`ChatResponse` serialized to disk under `nop.ai.service.log-dir` (default `/nop/ai/log`). (3) No sensitive data detection/masking before logging.
- **Recommendation**: (1) Add content size truncation for log output. (2) Add keyword-based masking for potential secrets. (3) Document that `logMessage` should be disabled in production unless explicitly needed.
- **Confidence**: likely

### [AR-MA6.1-05] NopAiModel DAO entity stores API key in plaintext in database

- **File**: `nop-ai-dao/src/main/java/io/nop/ai/dao/entity/_gen/_NopAiModel.java:166-167`
- **Evidence**:
  ```java
  /* API密钥: api_key */
  private java.lang.String _apiKey;
  ```
  The ORM column is `api_key VARCHAR` in `nop_ai_model` table (per `_NopAiModel` field mapping).
- **Severity**: P1
- **Status**: The API key is stored in the database as plaintext VARCHAR with no encryption, no masking in `toString()`, no column-level access control. Any database read (direct SQL, ORM query, data export) exposes the key.
- **Risk**: Database compromise or SQL injection vulnerability would expose all stored LLM API keys. Backup files would contain plaintext keys. Even authorized users with read access to the `NopAiModel` entity can see keys.
- **Recommendation**: (1) Use column-level encryption (e.g., Nop ORM's built-in encryption or AES encrypt in DAO layer). (2) Override `toString()` in `NopAiModel` to mask apiKey. (3) Add `@Masked` or equivalent annotation. (4) Consider using a dedicated secrets store instead of database storage.
- **Confidence**: certain

### [AR-MA6.1-06] LlmConfigHelper uses static mutable state (secretCache, secretDir) — test isolation risk

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/service/LlmConfigHelper.java:28-38`
- **Evidence**:
  ```java
  private static final ICache<String, String> secretCache = new MapCache<>("ai-secret-cache", true);
  private static File secretDir;

  public static void setSecretDir(File dir) {
      secretDir = dir;
  }
  ```
- **Severity**: P2
- **Status**: `LlmConfigHelper` uses static mutable fields (`secretCache`, `secretDir`). The `setSecretDir()` is called from `ChatServiceImpl.setSecretDir()` (injected via `@InjectValue`), but this static state leaks across tests and cannot be properly isolated. The `secretCache` is never cleared between test runs unless explicitly called.
- **Risk**: Tests that set `secretDir` could interfere with other tests running in the same JVM. Cached secrets from one test leak into another. This makes test suites order-dependent.
- **Recommendation**: (1) Make `LlmConfigHelper` instance-based with injected fields instead of static state. (2) Or ensure `clearSecretCache()` is called in `@Before`/`@After` of all integration tests. (3) Register a JUnit 5 `BeforeEachCallback` extension to auto-reset state.
- **Confidence**: certain

### [AR-MA6.1-07] logMessage defaults to true — verbose logging of all LLM traffic by default

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/AiCoreConfigs.java:17-18`
- **Evidence**:
  ```java
  IConfigReference<Boolean> CFG_AI_SERVICE_LOG_MESSAGE =
          varRef(s_loc, "nop.ai.service.log-message", Boolean.class, true);
  ```
  Also `_LlmModel.java:94`: `private boolean _logMessage = true;`
- **Severity**: P2
- **Status**: Both the global config and per-model config default `logMessage` to `true`. This means by default, every LLM chat request and response is logged through the chat logger pipeline. In production, this generates verbose logs and increases the surface for data leakage.
- **Risk**: (1) Performance overhead from serializing all requests/responses. (2) Data leakage surface — logged content may contain sensitive information. (3) Log storage growth. (4) Compliance risk if PII flows through LLM calls.
- **Recommendation**: Change the default to `false`. The logging feature should be opt-in for debugging/development, not the default production behavior.
- **Confidence**: certain

### [AR-MA6.1-08] AppConfig.var() direct credential access — no vault/secret-store integration

- **File**: `nop-ai-core/src/main/java/io/nop/ai/core/service/LlmConfigHelper.java:112`
- **Evidence**:
  ```java
  String apiKey = (String) AppConfig.var(apiKeyName);
  ```
  Same pattern in `DefaultAiChatService.java:268`. The API key is read directly via `AppConfig.var()` with no abstraction layer for secrets.
- **Severity**: P2
- **Status**: The credential loading path goes through `AppConfig.var()` which reads from config files, system properties, or environment variables. There is no integration with a secrets vault (HashiCorp Vault, AWS Secrets Manager, etc.). The fallback to plaintext files (`secretDir/*.txt`) is also unencrypted.
- **Risk**: Keys set in configuration files could be accidentally committed to version control. Environment variable-based keys are visible in process listings. No rotation mechanism. No encryption at rest for the key values at the config layer.
- **Recommendation**: (1) Create a `ISecretProvider` abstraction that `LlmConfigHelper` and `DefaultAiChatService` can delegate to. (2) Provide a default implementation that wraps `AppConfig.var()` for backward compatibility, then document the extension point for vault-backed implementations. (3) The file-based fallback should at minimum support encrypted files.
- **Confidence**: likely

## Key Management Assessment

| Criterion | Status |
|-----------|--------|
| Hardcoded keys in source | Not found (good) |
| Keys in config files | Supported via `AppConfig.var()` — risk of committing |
| Keys via env vars | Supported — best available option |
| Keys via secret files | Supported (plaintext in `secretDir/*.txt`) — no encryption |
| Keys in database | Supported (`NopAiModel.apiKey` VARCHAR) — no encryption |
| Keys in HTTP headers | Standard Bearer/header — OK for most providers |
| Keys in URL query params | Gemini: P0 — key in URL |
| Keys in log output | Logged via DefaultChatLogger when `logMessage=true` (default!) |
| Keys in API responses | Exposed via NopAiModelOutputBean (P1) |
| Secret rotation support | None |
| Vault/secret-store integration | None |
