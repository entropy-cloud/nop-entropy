# 崔添翼最新论文！DeepSeek Harness从插件机制开启自进化

> 抓取: 2026-08-19（curl 原始 HTML + stdlib 转换；图片未保留；标题/作者经页面 og 元数据核验与链接一致）

智猩猩AI整理
编辑：BugMaker

DeepSeek这次没有只发布一个新模型。

最新开放的 DeepSeek Harness，把目标直接放到了模型之外的 Agent 运行层。

DeepSeek把它概括成一句话：“一切皆插件（Everything is a Plugin）”。

工具、LLM适配器、文件访问，甚至Agent Loop本身，都可以作为插件挂载到同一个运行时上下文中。

而当Harness本身也被拆成可以动态替换的组件后，问题就不只是“插件够不够多”。

论文进一步设想了一种更激进的场景：未来的自进化Agent Harness（Self-Evolving Agent Harness），可能在持续处理请求的同时，由AI生成并部署对自身组件的修改。

Agent能修改自己的Harness是一回事，每次修改之后还能不能恢复状态、重新协调依赖，则是另一回事。

真正处在底层的是Cordis，它处理的正是组件动态加入、退出和依赖变化之后的运行时问题。

北京大学与DeepSeek-AI联合发表了一篇长达80页的论文《一种面向时空可组合性的编程范式》（A Programming Paradigm for Spatiotemporal Composability），系统给出了Cordis背后的形式化基础。

这项工作只有三位作者。

一作Yifan Shi同时署名北京大学与DeepSeek-AI，此前也曾出现在DeepSeek-V3、DeepSeek-R1等技术报告的作者名单中。

第二作者张伟是北京大学计算机学院软件研究所副教授，长期研究软件工程、程序设计语言，和这篇论文讨论的动态组合、编程范式高度相关。

第三作者则是崔添翼，来自DeepSeek-AI，同时也是目前的DeepSeek Harness团队负责人。他本科毕业于浙江大学计算机系，此前曾在Jane Street任职多年，2026年加入DeepSeek后负责Harness方向。

三个人的背景也正好对应了这项工作的落点：一边是程序设计语言与软件工程，一边是DeepSeek正在推进的Agent Harness。

这项工作聚焦运行时动态组合（Dynamic Composition）：组件加入、退出或被替换后，不仅要能够撤回自己留下的副作用，还要让组件之间的依赖随环境变化自动重新协调。

对于自进化Harness，难点已经不只是把新组件装进去，而是旧组件退出之后，状态能不能恢复，依赖它的其他组件能不能继续正确运行。

01

自进化Harness开始改自己后，

整体重启已经太粗了 

模块导入、函数调用、类继承通常在运行前就已经确定。但插件系统不同，组件会在运行过程中被加载、卸载和重新配置。

论文还专门讨论了自进化Agent Harness。作者设想，未来AI可能在Harness持续服务的同时，生成并替换自己的Harness组件，模型自动生成可复用工具，则可以看作这种组件级自修改更早的一种形态。

修改发生得越频繁，“每次出问题就重启”就越难成立。

论文把这里的问题拆成两个方向。

一个是时间可组合性（Temporal Composability）。

组件被移除以后，它创建的资源、注册的事件和修改的状态，都应该能够被完整撤销，而不是把整个进程一起重启。

另一个是空间可组合性（Spatial Composability）。

组件需要明确声明自己依赖什么。当依赖出现、消失或者更换提供者以后，系统应该自动协调相关组件，而不是让每个组件自己检查。

论文用VSCode说明这种差距。

在安装量最高的100个扩展中，87个包含可执行代码，移除时需要重启Extension Host。另一方面，只有7个声明了对非内置扩展的extensionDependencies 。

到了Agent Harness里，问题会更突出。

论文设想未来的Harness可能持续生成并部署自己的组件修改。如果每次修改都需要整体重启，进程内缓存、连接和正在执行的任务都会受到影响。一旦错误修改破坏了负责恢复的进程，恢复本身也会成为问题。

02

Cordis的核心，是让每次修改

都留下“返回键” 

时间可组合性对应的是论文提出的可撤销效应（Revertible Effects）。

传统副作用只关心“做了什么”。

这里每次上下文变换不仅产生新状态，还必须同时提供对应的逆操作（Inverse）。运行时执行修改的同时，把逆操作记录下来。

组件加载时，不断积累这些修改。

组件卸载时，则利用积累的逆操作恢复上下文。

组件级的卸载逻辑不再需要单独维护。开发者为原子操作提供对应的逆操作后，Cordis会在运行时持续追踪并组合这些逆操作，组件退出时再按相应顺序完成恢复。

空间上的问题则由反应式协效（Reactive Coeffects）处理。

组件先声明自己的依赖规范。上下文每发生一次改变，运行时都会重新判断这些依赖，并把变化划分成激活（Activating）、停用（Deactivating）和中性（Neutral）。

依赖满足，组件进入激活流程。

依赖消失，相关组件进入停用流程。

论文进一步把效应和协效统一进一个上下文，并给出了完整的动态组件生命周期。真实系统里的加载也不再被假设成“一瞬间完成”，而是允许经历 Inactive、Reloading、Active、Unloading 等状态。

加载途中出现错误，也会进入恢复路径，而不是留下只加载了一半的组件。

这也是Cordis与自进化Harness真正接上的地方。

它并不负责让AI学会修改代码，而是处理修改发生之后的运行时后果：旧状态怎么撤回，依赖关系怎么重新协调。

对持续修改自身组件的Harness来说，这两件事才决定了“能修改”能不能进一步变成“持续修改”。

03

论文写的是Cordis，而DeepSeek

真的把它放进了Harness 

这些机制最终被作者实现成了 Cordis。

论文把Cordis定位为一个时空可组合性的元框架（Meta-framework）。

底层核心库负责效应追踪（Effect Tracking）和协效解析（Coeffect Resolution），组件加载器进一步提供配置协调和热模块替换（Hot Module Replacement，HMR）。

HMR还采用事务式重新加载。

如果新模块导入失败，例如遇到语法错误，系统会恢复此前保存的模块缓存，并重新构建被替换的旧组件，避免系统停在“新旧各一半”的状态。

而现在，这套设计已经和DeepSeek新发布的Harness直接接上。

DeepSeek官方明确表示，Harness由Cordis驱动，并采用“一切皆插件”的架构。模型适配器、工具注册表、Session Log，甚至Agent Loop本身都被做成插件，可以通过配置进行组合和替换。

但这里需要区分一件事。

论文并没有拿DeepSeek Harness做实验。

论文真正给出的生产案例是Koishi。

这个建立在Cordis上的开源聊天机器人应用框架经过四年发展，已经积累了超过4000个社区插件，覆盖即时通信适配器、数据库驱动、管理控制台等不同能力。

需要说明的是，Koishi目前运行的是Cordis v3，论文介绍的是重新设计了效应、协效语义和Loader的Cordis v4，两代版本共享核心组合模型。

在Koishi里，关闭一个插件可以直接撤回对应效应，而不需要重启宿主。更换存储后端或者重新连接适配器时，也只重新激活依赖发生变化的组件。

作者自己也没有把这组结果包装成性能benchmark。

论文明确说明，Koishi属于存在性和采用度验证，不是和其他架构进行受控定量比较。当前证据来自单一生态和单一宿主语言，运行开销以及开发效率提升仍需要进一步研究。

Koishi证明的是Cordis已经能支撑一个长期运行的开放插件生态。

但论文最后把更进一步的验证方向明确指向了自进化Agent Harness。

作者设想，未来AI可能在很少人工干预的情况下，持续生成和替换自己的Harness组件。这时Cordis真正需要面对的，是组件快速替换以后能否完整恢复，依赖拓扑频繁变化以后能否继续保持协调。

换句话说，论文想验证的并不是“Agent会不会自己写一个新插件”，而是更底层的问题：

当Agent开始持续修改承载自己的Harness以后，系统能不能做到可恢复、可协调，并且持续演化下去。

所以DeepSeek Harness这次真正值得关注的，并不只是“一切皆插件”这个架构口号。

当Tool、模型适配器乃至Agent Loop都被拆成可以重新组合的组件以后，Harness本身也开始具备被持续修改的结构基础。

论文解决的是更往下一层的问题：这些修改发生之后，旧组件如何安全退出，副作用如何恢复，依赖关系又如何重新建立。

现在还不能说DeepSeek Harness已经实现了论文设想的持续自进化。

但Cordis已经进入DeepSeek Harness底层，而论文给出的目标也很清楚：

为未来可恢复、可协调、持续自进化的Agent Harness，补上一套动态组件运行时基础。
